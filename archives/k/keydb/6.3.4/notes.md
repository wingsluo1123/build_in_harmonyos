# KeyDB 6.3.4 HarmonyOS adaptation notes

## Scope

- Requested package version: `keydb/6.3.4`
- Upstream: https://github.com/Snapchat/KeyDB (tag `v6.3.4`)
- Build system: raw Makefile (Redis 6.3 lineage, but re-implemented in C++)
- Build host: Windows + WSL (Ubuntu 24.04), cross-compiling with the
  DevEco Studio OHOS clang (aarch64-linux-ohos)
- Local target: verify the cross build only. CI compiles natively on
  OHOS/aarch64, which is where the upstream Tcl suite runs.

## Source verification

The upstream repository was checked before writing anything, because the
library name suggests a plain Redis fork and that assumption would have been
wrong in the details:

| Item | Value |
|------|-------|
| Tags present | `v6.3.4` (and v6.3.0-v6.3.3, v6.2.x, v6.0.x, v5.x, v0.9.x) |
| Source size | 5.9 MB tarball; 38 MB unpacked |
| Language | C++ (`src/*.cpp`: 66 files; `src/*.c`: 38 files) |
| Layout | `src/`, `deps/`, `tests/`, `runtest` - the Redis 6.3 tree |
| sha256 | `229190b251f921e05aff7b0d2f04b5676c198131e2abbec1e2cfb2e61215e2f3` |

KeyDB really is the multi-threaded Redis fork: `src/server.cpp`,
`src/rdb.cpp`, `src/fastlock.cpp` and the async I/O worker pool are C++
rewrites of the Redis 6.3 equivalents, and the thread-affinity code that
matters for this port lives there.

The patches are generated by the repository's own `refresh-patch --auto`
routine, so they carry its per-file naming convention

| `0007-tests-support-tmpfile.tcl.patch` | configurable test temporary root |

## What the port required

Six distinct platform problems, all in the "musl is not glibc" family plus
one build-system issue. They are grouped into four patches because they
share root causes.

### 0001-ohos-pthread-compat.patch

OHOS ships a musl libc. Five GNU extensions KeyDB relies on are absent from
both the headers and the library:

| Symbol | Used by | Handling |
|--------|---------|----------|
| `pthread_setaffinity_np` | `src/rdb.cpp`, `src/server.cpp` | forward to `sched_setaffinity` |
| `pthread_getaffinity_np` | (declared for symmetry) | forward to `sched_getaffinity` |
| `pthread_cancel` | `src/bio.cpp`, `src/debug.cpp` | return `ENOSYS` |
| `pthread_setcancelstate` | `src/server.cpp` | report the previous state |
| `pthread_setcanceltype` | `src/server.cpp` | report the previous type |

Details worth keeping:

- `cpu_set_t` and the affinity prototypes only exist behind `_GNU_SOURCE` in
  the OHOS `sched.h`, and `config.h` is included before `fmacros.h` defines
  it. `pthread_compat.h` therefore defines `_GNU_SOURCE` itself and is
  included from `config.h`, which every translation unit reaches through
  `server.h`.
- `pthread_cancel` deliberately returns `ENOSYS` rather than success. The
  upstream callers only join a thread after cancellation reports success, so
  a success-returning no-op would deadlock on a thread that keeps running.
  This follows the same reasoning as the official `redis` recipe.
- The shim object is added to `REDIS_SERVER_OBJ` only. It is linked exactly
  once; adding it to `FINAL_LIBS` as well produced duplicate symbols because
  the server link line already expands its own object list.

### 0001 also fixes `program_invocation_name`

`src/setproctitle.c` updates the glibc globals `program_invocation_name` and
`program_invocation_short_name`. musl does not export them. Rather than
deleting the update, the patch defines local storage for non-glibc builds so
the existing code path keeps working unchanged.

### 0002-run-build-and-test-scripts-through-sh.patch

`release_hdr := $(shell sh -c './mkreleasehdr.sh')` and the `test:` target's
`./runtest` both depend on the executable bit, which the source archive does
not reliably preserve. Both are invoked through `sh` instead.

### 0003-make-libatomic-optional.patch

The Makefile appends `-latomic` on any Linux host that is not Darwin/FreeBSD.
AArch64 OHOS provides the atomics natively and the sysroot has no
`libatomic`, so the flag is wrapped in a `NO_LIBATOMIC` guard.

### 0004-configurable-test-temp-root.patch

The Tcl suite writes Unix sockets under `./tests/tmp`. OHOS paths for Unix
sockets are length-limited, so the root becomes configurable through
`KEYDB_TEST_TMPDIR` while defaulting to the upstream value.

## Dependency decisions

| Dependency | Source | Why |
|------------|--------|-----|
| libuuid | `uuid/2.40.1` (Conan) | Not in the OHOS sysroot; KeyDB uses it for replication identities |
| libcrypto | `openssl/1.1.1w` (Conan) | Linked by default, no bundled copy |
| malloc | `MALLOC=libc` | The bundled jemalloc is a host-built copy that cannot be cross-compiled here |
| hiredis, Lua, linenoise, hdr_histogram | bundled | The Makefile builds these itself and they compiled cleanly |
| Tcl | `tcl/8.6.16` (build-only) | Required by the upstream suite; declared only for native builds |

`hiredis/1.2.0` and `jemalloc/5.3.0` are available in the artifact repository
and were verified with `conan install` (R35), but the build does not pull
them in: the bundled copies build fine and using them avoids a second
integration surface. This is noted so a reviewer does not read the task
brief's dependency list as a requirement.

## Build flags

```
CC/CXX/LD/AR/RANLIB   from tools.build:compiler_executables
MALLOC=libc           bundled jemalloc cannot cross-compile
BUILD_TLS=no          TLS is not needed and would add another dependency
USE_SYSTEMD=no        no systemd on OHOS
NO_MOTD=yes           the login MOTD needs libcurl, which the sysroot lacks
NO_LIBATOMIC=yes      AArch64 atomics come from the compiler
USEASM=no             the bundled spinlock assembly is x86-only
KEYDB_CFLAGS/LDFLAGS  point at the build-local dependency prefix
```

`USEASM=no` matters: the Makefile enables `fastlock_x64.o` when
`uname -m` is `x86_64`, which is true on the build host but wrong for an
aarch64 target. Leaving it unset produced `fastlock_x64.o is incompatible
with aarch64linux` at link time.

## Why the upstream suite does not run in this local build

The Tcl suite starts the freshly built `keydb-server` and talks to it over a
Unix socket. This machine cross-compiles from Windows/WSL to OHOS, so the
produced binaries need `/lib/ld-musl-aarch64.so.1`, which only exists on the
device. The recipe therefore runs `make test` only when
`conan.tools.build.cross_building()` is false.

A second, narrower reason: the recipe declares `tcl/8.6.16` as a build
requirement only for native builds. The `tcl` recipe in this repository is
written for a native OHOS host (`tcl_cv_sys_version=Linux-6.6` plus a native
clang); configuring it from an x86_64 Linux build machine fails with
`C compiler cannot create executables`. Cross-building Tcl only to drive a
cross-built server would be pointless anyway, since the test process has to
execute the server.

On CI (native OHOS/aarch64) both conditions disappear and `make test` runs
in `build()`, before packaging.

## Device run: two adaptation defects found and fixed (2026-10-02)

The first native run compiled cleanly but the upstream suite could not start
a single server ("Can't start the Redis server" / "No PID detected in log").
Both causes were real portability defects, found with the freshly built
binaries on the device and fixed in this patch set.

### 1. `keydb-server` segfaulted at startup (rc=139, no output)

Evidence chain, all reproduced on the device:

| Step | Observation |
|------|-------------|
| `keydb-cli --version` | prints `keydb-cli 6.3.4`, exit 0 |
| `keydb-server --version` | **no output, exit 139 (SIGSEGV)** |
| `src/Makefile` object lists | `REDIS_SERVER_OBJ` contains `setproctitle.o`; `REDIS_CLI_OBJ` does not |
| `src/server.cpp:7516` | `main()` calls `spt_init(argc, argv)` before any argument handling |
| `src/setproctitle.c` `spt_init()` | `strdup(program_invocation_name)` with the compat shim defining that global as `NULL` |

musl does not export the glibc `program_invocation_name` /
`program_invocation_short_name` globals, and the previous compat patch
declared them as `NULL` pointers. `strdup(NULL)` crashes the process. The
`keydb-cli` binary never links `setproctitle.o`, which is exactly why only
the server died.

Fix (in `0001`): `spt_init()` now seeds both globals from `argv[0]` (full
path and basename) before the existing deep copy, which is what glibc does.
Verified on the device: `keydb-server --version` prints
`KeyDB server v=6.3.4 ... malloc=libc bits=64`.

### 2. arm64 fork-bug probe aborted the server (`server.cpp:6541`)

After the segfault fix the server still aborted, but this time with an
assertion: `server.cpp:6541 '!ret' is not true` inside
`linuxMadvFreeForkBugCheck()`. A minimal probe program built with the same
clang on this device shows:

```
mprotect=0 errno=0
MADV_FREE defined = 8
madvise(MADV_FREE)=-1 errno=22 (Invalid argument)
madvise(MADV_DONTNEED)=0 errno=0
```

So the OHOS kernel rejects `MADV_FREE` with `EINVAL` while `MADV_DONTNEED`
works. Upstream asserts on the `madvise` result, which kills every server at
startup on such kernels - including the graceful "Failed to test the kernel"
path (return value 2) that upstream itself provides.

Fix (new `0005`): when `madvise(MADV_FREE)` is unsupported, log a warning and
return 0. The bug being probed is specific to kernels that *do* implement
`MADV_FREE`, so an unsupported advice value means the probe cannot run and
the kernel is not affected by it. The server log records the skip:

```
# madvise(MADV_FREE) unsupported on this kernel (errno=22); skipping the arm64 fork bug probe
```

## How this patch set was produced

The patches are produced by the repository's own tooling, in the mode that
does not apply its build-artifact exclusion rules:

1. `src/Makefile` and `src/config.h` edits cannot be produced by
   `refresh-patch`'s rule-based fallback: that path treats any modified file
   named `Makefile` or `config.h` as a build artifact and drops it silently
   (`_GENERATED_NAMES` in `scripts/ohc/refresh_patch.py`), and it never
   rewrites the `patch_file` list in `conandata.yml`.
2. `refresh-patch` therefore runs in its precise mode, driven by the edit
   tracker (`scripts/ohc/edit_tracker.py`): a baseline fingerprint is taken
   from the pristine upstream tree, the edited files are discovered by
   comparing hashes, and newly created files are registered explicitly.
   Precise mode generates a patch for every tracked file with no exclusions.
3. The pristine tree is the upstream tarball, sha256
   `229190b251f921e05aff7b0d2f04b5676c198131e2abbec1e2cfb2e61215e2f3`
   (identical to `conandata.yml`).
4. The generated patches were verified by applying them to the pristine tree
   in the order declared in `conandata.yml`; the result matches the adapted
   tree byte for byte.

`conandata.yml` lists the generated file names, so the recipe stays
consistent if the tooling re-runs.

- **S1** — the five commands are aarch64 ELF, and the musl pthread shim
