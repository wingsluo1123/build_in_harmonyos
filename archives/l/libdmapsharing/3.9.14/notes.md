## 遇到的问题与解决方案

| # | 问题 | 根因 | 解决方案 |
|---|------|------|----------|
| 1 | libsoup3 与 avahi-glib 各自依赖不同 glib 包（glib2 vs glib） | 两套 glib → 双 GObject 类型系统 SIGABRT | 全链统一 pin glib/2.84.0.1.1（shared）；avahi-glib 的 glib/2.84.0.1 用 override 对齐到 2.84.0.1.1（libsoup3-r3/libgepub 先例） |
| 2 | configure PKG_CHECK_MODULE avahi-client >= 0.6 找不到 avahi-client.pc | avahi-glib 单合并 cpp_info，PkgConfigDeps 只产 avahi-glib.pc | 配方 generate() 手写 avahi-client.pc（+ avahi-common.pc）shim 指向 avahi-glib 包目录 |
| 3 | configure 的 AS_TMPDIR `umask 077 && mktemp` 生成 2700+setgid 目录，HMFS 拒绝写入（config.status: Permission denied） | hmfs 安全机制（E011/E112/E118） | 运行时文本补丁生成的 configure 移除 `umask 077`（avahi/avahi-glib 同款） |
| 4 | automake 批量头安装 `install -c -m 644 f1..fN dir/` 被 HMBS install shim 拒绝（exit 64） | HMBS 只接受单文件两参 | 写 cp/mkdir 安装 shim 并重定向生成 Makefile 的 INSTALL 变量（adms/libgsf/xeyes 先例） |
| 5 | glib-mkenums 是 python3 脚本，HMFS 拒绝 shebang exec | HMFS exec 限制 | _stage_glib_python_tools 编译 C launcher（avahi-glib 同款） |
| 6 | CI worker 导出 AR/AS/STRIP/NM/RANLIB 为 PATH 上不存在的 llvm-* 名字 | 工具链环境 | generate() 里 os.environ.pop + 从 PATH 定位真实工具（libsoup3/gupnp 先例） |
| 7 | 静态链接 libdmapsharing-4.0.la 时 libtool 报 `libavahi-client.la is not a valid libtool archive` | libtool 静态归档依赖扫描要读 avahi 依赖的 `.la`；avahi-glib 包只装 `.a` 不装 `.la`，且 round-2 生成的 shim 首 4 行不含 `# Generated by libtool` 魔术行，被 ltmain.sh 的 func_lalib_unsafe_p 拒绝 | generate() 新增 `_fix_avahi_la()`：把真实 avahi `.a` 与 `.la` shim 一起 staging，并让 avahi .pc shim 的 `Libs:` 指向 `-L<staging> -lavahi-*`（bake 进 MDNS_LIBS），libtool 能从伴随 -lavahi-* 的 -L 推导出 staging 里的 `.la`；shim 前 4 行含 `# Generated by libtool` 魔术可见行（见下方 round-3 根因） |

START_TEST 宏内联在主源文件中，libdmapsharing/Makefile.am BUILT_SOURCES 触发

| suite | 用例数 | 源文件 |
|-------|-------|--------|
| dmap-av-connection | 5 | libdmapsharing/dmap-av-connection.c |
| dmap-av-record | 5 | libdmapsharing/dmap-av-record.c |
| dmap-av-share | 24 | libdmapsharing/dmap-av-share.c |
| dmap-connection | 4 | libdmapsharing/dmap-connection.c |
| dmap-md5 | 2 | libdmapsharing/dmap-md5.c |
| dmap-utils | 5 | libdmapsharing/dmap-utils.c |
| **合计** | **45** | |

官方 `make check`（check-local）会额外做 gcov 覆盖率重建（
`make clean; make CFLAGS="-fprofile-arcs -ftest-coverage"` + gcov + summarize），
OHOS 无 gcov 链且该步仅为覆盖率统计，真正的功能断言在 `../tests/unit-test`。
配方直接运行 unit-test 二进制并解析 Check 汇总行（`Checks: N, Failures: F,
Errors: E`）输出 HMBS_UPSTREAM_TEST_RESULT。数字来源单一（Check 汇总行），
无算术修补。

### 平台限制分析（真机确认后更新）
- pure 单元（md5/utils/connection/av-record 大部分）不依赖网络/守护进程。
- dmap-av-share 的 _serve_publish* 调用 dmap_share_publish（mDNS publish），
  OHOS 无 avahi 守护进程时 publish 可能失败 → 需真机实测确认通过/失败，
  失败则按 ohos_feature gap 记录并给证据。

### 测试计数解析（Check 汇总）——按 suite 聚合，勿只取最后一行
unit-test.c 对 6 套 suite 各调用一次 run_suite()（每次内部 srunner_run_all +
srunner_free），因此 libcheck 每套 suite 都输出一行
`N%: Checks: X, Failures: Y, Errors: Z`，共 6 行。配方 _run_upstream_unit_test
必须把 6 行全部累加（Checks 求和 = 45 发现/执行总数；Failures+Errors 求和 =
失败总数），而不是只取最后一行（那仅是 dmap-utils 的 5 条）——否则
HMBS_UPSTREAM_TEST_RESULT 会误报 discovered=executed=passed=5，与 MANIFEST
声明的 upstream_test_total=45 不符。恒等式 passed+failed==executed、
executed<=discovered 由累加后自检保证。

### test_package GObject 类型注册——必须显式触发
GObject 类型是惰性注册的：仅链接/调用 g_type_from_name 不会让类型进入类型系统
（返回 0）。test_dmapsharing.c 的 check_gobject_types 必须先调用各
dmap_*_get_type()（dmap_av_connection_get_type / dmap_av_record_get_type /
dmap_share_get_type / dmap_connection_get_type）强制注册，再断言返回的非 0 GType
与其规范名一致（g_type_from_name("DmapAvConnection")==get_type()）。这样既验证
类型可用，也能在“第二份 GObject 拷贝”场景下于 get_type() 注册时触发
“cannot register existing type”SIGABRT。

## 2026-09-25 修复：requirements() 重复 glib 声明

> ⚠️【已更正】本条的"删除 override、只留普通 requires"方案已被下一轮（第 2 轮更正
> 小节）推翻：普通 exact 声明无法覆盖 avahi-glib 的 glib/2.84.0.1 exact pin，会触发
> Version conflict。最终方案见下方「第 2 轮更正」。

真机 compile 阶段失败：`ConanException: Duplicated requirement: glib/2.84.0.1.1`。
conanfile.py 的 requirements() 里对 glib 调用了两次 requires —— 一次带
options/transitive，另一次 `override=True`。Conan 2 禁止同一 requirement 声明两次。

修复：删除 `override=True` 那一行，只保留单一 exact 直接声明
`self.requires("glib/2.84.0.1.1", options={"shared": True}, transitive_headers=...,
transitive_libs=...)`。根包 exact requirement 在版本解析中优先于传递依赖，因此
avahi-glib 的 glib/2.84.0.1 pin 仍会被对齐到 2.84.0.1.1（与 libsoup3-r3/libgepub
链同一写法，那两项已验证可正常解析同款 avahi/glib 冲突）。

## 2026-09-25（第 2 轮）更正：glib 版本冲突改为 override 声明

上一轮把 glib 的 `override=True` 声明删掉、只留普通 exact 直接 requires，结果真机
报新错误：
`ERROR: Version conflict: Conflict between glib/2.84.0.1 and glib/2.84.0.1.1 in the
graph. Conflict originates from avahi-glib/0.9_rc5`

根因：conan 2 对同一包在图中出现两个不同 exact pin（avahi-glib pin glib/2.84.0.1，
libsoup3-r3 pin glib/2.84.0.1.1）直接判 Version conflict，根包的普通 exact 声明
并不会自动就近覆盖传递依赖的 exact pin。

修复（requirements()）：
- 恢复单一声明 `self.requires("glib/2.84.0.1.1", override=True)`（override 依赖
  全图钉到 2.84.0.1.1，同时拿掉普通 requires，避免 Duplicated requirement）。
- 注意：override 依赖不建图边、不进 self.dependencies（conan 会从
  transitive_deps 移除），但 glib/2.84.0.1.1 仍是 libsoup3-r3 的真实直接依赖，
  图中必有该节点。因此新增 `_glib_pkg()` 辅助方法，经 libsoup3/avahi-glib 的
  依赖链取回 glib 的 ConanFileInterface（package_folder），并让
  `_fix_glib_pc_files` / `_stage_glib_python_tools` / generate() glib-bin PATH /
  `_prepend_runtime_libdirs` / package_info 全部改走它（读取失败时跳过不硬崩）。
- package_info：glib 不再出现在 cpp_info.requires（conan 2 拒绝 override 依赖进
  cpp_info.requires，会报 not a direct requirement）；glib 的链接信息仍经
  libsoup3-r3（其 cpp_info.libs 含 glib-2.0/gobject-2.0/gio-2.0/gmodule-2.0/
  gthread-2.0）与 avahi-glib transitive_libs 传递，消费者链接不受影响。

参数说明：glib 的 shared=True 由 libsoup3-r3 自己的 glib 要求携带，因此仍是单份
共享 glib，单 GObject 拷贝策略不变。

## 2026-09-26 修复：readonly_tmp 导致 configure "C compiler cannot create executables"
- 真机（commentId=-1790399202529）compile 阶段失败，HMBS 平台诊断 `[readonly_tmp]`。
- 证据：configure 早期 AC_PROG_CC 编译器可用性探测失败 `checking whether the C
  compiler works... no` / `sed: can't read conftest.c: No such file or directory` /
  `configure: error: C compiler cannot create executables`（Error 77）。
- 根因：OHOS 真机 /tmp 只读（erofs），clang 无法在 /tmp 创建 conftest 临时文件/
  可执行体，AC_PROG_CC 世界探测直接失败。配方 generate() 原仅当
  `HMBS_AUTOCONF_MKTEMP_FALLBACK` 环境变量存在时才把 TMPDIR/TMP/TEMP 指到可写目录，
  而 HMBS 实际注入的是 `HMBS_PLATFORM_CAPABILITIES.tmpdir` / HMBS_TMPDIR，故编译器
  仍在只读 /tmp 上被夹住。
- 修复（conanfile.py，对标 libsieve/2.2.6 与 libecoli/0.11.7 已验证先例）：
  新增 `_hmbs_writable_tmpdir()`——按优先级探测可写临时根：HMBS_TMPDIR >
  HMBS_PLATFORM_CAPABILITIES.tmpdir > TMPDIR/TMP/TEMP(非/tmp) >
  HMBS_AUTOCONF_MKTEMP_FALLBACK > ~/tmp > build_folder/.tmp，并用真实
  makedirs+mkstemp+write+unlink 探针验证可写（HMDFS 忽略 chmod/os.access）。
  generate() 用其返回值定义 TMPDIR/TMP/TEMP 写入 dmap_env，build() 的
  configure/make/unit-test 均走 `env=["conanbuild","conanrun","dmap_env"]` 透传。
  只重定向临时根，不动任何上游测试。
- configure 的 AS_TMPDIR `umask 077 && mktemp` 补丁（`_patch_generated_configure`）
  已存在且保留，处理 config.status 写 confXXXXXX 目录的问题，与本次编译器临时根
  是不同故障面。

## 2026-10-12 修复：CI checkout-pr 无法 git apply 二进制文件（GitCode .diff 不含 binary patch 数据）

  其他软件树均为纯文本,C 源码，故从未触发此路径。
- 修复（conanfile.py + 删二进制，保持字节级忠实）：
  1. `src/media/{test.jpeg,test.mp3,another-test.png,another-test.mp3}`（测试夹具，
     供 test-dmap-image-record / test-dmap-av-record 读取）从 git 移除，改为在
     `media_data.py` 中以 base64 文本保存，source() 拷贝 src/ 后在
     `src/media/` 逐字节还原（与官方 3.9.14 归档 sha256 4ad60d94... 严格一致）。
     测试输入不变 → 45 用例口径与全部 gaps 计数不变。
  2. `src/doc/html/*.png`（7 个 16x16 gtk-doc 生成导航图标，纯生成文档，configure
     已 `--disable-gtk-doc`、文档不参与 build/install/package）直接删除，无需还原。
  3. `conanfile.py` `exports_sources` 增加 `media_data.py`，source() 用
     importlib 按显式路径加载（export_sources_folder 未必在 sys.path）并还原。
- 净效果：main→PR 的 diff 不再含任何二进制文件（11 个二进制文件先加后删，净 diff 为 0），
  `git apply pr.diff` 可完整通过；vendored 源码树在真机编译/运行时仍为官方字节级一致。

## 2026-09-28 修复：configure "Must have glib-2.0 installed"（_glib_pkg 不可达）
- 真机（commentId=-1790571550690）compile 阶段失败：
  `checking for glib-2.0 >= 2.66... no` → `configure: error: Must have glib-2.0 installed`。
  configure 已找到 pkg-config（`checking for pkg-config... yes`），唯一可能是
  glib-2.0.pc 不在 configure 的 PKG_CONFIG_PATH 里 → `_fix_glib_pc_files()` 未产出
  glib-2.0.pc shim（它返回 None，即 `_glib_pkg()` 返回 None）。
- 根因：conanfile.py requirements() 用 `self.requires("glib/2.84.0.1.1", override=True)`
  解决 avahi-glib glib/2.84.0.1 与 libsoup3-r3 glib/2.84.0.1.1 两个 exact pin 的
  Version conflict。override 依赖被 conan 2 从「声明该 override 的 recipe」的
  self.dependencies 中剥离（不建图边）。配方原 `_glib_pkg()` 只做固定两跳
  （libsoup3/avahi-glib → glib）查找，在 conan 2.x 的 override 依赖视图下返回 None，
  于是 glib-2.0.pc 缺失 → configure 在 glib 检查处失败。
- 修复（conanfile.py）：
  1. `_glib_pkg()` 改为对整棵可达依赖图做显式 BFS（从 self.dependencies 的各直接依赖
     出发，沿每个节点的 .dependencies 逐层扩散，返回首个 name=="glib" 且
     package_folder 非空的节点）。glib 是 libsoup3-r3 链的硬依赖，必然在图中，无论它
     落在哪一层都能被找到，不再依赖单一父链的两跳可达性。
  2. `_fix_glib_pc_files()` 在 BFS 仍找不到 glib 时不再静默返回 None，而是抛
     ConanException 并列出实际直接依赖，让下一次预检给出确凿诊断而非暧昧的
     configure 错误（宁缺毋假，不伪造 glib 可用）。
- 说明：override 声明（版本冲突解法）与 _glib_pkg 改 BFS 是正交的：前者只决定版本解析，
  后者只解决 glib 包目录的运行时可达性。glib 的 shared/单 GObject 拷贝策略不变。


## 2026-09-28 修复第2轮：configure 仍 "Must have glib-2.0 installed"（shim 目录未被 pkg-config 搜索）
- 真机（commentId=-1790573642427）compile 阶段仍失败在
  `checking for glib-2.0 >= 2.66... no` → `configure: error: Must have glib-2.0 installed`。
  但本轮 _glib_pkg() BFS 已可用（未抛"不可达"异常，说明 glib 包目录已找到，glib-2.0.pc
  shim 已写出）。故失败不再来自 shim 缺失，而是来自 **shim 所在目录没有被 configure 的
  pkg-config 实际搜索到**。
- 根因判定（关键证据）：configure.ac 中 `check >= 0.9.4`（第73行）在 glib（第98行）之前

  configure 采纳。
- 修复（换个路线，不再依赖 dmap_env 注入独立目录）：把 configure 需要的**全部手写 shim 直接

- 测试口径、上游45/适配4 用例计数不变；本改动只影响 configure 阶段 PKG_CONFIG_PATH 的

## 编译失败修复：automake maintainer 规则误触发（mtime 丢序）

### 现象（真机证据）
`conan create` 已成功跑完 configure，随后 `make -C libdmapsharing -j1` 阶段：
```
make[1]: Entering directory '.../b'
 cd . && /bin/sh .../b/missing automake-1.18 --gnu
.../missing[85]: automake-1.18: inaccessible or not found
make[1]: *** [Makefile:434: Makefile.in] Error 1
make: *** [Makefile:630: Makefile.in] Error 1
```
即 GNU make 在编译前试图重生成 `Makefile.in`，但 OHOS 真机无 automake
（PATH 无 aclocal/automake/autoconf），`missing` 助手报“inaccessible or not found”。

### 根因
release tarball 已带预生成 configure/Makefile.in/aclocal.m4，本不需任何
autotools 工具。但 automake 的 maintainer-mode 规则按 **mtime 早于
prerequisites 才触发**：源码树经 conan cache export → source() 的 copytree
物化时，若 `configure.ac`/`aclocal.m4`/`Makefile.am` 的 mtime 被复制成新于对应
`Makefile.in`，GNU make 就唤醒 `Makefile.in` 的重生成规则 → 调用版本化
`automake-1.18` → 无工具 → 在真正编译前失败（DRAFT-ohos-autotools-maintainer-
noregen / DRAFT-E656 同族）。这是时间戳问题，不是工具缺失；不能靠补
automake 依赖（会重生成不同版本 bootstrap 产物、破坏按 SHA 核对输入的一致性）。

### 方案（零侵入、不改上游）
build() 开头（configure 之前）调用新增 `_normalize_bootstrap_timestamps(src)`，
按 autotools 依赖链对 mtime 分层，使 maintainer 规则休眠、直接用预生成文件：
- T0=2000-01-01：源代码/控制文件 `configure.ac`、所有 `Makefile.am`、`m4/*.m4`
- T1=2001-01-01：`aclocal.m4`（由 T0 经 aclocal 生成）
- T2=2002-01-01：生成文件 `Makefile.in`（全部子目录）、`configure`、`config.h.in`
  及所有 `*.in` 模板

固定 200x 时间戳远低于当次 configure 产物（真实 Makefile/config.status 为
当前 202x 年），因此 `config.status --recheck`（configure < config.status → 重跑
configure）同样处于休眠，不会重跑 configure。

## 2026-09-28 修复第3轮（.la round-2 收尾）：libtool "is not a valid libtool archive"

### 现象（真机证据，commentId=-1790592225613）
round-2 的 `_fix_avahi_la`（staging 真实 .a + .la shim + avahi .pc `Libs:` 指向
`-L<staging> -lavahi-*`）已让 libtool 通过伴随 -lavahi-* 的 `-L<staging>` 推导出
`<staging>/libavahi-client.la`（错误路径已变成 ohos-avahi-la 目录，说明 -L 已被
采纳），但随后 CCLD 仍失败：
```
libtool: error: '.../ohos-avahi-la/libavahi-client.la' is not a valid libtool archive
make[1]: *** [Makefile:696: libdmapsharing-4.0.la] Error 1
```
所以 round-2 的「把 -L<staging> bake 进 MDNS_LIBS」机制本身生效了；唯一剩余阻塞是
`.la` shim 自身格式被判非法。

### 根因（源码定位 ltmain.sh）
CCLD 走 `func_mode_link` 的 `%DEPLIBS%` 分支，对每个依赖 `.la` 先做合法性门禁：
```sh
func_lalib_unsafe_p "$lib" \
  || func_fatal_error "'$lib' is not a valid libtool archive"
```
`func_lalib_unsafe_p` 只检查 .la **前 4 行**里是否有一行匹配 case 通配
`#\ Generated\ by\ *$PACKAGE*`，其中 `$PACKAGE` 是 libtool 自身硬编码的 'libtool'：
```sh
case $lalib_p_line in
    \#\ Generated\ by\ *$PACKAGE* ) lalib_p=yes; break;;
esac
```
round-2 的 shim 第 2 行写的是 `# Generated by libdmapsharing conanfile _fix_avahi_la`，
字面是 "libdmapsharing" 而非 "libtool"，不匹配 `# Generated by libtool`，故被判
"not a valid libtool archive"。

### 修复（conanfile.py _fix_avahi_la 第 2 行）
shim 前 4 行改为含 libtool 魔术可见行：
```
# lib{b}.la - a libtool library file
# Generated by libtool (shim for avahi-glib, which ships no .la)
```
第 2 行匹配 `# Generated by libtool*` → func_lalib_unsafe_p 通过。再补
`name='lib{b}.la'` 字段（与真实 .la 结构一致）。libdir/dependency_libs 仍指向
staging，保持自包含。不改源码、不改测试口径、不进 patches/。

## 编译失败修复（第 4 轮真机）：tests 链接 -lavahi-avahi-* 找不到库

### 现象（真机证据）
库本体 `make -C libdmapsharing` 全部 .lo 编译通过，随后 `make -C tests unit-test`
CCLD 链接失败：
```
ld.lld: error: unable to find library -lavahi-avahi-client
ld.lld: error: unable to find library -lavahi-avahi-common
clang-15: error: linker command failed with exit code 1
make: *** [Makefile:624: unit-test] Error 1
```
AVAHI/MDNS 的 -L<staging> 已正确解析（库链接因此通过），但链接行里出现
**名字双重前缀** `-lavahi-avahi-client` / `-lavahi-avahi-common`。

### 根因（源码定位）
conanfile.py `_fix_avahi_la()` 生成 .la shim 的 dependency_libs 时写的是：
```python
dl = " ".join(["-L%s" % staging] + [f"-lavahi-{d}" for d in chain[b] or []])
```
而 chain 的值已经是**带 avahi- 前缀的全名**（如 'avahi-client'、'avahi-common'），
再拼 `-lavahi-` 前缀就变成 `-lavahi-avahi-common`（双重前缀）。libtool 静态
归档依赖扫描在链接 unit-test 时读 libdmapsharing-4.0.la 的 dependency_libs

这串双重前缀的 -lavahi-avahi-* 被原样并入最终链接行，llvm 找不到对应库。
staging 里的真实 .a 文件名是 libavahi-common.a / libavahi-client.a，正确
标志应为 `-lavahi-common` / `-lavahi-client`。

### 方案（对准根因）
把 shim dependency_libs 的链接标志改为 `-l{d}`（d 已是全名，-lavahi-common
/ -lavahi-client），去掉重复的 -lavahi- 前缀：
```python
dl = " ".join(["-L%s" % staging] + [f"-l{d}" for d in chain[b] or []])
```
staging 同时放了真实 .a，-lavahi-* 可正常解析；不改源码、不改测试口径、
不进 patches/。pc_libs（avahi .pc shim 的 Libs:）原本就是 `-lavahi-client`
等正确形式，无需改动。

   而该测试调用的是字面 `/tmp`、不走环境变量，故 TMPDIR 重定向对它无效。这是真实的
   **ohos_feature 平台限制**，1 例受影响（其余 4 例 av-record 用例通过）。
2. **Check 早期退出截断覆盖**：生成文件 tests/unit-test.c 的 run_suite() 在
   srunner_run_all() 后 `if (nf != 0) exit(EXIT_FAILURE)`，任一 suite 有失败就退进程。
   suite 按固定顺序跑（av-connection, av-record, av-share, connection, md5, utils），
   故 _read_test 一失败，进程在 av-record 之后即退出，后续 4 套（av-share 24 /
   connection 4 / md5 2 / utils 5＝35 例）永不执行，配方即便累加所有汇总行也只能
   得到 10（前两套），拿不到 45 的完整覆盖证据。

### 方案
1. **不删断言、不跳测，仅去掉“首败即退”**：新增 `_patch_unit_test_no_early_abort(src)`，
   在 `make -C libdmapsharing`（生成 unit-test.c）之后、`make -C tests unit-test`
   编译之前，对生成的 tests/unit-test.c 用正则删除
   `if (nf != 0) { exit (EXIT_FAILURE); }` 块。每个 srunner_run_all() 仍跑完全套内
   全部用例并逐套打印 `N%: Checks: X, Failures: Y` 汇总行，失败照常可见——这是
   Check 版的 ctest 继续跑，只为拿到 45 例完整覆盖证据，不弱化任何断言、不静默跳过。
   tests/ 编译命令不含 WARN_CFLAGS/-Werror，遗留的 set-but-unused `nf` 不会致编译失败。
2. **只读 /tmp 按 ohos_feature gap 上报**：`_run_upstream_unit_test()` 解析日志时若
   匹配到 `dmap-av-record.c:<line>:F:_read_test:... Failed` 的只读 /tmp 特征，
   向 HMBS_UPSTREAM_TEST_RESULT 增加
   `gaps:[{count, category:"ohos_feature", detail:"mkstemp('/tmp/...') on read-only
   /tmp erofs -> ck_abort (TMPDIR redirect cannot apply to literal /tmp)", evidence:
   "unit-test.log: dmap-av-record.c:281:F:_read_test: Failed"}]`。
   计数仅匹配真实失败行（不做算术修补），缺口总数须等于“声明总数－通过数”，由下一次
   真机日志验证。


## 2026-09-28 修复：test_package 编译找不到 libsoup/soup.h + 上游 45 例全覆盖 gap 分类

### 现象（真机证据，commentId=-1790605610488）
上一轮修复后 make install 通过，上游 unit-test 跑满 45 例（发现 45 执行 45
通过 32 失败 13），但随后 test_package 编译失败：
```
dmap-connection.h:26:10: fatal error: 'libsoup/soup.h' file not found
#include <libsoup/soup.h>
make[2]: *** [CMakeFiles/test_dmapsharing.dir/...: test_dmapsharing.c.obj] Error 1
ERROR: libdmapsharing/3.9.14 (test package): Error in build() method, line 32
```
上游 13 例失败来自三个 OHOS 平台 gap：
- 10 例 dmap-av-share 在 line 1032 ck_abort（_build_share_test 里
  stat("/etc/services")/stat("/etc/group")，OHOS 无这些传统文件）
- 2 例 _serve_publish_test/_serve_publish_collision_test 在 line 1153/1193
  ck_assert(ok)（dmap_share_publish 需 avahi mDNS 守护进程，OHOS 无，
  "Unable to initialize mDNS: Daemon not running"）
- 1 例 _read_test（只读 /tmp，上轮已确认）

### 根因（两处）
1. **test_package 缺 libsoup 头路径**：libdmapsharing 静态库的 package_info 手写
   给 consumer 补依赖 include 目录时，对 libsoup3 只加了 `<libsoup3>/include` 等
   通用子目录，漏了 libsoup3 真实发布的 `include/libsoup-3.0`（其 cpp_info 里
   `includedirs=["include/libsoup-3.0"]`），故 `<libsoup/soup.h>` 无 -I 可解析。
   同时依赖 CMakeDeps 对静态库 cpp_info.requires 的传递头路径传播在本机未生效。
2. **上游 13 例失败未逐类打 gap**：旧 `_run_upstream_unit_test` 只对 `_read_test`
   计 ohos_feature gap，其余 12 例 av-share 失败无缺口条目，导致 gaps.sum(1) !=
   声明总数-通过数(13)，门禁会拒。

### 方案
1. **package_info include 传播改为“优先采用依赖自身发布的 includedirs”**：遍历
   glib/libsoup3/avahi-glib/check 时，把每个依赖 `cpp_info.includedirs`（相对路径、
   非绝对）按 package_folder 拼接全部加入 consumer 的 self.cpp_info.includedirs，
   保留 `include` + `include/glib-2.0` + `lib/glib-2.0/include` 兜底。libsoup3 的
   `include/libsoup-3.0` 由此进 -I，`<libsoup/soup.h>` 可解析，不再依赖 CMakeDeps
   传递是否生效。
2. **_run_upstream_unit_test 按失败行特征逐类打 gap**（计数只来自确定性失败行，
   不做总数算术）：
   - `dmap-av-share.c:1032:F:`（10 例，_build_share_test 的 stat → ck_abort）→
     ohos_feature（缺 /etc/services、/etc/group）
   - `dmap-av-share.c:1153|1193:F:_serve_publish`（2 例，publish ck_assert）→
     ohos_feature（无 avahi mDNS 守护进程）
   - `dmap-av-record.c:<n>:F:_read_test`（1 例）→ ohos_feature（只读 /tmp）
   - 残余未分类失败行 → test_failure（透明上报，绝不静默吞）
   gaps.sum 恒等于 failed；恒等式 passed+failed==executed 与 gap 无关、仍自检。
   category 全用 ohos_feature（各为具体平台能力/文件集差异），无 missing_dependency。

不改上游测试源码/断言，不进 patches/。test_package 新增用例数与上游 45 例
统计口径不变。

## 2026-09-28 轮：automake-1.18 regen 触发修复

### 真机失败
'make -C tests unit-test -j1' 中 `missing automake-1.18 --gnu tests/Makefile`
→ 'automake-1.18: inaccessible or not found' → Error 127。

### 根因
build() 曾在所有源码补丁**之前**调用 `_normalize_bootstrap_timestamps(src)`。
随后 `_patch_check_cflags` 与 `_patch_tests_check_cflags` 重写 configure /
Makefile.in / Makefile.am，把它们的 mtime 更新为当前时间。由于
`_patch_tests_check_cflags` 先写 Makefile.in 再写 Makefile.am，最终
tests/Makefile.am 的 mtime 比 tests/Makefile.in 更新，触发 automake 维护者
重生成规则 `tests/Makefile.in: tests/Makefile.am ...` → 调用 automake-1.18
（OHOS 无此工具）→ 失败。

### 修复
将 `_normalize_bootstrap_timestamps(src)` 调用移到**所有 self._patch_* 之后、
./configure 之前**，作为 configure 前最后一次源码变更。这样最终(已补丁)字节上
维持 source(2000) < aclocal.m4(2001) < generated(2002) 的时间戳层级，
所有 maintainer regen 规则保持静默，configure/Makefile.in 原样使用。

等修复属同一消费者构建、方向一致，但未覆盖链接期符号。

`-L<glib libdir> -lintl`（glib 在 test_package 是直接依赖，经
`self.dependencies.get("glib").package_folder/lib` 取），与主配方
`_configure_args` 相同的 glib 附带 libintl 解析方式（libgtop-tools 先例）。
