# libica 4.4.1 Adaptation Notes

## Outcome

**Structurally unadaptable on OpenHarmony PC / aarch64.** Not a matter of
insufficient effort or missing toolchain options — the library's semantics are
bound to IBM Z (s390x) hardware that does not exist on the target.

## Build Environment

- **System**: OpenHarmony (OHOS) 6.0.0.47
- **Target**: aarch64 (DEVICE: DAYU200 / RK3568)
- **Build System**: autotools (configure + make)
- **Compiler**: OHOS clang 15.0.4 (`aarch64-unknown-linux-ohos`)
  - 证据强度说明：`aarch64-unknown-linux-ohos` 可由 `reports/raw-logs/ica_confF.log`
    **第 74 行** `checking host system type... aarch64-unknown-linux-ohos`
    逐字复核（可 `sed -n '74p'` 验证）；但 **`15.0.4` 这个版本号在该日志中
    不出现**（日志只记录编译器**路径**，不含版本串）。它是构建机的 SDK 环境描述，
    属**未随包佐证**的信息，请勿把它当作本包"可机械复算"的计数之一。
- **Upstream**: libica 4.4.1 — https://github.com/opencryptoki/libica

## Why the build fails (three independent, architecture-level causes)

`configure` **succeeds** (exit 0, host correctly detected as
`aarch64-unknown-linux-ohos`) once `config.sub`/`config.guess` are taught the
OHOS triplet — i.e. the failure is provably in libica's own sources, not in the
toolchain.  `make` then fails with **39 `error:` lines** and produces only
**2 object files**:

| # | Root cause | Evidence |
|---|---|---|
| 1 | s390-only kernel UAPI header | `src/include/s390_ecc.h:19`, `s390_rsa.h:18` → `fatal error: 'asm/zcrypt.h' file not found` (2 occurrences) |
| 2 | s390 register-class inline asm | `src/include/s390_crypto.h` → **36 log lines** of `invalid output/input constraint '+a'/'+d'/'=d'`, which **deduplicate to 18 distinct failing sites**. The shared header is included by exactly **two** translation units (`icainfo.c` and `init.c`), so each of the 18 sites is reported twice: 18 × 2 = 36. |
| 3 | architecture-specific assembly | `src/mp.S` (generated by `src/mp.pl` + `src/perlasm/s390x.pm`, the only perlasm backend) → 51 errors on aarch64 clang; also fails on native host x86_64 gcc (`bad register name '%r1'`) |

Counts close exactly: `37 non-fatal + 2 fatal = 39` (the non-fatal 37 =
36 constraint lines + 1 `program_invocation_name`, a glibc-only symbol absent
from OHOS musl — a platform libc difference, listed separately from the three
arch causes).

> **Note on this build's configuration** (avoids over-claiming): the autotools
> build passes `-DNO_SW_FALLBACKS` (from upstream `src/Makefile.am:16`, i.e.
> upstream's own default, **not** something injected here). That switch is about
> s390 *mechanism* selection and is **not** used as evidence below — see the next
> section, which rests on `configure.ac` and a whole-repo grep instead.

## No portable / software backend exists

- `configure.ac` offers only `--enable-fips` / `--enable-debug` /
  `--enable-sanitizer`: **no architecture switch, no `--disable-hw`, no
  software backend**.
- Repo-wide grep for `__aarch64__|__x86_64__|--disable-hw|software backend`
  returns **0 hits**.
- OpenSSL is used only for BN/EC parameter encoding and FIPS self-test — it is
  **not** the crypto backend; all real operations go to CPACF instructions or
  the CEX card.
- `-DNO_CPACF` (the libica-cex build) is **not** a software fallback: it only
  switches from CPACF instructions to the CEX card — still mainframe hardware.

> **Most common misreading**: the comment at `src/ica_api.c:383`
> (*"the software fallback will still work without an adapter handle"*) refers
> to switching between *s390 mechanisms* (CPACF instead of CEX), **not** to a
> portable software implementation.  Its capability probes themselves execute
> s390 instructions (`s390_kmc`, `s390_kimd`, `s390_ppno`, `s390_kma`,
> `s390_kdsa`, `s390_pcc`).

## Upstream test suite

48 upstream tests; **0 are executable on aarch64** (N=0).  The 5 tests that do
not literally reference hardware still call libica symbols (42/16/9/103/7
`ica_*` calls respectively); `mp_test.c` exercises `mp.S` directly — the very
assembly that cannot be assembled.  Upstream CI is 3/3 `arch: s390x`
(`.travis.yml` lines 10/15/20).

## What this package delivers

This is a **failed-adaptation record package** (same shape as
`archives/b/bltool/0.2.4` and the other `status: failed` entries): the recipe
builds the *record*, so `conan create` succeeds and CI stays green, while
`status: failed` in `manifest.yaml` records the truthful outcome.

**Scope of `test_package`**: it verifies that this *record* is present,
complete, truthful and internally consistent — it recomputes the failure counts
from the shipped raw logs and checks that every evidence path cited by
`manifest.yaml` resolves inside the package.  It **does not** verify that the
libica library itself builds or functions on aarch64; it cannot, because
upstream libica does not compile there.

## Why no "buildable libica" recipe is committed

Committing a recipe that "builds" libica on aarch64 would necessarily be a
fake adaptation: deleting `mp.S` breaks the `ica_mp_mul512`/`ica_mp_sq512`
symbols, stubbing the s390 inline asm amounts to rewriting the entire crypto
library, and keeping empty API shells yields wrong crypto results.  Any of
those routes would additionally force fabricated test pass rates, violating the
"numbers must be truthful" rule.  This record therefore documents the failure
instead of faking a success.
