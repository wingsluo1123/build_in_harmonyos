# multimon 1.0 路径 B 三臂证据

## 单一知识主张

固定宽度二进制记录运行在字节流之上时，`read()` 的返回边界不是记录边界。解析器必须把不足一个完整记录的残余字节保存为下一次读取的前缀；EOF 时还必须区分无残余的正常结束和带残余的截断记录。

## 当前库的真实触发链

1. `multimon -t raw` 对调用者提供的路径执行 `open()`，随后直接 `read()`，没有上层偶数字节保证。
2. 上游使用 `short buffer[8192]`，仅转换本次读取中的完整 `short`。
3. 奇数字节读取的末字节只打印告警，未进入下一轮。
4. 下一轮从新缓冲区首地址开始解释，整个 16 位 PCM 序列永久错位。

修复改用字节缓冲区，以 `memcpy()` 提取完整本机 16 位样本，保留 `total % sizeof(short)` 个残余字节；`EINTR` 保留状态重试，其他读取错误失败，EOF 携带残余时以截断记录失败。当前生产验证是阻塞文件/管道路径；非阻塞描述符在 `EAGAIN/EWOULDBLOCK` 时还必须保留残余并等待可读事件，不能原地忙重试。

## 同输入三臂实验

共同条件为真实 HarmonyOS PC AArch64、SourceForge 官方 1.0 源码、安装后的生产 `gen`/`multimon`。`gen` 生成同一段 `123A` DTMF 原始 PCM；消费者通过继承匿名管道及 `/proc/self/fd/<n>`，先启动 `multimon`、再写 1 字节，并用 `FIONREAD` 确认该字节已被单独取走后才写剩余数据。原实现、伪修复和正确修复各重复 3 轮，结果分别稳定为失败、失败和通过。

| 臂 | 实现 | 结果 | 判定 |
|---|---|---|---|
| A 原实现 | 奇数尾字节只告警并丢弃 | 规则文件得到 4/4；分片管道得到 0/4，测试退出 1 | 缺陷稳定复现 |
| B 伪修复 | 重试 `EINTR/EAGAIN`，把告警改成“重试” | 仍未保存残余，分片管道得到 0/4，测试退出 1 | 重试不能修复已消费字节的所有权 |
| C 正确修复 | 保存残余字节并在下一轮补齐；截断 EOF 失败 | 规则文件与管道完整 stdout 相同，得到 4/4；测试退出 0 | 记录边界和终态语义同时成立 |

撤销 `0003-preserve-partial-pcm-samples.patch` 后，同一测试稳定恢复 A 臂失败。

## 可执行复现

```bash
conan create archives/m/multimon/1.0 \
  -pr:h=ci/conan/profiles/ohos-aarch64 \
  -pr:b=ci/conan/profiles/ohos-aarch64 \
  --build='multimon/*'
```

test_package 从依赖对象取得真实包目录，不经 `PATH` 搜索同名程序。它验证规则文件、分片继承管道、干净 EOF 和截断 EOF 四个完整流程。

## 查重与边界

- E13539 处理 JPEG marker 在任意分块边界被拆开时的扫描器重叠窗口；本条处理固定宽度记录的 `read()` 残余所有权和 EOF 截断判定，输入模型、状态量和最小修复均不同。
- FIFO、管道、socket、字符设备以及其他可能产生任意短读的字节流均可能命中；常规文件恰好返回偶数字节不能证明实现正确。
- 对变长协议、已有带长度重组层或 API 明确保证整记录交付的输入不适用。
- 仅告警、仅重试、对本轮长度向下取整或假定下一次读取会恢复对齐都不是等价修复。
