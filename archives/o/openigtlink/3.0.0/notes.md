# openigtlink 3.0.0 适配笔记

## 编译环境

- 构建系统: cmake（上游 CMake + CTest；`Documentation`/`Examples` 全程关闭）
- 编译日期: 2026-10-14
- 编译器: clang 15 / clang++（OHOS SDK 26.0.0.18 native/llvm）
- 目标: OpenHarmony / HarmonyOS PC，aarch64-linux-ohos，musl libc，Release
- Conan: 2.29.1（OHOS 适配版），profile `ci/conan/profiles/ohos-aarch64`
- 依赖: **零第三方 Conan 依赖**，仅 POSIX pthread / libm / socket 族，OHOS sysroot 原生提供

## 编译步骤

```bash
# 上游测试入口：CMake 项目，没有 make check，CTest 就是上游入口
conan create archives/o/openigtlink/3.0.0 \
  -pr:h=ci/conan/profiles/ohos-aarch64 -pr:b=ci/conan/profiles/ohos-aarch64
```

配方要点：

1. `source()` 取官方 tag `v3.0` 的 GitHub archive tarball（sha256 已校验）。
2. `build()`：`apply_conandata_patches()` → `cmake.configure()` → `cmake.build()` → `cmake.test()`。
   `cmake.test()` 即层 1 上游官方测试，62 个唯一 CTest 用例在本机原生执行。
3. `BUILD_TESTING=ON`；`USE_GTEST=OFF` 走上游 `igtlTestConfig.h.in` 内置的非-gtest 回退，
   免除 configure 期通过 `ExternalProject` 下载 googletest/googlemock 1.7.0（2016 年产物）的联网依赖。
   `ADD_TEST` 注册面与用例数在两条路径下完全相同。
4. `CMAKE_POLICY_VERSION_MINIMUM=3.5`：上游 `cmake_minimum_required(VERSION 2.4)` 与 CMake 4.1.2 不兼容。
5. `OpenIGTLink_INSTALL_LIB_DIR=lib` / `OpenIGTLink_INSTALL_INCLUDE_DIR=include`：改为 Conan 标准布局。

## 遇到的问题与解决方案

| # | 问题 | 根因 | 解决方案 |
|---|------|------|----------|
| 1 | configure 期 CMake 4.1.2 硬错误：`The file .../OpenIGTLinkTargets.cmake was generated by the export() command. It may not be used as the argument to the include() command.`（4 处） | 上游 `OpenIGTLinkConfig.cmake.in` 与 `UseOpenIGTLink.cmake.in` 用 `include()` 引入 `export()` 产物；CMake ≥ 3.0 起由 CMP0024 判为硬错误，且 CMake 4.x 已移除 OLD 行为（`-DCMAKE_POLICY_DEFAULT_CMP0024=OLD` 无效） | 补丁 0001 / 0004：把该 `include()` 包进 `if(NOT TARGET OpenIGTLink)` 守卫，安装树不受影响 |
| 2 | 包安装后 `include/` 只有 3 个 configure 生成的 `igtlConfigure.h`/`igtlTypeConfig.h`/`igtl_typeconfig.h`，**零个库头文件**，任何下游都无法编译 | 上游 `Source/CMakeLists.txt:75` 只在 `MSVC OR CMAKE_GENERATOR MATCHES "Xcode"` 时填充 `OpenIGTLink_INCLUDE_FILES`，且该 `IF` 没有 `ELSE` 分支；Unix Makefiles 下该变量恒为空，`INSTALL(FILES ...)` 装 0 个文件（上游真实缺陷） | 补丁 0002：三处条件改为无条件收集（73 个公开头文件），安装布局保持上游意图的**平铺** `include/` |
| 3 | `conan create` 编译上游测试树失败：`Testing/igtlImageMessageTest.cxx:91: error: use of undeclared identifier 'typeof'`（共 12 条诊断） | profile 的 `compiler.cppstd=17` 让 CMakeToolchain 发 `-std=c++17`（严格 ISO），GNU 关键字 `typeof` 不再可见；`Testing/igtlTestConfig.h.in` 的非-gtest `EXPECT_THAT` 回退宏（第 221/222 行）用了 `typeof` | 补丁 0003：改为保留名拼写 `__typeof__`（各语言模式均可用）。**不能**换成 `decltype`：左值下标会得到引用类型，`std::vector<int&>` 非法 |
| 4 | 手工构建（未设 cppstd）反而全绿，掩盖了问题 3 | 未指定 `-std` 时 clang 默认 `gnu++17`，`typeof` 恰好可用 | 编译期兼容性必须以 `conan create`（真实工具链 flags）判定；手工构建只作快速定位 |
| 5 | 上游 62 个用例里没有任何 socket/网络用例，而本库就是网络协议库 | 上游 `Testing/CMakeLists.txt` 第 66-68 / 133-135 行把 `igtlSocketTest`/`igtlClientSocketTest`/`igtlServerSocketTest` 注释掉了；这 3 个源文件在非-gtest 回退下也编译不过（用了 `testing::_`/`AtLeast`/`Invoke` 等仅 gmock 提供的设施） | 不强行启用上游死代码；改由消费者测试从公开 API 侧补一条 127.0.0.1 回环往返（`igtl::ServerSocket`/`igtl::ClientSocket` 发收一条 TRANSFORM 并解码） |
| 6 | 上游 `igtlPositionMessageTest` 被注册两次，`ADD_TEST` 语句 63 条但 CTest 只有 62 个用例 | `Testing/CMakeLists.txt` 的 protocol-version-3 分支里重复 `ADD_TEST(igtlPositionMessageTest ...)` | 不改上游；统计上游用例数时按 62 个唯一用例记录 |
| 7 | 消费者测试首版断言 `Socket::Send()` 返回值等于字节数，失败 | `igtl::Socket::Send()` 成功返回 **1**（不是字节数），失败返回 0；只有 `Receive()` 返回字节数 | 消费者测试改为 `== 1` |

## 源码修改

四个补丁，全部为 portability 类、无平台守卫、`platform_only: False`（对任何平台都是修正）：

| 补丁 | 目标 | 变更 |
|------|------|------|
| `0001-OpenIGTLinkConfig.cmake.in.patch` | `OpenIGTLinkConfig.cmake.in` | `include(${OpenIGTLink_LIBRARY_TARGETS_FILE})` 包进 `if(NOT TARGET OpenIGTLink)`（+7/-1） |
| `0002-Source-CMakeLists.txt.patch` | `Source/CMakeLists.txt` | 三处 `IF( MSVC OR ${CMAKE_GENERATOR} MATCHES "Xcode" )` → `IF(TRUE)`，使 73 个公开头文件在所有 generator 下都被收集并安装（+10/-3） |
| `0003-Testing-igtlTestConfig.h.in.patch` | `Testing/igtlTestConfig.h.in` | 非-gtest `EXPECT_THAT` 回退宏的 `typeof` → `__typeof__`（+6/-2） |
| `0004-UseOpenIGTLink.cmake.in.patch` | `UseOpenIGTLink.cmake.in` | 文件头部加 `IF(TARGET OpenIGTLink) RETURN() ENDIF()`，同一 CMP0024 守卫（+8/-0） |

补丁集与工作树的等价性验证：把 4 个补丁依次应用到官方 tarball 解压出的纯净源码，
`diff -r --brief <patched> <work>` 无任何差异。

## 依赖版本

无第三方依赖。仅使用 OHOS sysroot 提供的 `libc`（musl）、`libm`、`libpthread`、`libc++_shared`。
`libpthread.a` / `libm.a` 在 OHOS sysroot 中是 8 字节的空归档 stub（`!<arch>`），`-lpthread -lm` 仍合法。
产物 `libOpenIGTLink.so.3.0.0` 的 `DT_NEEDED` 闭包只有 `libc++_shared.so` 与 `libc.so`，无第三方 `.so` 泄漏。

## finish Step 3（G0 干净构建验证）失败的真实根因 —— 框架侧限制，非配方缺陷

`finish` 的 Step 3 输出：

```
ℹ️ G0: 应用 4 个补丁...
✅ G0: 4 个补丁全部应用成功
ℹ️ G0: 运行 configure...
❌ G0: configure 失败 (exit 127)
```

根因：`scripts/ohc/clean_verify.py` **硬编码 autotools 三步**（`<bash> ./configure --prefix=...`
→ `make -j1` → `make install DESTDIR=`），其 `add_argument` 没有任何"构建系统"参数。
openigtlink 上游是**纯 CMake 工程**，源码树里根本不存在 `./configure`，因此 exit 127 是
`command not found`，而不是配置错误。此外 G0 的 `is_expected` 分支只认 `conanfile.py` 里出现
字面量 `replace_in_file`，本配方 `package()` 只用 `cmake.install()`，所以 G0 必然走 fail 分支。

处置：**不为此修改配方**（该门禁在 `finish` 中是**非阻塞**的，打印 ⚠️ 后继续）。
G0 的真实目的是"从官方 tarball 重新解压 → 打补丁 → 真实编译"，这一点由下面两条更强、
更贴近真实 CI 的证据覆盖：

- **G2 `conan create`**（finish Step 4 内）：从官方 tarball `source()` → 应用 4 个补丁 → 真实
  `cmake configure/build` → 62 个上游 CTest 用例 → `cmake install` → 消费者测试。
  日志 `reports/conan-create.log`（本次运行为**缓存命中重跑**，仅 Export + Cache + test_package，
  故不含 CTest 段；`error:` 计数 **0**）。**从零构建的完整证据取 W3**：`reports/w3-local-ci.log`
  （126 个 TU 编译、62 用例全过、`error:` 计数 **0**）。
- **W3 本地 CI 模拟**（`ci/conan/build_and_test.sh`，finish Step 5）：与真实 CI 同一脚本入口。

G0 唯一有效的输出是"4 个补丁全部应用成功"，该结论与纯净源验证一致。

## 注意事项

- 守护 `OpenIGTLink_INCLUDE_FILES` 的那个 `IF` 一旦回归，包会再次变成「零头文件」但**构建仍然全绿**
  （上游自带的 `Testing/` 走源码树相对路径，不需要安装头文件）。任何改动后必须复核
  `find <package_folder>/include -name '*.h' | wc -l`，或直接看消费者测试能否编译。
- `USE_GTEST=ON` 会在 configure 期联网下载 googletest 1.7.0；不要为了「更接近上游默认」而打开它。
- 上游 3 个 socket 测试源文件在非-gtest 回退下编译不过，且未被注册，属上游死代码，不要试图启用。

## 对话记录

### 对话 #1 [2026-10-14]
- 问题: 上游 v3.0 在 CMake 4.1.2 下 configure 直接硬失败，报 CMP0024（`include()` 了 `export()` 产物）。
- 操作: 先试 `-DCMAKE_POLICY_DEFAULT_CMP0024=OLD`，实测 CMake 4.x 已移除该政策的 OLD 行为，`configure_rc=1`；改为打真实补丁。
- 结果: `OpenIGTLinkConfig.cmake.in` 与 `UseOpenIGTLink.cmake.in` 各加一处 `if(NOT TARGET OpenIGTLink)` 守卫（补丁 0001/0004），configure_rc=0，CMake Error 数 0。

### 对话 #2 [2026-10-14]
- 问题: 消费者测试第一次编译不过——`#include <igtlTransformMessage.h>` 根本找不到文件。
- 操作: 在既有构建树执行 `cmake --install . --prefix <dir>` 看真实安装布局。
- 结果: `include/` 只有 3 个 configure 生成的头文件，73 个库头文件一个都没装。追到 `Source/CMakeLists.txt:75` 的 `IF( MSVC OR ${CMAKE_GENERATOR} MATCHES "Xcode" )` 没有 ELSE 分支，补丁 0002 修为无条件收集。此后消费者测试可编译、可运行。

### 对话 #3 [2026-10-14]
- 问题: 本地手工构建与 ctest 全绿（62/62），但 `conan-verify` 的 G2 `conan create` 编译上游测试树失败：`use of undeclared identifier 'typeof'`。
- 操作: 定位到 `Testing/igtlTestConfig.h.in:221/222` 的 `typeof`；写定向实验——同一 TU 分别用 pristine 头文件与修复后头文件在 `-std=c++17` 下编译。
- 结果: pristine → 12 条 error，修复后 → 0 条 error；25 个「已注册」测试 TU 严格模式编译失败数 0。根因是 profile 的 `compiler.cppstd=17` 触发严格 ISO 模式，而手工构建未设 `-std` 时 clang 默认 `gnu++17`，`typeof` 恰好可用——这正是「手工构建全绿 ≠ CI 全绿」的实例。

### 对话 #4 [2026-10-14]
- 问题: 本库是网络协议库，但上游 62 个用例里没有任何 socket/网络用例。
- 操作: 检查上游 `Testing/CMakeLists.txt`，并尝试在非-gtest 回退下编译那 3 个 socket 测试。
- 结果: 上游把 `igtlSocketTest`/`igtlClientSocketTest`/`igtlServerSocketTest` 的 `ADD_EXECUTABLE`/`TARGET_LINK_LIBRARIES` 全部注释掉了（第 66-68、133-135 行），且它们依赖仅 gmock 提供的 `testing::_`/`AtLeast`/`Invoke`，非-gtest 路径下编译不过。因此不启用上游死代码，改在消费者测试里用公开 API 补一条回环往返。
