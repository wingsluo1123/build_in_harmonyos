## 已知上游缺陷（本轮未打补丁，如实记录）
- 现象：`proxycheck -t 2 -d 127.0.0.1:9 -c chat 127.0.0.1:1`（`-c chat` 不带 `:sendstr:expectstr`）
  -> **SIGSEGV，rc=139**；带参数形式 `-c chat:foo:bar` 正常（rc=0）。
- 根因（读源码定位，非猜测）：`proxycheck.c:407-409` 在 `-c` 参数不含冒号时把 `check_arg`
  置为 `NULL`，`proxycheck.c:539` 直接 `check->init(check_arg)`；chat 的 init 即
  `expecti(char *arg)`（`proxycheck.c:833`）第一句 `strchr(arg, ':')` 未做 NULL 保护
  -> 空指针解引用。同函数对 `!p || !p[1]` 已经有 `usage("send:expect strings expected")`
  的正确报错路径，只缺 NULL 这一道。
- 该缺陷与平台无关（glibc 同样会崩），因此不属 OHOS 适配引入；本轮按“探索阶段不生成补丁”
  的口径未改上游源码，消费者测试用带参数的合法形式覆盖同一代码路径。
  1 行 `if (!arg) usage(...)` 守卫可作为后续候选修复（需 `refresh-patch --auto` 重跑验证）。
- `proxylogger` 设计为 inetd/xinetd helper：main() 用 `getpeername(0, ...)` 取对端地址，
  stdin 不是 socket 时直接 `return 1`。因此它不是可独立驱动的 CLI，测试里按该契约断言退出码。

## TEST 块签名修复与改前/改后对照（2026-10-12，统筹 13:0x 派单裁定① 批准）

### 根因（行级取证）
- `event.h:47` `typedef void ev_io_cbck_f(void *data, int revents, int fd, struct ev_ct *ct);`
- `event.h:57` `typedef void ev_tm_cbck_f(void *data, struct ev_tm *tmr, struct ev_ct *ct);`
- 实现侧调用点与 typedef **一致**：`event.c:902` `tmr->evtm_cbck(tmr->evtm_data, tmr, ct);`、`event.c:911` `efd->cbck(efd->data, revents, efd - ct->efd, ct);`
- 形参声明点也一致：`event.c:662/702`（`ev_io_cbck_f *cb`）、`event.c:747/810/819`（`ev_tm_cbck_f *cbck`）
- 唯独 `#if TEST` 块内两个定义仍是**旧约定**：`event.c:925` `pc(struct ev_ct *, struct ev_tm *, void *)`、`event.c:933` `rt(struct ev_ct *, int fd, int events, void *)`
  ⇒ 运行期按 typedef 传 `(data, tmr, ct)`，`pc` 却把第 1 个实参（`char*`）当 `struct ev_ct*` 解引用 → SIGSEGV。
- 上游 `Makefile.in` 从不编译该块（`grep -nE 'DTEST|TEST' Makefile.in` 无命中，rc=1）⇒ 签名漂移自 2004 年起未被任何构建发现；**纯源码级缺陷，非 OHOS/musl 引入**（glibc 下同崩）。
