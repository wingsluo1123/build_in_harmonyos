# 适配技能反馈：Viskores 1.1.1

使用 openharmony-compile-agent v12.22，HarmonyOS PC 原生 Conan/CMake/Ninja。
此反馈与一个软件的适配证据放在同一归档内，不修改技能或基础设施。

## 有效部分

- W0 无外部 Conan 依赖、上游清点、在 build() 内执行全量测试及 W4 独立审计，
  能防止只凭编译/版本输出认定功能可用。
- E092/E1655 的平台规则与 E504/E077 的安装 ELF 经验可复用；本次另用相同路径的
  字节替换对照确认机制，未把已有经验重复申报为知识创新。
- 对测试修改提供独立输入位模式、有理数参考、原始作者文档与硬件对照，有助于区分
  错误 oracle 与实际算法/平台缺陷。全量原始失败仍保留。

## 发现的问题与处理

- Conan `CMake.build(cli_args=["-jN"])` 的直观资源限制会被 helper 生成的后置原生
  `-jM` 覆盖；已提交一组成对草稿及独立官方 zlib 四组对照，可复跑并重算并发。
- 首次官方 W3 的 G0b 使用三位编号规则，拒绝主分支已有 E1000+ 正式条目。KC5 同样只数
  三位编号；KC2 命中其他正式条目的占位符词汇。这些是共享框架阻塞，未修改或绕改。
  既有协调修复 PR #16109、#16376 首次查询时开放。首次失败日志完整保留且没有成功标记。
  随后同步维护者已合入的 `a9a60dda6` 热修复，KC 与图谱结构检查均通过；
  后续官方 W3 的最终结果以 native-result.json 和实际官方日志为准。
- 技能通用 submit-only 说明与本机 README 的 SDK profile / AtomGit API 直接提交约定
  存在环境流程差异。先保留真实 native 与失败证据，待主分支修复后再验证官方流程；
  不手写 `.ci-result.json`、不把 native 成功标成 W3 成功。

## 建议

- 在模板编译资源建议中同时展示 CMake 参数层与 Ninja 参数层，给出原生命令实测，避免只
  观察前置 `-j`；区分限制策略与实际发生的 OOM/EAGAIN，不根据风险虚报故障。
- 把共享图谱命名、索引与占位符规则的修正集中到已有基础设施 PR，适配 PR 保持原子性。
- 对大套件证据采用固定历史提交、逐文件SHA、简短台账及独立重算入口，避免把数万行
  测试输出混入代码审查；不要用删原始结果或只保留成功摘要代替完整证据。

## 经验边界

本次仅默认 CPU/Serial、标准库及软件渲染；没有验证可选 GPU/多线程/外部后端。
安装 RUNPATH 方案针对当前无外部 Conan 共享依赖布局，启用外部依赖时应独立复核。
专项 C 资格、B 知识入库与远端 CI/AI 均由相应评审流程裁定。
