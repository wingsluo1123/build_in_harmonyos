# HarmonyOS device acceptance

This harness builds or accepts two Stage HAPs: the packaged wvkbd system IME and
a separate temporary editor. The editor imports the **exact PIC consumer archive built by
Conan**, which executes C01–C04 from the installed package's test resources.
The IME product does not contain those test resources.

The runner targets the approved HarmonyOS 6.1/API 23 2in1 device. It requires
exactly one connected HDC target, and refuses to replace either pre-existing
`org.openharmony.wvkbd` or `org.openharmony.wvkbd.test` install.

## Local configuration

### Use externally signed HAPs

For manual signing, sign the two unsigned HAPs from the current Conan/Hvigor
build, then supply both outputs using `WVKBD_IME_HAP` and `WVKBD_EDITOR_HAP`.
Also set `WVKBD_HDC` to the local HDC executable. This route does not require
SDK, Hvigor, Node, generators, consumer-library or signing-config settings in
the runner and never invokes a build, signing tool or account workflow.
Conan's normal native package/consumer build still runs before device acceptance.

Equivalent Conan configuration keys are `user.wvkbd:ime_hap` and
`user.wvkbd:editor_hap`; direct runner options are `--ime-hap` and `--editor-hap`.
Prefer environment variables for private paths so Conan's profile summary does
not print them. The runner's own diagnostics never print external paths.

Both paths must be supplied together and name existing files. A partial pair
fails even when source signing settings are also present. A complete pair takes
precedence over source-build settings. The runner copies both files into its
temporary directory and checks each `module.json` bundle identity before any
installation: IME must be `org.openharmony.wvkbd`, editor must be
`org.openharmony.wvkbd.test`. Missing/ambiguous/invalid manifests or swapped
bundles fail. This metadata check does not verify a development signature or
build provenance; HDC/platform installation must still accept the actual
signatures, and the supplied pair must come from the current test build.
Original signed and unsigned files are never modified or removed.

### Build and sign from source

Use local DevEco debug signing materials **for these two bundle IDs and this
device**. Keep credentials and signing paths outside the repository. If they
do not exist, authorize DevEco's active Huawei developer account to issue the
two debug profiles first. A profile from another sample is not suitable.
This runner does not log into an account or issue profiles.

Create an external UTF-8 JSON file mapping exactly these two bundle names to
their complete DevEco `signingConfigs` objects. Each object has `name`, `type`,
and `material`, as generated by DevEco; `material` contains the local
`storeFile`, `storePassword`, `keyAlias`, `keyPassword`, `certpath`, `profile`
and `signAlg` values. Do not put that file or its contents in Git. Hvigor builds
the temporary HAPs unsigned; the local SDK HAP signing tool signs and verifies
them. Decrypted passwords travel over the launcher's standard input and are not
placed in process arguments or printed.

Supported Conan configuration keys (all under `user.wvkbd:`) are `hdc`,
`hdc_serial`, `sdk`, `hvigor`, `node`, `base_sdk`, `signing_config`,
`ime_hap`, and `editor_hap`.
Their equivalent environment variables are `WVKBD_HDC`, `WVKBD_HDC_SERIAL`,
`WVKBD_SDK`, `WVKBD_HVIGOR`, `WVKBD_NODE`, `WVKBD_BASE_SDK`, and
`WVKBD_SIGNING_CONFIG`. Prefer the environment for the optional target value
so Conan does not print it in its profile summary. The runner always uses the
sole default connection, and privately checks it against `hdc_serial` if set.

`sdk` names DevEco's SDK root; `base_sdk` names its `default/openharmony` SDK;
`hvigor` names the installed `tools/hvigor/hvigor/bin/hvigor.js` engine and
`node` the bundled Node executable. Offline module resolution uses that
installation's Hvigor and plugin. Keep SDK/build caches outside this tree.
Direct `compileNative` also requires the matching Conan CMakeDeps directory via
`WVKBD_CONAN_GENERATORS` or `wvkbd_DIR`; the source-build runner supplies it.

Run with an OHOS armv8 host profile and a native build profile:

```text
conan create archives/w/wvkbd/0.15 --version=0.15 -pr:h=<local-ohos-profile> -pr:b=default --build=missing
```

No device configuration means an explicit skip, **never a device pass**.
Any partial configuration, failed signed build, missing UI element, failed
case, stale marker or unsuccessful cleanup fails acceptance.

For an existing Conan build, `python run_harmonyos_device_test.py --help` lists
the equivalent command options. Direct source-build invocation additionally needs
`--generators`, `--consumer-library`, and `--package-root`: respectively the
Conan test package's CMakeDeps directory, its `libwvkbd_test_consumer.a`, and
the dependency's installed `share/wvkbd/0.15` directory. Signing objects are
injected only into a temporary build copy, which is deleted after the run.

## Device flow and evidence

The runner opens public Settings, uses its inspected search field to find
input methods, enables the task IME checkbox, selects the clickable row in the
public default-input-method picker, and waits until the selector displays
`wvkbd`. It then opens the separate editor with a unique run ID.

For keyboard interactions, the IME reports screen-space bounds from its own
ArkUI components. The runner taps those measured keys in order: `a`, Shift,
`b`, Space, Caps, `c`, Backspace, Enter. No editor text is injected by the
host. Visual checks use component snapshots of the Shift key and Shift label
only; they never capture the whole display or editor contents. D03 downsamples
the rendered non-ASCII Shift label to a 16×16 pixel mask and checks for an
arrow head and centered stem, rejecting an empty label or missing-glyph box.
Shift on/off is confirmed from the rendered key background colors.

Only the editor compares its private contents against the synthetic expected
value `aB `. Enter must invoke its Done callback with that value (a single-line
TextInput submits rather than inserting a newline). The test then focuses the
editor again, observes Shift off, taps Shift and requires the actual panel to
show Shift on. It records that active session's token and focuses a second real
TextInput. The runner waits for the old panel to be destroyed and the focus
callback to fire. On the tested HarmonyOS 6.1 device, this client handoff did not emit `inputStop`;
the runner records that observed behavior and requires a
successful focus request plus a distinct replacement `input_start` token. If
the platform does emit `inputStop`, it must precede destruction. Only after
that evidence does the test open a new session and require a distinct
start/create/show token with the actual panel showing Shift off before typing
`d` through the IME. The editor emits D04 when that `d` arrives, then requests
focus on its second TextInput. The `transition_focus` callback and lifecycle
markers carry an increasing sequence
number so repeated stop/focus events in the same run remain distinct to the
runner's log de-duplication. This records final cleanup without a runner tap
that could steal editor focus. The runner arms this boundary before typing and
requires the successful focus request, focus callback, old panel destruction,
and a distinct replacement session.

Passing output requires numeric `C01=1` through `C04=1`, `D01=1` (primary
text), `D02=1` (Enter), `D03=1` (the visible UTF-8 Shift arrow), and `D04=1`
(fresh session/plain `d`). D03 comes from UI inspection; the remaining cases
come from the editor. The runner separately requires a fresh IME service and
the old/new session lifecycle on either side of the recorded Shift/restart
boundary. The old session must show start/create/show/destroy and either an
ordered stop callback or the 6.1 handoff evidence (focus callback, successful
focus request, destroyed old panel, then a distinct replacement start). The new
session must show start/create/show/stop/destroy. During final HarmonyOS 6.1
handoff, the new `input_start` callback may precede destruction of the old
panel; the replacement panel still must be created and shown after old-panel
destruction. Earlier completed sessions
cannot satisfy this check. Device-log snapshots and UI observations form one
ordered trace; D04 must follow readiness of the correlated new session.
It samples only the two test log tags and drops pre-existing marker records.
No raw editor content, identity, endpoint or signing values are printed.
UI trees are scoped to Settings/the two test bundles and immediately deleted.
Visual data is restricted to one key and one symbol component; no full-screen
capture is made.

Both temporary bundles are uninstalled in `finally`, even after a partial
installation, failed launch, logging failure or incomplete report. Their
absence is queried before a cleanup pass is printed. Pre-existing bundles are
protected by a guard outside that cleanup block.

Host checks: `python -m pytest archives/w/wvkbd/0.15/test_package/tests -q`.
They cover configuration rejection, failure cleanup, stale/incomplete marker
rejection, session token reuse, and the pre-existing-install guard. Host checks
and unsigned assembly do not establish system IME runtime acceptance.

Acceptance evidence and final case counts are recorded in `PORTING_REPORT.md`
after the current-source Conan and device run completes.
