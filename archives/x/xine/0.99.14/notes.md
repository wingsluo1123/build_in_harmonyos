# xine 0.99.14 适配笔记

> 上游工程：SourceForge `xine` 项目中的 **xine-ui**（`xine` 播放器的 X11 前端）。
> 命名口径：本包在 Conan/归档侧的**包名取 `xine`**（目录 `archives/x/xine/0.99.14`、
> `conanfile.py name = "xine"`、分支 `feat/xine-0.99.14`），与任务立项标识一致；
> 文内出现的所有 `xine-ui` 均指**上游项目名**（tarball `xine-ui-0.99.14.tar.xz`、
> 生成器头 `Automatically generated by xine-ui version 0.99.14`、mime 文件
> `xine-ui.xml`、数据目录 `share/xine-ui/`），这些字符串由上游决定，不可改。
> `0.99.14` 这个版本号属于上游 xine-ui 版本线；媒体引擎 xine-lib 没有 0.99.x 版本
> （本仓库已归档 `xine-lib/1.2.13`，作为本包依赖）。
> CI 门禁耦合关系：L0n 要求分支名 == `<包名目录>-<版本目录>`，L0m-4 要求
> `conanfile.py name` == 包名目录，三者必须同名，故改名是整包一次性的。

## 编译环境
- 构建系统: autotools（`configure` + `make`，tarball 内已带预生成 `configure`；OHOS 上不重跑 autoreconf）
- 编译日期: 2026-10-17
- 编译器: clang / clang++（ohos-sdk 26.0.0.18 sysroot，`aarch64-unknown-linux-ohos`，musl libc）
- 平台: OpenHarmony PC / aarch64，原生构建（build == host），`uname -s` = `HarmonyOS`
- 类型: `package_type = application`，交付 3 个可执行文件 + 皮肤/图标/desktop/mime/man 数据
- 工作路径: 源码 `…/.tmp/builds/xine-ui-0.99.14.work`；归档 `<worktree>/archives/x/xine/0.99.14`
- 状态: published（conan create 全绿）

## 编译步骤

```bash
# 1) W0 依赖预检（逐个 conan download --only-recipe，全部 rc=0）
bash ci/scripts/preflight_check.sh xine/0.99.14

# 2) init-build（模式 B：探索性编译）
python3 <SKILL_ROOT>/scripts/ohc-run.py init-build xine 0.99.14 \
    --url="https://downloads.sourceforge.net/project/xine/xine-ui/0.99.14/xine-ui-0.99.14.tar.xz"

# 3) 语言预检（R47）：detected=c / task=cpp → 兼容族，继续

# 4) 拉取依赖到 Conan 图，手工模拟注入（探索阶段）
conan install …（AutotoolsDeps + AutotoolsToolchain + PkgConfigDeps）

# 5) 配置 + 编译（R1 参数最少化：只加 --prefix 与真实必要的门控）
./configure --prefix=$DEFAULT_PREFIX --without-fb
make -j1                                  # R9：HMDFS jobserver fifo EPERM，禁并行
make install DESTDIR=$TEST_PREFIX
make check                                # 上游无测试目标 → 20 个 check 目录全部无事可做
make -j1 -C src/xitk session_ctrl         # 上游 EXTRA_PROGRAMS 测试入口，实测编译

# 6) 固化配方
python3 <SKILL_ROOT>/scripts/ohc-run.py refresh-patch --auto xine 0.99.14   # 5 个补丁
python3 <SKILL_ROOT>/scripts/ohc-run.py conan-verify xine 0.99.14
python3 <SKILL_ROOT>/scripts/ohc-run.py finish xine 0.99.14 published
```

## 遇到的问题与解决方案

| # | 问题（首个真实错误） | 根因 | 解决方案 |
|---|---|---|---|
| 1 | `config.guess: cannot guess system type`（rc=1，configure 随即 `cannot guess build type`） | tarball 内 `config.guess` 是 2022-01-09 版，其 `case $UNAME_MACHINE:$UNAME_SYSTEM:…` 表里没有 HarmonyOS 分支；而 OHOS 上 build == host，`AutotoolsToolchain` **不会**下发 `--build/--host` 三元组，所以不能靠外部指定绕过 | `0001-config.guess.patch` 新增 `aarch64:HarmonyOS:*:*) GUESS=aarch64-unknown-linux-ohos`；`0002-config.sub.patch` 让 `config.sub` 接受 `ohos*` / `linux-ohos*` 以完成规范化。本包 `config.guess` 里确有 `umask 077`（`:119` 的 `set_cc_for_build()`），但**不在构建路径上**：新增分支直接赋值 `GUESS`、不调用该函数，实测 `sh config.guess` → `aarch64-unknown-linux-ohos`、rc=0，且把 `TMPDIR` 指向 HMDFS 时也不产生任何 `cgXXXXXX` 临时目录，故无需改动（pcre2 的 CI 失败 #7004 正是走进那条函数才被拒写，见问题 15 的对照） |
| 1b | G0 命中 **E566**，提示“已知风险 E566 未在配方中处理”（E566 推荐 `explicit-build-host-triplet`：显式传 `--build/--host` 以跳过 config.guess） | 实测：本包**未打补丁**的 `config.sub`（2022-01-09）直接拒绝该三元组 —— `sh config.sub aarch64-unknown-linux-ohos` → `Invalid configuration 'aarch64-unknown-linux-ohos': OS 'ohos' not recognized`，**rc=1**。即 E566 的方案在本 tarball 上**仍以修改 config.sub 为前提**，并不比补丁路线少改文件 | **有意偏离 E566**，走 config.guess/config.sub 补丁路线：与同上游家族、本仓库已合入的 `xine-lib/1.2.13`（0001/0002 同款补丁）保持一致，且不触碰 configure 的 build/host 别名判定路径。验证证据见 `reports/upstream-test-census.txt` §D（`checking build system type... aarch64-unknown-linux-ohos`，源日志 cfg5.log:54）与 `reports/w3-local-ci.log`（conan create PASS + L0/L1/L5）；`reports/conan-verify-report.md` 的 G2 只说明 create 成功，其 G4/L2/L4/L5 实为 SKIP（见「验证结果」小节口径）。 |
| 2 | `make: No rule to make target '/mime.types'`（misc/desktops 中断） | configure 用 `pkg-config --variable=plugindir libxine` 推导 `XINE_MIME`，而 **Conan 为 xine-lib 合成的 `libxine.pc` 不带 `plugindir` 变量** → 取到空串，拼成绝对路径 `/mime.types` | `0003-configure.patch`：`XINE_MIME` 三级回落（pkg-config plugindir → `xine-config --plugindir` → 空），空值时改用树内 `mime.default`，避免依赖未安装的插件目录 |
| 3 | `make: No rule to make target '"./mime.default"'` | `misc/desktops/Makefile.am` 的规则把前置条件写成带**字面双引号**的 `"$(srcdir)/mime.default"`，make 连引号一起当目标名，永远不可满足；OHOS 上不重跑 autoreconf，所以真正生效的是 `config.status` 实例化出来的 `Makefile`，其模板是 `Makefile.in` | `0004-…Makefile.am.patch` + `0005-…Makefile.in.patch` 同时去引号（R6：不能直接给生成的 `Makefile` 打补丁） |
| 4 | `src/fb/keys.c: call to undeclared function 'pthread_cancel'` → 补声明后 `ld.lld: undefined symbol: pthread_cancel` | **E085** 同族：OHOS sysroot 的 `pthread.h` 不声明、`libc.so` 也不导出 pthread 取消 API（独立链接探针证实）；鸿蒙 PC 也没有 framebuffer 控制台设备可驱动 | 配方固定 `--without-fb`。这里是**前端可选项**，门控即可；兄弟包 xine-lib 因 `pthread_cancel` 在核心路径上，只能改写源码 |
| 5 | `xine-remote` 未构建：configure 输出 `readline.h... not found` / `no readline found, xine network interface will be disabled` | `m4/readline.m4` 的 `AC_CHECK_READLINE` 只遍历硬编码前缀（`/usr/include`、`/usr/local/include`…），完全不查 `CPPFLAGS/LDFLAGS`，因此看不到 Conan 交付的 `readline/8.3`；其后续 ncurses 探测只试 `-lncurses`，而 OHOS ncurses 仅发布 `libncursesw.a`（无 `libncurses`/`libtinfo`） | 不修改上游 m4（属上游探测缺陷、且非核心播放路径）；登记为**不适用入口**并写明根因（`reports/test-report.md` §2） |
| 6 | `session_ctrl` 运行 rc=159（SIGSYS），无任何输出 | **E051** 已记录：`setreuid()` 在 OHOS 上被内核/安全策略以不可捕获的 SIGSYS 终止。`connect_to_session()`（定义于 `src/xitk/session_common.c:51`，`setreuid()` 在其 :68；由 `ctrl_test.c:38` 调用）无条件调用它。本包差分探针补充实测：`setuid(geteuid())` → rc=0 且存活，`setreuid(getuid(),getuid())` → rc=159，说明不是“所有凭证类 syscall 全禁”，选择替代调用时必须逐个探针 | 配方 `build()` **编译** `session_ctrl`（校验交叉编译与链接、保留上游测试入口）但**不执行**它；平台策略非适配缺陷，已在 notes/报告/test_package 三处如实声明 |
| 7 | configure conftest 运行期报 `Error loading shared library libxine.so.2` | configure/make 会立即运行刚链接出的探测程序，OHOS 动态链接器没有指向 Conan 缓存的默认搜索路径 | `generate()` 里 `Environment()` 前插所有依赖 `libdir` 到 `LD_LIBRARY_PATH`，`vars(self, scope="build").save_script("conanbuild_runpath")`，使 `autotools.configure()/make()` 自动生效（R49：只用 Conan 图内的私有路径，不碰 `/usr/local`） |
| 8 | pkg-config 可能命中设备系统上的 X11/jpeg/png/curl | 探测顺序不固定 → 配方声明的依赖图与实际链接结果不一致 | `env.define("PKG_CONFIG_LIBDIR", self.generators_folder)` 把 pkg-config 钉死在 Conan 生成的模块上 |
| 9 | `po/` 阶段 `AM_GNU_GETTEXT` 相关失败风险 / `msgfmt` 缺失 | 该处宏通过“是否存在预装 GNU gettext”决定 `USE_NLS`，OHOS 工具链不发布 gettext，CI worker 与本机结果会不一致 | 固定 `--disable-nls`，把决定权从环境探测变成显式声明 |
| 10 | `config.guess`/`configure` 报 `Permission denied` | E490 同族：HMDFS 解包与补丁应用会丢可执行位 | `build()` 开头对 `configure config.guess config.sub install-sh missing compile depcomp ar-lib ltmain.sh` 条件 `chmod +x` |
| 11 | `make -j2` 触发 jobserver fifo `EPERM` | HMDFS 对并行 make 的 fifo 权限处理限制 | `autotools.make(args=["-j1"])`（R9） |
| 12 | `refresh-patch --auto` 报 `无法定位源码目录: orig=None` | `ohc-run.py` 的 `find_project_dir()` 靠 `OHC_PROJECT_DIR` 定位归档；在 `.worktrees/` 下独立 worktree 时该变量未设置 | `export OHC_PROJECT_DIR=<worktree>` 后重跑，5 个补丁正常生成 |
| 13 | `.orig` 基线里混入本次改动，补丁集虚高 | HMDFS 上重复解包 `.orig` 与 `.work` 共享硬链接，改 `.work` 会同步改到 `.orig` | 用 python `tarfile` 从 sha256 校验过的 tarball 重新解出 `.orig`，恢复真实基线 |
| 14 | `finish` Step 1 重跑 `refresh-patch` 后补丁从 5 个变成 13 个，`conan-verify` G2 随即 FAIL（`build_and_test.sh` 提示 patch_file 路径不一致） | **in-tree 探索构建污染补丁基线**：`configure`/`make` 会就地重写 tarball 自带的“文档/打包脚本”文件（`doc/man/{de,en,es,fr,nl,pl}/*.1`、`misc/SlackBuild`、`misc/build_rpms.sh`），把 `$DEFAULT_PREFIX` 替换进去；这些不是适配改动，但 `.orig`/`.work` 差分把它们当成了补丁内容，而 `conandata.yml` 仍按 5 个文件名引用 → 路径失配。`refresh-patch` 的“精准模式”只比对 **22 个追踪文件**，其中 17 个被构建改写：8 个能干净反apply 而生成伪补丁（`0004-doc-man-en-*.1` ×3、`0007~0009-doc-man-nl-*` ×3、`0010-misc-SlackBuild`、`0011-misc-build_rpms.sh`），另 9 个报 `dry-run 失败` | 用 `.orig` 反向覆盖 `.work` 中这 17 个构建副产物（`diff -rq` 精确列举后逐个 `cp -p`），使两端只剩 5 个真实适配文件；重跑 `refresh-patch --auto` → 恰好 5 个补丁，`work hash` 由污染的 `c38a4afa020a4a8d` 回到干净基线的 `461951f4e5147c7d`（`orig hash` 始终 `fac5e461998783bb`） |
| 15 | **远端 CI build `#97272` 红**（PR #16499）：`conan create` 里 `./config.status: line 655: ./confhGIGfN/subs1.awk: Permission denied` → `config.status: error: could not setup config files machinery` → `Error in build() method, line 119 autotools.configure()`。其余门禁全绿（`L0n` 分支名精确匹配、L0j/L0k/L0m、KC `KC_ERRORS=0`、JC `JC_ERRORS=0`、`L0 all checks passed`） | 崩溃点属 **E129**（同族 **E114**），实测部分只到“mode 可复现、拒写不可复现”为止：HMDFS 上 `(umask 077 && mktemp -d "./confXXXXXX")` 建出的目录是 `drwx--S---`（group 位全空，且 HMDFS 会给新目录强制置 setgid），随后 `config.status` 往该目录写 `subs1.awk` 在 worker 上被拒。**本机在同一 HMDFS 挂载上建出的 `drwx--S---` 目录仍可写**，所以两侧权限检查落点不同这一判断（worker 上记录属主 uid 与进程 uid 不一致时落 group 分支，该机理归 `DRAFT-10863`）无法在本机证实，也不能反过来说“连 owner 也写不进去”。本机 W3/conan-verify 全绿的直接原因是 conan home 挂载点不同：本机 `/data/storage/el2/base/files/home/.conan2` 属应用私有挂载，四种 umask 下都得到 `drwx------`；CI 用 `/storage/Users/currentUser/.cache/conan2`，属 HMDFS（该日志的 `WARN: Build folder` 行可佐证） | `0003-configure.patch` 增加**第二个 hunk**：`configure:16709/16714`（`.orig` 行号，打完补丁后为 `:16717/:16722`）的 `umask 077` → `umask 022`（E129 rec 1，`rec_auto_fix: true`）。取值判据见注意事项 18。**有效性已由远端实测闭环**：除此之外无任何改动，重跑 build `#97351` → `## CI 校验通过`（`test_package` 通过、L0/L1 门禁通过、7 个步骤全绿），构成单变量前后对比（红两次 #97241→CI-030 / #97272→CI-001 同一签名，绿三次 #97351→CI-040 / #97427→CI-021 / #97445→CI-026；五次落在五台不同 worker，跨机一致故排除单机抖动）；本机复验只证明“改动无回归 + 仍可构建”。只改 `configure` 即可：`config.status` 由它生成，复验构建目录里的生成物已无 `umask 077`（`:626/:631` 均为 `umask 022`）。补丁集仍 5 个（同文件加 hunk 不产生新补丁、不重排序号，见注意事项 9） |

## 注意事项

1. **`--without-fb` 与 `--disable-nls` 是固定门控，不是环境妥协**：前者因 OHOS libc 无 pthread 取消 API 且无 fb 控制台；后者因 `AM_GNU_GETTEXT` 靠“是否预装 GNU gettext”决定 `USE_NLS`，不显式关闭会让 CI worker 与本机结果不一致。
2. **`session_ctrl` 只编译不执行**：若将来 OHOS 放开 `setreuid` 系统调用策略，可在 `build()` 追加执行步骤并提升上游实测用例数；当前必须保持不执行，否则 conan create 会被 SIGSYS 打断。
3. **`xine` 的 `--version/--help/--keymap` 全部以 rc=1 退出**（上游在打印后 `exit(1)`）。测试断言按 rc=1 判定，改成 rc=0 会造成假失败。
4. **`--keymap=file:<path>` 在 0.99.14 无效**（实测只打印版本横幅后 rc=1）：`src/xitk/main.c:1493-1497` 的 `file:` 分支设置 `gui->keymap_file` 后 `continue`（不显示、不退出），而 `main.c:1826` 在参数解析之后**无条件**把 `gui->keymap_file` 覆盖为 `$HOME/.xine/keymap`，传入的路径随即丢失。属上游缺陷，不改上游逻辑，故自定义 keymap 的闭环测试走 `$HOME/.xine/keymap` + `--keymap=remapped`（`main.c:1487-1489` 的真实路径）。
5. **无 X display**：构建机上不能播放真实媒体，`xitk` 的 `test` 目标亦需显示。消费者测试全部设计为 headless 可跑（keymap 发射器、桌面/mime/man 数据、`xine-check`）。
6. `misc/desktops` 的引号补丁必须 **`.am` 与 `.in` 成对**，OHOS 上不重跑 autoreconf，只改 `.am` 无效。口径边界：这条的硬要求是**生成物 `.in` 必须改**（否则不生效），`.am` 那半边属于源码可维护性；所以它与 0003 只补 `configure` 并不矛盾，`configure`/`configure.ac` 不对称的理由与回写要求见本文件**注意事项 14**。
7. 本包是**多媒体前端**（R40）：编译通过不等于适配完成，故补了字节级 keymap 闭环 + 跨序列化格式一致性 + HarmonyOS 诊断执行 3 个端到端鸿蒙特有消费者用例，验证的是真实功能路径而非“能跑起来”。**未验证面须人工确认**：核心播放链（X11/Xv 视频输出、`xitk` GUI、皮肤渲染、DVD/流媒体）在无 X display 的构建与 CI 环境上不可验证，27 条断言覆盖的是**显示无关的消费者面**；R40 的实质适配证据在补丁侧（三元组识别、XINE_MIME 三级回落、pthread_cancel 门控、运行路径修复，均非 `return 0` 空壳）。
