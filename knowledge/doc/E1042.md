# E1042: 32 位假设的老解包工具在 LP64 上的三类断裂：ULONG 宽度、on-disk 指针不推进、链接行硬编码 gcc

## 基本信息
- **严重度**: 2
- **类别**: portability, build-system, packaging, archive-format, data-corruption
- **作者**: Awstme <awstme@qq.com>

## 错误特征
```
"gcc: No such file or directory|argument unused during compilation: '-d[A-Z_]+|CRC-check error|One or more CRC-errors were found|Invalid archive file"
```

## 根因分析
三处独立断裂叠加：① declare.h 把 ULONG/LONG 定义为 unsigned long/long，LP64 下 8 字节，而 ACE on-disk 结构全按 32 位设计，解析宏 BUFP2LONG(p) *(ULONG*)((p+=4)-4) 指针步进 4 字节但按 ULONG* 读写，共享 head 缓冲的结构体槽位与步进错位；② read_header 用不推进指针的 BUF2LONG(tp) 读带 ACE_ADDSIZE flag 的 FILE 头 ADDSIZE 字段（acefile 0.6.8 确认真实 FILE 头必带 ADDSIZE），后续 PSIZE/SIZE/FTIME/ATTR/CRC32/TECH/FNAME 从 ADDSIZE 位置读起整体错位一格——FNAME_SIZE 读到 TECH.PARM=0（文件名列空）、CRC32 读到 ATTR（CRC 校验必失败）、FTIME 读到 SIZE（日期乱）；③ unix/makefile 链接行硬编码 gcc，命令行 CC= 只覆盖编译规则。

## 推荐方案
**方法**: fixed-width-typedef-plus-pointer-advance-plus-cc-link-line

**说明**: 三处最小补丁：① declare.h 的 ULONG/LONG 固定为 unsigned int/int（或 stdint.h 的 uint32_t/int32_t，Debian 004 同方向）；② read_header 的 BUF2LONG(tp) 改 BUFP2LONG(tp)（读 ADDSIZE 同时推进 tp，MAIN 头规范上不带 ADDSIZE flag 故不受影响）；③ makefile 链接行 gcc 改 $(CC) 并以命令行 CC=clang 覆盖（Debian 001 同方向）。不引入平台宏，保持通用。

**修复命令**:
```
make -f unix/makefile CC=/data/service/hnp/bin/clang -j1
```

**验证**:
```
用最小 stored 档案驱动四命令面断言：python3 mkace_test.py test.ace 生成夹具后 sh test_unace.sh <产物>/bin/unace test.ace work，期望 SUMMARY pass=7 fail=0（l 列出文件名与 21.09.26 型日期、t 打 2 次 CRC OK、e/x 提取内容逐字节一致）；只修 typedef 时文件名仍空即 ADDSIZE 错位仍在，只修 read_header 时字段仍乱即 typedef 宽度仍在。
```
