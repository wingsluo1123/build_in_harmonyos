# E1135: libc++ 不完整标准库特性的 __has_include 误判：改用 __cpp_* 特性宏

## 基本信息
- **严重度**: 2
- **类别**: compat, portability, libc, headers, clang
- **作者**: Z9X2
- **来源 PR**: "!8711"

## 错误特征
```
explicit specialization of non-template struct .formatter.|out-of-line definition of .formatter. does not match any declaration in namespace .std.|too few template arguments for class template .formatter.|_LIBCPP_HAS_NO_INCOMPLETE_(FORMAT|RANGES)
```

## 根因分析
OHOS clang 15 自带 libc++ 的 <format>/<ranges> 等头文件物理存在（__has_include 判真），但实现被 _LIBCPP_HAS_NO_INCOMPLETE_FORMAT、_LIBCPP_HAS_NO_INCOMPLETE_RANGES 抑制：version 头不导出对应的 __cpp_lib_* 特性宏，且 std::formatter 主模板声明为双模板形参且无默认 charT。上游库惯用 "#if __has_include(<format>)" 门控对 std::formatter 的单参特化，于是在该工具链上条件判真、特化写法与声明不匹配，头文件被 include 的瞬间即编译失败，未触碰任何库 API 的消费者也一并挂掉。

## 推荐方案
**方法**: replace-has-include-with-cpp-feature-macro

**说明**: 把库头中的特性门控从 __has_include(<头名>) 改为对应 __cpp_lib_* 特性宏判真（即 defined(__cpp_lib_format) 等价形式），使"启用条件"与标准库真实能力一致：在不完整 libc++ 上条件判假、功能优雅缺席但编译可用；在完整实现（clang 17/18、libc++ 完整模式、MSVC、libstdc++）上宏为真，行为与上游逐字一致。若上游测试文件已使用特性宏守卫，把库头对齐到同款守卫即零语义差异的最小移植补丁。

**修复命令**:
```
单行守卫替换：把预处理条件 if __has_include(\<format\>) 改为 if defined(__cpp_lib_format)（含 fmt/format.h 回退分支时保持 fmt 链不动）；补丁保存为 patches/NNNN-*.patch，conandata 标 patch_type=portability，附 strip 与三行上下文
```

**验证**:
```
最小探针编译并判返回值：printf "#include <version>\n#include <ranges>\nint main(){ return\n#if defined(__cpp_lib_ranges)\n 0;\n#else\n 1;\n#endif\n }\n" | clang++ -std=c++20 -x c++ - -o probe && ./probe; echo exit=$? —— exit 1 表示 <ranges> 头可见但 __cpp_lib_ranges 未定义，证实头存在不等于特性可用；对 <format> 同理换头名与宏名
```
