# E1383: 未初始化结构体指针成员在严格分配器上触发 invalid free（glibc/macOS 侥幸通过，OHOS 以 SIGTRAP 终止）

## 基本信息
- **严重度**: 3
- **类别**: platform, libc, musl, runtime, testing
- **作者**: DF30
- **来源 PR**: 14061

## 错误特征
```
rc=-5|SIGTRAP|invalid free|free\(\): invalid pointer|attempting free on address which was not malloc|AddressSanitizer:.*SEGV.*in entry_free|MallocScribble
```

## 根因分析
构造函数只 malloc 结构体而不初始化其指针成员；查询/解析未命中时回调不执行，这些成员保持垃圾值，随后无条件的清理函数对它们逐个 free()，形成对野指针的释放。glibc 与 macOS 在对象刚从整页映射、内容恰为 0 时 free(NULL) 是空操作，于是同一份代码静默通过；OHOS 的分配器不静默容忍非法释放，而是就地终止进程（实测退出码 -5 / signal 5）。所以根因是平台无关的上游内存安全缺陷，平台差异只决定它是否现形。

## 推荐方案
**方法**: zero-init-struct-right-after-malloc

**说明**: 在"只分配不初始化"的工厂函数里，malloc 之后立刻 memset(ptr, 0, sizeof(*ptr))，把所有指针成员先置 NULL。free(NULL) 是 POSIX 定义的空操作，失败路径不再触碰野指针，成功路径随后照常赋值，语义等价、无平台宏、可直接向上游提交

**修复命令**:
```
编辑目标源文件后在仓内刷新补丁：`python3 scripts/ohc-run.py track-edit add <software> <version> <src/file.c>` → 加 memset → `python3 scripts/ohc-run.py refresh-patch --auto <software> <version>`
```

**验证**:
```
修复前：macOS `MallocScribble=1 <bin> <args>` 或 glibc `MALLOC_PERTURB_=170 <bin> <args>` 应非零终止（ylva 实测 rc=134）；ASan（-fsanitize=address）跑同一路径，栈应为 free ← 清理函数 ← 调用方（ylva 实测 #2 entry_free）。修复后：同样命令 rc=0，OHOS 侧对应用例退出码不再是 -5
```
