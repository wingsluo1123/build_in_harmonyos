# E1394: Maven 多模块 reactor 用 `-pl <module> -am` 裁剪时，maven-dependency-plugin 可能不再取 reactor 产物，而改为从 Maven Central 下载「现成的」同名 jar——构建表面成功但产物已非源码编译所得；制品模块应为全 reactor 构建，或必须核对产物来源

## 基本信息
- **严重度**: 2
- **类别**: build-system, conan, packaging
- **作者**: C5C1

## 错误特征
```
Downloading from central: .*\.jar
```

## 根因分析
jaf-api 的 activationapi 模块并不以 <dependencies> 形式依赖 activation 模块，而是通过 maven-dependency-plugin 的插件配置引用 jakarta.activation:<version>。Maven 的 `-am`（also-make）只把「被依赖模块」纳入 reactor；插件配置里的引用不算依赖关系，故 `-pl activationapi -am` 时 activation 模块不参与构建，插件于是从远程仓库解析——实测日志为 `Downloading from central: .../com/sun/activation/jakarta.activation/2.0.0/jakarta.activation-2.0.0.jar`。结果：API jar 里的类来自中央仓预编译产物，而非本次源码编译，构建"成功"却偏离源码适配口径（且引入对远程仓库的隐式依赖，离线/受限网络下会直接失败）。

## 推荐方案
**方法**: build-full-reactor-and-verify-artifact-origin

**说明**: ①制品所需的模块一律用全 reactor 构建（`mvn clean package -B -DskipTests=false`），只有确认"该模块体积/耗时不可接受且其产物不被制品使用"（如 servlet 的 tck 模块）时才裁剪；②裁剪时必须在构建日志里确认没有出现 `Downloading from central: ...<制品>.jar`；③必要时在 package() 里断言产物来自 source_folder/<module>/target（本配方即按目录取 jar），并记录 sha256，避免"看似成功、实为拉包"。

**修复命令**:
```
mvn clean package -B -DskipTests=false # 全 reactor；裁剪时改 -pl <module> -am 但须核对日志
```

**验证**:
```
构建日志中检索 "Downloading from central: .*<你打算编译的制品名>.*\.jar"；或在 package() 前后对比该 jar 的 sha256 与本地 target/ 下产物的 sha256 是否一致
```
