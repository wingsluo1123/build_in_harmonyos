# E1403: 老 C 代码在 **musl（含 OHOS）** 上会遇到两类只在 glibc 成立的 API 假设——① `setpgrp(0, getpid())`（musl 只声明 `void setpgrp(void)` → 编译报 `too many arguments to function call, expected 0, have 2`）② `getpass()`（musl 不提供 → 链接报 `undefined symbol: getpass`）；修法是用 **`#ifdef __GLIBC__` 守卫** 的 portability 补丁（glibc 路径保持原样，不动 Debian 行为）

## 基本信息
- **严重度**: 3
- **类别**: portability, libc, patch, difference
- **作者**: AE9C

## 错误特征
```
too many arguments to function call, expected 0, have 2|undefined symbol: getpass|setpgrp|implicit declaration
```

## 根因分析
老代码（本例是 1990 年代的 irc2）按 glibc/BSD 的习惯使用 API： * BSD/glibc 提供 2 参 `setpgrp(pid, pgid)`；musl 只有 POSIX 的 `void setpgrp(void)` （且现代编译器把"声明为空参"当 `(void)`）→ 调用带参即编译错误； * glibc 提供 `getpass()`；musl 没有 → 链接期 `undefined symbol`。 两处都不是"上游写错了"，而是**宿主 libc 的差异**，因此补丁应当只影响非 glibc 分支。

## 推荐方案
**方法**: glibc-guarded-portability-patch-with-equivalent-posix-fallback

**说明**: ①先确认差异属于 libc 而非上游 bug（查 musl 头文件里的签名 / 是否存在该函数）；②补丁形态统一为 `#ifdef __GLIBC__ <原代码> #else <等价替代> #endif`——**glibc 分支保持字节不变**，保证 Debian/glibc 侧行为不受影响（评审也更愿意接受）；③替代实现要与原语义等价并尽量复用上游已有的平台分支（本例 `setpgrp` 改用 POSIX `setsid()`，与上游 HPUX/SVR4/_POSIX_SOURCE 分支同一处理）；④补丁进 `conandata.yml` 的 `patches`（`patch_type: portability` + `patch_description` 写明差异与影响面），并在 `build()` 里 `apply_conandata_patches()`、`export_sources()` 里 `export_conandata_patches()`；⑤补丁用程序化方式生成（复制原文件→脚本化修改→`diff -u`），避免手敲制表符导致上下文不匹配。

**修复命令**:
```
mkdir -p a b && cp -a src/x.c a/ && cp -a src/x.c b/ ; python3 -c "修补 b/…" ; diff -u a/x.c b/x.c > patches/000N-x-portability.patch ; patch -p1 --dry-run < patches/000N-x-portability.patch
```

**验证**:
```
① 编译报 `too many arguments to function call, expected 0, have N` → 查该函数在 musl 头里的签名 ② 链接报 `undefined symbol: X` → 查 musl 是否提供 X（`grep -r X $SYSROOT/include`）③ 打补丁后重跑 `make`
```
