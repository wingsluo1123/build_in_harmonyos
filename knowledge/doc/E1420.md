# E1420: OHOS 上 Go ELF 必须自签名才能 execve：判定签名必须读 .codesign section 头，字符串搜索会因 Go 二进制内嵌 codesign 字样假阳性

## 基本信息
- **严重度**: 2
- **类别**: ohos, toolchain, go, conan, permissions
- **作者**: 9229

## 错误特征
```
Permission denied|rc 126|PermissionError: \[Errno 13\] Permission denied
```

## 根因分析
OHOS 拒绝执行未携带有效 .codesign section 的 ELF（实测 rc 126 Permission denied），Go SDK 工具链（go/gofmt 及 pkg/tool/<os>_<arch>/*）与产出的 Go 二进制都要自签名。真正的坑在“判定是否已签名”：Go 运行时/标准库内嵌了 macOS 工具链用的 codesign 字样（如 os/exec、crypto 相关字符串），因此 b".codesign" in data 或 grep -a ".codesign" 会假阳性判定“已签名”，从而静默跳过签名步骤。最终现象只有一句 Permission denied（rc 126），而 ls -l 有 x 位、字节里也确实含 codesign 字样，报错完全不指向根因，极易误判为权限/挂载/noexec 问题而朝错误方向排查。

## 推荐方案
**方法**: readelf-section-check-and-conditional-sign

**说明**: 签名判定改用真实 ELF section：llvm-readelf -S <elf> 输出含 ".codesign" 才视为已签名；否则先 llvm-objcopy --remove-section .codesign 清残留，再 binary-sign-tool sign -selfSign 1 -inFile X -outFile X.signed，mv 覆盖后 chmod（chmod 需 try/except 兜底，见下）。

**修复命令**:
```
对每个待执行 ELF 先判 section 再签：for f in <elf...>; do llvm-readelf -S "$f" | grep -q '\.codesign' || { llvm-objcopy --remove-section .codesign "$f"; binary-sign-tool sign -selfSign 1 -inFile "$f" -outFile "$f.signed" && mv "$f.signed" "$f"; }; done
```

**验证**:
```
llvm-readelf -S <elf> | grep -c .codesign   # 期望 >=1；字符串式搜索误判：grep -c .codesign <elf>
```
