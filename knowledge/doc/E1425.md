# E1425: 按版本号直接拼 GitHub 归档 URL 会 404（tag 形态有 v<v>/<v>/<v>-RELEASE 三种）；且上游仓库名常与制品坐标不同（如 jaf-api ↔ jakarta.activation-api）——拼 URL 前必须探测 tag 形态并核对仓库名

## 基本信息
- **严重度**: 2
- **类别**: build-system, conan, environment
- **作者**: 884A

## 错误特征
```
404: Not Found
```

## 根因分析
各上游仓库的 release tag 命名不统一：jakartaee/servlet 用 `<version>-RELEASE`（6.1.0、v6.1.0 均 404，仅 6.1.0-RELEASE 为 200）；jakartaee/jaf-api、jakartaee/cdi 用裸 `<version>`。另外 Jakarta EE 系列常见"仓库名 ≠ 制品坐标"：activation 的上游仓库是 jakartaee/jaf-api，而制品坐标是 jakarta.activation:jakarta.activation-api。若按制品名拼仓库 URL 或不加探测，会得到 404（下载到 14 字节的 "404: Not Found" 文本，而非压缩包）。

## 推荐方案
**方法**: probe-tag-shapes-and-verify-archive-bytes

**说明**: ①先用 HTTP 状态码探测候选 tag 形态（`v<version>`、`<version>`、`<version>-RELEASE`），取 200 的那个写进 conandata.yml 并在注释里记录探测结论；②不要假定仓库名 = 制品名，用上游 CONTRIBUTING/SCM 段或搜索确认仓库；③下载后除 sha256 外，顺带校验文件大小与魔数（gzip 头 1f 8b），可第一时间发现把 "404: Not Found" 文本当成压缩包的情况。

**修复命令**:
```
curl -sS -o /dev/null -w "%{http_code}" -L "https://codeload.github.com/<owner>/<repo>/tar.gz/refs/tags/<candidate>"
```

**验证**:
```
for t in v6.1.0 6.1.0 6.1.0-RELEASE; do printf "%-14s " "$t"; curl -sS -o /dev/null -w "%{http_code}\n" -L "https://codeload.github.com/jakartaee/servlet/tar.gz/refs/tags/$t"; done
```
