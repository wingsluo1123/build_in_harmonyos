# E1428: 判断一个库"能不能在本环境适配"，**要看它的发布物里是否已含构建产物，而不是看实现语言**——同为 Rust 系：`install-mimic` 只发源码（Debian 用 `cargo build --release`）→ 本机无 Rust（rustup 直接拒绝 HarmonyOS）→ **系统级不可用、放弃**；而 `ink-generator` 上游把 **wasm 预构建好**随 npm 发布 → **零工具链、零依赖，直接可打包**。另：比赛/清单里的版本号可能**在任何公开发布渠道都不存在**（本例要 0.4、npm 只到 0.3.8）→ 按既定规则用最新可获取版本并在 manifest/notes/PR 显著披露

## 基本信息
- **严重度**: 3
- **类别**: toolchain, packaging, feasibility
- **作者**: 839D

## 错误特征
```
unrecognized OS type: HarmonyOS|no acceptable cc|需要 cargo 编译但本机无 Rust|发布物已含预构建产物
```

## 根因分析
同一语言生态里，包的"发布形态"差异极大：有的只发布源码+构建脚本（消费方必须自带编译器）， 有的把产物（wasm/字节码/jar/预编译二进制）一起发布。前者对缺失工具链的环境是硬阻塞， 后者则与语言无关地可用。适配侦察若只按"语言/依赖列表"判断，就会把可行的包误判为不可行 （或反之，浪费时间在必然失败的构建上）。 另外清单版本号常来自需求方而非发布方，可能对应不到任何真实发布物。

## 推荐方案
**方法**: check-published-artifacts-before-language-and-pin-but-disclose-missing-versions

**说明**: ①**先看发布物**：下载上游发布包（npm tarball / wheel / jar）列出内容，若已含预构建产物（wasm/so/node/jar）→ 该包**不需要**相应工具链，直接按"解包+自检+打包"处理；②**再看构建钩子**：`scripts.postinstall`/`build.rs`/`configure` 是否要求本地编译器；③**最后才看依赖列表**（有预构建产物时，语言级依赖往往不适用）；④**版本核对**：清单版本若在任何渠道都不存在 → 用最新可获取版本，并在 manifest/notes/PR 三处披露（不默默换版本、也不因版本不符就放弃一个可做的包）；⑤把"哪些证据支持该判定"写进 notes（本例：`ink_generator_bg.wasm` 1020564 B 随包发布 vs install-mimic 的 `cargo build --release`）。

**修复命令**:
```
curl -sSL <npm tarball> -o p.tgz && tar tzf p.tgz | head -20 ; npm view <pkg> versions --json ; rustup --version 2>&1 | head -2
```

**验证**:
```
①`npm pack --dry-run`/下载 tarball 后 `tar tzf` 看是否含 `*.wasm`/`*.node`/预编译产物；②`npm view <pkg>@<ver> scripts.postinstall`（有无编译钩子）；③`npm view <pkg> versions`（清单版本是否存在）；④对照 `rustup` 类工具链在本平台是否可用（`rustup` 会直接报 `unrecognized OS type: HarmonyOS`）
```
