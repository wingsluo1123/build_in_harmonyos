# E1463: 自建校验的两条断言纪律——①**消费者校验的断言必须以源码/docstring 为准**（本轮我把 `Projection(keys, space)` 当成"对值施加函数"，实测返回 `'x'` 期望 `'X'` 判 FAIL；实际语义是"按键投影"，可调用时被当作键的谓词）②**测试结果必须 passed/failed/errors 三项统计**，并把 `ModuleNotFoundError`/`ImportError`（说明没真跑起来）与"解析不到通过计数"单项判为**不成立**——否则会把"缺依赖"或"没真跑"记成通过

## 基本信息
- **严重度**: 2
- **类别**: testing, quality
- **作者**: 288A

## 错误特征
```
结果不符：得到 .*期望|未解析到 pytest 通过计数|ModuleNotFoundError.*记为通过|凭 API 名字推断语义
```

## 根因分析
两类反复出现的误判，根因都在"用想当然代替证据"： ① **API 语义靠名字推断**：`Projection` 听起来像"投影值"，但源码签名是 `Projection(keys: _Matchable, space: Mapping)` —— `keys` 可为列表/可迭代/可调用/正则， 可调用时被当作**键的谓词**（`_dispatch()` 把 callable 直接用、把容器转成 `__contains__`）。 断言写错 → 校验报 FAIL，看似"产物有问题"，实则校验本身有错（本轮即此）。 ② **测试结果只看通过数**：只 `grep -c "passed"` 会把两种情况记成通过： （a）测试因缺依赖根本没跑（`ModuleNotFoundError`/`ImportError`）；（b）输出格式变化导致 解析不到计数（此时 `passed=0` 也可能是"没跑"而非"没有失败"）。

## 推荐方案
**方法**: source-of-truth-assertions-and-three-way-test-accounting

**说明**: ①**断言以源码为准**：写 `<mod>.<API>(…)` 调用前，先读该 API 的 docstring 示例或 `__init__` 签名，按示例构造入参与期望值；本地验证时把实际输出与将写入脚本的期望值**逐项对照**（本轮教训：本地已打印 `Projection: x`，我却写了期望 `'X'`）。②**结果三分类**：统计 `passed/failed/errors` 三项；出现 `ModuleNotFoundError`/`ImportError` → 判"测试不成立"（让 build 失败或记环境阻塞），出现 failed/errors → 判真实失败；**解析不到通过计数**同样判不成立，避免"没真跑"被记成通过。③消费者校验与上游测试分开统计（前者 N 项 fails/skips，后者 passed/failed/errors），PR 里分别给出。

**修复命令**:
```
re.findall(r"(\d+) passed", out); re.findall(r"(\d+) failed", out); re.findall(r"(\d+) error", out); "ModuleNotFoundError" in out
```

**验证**:
```
① 写断言前先看被测符号的 docstring/源码示例（`grep -nA20 "class <X>" <src>`）② 本地用**解包后的源码 + 真实依赖**跑一遍候选调用，并把输出**与断言值逐项对照**（只打印不对照等于没验证）③ 统计用 `re.findall(r"(\d+) passed|(\d+) failed|(\d+) error", out)` 三项齐看
```
