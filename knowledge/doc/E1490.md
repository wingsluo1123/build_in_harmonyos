# E1490: Old C code with multiple same-name global definitions needs -fcommon under modern clang/GCC

## 基本信息
- **严重度**: 2
- **类别**: portability, cmake, linking
- **作者**: ohc-collaborator <8541>

## 错误特征
```
ld\.lld: error: duplicate symbol.*in archive.*|multiple definition of.*|clang.*error: linker command failed
```

## 根因分析
Pre-2015 C code commonly declares shared lookup tables (e.g. musepack r475 Res_bit/__Cc/__Dc defined in both mpc_decoder.c and requant.c) as multiple "tentative definitions" (int tbl[N]; without extern). Legacy GCC merged them at link time (-fcommon default). GCC >= 10 and modern clang (>= 11, incl. OHOS clang 15) default to -fno-common, so every translation unit emits a real symbol and ld.lld reports duplicate symbol errors when the archive is linked.

## 推荐方案
**方法**: append-fcommon-flags

**说明**: Append -fcommon to the project's compiler flags in the least invasive way: for CMake use set(CMAKE_C_FLAGS "${CMAKE_C_FLAGS} ... -fcommon") (append, never overwrite the existing variable so toolchain/env flags survive, R33); for autotools add it to CFLAGS. Verify no symbol is intentionally duplicated across DIFFERENT archives (that would still fail with -fcommon). A cleaner but more invasive alternative is converting the definitions to extern declarations plus a single defining TU - prefer -fcommon for third-party snapshots to keep the patch minimal.

**修复命令**:
```
set(CMAKE_C_FLAGS "${CMAKE_C_FLAGS} -O2 -fcommon") # then re-run cmake && make
```

**验证**:
```
cd build && make 2>&1 | grep "duplicate symbol"; nm libfoo.a | grep " [BbDCd] SYMBOL" shows the symbol defined in several .o of the same archive
```
