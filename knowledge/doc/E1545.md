# E1545: 文本解析器必须区分原始字节、Unicode 标量和显式字符串长度

## 基本信息
- **严重度**: 2
- **类别**: conformance, data-integrity, parser, unicode
- **作者**: 2301_80739235
- **来源 PR**: https://atomgit.com/OpenHarmonyPCDeveloper/build_in_harmonyos/pull/14502

## 错误特征
```
embedded-NUL-truncation|empty-key-collision|non-RFC3629-UTF8-accepted
```

## 根因分析
原始输入字节、转义后的 Unicode 标量、解码结果长度属于独立契约。用 strlen/strcmp 表示协议字符串会截断合法 escaped-NUL 并把不同键混同；宽松5/6字节UTF-8会接受超长编码或越界标量。只修输出或忽略旧错误 golden 不能恢复端到端语义。

## 推荐方案
**方法**: separate-byte-scalar-length-domains

**说明**: 先验证原始字节，按RFC3629严格解码和编码；内部保存bytes加length，以长度和memcmp比键。增加兼容的带长度API，旧C字符串接口仅作受限包装；JSON编码器使用显式长度并转义控制字符。旧golden与官方规范矛盾时保留原输入/ID/SHA并显式验证完整规范修正输出，不能删用例。

**修复命令**:
```
对解析节点和编码器采用显式长度接口；保留旧API包装；执行原完整官方输入清单及全结构 roundtrip，分别记录非法原始NUL与合法escaped-NUL的结果。
```

**验证**:
```
完整规范语料逐项比较 typed 输出及失败诊断；最小 escaped-NUL 键与空键对照；目标原生消费者及平台专项；源码归档与官方补丁重放 SHA 对照；唯一运行证据链验证。
```
