# E1558: EXIT trap output of a redirected shell function reaches the tty in mksh/bash/zsh (only dash restores stdout first), so cd-on-exit idioms like cd "$(shfm)" get an empty string

## 基本信息
- **严重度**: 2
- **类别**: ohos, portability, posix, runtime, shell
- **作者**: 6E2B

## 错误特征
```
cd-on-exit stdout is ''|exit trap output missing from stdout|\$\(shfm\) is empty
```

## 根因分析
In mksh (the OHOS /bin/sh), bash (also --posix) and zsh the redirect of a function call such as `main "$@" >/dev/tty` is still active when the EXIT trap runs after `exit` inside that function, so `printf '%s\n' "$PWD" >&1` in the trap lands on /dev/tty; only dash pops the redirect before the trap and prints to the caller's stdout. shfm 0.4.2 prints its cd-on-exit directory exactly this way, so `$(shfm)` is empty under mksh/bash/zsh while the same script passes on a Debian host whose /bin/sh is dash.

## 推荐方案
**方法**: save-stdout-fd3-before-redirect

**说明**: Save the caller's stdout once at top level (`exec 3>&1`) before the redirected call, make the trap write to `>&3`, and start child processes with `3>&-` so they cannot keep the capture pipe open. Prove it with a pty-driven consumer test that runs the packaged script under bash (and mksh when available) and asserts the stdout of the cd-on-exit capture.

**修复命令**:
```
exec 3>&1; main "$@" >/dev/tty   # in the trap: printf '%s\n' "$PWD" >&3 ; children: cmd 3>&-
```

**验证**:
```
for sh in dash bash mksh zsh; do printf '%s -> [' $sh; $sh -c 'f() { trap "echo TRAP" EXIT; exit 0; }; f >/dev/null'; echo ']'; done   # only dash prints TRAP; with `exec 3>&1` before the call and `echo TRAP >&3` all four print it
```
