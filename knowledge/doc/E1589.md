# E1589: autotools 探测污染：依赖库预置进 LIBS 使 AC_CHECK_FUNCS 假阳（uuid_compare "yes"）→ 生成变量为空 → 链接缺 -luuid；应保持 CPPFLAGS/LDFLAGS/LIBS 职责单一

## 基本信息
- **严重度**: 2
- **类别**: detection, portability, build-system, autotools, linking
- **作者**: unknown

## 错误特征
```
checking for uuid_compare\.\.\. yes|undefined symbol: uuid_|undefined reference to `uuid_|undefined reference to .*uuid|LIBUUID.*=$
```

## 根因分析
configure 的 AC_CHECK_FUNCS/AC_SEARCH_LIBS 链接测试会把当前 LIBS 变量一并带上。构建系统（或自动化环境注入）若把依赖库当作 -l 参数预置进 LIBS，链接测试无需项目自身的 AC_CHECK_LIB 就能解析符号 → configure 判定"libc 自带该函数" → 项目生成的 Makefile 变量（LIBUUID/LIBINIH 等）留空 → 正式链接时这些库不在命令行 → undefined reference。LDFLAGS 只需给 -L 搜索路径即可让 AC_CHECK_LIB/AC_SEARCH_LIBS 正确工作，不必预置 -l。

## 推荐方案
**方法**: keep-configure-link-tests-clean-separate-cppflags-ldflags-libs

**说明**: 卫生规则三分离——依赖头只放 CPPFLAGS（若项目构建规则忽略 CPPFLAGS 则同时补 CFLAGS/CXXFLAGS）；依赖库搜索路径只放 LDFLAGS（-L）；不要把 -l 预置进 LIBS，LIBS 只保留项目自身链接测试必需的最小集合（如 xfsprogs 的 AC_HAVE_LIBURCU_ATOMIC64 需要 -lurcu，其余交给项目自己的 AC_CHECK_LIB/AC_SEARCH_LIBS 去发现）。识别信号（三处互证）：① configure 输出 "checking for <dep_function>... yes"（而非 "in -l<lib>... yes"）；② 生成的 Makefile 变量（include/builddefs 的 LIBXXX）为空；③ 链接期 undefined reference。输入：项目 configure.ac 的探测宏与依赖列表；输出：干净的注入策略（每变量职责单一，探测结果与链接参数一致）。修复后应用对照 configure（LIBS= 与 LIBS=-luuid 两次）验证变量恢复非空。

**修复命令**:
```
grep -n "AC_CHECK_FUNCS\|AC_SEARCH_LIBS\|AC_CHECK_LIB" configure.ac   # 审计探测宏，圈出"函数属于依赖库"的条目
```

**验证**:
```
LIBS="-luuid" ./configure && grep -n "^LIBUUID" include/builddefs; LIBS= ./configure && grep -n "^LIBUUID" include/builddefs; grep -n "AC_CHECK_FUNCS\|AC_SEARCH_LIBS\|AC_CHECK_LIB" configure.ac
```
