# E1590: 解释型脚本工具打包（application，变体 C）：上游 tarball 里脚本是 0664，conan copy() 装出来的 bin/<tool> 没有可执行位，必须在 package() 里显式 chmod 0755；且 HMDFS 上 os.access(X_OK)/shutil.which() 不可靠，test_package 应直接用被测包的绝对 bindirs 路径

## 基本信息
- **严重度**: 2
- **类别**: platform, packaging, testing
- **作者**: unknown

## 错误特征
```
.*not found in PATH.*package bin/ not on PATH|Permission denied.*bin/|X_OK.*False|executable bit|bin/.*0600|bin/.*0660
```

## 根因分析
脚本工具没有编译阶段，"安装"就是 copy —— conan 的 copy() 会保留源文件权限，而上游 release tarball 里的 src/<tool> 实际是 0664（发行版/官方 installer 靠 `install -m 755` 或 postinst 补权限，例如 tuptime 的 tuptime-install.sh:121）。于是 conan create 出来的 bin/<tool> 不可执行：直接执行报 Permission denied，os.access(path, X_OK) 返回 False。第二个坑是 HMDFS 上权限语义不可靠（见 E046）：即使文件实际可执行，X_OK 探测也可能为 False，导致 shutil.which()/PATH 解析把好文件判成"缺失"——表现为 test_package 里 `'tuptime' not found in PATH — package bin/ not on PATH`，尽管 conanrun 环境确实把 bin/ 加进了 PATH。

## 推荐方案
**方法**: chmod-in-package-and-resolve-bindir-absolutely

**说明**: (1) package() 里对脚本显式 `os.chmod(os.path.join(self.package_folder,'bin','<tool>'), 0o755)`——可执行位是交付物的一部分，不是装饰；(2) test_package **不要**依赖 PATH/shutil.which 解析被测产物：用 `self.dependencies[ref].cpp_info.aggregated_components().bindirs` 拿绝对目录再拼文件名，并把该绝对路径作为参数传给断言脚本（测试脚本里 PATH 查找只作 fallback）；(3) 脚本用显式解释器启动（`sys.executable` + 脚本路径），避免依赖 PATH 里可解析的 python3；(4) 不要用 `os.access(X_OK)` 做存在性/可执行性判断（HMDFS 常假阴性），用 `os.path.isfile()` + `os.stat().st_mode` 或直接试跑；(5) 断言仍要真实执行被测物（R34），并留一条脚本确实可被 shebang 直接执行/或被解释器执行的往返用例。

**修复命令**:
```
python3 -c "import os;os.chmod('bin/<tool>',0o755)"   # 在 recipe 的 package() 内完成，勿手改缓存
```

**验证**:
```
ls -l <pkg>/bin/<tool>; python3 -c "import os;p='<pkg>/bin/<tool>';print(oct(os.stat(p).st_mode), os.access(p, os.X_OK))"; <pkg>/bin/<tool> -v; echo "exit=$?"
```
