# E1600: aarch64 上默认量化引擎被选成 x86 专用的 kX86（判据 fbgemmSupportedCPU() 在 ARM 也返回真），使默认量化路径抛 `unknown architecure`——而 supported_engines 看起来一切正常，须改判据为"仅 x86"并回落 QNNPACK

## 基本信息
- **严重度**: 2
- **类别**: platform, arm64, quantization, upstream-defect
- **作者**: unknown
- **来源 PR**: 12795

## 错误特征
```
unknown architecure|unknown architecture.*qengine|kX86.*aarch64|fbgemmSupportedCPU\(\).*true.*arm|QEngine.*kX86.*not available
```

## 根因分析
aten/src/ATen/Context.cpp 用 fbgemm::fbgemmSupportedCPU() 决定默认量化引擎，该函数在非 x86 分支仅返回 cpuinfo_initialize()，在 aarch64 上为真（FBGEMM 含部分 ARM 支持，判断本身不算错），于是默认引擎被设为 at::kX86；但 kX86 派发的 fbgemm::ExecuteKernelU8S8 其 arch switch 只实现 x86 的 inst_set（avx2/avx512），非 x86 即落入 `unknown architecure`（上游原文拼写）分支抛错。上游该段代码上方注释写着 "Make it default qengine for X86 CPU platforms"，即意图本就是仅 x86，只是判据选得不够严导致 ARM 被误纳入。陷阱在于 supported_engines 会同时列出 qnnpack/x86/fbgemm，看起来"都在"，掩盖了默认值选错这一事实。

## 推荐方案
**方法**: restrict-default-qengine-to-x86-and-fall-back-to-qnnpack

**说明**: 在 Context.cpp 的默认引擎判据里加架构门控：仅当 __x86_64__/_M_X64/__i386__/_M_IX86 时才保留 kX86，非 x86 且启用了 USE_PYTORCH_QNNPACK 时回落 kQNNPACK（与上游注释意图一致）。判定顺序建议：先看默认值而不是 supported_engines（后者只说明注册了），再逐个引擎实跑一次量化算子确认哪几个"真能算"。权衡需如实登记：该改法会让一例上游用例失败（QNNPACK 的 qnnpack_add() 显式拒绝空张量，而上游用例构造空 out 走 channels-last 的 quantized.add），但换来量化能力从"完全不可用"变为"QNNPACK 可实际计算"，且该边界属 QNNPACK 自身能力范围。

**修复命令**:
```
python3 -c "import torch;torch.backends.quantized.engine='qnnpack';print(torch.ao.nn.quantized.dynamic.Linear(32,16)(torch.randn(4,32)).shape)"
```

**验证**:
```
python3 -c "import torch;print('default:',torch.backends.quantized.engine);print('engines:',list(torch.backends.quantized.supported_engines))"
```
