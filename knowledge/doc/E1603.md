# E1603: OHOS musl 缺 pthread_cancel：用 meson cc.has_function() 特性探测 + 有界 poll 建立可打断等点（不要写平台宏，也不要指望 close() 唤醒阻塞 read）

## 基本信息
- **严重度**: 2
- **类别**: platform, compat, ohos, libc, musl
- **作者**: unknown
- **来源 PR**: (pending)

## 错误特征
```
undefined symbol: pthread_cancel|pthread_cancel|pthread_setcancelstate|pthread_setcanceltype|pthread_testcancel|HAVE_PTHREAD_CANCEL|fuse_loop_wait_for_input|fuse_prune_nodes|fuse_stop_cleanup_thread|prune_thread_stop|fuse_session_loop_mt
```

## 根因分析
OHOS musl libc 不实现 POSIX 线程取消，pthread_cancel / pthread_setcancelstate / pthread_setcanceltype / pthread_testcancel 四个符号在 sysroot 里既不声明也不导出（E085）。libfuse 依赖其中两处语义：lib/fuse.c 的 LRU 清理线程用 pthread_cancel 打断 sleep()，否则 fuse_stop_cleanup_thread() 后的 pthread_join 永久挂死；lib/fuse_loop_mt.c 的 worker 用 pthread_cancel 把阻塞在 read() 的线程拽出来，否则 fuse_session_loop_mt() 退出路径无法 join。很自然的兜底想法是「主线程 close(se->fd) 让 worker 的 read() 返回」——在 OHOS 上实测不成立：另一线程 close(fd) 不会唤醒已阻塞在同一 fd 的 read()，reader 永不返回，join 依然挂死。因此必须在进入阻塞调用之前就存在一个可被打断的等点。第二个独立陷阱在守卫写法：meson 的 configuration_data.set() 对布尔为真时写出的是「无值」#define HAVE_X（假时写 #undef HAVE_X），于是从 autotools（#define HAVE_X 1）迁来的代码若写成 #if HAVE_PTHREAD_CANCEL，在探测为真时会展开成 `# if` 并直接预处理报错——只能用 #ifdef/#ifndef。

## 推荐方案
**方法**: meson-feature-detect-plus-bounded-poll-instead-of-cancel

**说明**: 按四条落点改造：(1) 特性探测而非平台宏（R8）——在 meson 里用 private_cfg.set('HAVE_PTHREAD_CANCEL', cc.has_function('pthread_cancel', prefix: '#include <pthread.h>'))，C 侧一律 #ifdef/#ifndef 守卫，禁止写 #ifdef __OHOS__ 或假设「非 Linux 就没取消」；(2) 有界 poll 作为可打断等点——worker 在真正 read() 之前先 poll(fd, POLLIN, 100ms)，循环中每次检查 fuse_session_exited()，同时把 channel fd 置 O_NONBLOCK，使「poll 可读但 read 抢不到」的竞态表现为 -EAGAIN（当 continue 处理），退出时用 saved_flags 恢复原 flags；注意无 fd（fd < 0）时 poll 立即返回，函数应视 exited 状态返回，实测 fuse_session_loop_mt() 在无 channel 时约 23ms 返回 -EBADF；(3) 清理线程用停止标志——sleep() 无法被「取消」，改成按 1 秒切片睡眠并在每片检查 volatile int prune_thread_stop，停止函数置位后 pthread_join 正常收敛；(4) 验收方式——OHOS 无 /dev/fuse 不能真挂载，改在 test_package 里 fuse_session_new()（不 mount）+ fuse_session_loop_mt() 断言其能在无 channel 时自行收敛并返回 -EBADF，这条断言正好覆盖「无 pthread_cancel 的释放路径不会死锁」。另须修 lib/meson.build 的 host_machine.system() 判定把 'harmonyos' 与 linux 并列纳入 mount.c（E090）。任何 OHOS 移植遇到「另一线程阻塞在 read/accept」的释放问题，都先建立有界等点，不要指望 close()。
