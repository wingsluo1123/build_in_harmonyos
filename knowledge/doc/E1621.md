# E1621: Bind host tools in generated Meson machine files, fail close

## 基本信息
- **严重度**: 2
- **类别**: ohos, meson, conan, pkg-config, linkage
- **作者**: unknown
- **来源 PR**: 10484

## 错误特征
```
Meson cross build cannot resolve generated dependency modules|generated .pc files expose bare -lintl|archive tool missing|consumer link fails with unresolved intl or GLib symbols|native OHOS worker rejects test_package with tools.build:sysroot is required|consumer links but target test_package cannot load the tested shared-library SONAME under conanrun|inline LD_LIBRARY_PATH assignment is not exported by the target shell|Windows self.run reports '. is not recognized' before Meson starts|extensionless GLib generator scripts are not executable on a Windows host|CI consumer test returns 127 with missing shared-library SONAME despite a logged LD_LIBRARY_PATH
```

## 根因分析
A Windows-hosted OHOS Meson build has two separate boundaries: host-side tools used while configuring and generating code, and target-side libraries exported to consumers. Supplying only a cross compiler or only .pc files leaves Meson without pkg-config/archive tools, while declaring intl as a system name or a bare -lintl loses the task-owned provider path and breaks the consumer closure. Conan may generate only POSIX .sh environment files for an OHOS host profile; the default self.run() wrapper then sends '. ".../conanbuild.sh"' to Windows cmd.exe, failing before the command starts. GLib generator entries can also be extensionless Python scripts, which Windows Meson cannot execute directly. Native OHOS workers may provide a compiler-default sysroot without exposing tools.build:sysroot; requiring that conf unconditionally rejects a valid native profile. Separately, a test_package that calls self.run(..., env="conanrun") without generating VirtualRunEnv receives no package runtime path; even when the direct package exports runenv_info, transitive shared-library libdirs are not guaranteed to be present in the generated shell environment. On some target shells, an inline assignment with shell parameter expansion is logged but is not exported as a loader environment, so the runtime closure must be exported explicitly before exec. A native OHOS worker can also run clang while its lld helper cannot load an SDK-side libxml2; the consumer compile subprocess must prepend the compiler-adjacent SDK lib/lib64 directories to its host-tool LD_LIBRARY_PATH without applying that path to the target consumer runtime.

## 推荐方案
**方法**: Bind host tools in generated Meson machine files, fail closed when pkg-config/pkgconf is absent, configure the target prefix as '/', and expose GLib plus the actual intl provider as Conan transitive requirements. On Windows/OHOS, generate task-owned .cmd wrappers only for extensionless host scripts and run Meson commands with env=None so Conan does not apply a POSIX .sh wrapper to cmd.exe; retain the normal environment wrapper on POSIX workers. Require tools.build:sysroot only when cross_building(self) is true; otherwise let the native OHOS compiler use its default sysroot. If a sysroot is present, pass it explicitly. Ensure generated pkg-config data carries provider library directories and static-compilation defines. For runnable shared-library consumers, generate VirtualRunEnv, derive an absolute de-duplicated runtime closure from the tested package and non-build/non-test Conan dependency libdirs, stage the shared objects beside the consumer under a task-private runtime directory, bind one DT_RPATH containing both $ORIGIN/runtime and the absolute staging path, verify each staged entry is a non-empty readable regular file, and still use an explicit `export LD_LIBRARY_PATH=... && executable` command before execution. The origin-relative entry is required because a worker may execute the consumer in a loader namespace where its absolute Conan cache path is not visible; the ordinary directory name avoids a loader boundary observed with the hidden directory.
