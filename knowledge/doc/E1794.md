# E1794: "meson 消费 GLib/Pango 栈的 .pc 传递链断裂：隐形传递静态依赖（pcre2/libffi）不生成 .pc 导致 pkg-config 解析失败——正解为信任 PkgConfigDeps 组件级生成而非手工修上游 .pc"

## 基本信息
- **严重度**: 2
- **类别**: ohos, build-system, meson, toolchain, linking
- **作者**: unknown

## 错误特征
```
Package 'libpcre2-8', required by 'glib-2.0', not found|Package 'libffi', required by 'gobject-2\.0', not found|Could not generate cflags for \w+:|ERROR: Dependency lookup for \w+ with method 'pkg-config' failed
```

## 根因分析
GLib/Pango 系 conan 包的上游 .pc 文件携带跨包 Requires(.private) 链：glib-2.0.pc 的 Requires.private 引用 libpcre2-8（pcre2 包），gobject-2.0.pc 引用 libffi——而 pcre2/libffi 在 GLib 栈消费场景中是"隐形传递静态依赖"（用户配方不直接 requires 它们），Conan 的 PkgConfigDeps 只为**直接可见的依赖图**生成组件级 .pc，不为隐形传递依赖生成。结果：当 meson 项目的依赖（如 pangoft2）通过 pkg-config 解析时，链条在 glib-2.0 → libpcre2-8 处断裂，报 "Package not found"。深层原因有两类：(1) 若配方用上游包自带的 .pc（拷贝+改 prefix），上游 .pc 的 Requires 链引用了用户依赖图中不存在的包；(2) 若 PkgConfigDeps 生成 .pc 但依赖图只含 GLib 不含 pcre2（pcre2 是 glib 的 requires 而非用户配方直接 requires——在 glib 以 shared binary 消费时其 requires 图可能被扁平化省略传递静态依赖）。

## 推荐方案
**方法**: trust-pkgconfigdeps-component-pcs

**说明**: 不要手工拷贝/改写上游 .pc 文件（"pc-fix" 死路——上游 .pc 携带的跨包 Requires.private 链会把你没依赖的包引进来炸掉）。正确做法：(1) 确保配方 requirements() 声明**完整的直接依赖集**（pango/gangoft2 场景声明 pango 包即可，其组件 pc 会生成）；(2) 信任 conan 标准流：PkgConfigDeps 会为整个可见依赖图生成组件级 .pc（glib-2.0/gobject-2.0/pangoft2/pangocairo/fmt 等，prefix 已指向真实包目录，Requires 链只含可见组件）；(3) MesonToolchain 默认把 pkg_config_path 指到 generators 目录——不要手动覆盖；(4) 验证方法：source conanbuild.sh 后 `pkg-config --cflags --libs pangoft2` 应全部解析成功。若确需传递静态依赖的 .pc，在配方中显式 self.requires 那个传递包（使其进入可见依赖图），而非手工造 .pc。

```

```

