# E1828: conan 2.29.1 的 patch_ng 可容忍重复 hunk 段（apply=True 且恰好应用一次），但该形态补丁在 git apply 严格模式下必败——入库补丁必须双引擎验证（git apply --check -p1 + patch_ng），能重生成时优先用 git diff 从已验证树重新生成

## 基本信息
- **严重度**: 1
- **类别**: toolchain, conan, patch
- **作者**: unknown

## 错误特征
```
patch.*already applied|already.patched|Hunk.*failed|patch_ng.*duplicate|apply_conandata_patches.*fail
```

## 根因分析
手动构建时代用 GNU patch 生成/应用的补丁，可能在同一文件里保留重复 hunk 段（如 postgresql_harmony.patch 的 miscinit.c）且 hunk 行计数有偏差。patch_ng 对该形态宽容（实测 apply=True、恰好应用一次），git apply 严格模式则报 semantic conflict 必败（2026-09-04 实测）——AI Review 与 git apply 消费者都会踩坑。"patch_ng 通过"只证明 conan 构建链路可用，不证明补丁可移植。

## 推荐方案
**方法**: dual-engine-patch-verify-regen-preferred

**说明**: (待补充)

**修复命令**:
```
①历史补丁入库前做双引擎验证（git apply --check -p1 + patch_ng），任一失败即处理；②能改写场景（自有适配补丁）优先以已验证构建树为基准 git diff 重新生成——精确 hunk 计数、无重复段，生成前 git status 复核改动面；③确需原样保留（第三方只读补丁）时以双引擎结论为准，GNU patch 单引擎通过不可作为入库依据；④重生成/清洗后在 notes.md 记录偏离
```

**验证**:
```
1) 干净源码树上 `git apply --check -p1` 补丁（严格模式，重复 hunk 段此步必现 semantic conflict）；2) python3 -c 用 patch_ng（strip=0，conan 实际调用形态）apply 并断言 rc；3) 应用后 grep -c 关键标记验证只应用一次；4) conan create 走 apply_conandata_patches 全流程确认 G2 PASS
```
