# E1832: conan 2.29.x AutotoolsToolchain.defines 是只读 property（extend 是静默 no-op），注入编译宏必须用 tc.extra_defines；症状是守卫代码整体编译剔除、L2 几乎全绿但个别命令踩平台坑

## 基本信息
- **严重度**: 1
- **类别**: toolchain, conan, api-trap
- **作者**: unknown

## 错误特征
```
tc.defines.extend|defines.*no.?op|宏未定义|guard.*compiles? out|CPPFLAGS.*missing -D|could not look up effective user ID
```

## 根因分析
AutotoolsToolchain 的 defines 是 @property：每次调用返回 [ndebug, gcc_cxx11_abi] + extra_defines + conf_flags 拼接出的新列表。tc.defines.extend([...]) 修改的是这份临时列表，对 toolchain 无任何效果，也不报错。真正进入 CPPFLAGS 的公共可变属性是 tc.extra_defines（__init__ 里初始化的普通 list）。叠加风险：OHOS PC 系统 clang 原生预定义 __OHOS__，历史 __OHOS__ 守卫补丁"碰巧"不需要注入即可工作，把守卫宏改名后注入链路断裂才会暴露——且 --version 冒烟测试大多不触达平台守卫路径，34/35 全绿极具迷惑性。

## 推荐方案
**方法**: use-extra-defines-verify-injection

**说明**: (待补充)

**修复命令**:
```
①配方内注入宏一律写 tc.extra_defines.extend([...])，禁用 tc.defines.extend；②改写守卫宏后必须全量重建并验证注入链路三处落点（toolchain.sh → Makefile → configure 日志）；③冒烟全绿≠宏生效，须挑一个已知依赖守卫代码的运行期行为做正测（本例 pg_upgrade --version 的 getpwuid 回退）
```

**验证**:
```
1) grep CPPFLAGS build树/conan/conanautotoolstoolchain.sh —— 确认含 -D<宏>；2) grep '^CPPFLAGS' build树/build-release/src/Makefile.global（或等价 Makefile）；3) configure 日志 grep "using CPPFLAGS"；4) 运行期行为复测（如 pg_upgrade --version 不再报 user does not exist）
```
