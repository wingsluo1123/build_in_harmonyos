# E1852: boost 组件包拆分方法论：从完整 boost 包底稿裁剪单组件 conan 包的通用四步法（b2 不可用时的手动编译）

## 基本信息
- **严重度**: 1
- **类别**: ohos, portability, build-system, packaging, testing
- **作者**: j669539

## 错误特征
```
b2.*incompatible|SHELL.*common\.jam|match-command-output|boost.*component.*split|boost1\.84-[a-z]+
```

## 根因分析
boost 完整包（如 archives/b/boost/1.84.0）在 OHOS 只能手动编译（b2 的 SHELL 执行机制不兼容，E068/E099），且体积大（头文件树 244MB）、依赖多（zlib）。下游只需单个组件时按官方 Jamfile.v2 定义裁剪为独立组件包，可显著缩小体积与依赖面；但每个组件的源清单、include 路径、依赖、测试形态都不同，需要统一流程。

## 推荐方案
**方法**: 组件包拆分四步法（可复用）：①【裁剪依据】读 libs/<comp>/build/Jamfile.v2 提取官方源文件清单（如 math 的 C99_SOURCES×21 + TR1_SOURCES×21，每名 3 变体 = 126 文件），逐一核对磁盘无缺失；②【配方模板】复制 boost/<ver> 完整包底稿的 conanfile.py 骨架（_compile_lib 手动 clang++ 编译 + llvm-ar 归档），替换源清单与 include 路径（注意 libs/<comp>/src 的 pch.hpp 需要 -I 该目录）；③【依赖裁剪】grep 源码引用决定 requirements（math/system 不引 zlib → requirements 为空；iostreams 才需要 zlib）；④【测试选型】上游测试优先选不依赖 boost_unit_test_framework 编译库的纯 C/独立测试（如 math 的 test_tr1.c 是纯 C——__cplusplus 未定义时走 tr1_c_macros.ipp，须 clang C 模式编译 + -lc++；system 的 lightweight_test 系 94 个直接编译运行），test_package 覆盖 header-only API + 编译库 C 接口 + CMake 组件消费链路。命名用 <boost版本前缀>-<组件>（先例 qt5-qt3d/openssl-4），与完整包互不冲突；cmake_file_name 用独立命名空间（BoostMath::）避免与 Boost:: 冲突。
