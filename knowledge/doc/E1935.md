# E1935: Materialize Meson data-package public aliases when OHOS cannot install symlinks

## 基本信息
- **严重度**: 2
- **类别**: hmdfs, ohos, meson, conan, symlink
- **作者**: Codex <codex@noreply.local>
- **来源 PR**: https://atomgit.com/OpenHarmonyPCDeveloper/build_in_harmonyos/merge_requests/9128

## 错误特征
```
Symlink creation does not work on this platform|Skipping all symlinking|install_symlink.*folder-open|cursor alias missing|folder-open.svg missing|left_ptr missing|hand2 missing|xterm missing|watch missing
```

## 根因分析
Meson data-only projects may use install_symlink() to publish consumer-visible resource aliases. On HarmonyOS PC / HMDFS and some Windows destdir paths, symlink creation can be skipped even when meson.install() exits successfully. The package then lacks public resource names such as folder-open.svg or XCursor aliases, so consumers can fall back to wrong icons/cursors despite basic directory checks passing.

## 推荐方案
**方法**: meson-resource-alias-regular-file-materialization

**说明**: Keep upstream Meson install behavior, then in Conan package() materialize missing public aliases as regular files copied from the canonical source resource. Test from the consumer package root, accepting either a valid symlink or a byte-identical regular fallback. This preserves the public data contract without relying on symlink creation.

**修复命令**:
```
|
```

**验证**:
```
After meson.install(), check every public alias. If a symlink exists, verify its basename target. If an ordinary fallback file exists, compare bytes with the canonical source resource. Also verify the dataonly pkg-config file through PKG_CONFIG_PATH when present.
```
