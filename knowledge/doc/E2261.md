# E2261: 判定上游测试须按该语言生态惯例（D 的 unittest 在源码里，不在 t/ 目录）；「未接入构建流程」也不等于「不存在」

## 基本信息
- **严重度**: 2
- **类别**: portability, build-system, testing, declaration, per-language
- **作者**: ohpcd <ohpcd@localhost>
- **来源 PR**: 10885

## 错误特征
```
上游无自动化测试套件|上游没有测试|no test suite|tests? not found|上游测试用例通过率.*不适用|upstream_tests: \[\]|无 t/ 目录
```

## 根因分析
「上游测试在哪」没有跨语言统一答案——它由**语言/构建生态的惯例**决定，是不同的目录与驱动机制。若把上一个项目的布局当默认（尤其刚从 Perl/autotools 切过来时，t/ + prove 印象深刻），就会「找不到 → 判定为无测试」，而且这个误判**不会报错**：MANIFEST.yml 的 upstream_tests 写成空数组、通过率填「不适用」，CI 的 L0e 只校验该文件存在，不校验内容真伪，于是漏报一路通过。第二层成因是语义混淆：上游**有**测试但**未接入构建路径**（构建系统里没有 test 目标）时，作者容易把「跑不了/没接」直接表述成「不存在」——这两个结论的证据强度与后续动作完全不同。gir-to-d 实证：D 语言惯例是把 unittest 块内嵌在 source/ 各模块内、由 dub test（即 -unittest 编译）驱动；上游 26 个文件里确无 t/、tests/，也无 .github/workflows，但测试**就在源码里**（4 块 / 12 条 assert）。

## 推荐方案
**方法**: per-language-test-discovery-then-real-run

**说明**: 判定上游测试分三步，缺一不可：①**按该语言生态惯例穷举候选**（见 affected_scope 的语言表）——不能只查 t/；②**查构建系统是否接入**（有 test 目标 = 可经该路径跑；无 = 需手工驱动，但**测试仍存在**）；③**实跑一次取真实通过/失败数**。申报时严格区分三种状态并分别写清：**有且已接入**（如实报通过率）、**有但未接入**（列出块数/断言数、给出等价驱动命令、说明 upstream_test_in_build=false）、**确实没有**（须给出已穷举的证据，而非仅「没找到 t/」）。

**修复命令**:
```
grep -rn 'unittest|#\[test\]|func Test|def test_' . ; grep -n 'test' Makefile meson.build CMakeLists.txt package.json ; <按语言驱动命令实跑>
```

**验证**:
```
① 先按该语言惯例**穷举**候选位置，而不是只查一种：`find . -iname 't' -o -iname 'test*' -o -iname '*_test.*' -o -iname 'spec'` 与 `grep -rn 'unittest\|#\[test\]\|func Test\|def test_\|describe(' --include='*.<ext>' .`；② 再看构建系统是否接入：`grep -n 'check\|test' Makefile GNUmakefile meson.build CMakeLists.txt package.json 2>/dev/null`；③ 最后**实跑一次**取真实数（D：`ldc2 -I<ldc>/include/d -I<src> -L-L<ldc>/lib -unittest -main -of=ut <src>/source/gtd/*.d && ./ut`）。判据：能跑到具体通过/失败数才算数，`ls` 没看到目录**不构成**「无测试」的证据。
```
