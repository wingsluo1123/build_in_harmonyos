# E2338: OHOS musl 的 fopencookie 回调不同步触发（延迟到退出/close 缺失/fclose=-9）：cookie 式 FILE 虚拟化在该平台不可用，须门控回退 libc

## 基本信息
- **严重度**: 3
- **类别**: platform, portability, libc, runtime, stdio
- **作者**: unknown

## 错误特征
```
fclose.*-9|fclose.*EBADF.*fopencookie|cookie callback.*(never invoked|deferred|at exit)|fwrite.*fopencookie.*no data
```

## 根因分析
OHOS 的 musl 变体在 fopencookie 实现上偏离 glibc 与原版 musl：独立探针（30 行、不含任何三方代码）注册 {NULL,cw,NULL,cc} 后 fwrite+fclose，写回调确实两次收到正确的注册 cookie（排除调用方传参错误），但两次触发都发生在 fclose 返回 -9（EBADF）之后的进程退出刷新阶段，close 回调从不触发——即回调不随 stdio 操作同步执行，fclose 以 EBADF 失败。任何依赖"cookie 回调同步到达"的 FILE 虚拟化设计（purelibc stdio 层、BSD funopen 移植、日志/重定向 fd 包装器）因此静默丢数据或报错。上游非回归：purelibc 1.0.10 的 stdio.c 与 1.0.8 仅空白与 glibc-2.39 fileno 兼容差异。

## 推荐方案
**方法**: glibc-guard-fallthrough-to-libc-via-dlsym

**说明**: 在配方补丁中用 #if defined(__GLIBC__) 门控 cookie 覆盖层：musl 下各 stdio 覆盖函数经惰性 dlsym(RTLD_NEXT,"fopen"/"fdopen"/...) 回退 libc 真实现（glibc 上逐位保持上游行为）；把消费者测试收缩到可移植面（直接 syscall 包装器截获：open/write/close 经 _pure_syscall 到用户处理器，glibc/musl 断言一致）；notes.md/PR 正文写明降级范围并附探针证据，不静默交付会丢数据的层。

**修复命令**:
```
patch -p1 -i patches/0005-stdio.c.patch
```

**验证**:
```
设备侧最小复现：clang -D_GNU_SOURCE 编译 30 行探针（fopencookie(0x1234,"w",{NULL,cw,NULL,cc}) + fwrite 5 字节 + fclose），期望输出：cw 触发且 cookie==0x1234、触发时机在 fclose 返回 -9 之后、cc 不触发；glibc 机器同程序 fclose=0 且回调同步。
```
