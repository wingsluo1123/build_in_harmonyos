# E2347: C stdio getc/fgetc return value read into plain char never equals EOF(-1) on unsigned-char targets -> infinite loop

## 基本信息
- **严重度**: 2
- **类别**: portability, c-language, signedness, stdio
- **作者**: unknown

## 错误特征
```
kevlar build hangs|md2html hangs|rst2html hangs|process.*100% CPU|output file empty|char c = getc|char c = fgetc
```

## 根因分析
C leaves plain char signedness implementation-defined. On targets where plain char defaults to unsigned (e.g. OHOS arm64 clang 15), `getc()` returns EOF as int -1, but storing it into `char c` truncates -1 to 0xFF (255), so `c != EOF` stays true forever. Upstream loops such as `for (char c = getc(infile); c != EOF; c = getc(infile))` spin at 100% CPU and never terminate, producing empty output files. Build hosts with signed-char defaults pass, so the bug only surfaces on the target.

## 推荐方案
**方法**: int-receiver-for-stdio-return

**说明**: Change the loop variable to int: `for (int c = getc(infile); c != EOF; c = getc(infile))`. int preserves the -1 == EOF semantics on every platform. This is a source-level minimal patch that does not change API or ABI and works on both signed- and unsigned-char targets. Do not rely on -fsigned-char alone (see E419) because it changes the semantic mode for the whole TU and does not address the int->char truncation pattern directly.

**修复命令**:
```
apply patches/0002-src-kevlar_rst_to_html.c.patch (char c -> int c) and re-run the affected CLI
```

**验证**:
```
run the built binary on the target: `bin/kevlar build` in a kevlar site dir completes instead of hanging; or compile a 2-byte file reader and observe getc() reading past EOF.
```
