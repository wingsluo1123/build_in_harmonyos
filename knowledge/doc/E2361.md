# E2361: gnulib 的 AC_LIB_HAVE_LINKFLAGS 不查 pkg-config 只查系统目录与 LD_LIBRARY_PATH：交叉构建下"没人提供这个库"也会被 /usr/local 判成找到，链接行被污染且构建全绿

## 基本信息
- **严重度**: 3
- **类别**: autotools, linking, cross-compile, dependency, hermetic
- **作者**: username- <ajOovSKTZQ0vaLwZB.username-@noreply.gitcode.com>

## 错误特征
```
checking for libgnutls\.\.\. yes|checking for libidn\.\.\. yes| STARTTLS support via GnuTLS should be built\.\.\. yes| non-ASCII support via Libidn should be built\.\.\. yes| DT_NEEDED libgnutls|DT_NEEDED libidn| /usr/local/lib.*-lgnutls
```

## 根因分析
AC_LIB_HAVE_LINKFLAGS（m4/lib-link.m4）是 gnulib 的宏，不是 pkg-config 封装：它按 $LDFLAGS/$LIBS 里已有的 -L、再按 LD_LIBRARY_PATH、最后按编译器默认系统目录（/usr/local/lib、 /usr/lib）逐级找库。于是 * 不能用 self.requires() 喂给它（它不认 conan 的路径）， * 更关键的是——依赖在制品仓和仓库里都不存在时， 只要构建机前缀里有同名 .so/.a，探测依然成功， 链接行被塞进 -L/usr/local/lib -lxxx，产物带上一个 没有任何包负责交付的 DT_NEEDED。 这与 CMake 侧 CMAKE_DISABLE_FIND_PACKAGE_<name> 是同一类 问题：系统前缀里的第三方包对 hermetic 交叉构建是负面因素。 附带现象：这类产物在构建机（有那份库）与真机（没有或版本 不同）表现不一致，构建日志里没有任何可疑之处。

## 推荐方案
**方法**: disable-system-prefix-lib-probes

**说明**: 把"没有配方、只可能被系统前缀满足"的探测一律显式关掉： tc.configure_args += ["--without-gnutls", "--without-stringprep"] 并在 notes.md / README.md 里写清楚功能裁剪（关掉 GnuTLS 即没有 --starttls；关掉 libidn 即非 ASCII 用户名不参与 stringprep 规范化）。功能确实必须保留时，不要把依赖留给 系统目录碰运气，而是做成真正的配方并把 -I/-L/PKG_CONFIG_PATH 前置指向它。

**修复命令**:
```
./configure --without-gnutls --without-stringprep
```

**验证**:
```
grep -n 'AC_LIB_HAVE_LINKFLAGS\|AC_CHECK_LIB\|AC_SEARCH_LIBS' configure.ac # 构建日志里看判定与链接行： grep -nE 'checking for lib(gnutls|idn)\.\.\.|STARTTLS support|non-ASCII support' conan-create.log grep -nE '\-lgnutls|\-lidn|/usr/local/lib' conan-create.log
```
