# E2371: ILP32 时代 C 库在 OHOS LP64 (aarch64/bionic) 的类型宽度假设缺陷：wchar_t 与 unsigned long 混用、零长度 read 返回 -1

## 基本信息
- **严重度**: 3
- **类别**: portability, posix, cli-tool, consumer-test, lp64
- **作者**: unknown

## 错误特征
```
CLI 每行只输出首字符|CLI 每行只读取首字符|output truncated.*first character|putu8s.*wchar_t|read\(fd.*0\).*-1
```

## 根因分析
ILP32 时代（2000-2012）C 源码中"码点/宽字符 = 4 字节"的隐含假设在 LP64 上失效：(1) 边界层函数以 wchar_t(4B) 作形参而调用方按 UTF32=unsigned long(8B) 传缓冲，LP64 下 wchar_t != unsigned long，输出循环在首个码点高 4 字节 0 处当 L'\0' 终止，每行只输出首字符；(2) read(fd,buf,0) 零长度调用 glibc 返回 0 而 bionic 返回 -1，依赖该返回值的尾字节循环（while (BytesRead > 0 || BytesSoFar < BytesNeeded)）会过量吞读整行余下输入，每行只读入首字符。症状（CLI 每行单字符）与根因（类型/系统调用）分离，库 API 级测试全部通过，极易误判为平台 execve/文件系统问题。

## 推荐方案
**方法**: align-boundary-types-and-guard-zero-read

**说明**: 边界层函数形参改为与调用方 extern 声明一致的显式宽度类型（UTF32/uint32_t，不用 wchar_t 表达码点语义）；零长度 read 用守卫消除（仅在 BytesSoFar < BytesNeeded 时读取，BytesRead <= 0 终止）；同时新增消费者 CLI 端到端用例（dependencies 元数据定位被测包可执行文件，不依赖 PATH）断言多字符输入输出的完整性，防止回归。

**修复命令**:
```
"补丁1: -fputu8(wchar_t c,FILE *fp) / +fputu8(UTF32 c,FILE *fp); -putu8s(wchar_t *str,FILE *fp) / +putu8s(UTF32 *str,FILE *fp). 补丁2: do{BytesRead=read(fd,&c[BytesSoFar+1],BytesNeeded-BytesSoFar);BytesSoFar+=BytesRead;}while(BytesRead>0||BytesSoFar<BytesNeeded) 改为 while(BytesSoFar<BytesNeeded){BytesRead=read(...);if(BytesRead<=0)break;BytesSoFar+=BytesRead;}. test_package: numconv = Path(dep.package_folder, dep.cpp_info.bindirs[0], \"numconv\"); self.run(f'sh \"{script}\" \"{numconv}\"', env=\"conanrun\")"
```

**验证**:
```
库级探针逐码点打印 IntToString 结果应完整；CLI 管道用例 printf '6453' | numconv -f Western -t Arabic_Western 输出应为 4 字符 8 字节（٦٤٥٣），修复前为单字符；test_package CLI 端到端用例（dependencies 元数据定位 bindirs）应通过。
```
