# E2538: linux-pam-dep-plus-meson-tripod

## 基本信息
- **严重度**: 2
- **类别**: ohos, portability, meson, conan, pam
- **作者**: unknown

## 错误特征
```
'C shared or static library .pam. not found|Prefix is not below root prefix|security/pam_appl.h.*not found'
```

## 根因分析
OHOS 的 sysroot 与 harmonybrew 均不提供 libpam（meson `cc.find_library('pam')` 是 required 默认 true 的硬依赖，configure 直接 fatal：'C shared or static library pam not found'），但制品仓已发布 linux-pam/1.7.2（libpam.so.0 + include/security/*.h + 模块目录，OHOS 构建可用）。消费侧接线有两个连环坑：(1) meson 的 find_library 只走编译器链接行搜索路径，不读 pkg-config / CMakeDeps 式注入——conan 构建环境的 PATH/LDFLAGS 里依赖包目录默认不可见，必须用 Environment 把依赖包 lib/ 前置进 LIBRARY_PATH（链接探测）、include/ 前置进 CPATH（头文件探测），并给 meson test 运行期加 LD_LIBRARY_PATH（PAM 模块 DT_NEEDED libpam.so.0 需可解析）；(2) 上游为 distro 打包写的 rootprefix 自检（prefix 必须等于 rootprefix 或在其之下）与 conan meson 约定（-Dprefix=/ + install 时 DESTDIR=package_folder）结构性冲突——显式 -Dsplit-usr=true 使 rootprefix 归位 '/' 即通过，rootlibdir 相对 libdir 派生，pam 模块经 DESTDIR 落到 package_folder/lib/security。

## 推荐方案
**方法**: linux-pam-dep-plus-meson-tripod

**说明**: 配方 requirements 引 linux-pam/1.7.2（同法引 sqlite3 等其它 find_library 依赖）；generate() 里用 Environment(scope=build) prepend LIBRARY_PATH=各依赖包 lib、CPATH=各依赖包 include、LD_LIBRARY_PATH=各依赖包 lib；MesonToolchain project_options 设 split-usr=true（conan 默认 prefix=/ 约定下通过上游 rootprefix 自检）；验证口径=上游 tst-dlopen 真机 dlopen 自建 PAM 模块成功 + 消费者真调导出 API。反例：只加 PkgConfigDeps 不注入 LIBRARY_PATH 时 find_library 仍报 not found；rootprefix/prefix 手工指到 package_folder 会因 conan 实际 configure 传 prefix=/ 而误判失败。
