# E2548: 现代 config.guess（2024-07-27，tool_requires automake/1.18）无 HarmonyOS 分支 → OHOS 落到 dummy.c 临时探测段，HMDFS 上 dummy.c: Permission denied → cannot guess build type；本地通过/CI 失败根因是 automake 工具链代际不一致

## 基本信息
- **严重度**: 2
- **类别**: ohos, autotools, toolchain, conan, config.guess
- **作者**: unknown

## 错误特征
```
config.guess: line [0-9]+: .*dummy\.c: Permission denied|unable to guess system type|cannot guess build type|config.guess timestamp = 2024-07-27
```

## 根因分析
机理链（libg15 1.3.0-svn324 PR #11727 CI #59402 实证，config.guess timestamp=2024-07-27）：(1) 2024 代 config.guess 主 case 无 `*:HarmonyOS:*:*)` 分支（本地系统 automake 1.16 自带的 2023-08-22 版有该分支）；(2) HarmonyOS 不匹配任何分支 → 落到脚本尾部 "No uname command or uname output not recognized" 段，先 `set_cc_for_build` 再 `cat > "$dummy.c"`；(3) `set_cc_for_build` 用 `(umask 077 && mktemp -d "$TMPDIR/cgXXXXXX")` 建 0700 临时目录，HMDFS 共享缓存上 setgid 继承（2700）后跨 UID 不可写 → `dummy.c: Permission denied` → "unable to guess system type" → configure: cannot guess build type。(4) 本地通过/CI 失败根因：本地 PATH 回退到 $HOME/usr/local/bin 的 automake 1.16（其 config.guess 已带 HarmonyOS 分支，直接 echo 三元组退出），CI worker（USER=100）因 E443 跨 UID 0770 不可执行该目录，automake 解析到 tool_requires automake/1.18 → 2024 原版 config.guess

## 推荐方案
**方法**: post-bootstrap-config-guess-injection

**说明**: bootstrap（automake --add-missing）后再打 config.guess 补丁：在主 case 的 esac 前（锚 "# Do we have a guess based on uname results?" 注释，唯一；回退锚 *:NetBSD:*:*）注入现代 GUESS= 形态分支 `*:HarmonyOS:*:*` → case "$UNAME_MACHINE" 归一化 → `GUESS=${MACHINE}-unknown-linux-ohos` + `;;`。脚本末尾有统一 `echo "$GUESS"` 出口，GUESS= 赋值即生效，直接输出三元组并退出，完全不触碰 dummy.c 临时目录。guard：grep -c HarmonyOS >0 跳过（本地已补场景）。config.sub 2024 已认 ohos，无需改

**修复命令**:
```
在 conanfile.py build() 中 bootstrap 后以 replace 注入上述分支（见 libg15 1.3.0-svn324 配方 _fix_config_guess_ohos）；或对该脚本运行 E007 官方 scripts/patch-autotools-ohos.pl（其 §1.2 注入分支即现代 GUESS= 形态）
```

**验证**:
```
# 副本验证（只读 TMPDIR=/tmp 证明不触碰临时目录）
```
