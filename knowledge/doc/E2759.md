# E2759: OHOS libc 的 paths.h 只导出 24 枚 _PATH_ 宏、不含 _PATH_MEM/_PATH_KMEM ⇒ 上游直接用这两个宏的包编译期即挂；须加 #ifndef 特征守卫回退字面量，⛔ 平台宏判分支、⛔ 命令行注入带引号的宏值

## 基本信息
- **严重度**: 2
- **类别**: libc, musl, headers, compile-error, macro-constant
- **作者**: unknown

## 错误特征
```
'use of undeclared identifier .*_PATH_MEM|use of undeclared identifier .*_PATH_KMEM'
```

## 根因分析
memdump.c 在 SVR5/4 分支里无条件引用 _PATH_MEM 与 _PATH_KMEM。这两个名字不是 libc 函数或符号，而是 paths.h 里的字符串字面量宏。OHOS 工具链的 paths.h 实测只导出 24 枚 _PATH_ 宏（_PATH_BSHELL、_PATH_CONSOLE、_PATH_DEFPATH、_PATH_DEV、_PATH_DEVNULL 等），_PATH_MEM 与 _PATH_KMEM 命中 0 ⇒ 预处理后没有该宏名，编译到引用处报「use of undeclared identifier」。属「头文件宏常量层」的缺失，与 libc 函数符号缺失、未实现 syscall、socket 结构与常量差异都不在同一层。

## 推荐方案
**方法**: feature-guard-inline-fallback-mirroring-upstream-own-branch

**说明**: 照上游自己已有的 SUNOS5 分支形状（该分支体内就是 define _PATH_MEM 为字面量 /dev/mem）加特征守卫：ifndef _PATH_MEM / define / endif，KMEM 同理，共新增恰 6 行。补的是「宏不存在」这个可探测特征，不是「平台是 OHOS」这个身份 ⇒ 跨 libc 行为不变（glibc 侧守卫不触发），且补丁新增行不含平台宏，过 PF5。

**修复命令**:
```
grep -c "^+.*__OHOS__" archives/m/memdump/1.01/patches/0001-memdump.c.patch
```

**验证**:
```
printf "#include <paths.h>\\nint main(){return 0;}\\n" > ~/tmp/uc2/p.c && clang --target=aarch64-unknown-linux-ohos -E -dM ~/tmp/uc2/p.c | grep -c "_PATH_"
```
