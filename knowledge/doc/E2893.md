# E2893: "PKG_CHECK_MODULES 使 autoconf 2.72 把 ac_fn_c_try_link 定义排在首次调用之后，链接探测假失败但 configure 退出码仍为 0"

## 基本信息
- **严重度**: 3
- **类别**: build-system, autotools, pkg-config, autoconf, silent-misprobe
- **作者**: "new_hw-10"

## 错误特征
```
"configure: line N: ac_fn_c_try_link: command not found 出现在 configure 正常退出且构建最终成功的日志里"
```

## 根因分析
"configure.ac 里出现 pkg.m4 的 PKG_CHECK_MODULES 时，autoconf 2.72 生成的 configure 会把 C 链接探测辅助函数 ac_fn_c_try_link 的函数体发在两处，且两处都排在它的首次调用之后（实测首次调用第 1537 行、首个定义第 4594 行，定义块共 2 个）。首调用落在 AC_PROG_CC 之后那些探测里，此时函数尚未定义，于是每条先被调到的链接探测都报 command not found 并被判为否，config.h 里的 HAVE_ 宏因此成批假阴性。同一份 configure.ac 只把 PKG_CHECK_MODULES 换成等价的 AC_CHECK_LIB，定义就回到首次调用之前（首个定义第 1477 行早于首调用第 1568 行，定义块 1 个），说明触发变量是 PKG_CHECK_MODULES 的宏展开本身，与 autoconf 与 automake 是否同族、automake 取哪个发布无关。"

## 推荐方案
**方法**: "detect-and-declare-misprobe-before-delivery"

**说明**: "把 configure 日志里的 command not found 当作交付前硬查项而不是噪音：命中即认定这批链接探测结论失真，再按消费面分流。上游源码 grep 不消费相关 HAVE_ 宏时，产物行为无损，可在已知限制与 notes 里逐条列明哪些探测被假失败、以及判据是消费点为零；上游确实消费时不得照原样交付，须消除 PKG_CHECK_MODULES 这条展开路径（改用显式 AC_CHECK_LIB 与 AC_CHECK_HEADERS 组合，或按其依赖语义自己拼装），改完必须用 verification_cmd 复测定义行号回到调用之前才算修好。"

**修复命令**:
```
"grep -n -e 'command not found' 本次构建的 configure 日志; 再分别 grep -rn HAVE_STRCASECMP 与 grep -rn HAVE_ALARM 上游源码目录, 统计消费点数量"
```

**验证**:
```
"cd <生成的 configure 所在目录>; u=$(grep -n 'if ac_fn_c_try_link' configure | head -1 | cut -d: -f1); d=$(grep -n '^ac_fn_c_try_link ()' configure | head -1 | cut -d: -f1); k=$(grep -c '^ac_fn_c_try_link ()' configure); d 非空且 d 大于 u 即命中本条，随后 grep -c 'command not found' <configure 运行日志> 并 grep -rn 'HAVE_' <上游目录> 判断消费面"
```
