# E2938: 鸿蒙根文件系统只读且没有 /usr/share/X11/bitmaps，X11 默认路径查找必然 miss：库必须按确定错误码返回而不是 abort()，并为此在 test_package 里断言「失败路径」而非只断言成功路径

## 基本信息
- **严重度**: 2
- **类别**: ohos, portability, testing, error-handling, x11
- **作者**: 2301_76770579
- **来源 PR**: 13894

## 错误特征
```
BitmapOpenFailed|BitmapFileInvalid|Could not open /usr/share/X11|attempt to access a read-only file system|EROFS|abort\(\)|SIGABRT
```

## 根因分析
上游 X11 库普遍按「X11 数据目录存在于系统根文件系统」的假设编写：位图、光标字体、键盘映射等都从 /usr/share/X11/... 之类的**绝对路径**查找，找不到时一部分实现直接 abort()/exit()，一部分返回错误码。鸿蒙 PC 的 HMFS 根文件系统是**只读**的，而且不含 /usr/share/X11/bitmaps 这类目录，于是所有按默认路径的查找都必然 miss。此时若实现走 abort() 分支，任何只是「想让用户选一个图标」的应用都会整进程崩溃——这在只读根上是必现而不是偶发。另一个副作用是上游测试通常只在**可写的源码目录**喂自带的样例文件，永远覆盖不到失败路径。

## 推荐方案
**方法**: assert-deterministic-error-code-on-failure-paths

**说明**: 在 test_package 里补一组「失败路径」断言，覆盖上游测试从不触及的分支：① 畸形输入必须返回确定的**内容错误码**（示例：BitmapFileInvalid），且不得 abort、不得写坏出参；② 只读根上不存在的路径必须返回确定的**打开错误码**（示例：BitmapOpenFailed）。断言对象只选公共头文件里的状态常量与可观测的返回值/出参，不 grep 二进制、不依赖 tr/strings 等外部工具（这些在 OHOS 上未必存在）。这三条断言同时满足「鸿蒙特有测试」的申报要求：既是真的调用被测 API，又针对鸿蒙平台特性。

**修复命令**:
```
cd test_package && cmake -S . -B build && cmake --build build && ctest --test-dir build
```

**验证**:
```
conan create . -pr:h=ci/conan/profiles/ohos-aarch64 -pr:b=ci/conan/profiles/ohos-aarch64
```
