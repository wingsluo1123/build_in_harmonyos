# E2945: "在 autoreconf 之后（不是之前！autoreconf 会重装 config.guess/config.sub

## 基本信息
- **严重度**: P0
- **类别**: autotools
- **作者**: unknown

## 错误特征
```
"Invalid configuration `aarch64.*ohos': (OS `ohos' not recognized|Kernel `linux' not known to work with OS `ohos')|configure: error: .*config\\.(guess|sub) failed|error: cannot run .*\\./config\\.sub"
```

## 根因分析
"autoreconf/libtoolize 生成的 config.guess 与 config.sub 早于 HarmonyOS 支持（三元组猜測器不认识 ohos OS 与 linux-ohos 内核组合），configure 第一阶段就中断。该错误有先后两副面孔：先报 'OS `ohos' not recognized'，补完 OS 类型表之后紧接着报 'Kernel `linux' not known to work with OS `ohos''，因为 kernel-OS 校验表是独立的一张表。框架 patch-autotools-ohos.pl 的第三个 hunk（kernel 表）守卫条件是全局搜 /linux-ohos/，而它的第二个 hunk 刚写入 basic_os=linux-ohos 已经让该条件成立，所以 kernel hunk 恒被跳过——属于死代码，不是环境差异。另一层坑：若用带尾部 [ \\t]* 的正则分组去重建 config.sub 的 case 分支，该 [ \\t]* 会吞掉下一行缩进并多出一个裸 ;;，config.sub 变成 shell 语法错误，而 configure 只报 'cannot run <shell> ./config.sub'，极易误判为缺 shell。"

## 推荐方案
**方法**: "在 autoreconf 之后（不是之前！autoreconf 会重装 config.guess/config.sub 并覆盖补丁）对三处同时打补丁：ohos-linux 三元组分支、OS 类型表、kernel-OS 校验表；kernel 表的守卫条件要针对 kernel 列表本身而不是全局 /linux-ohos/ 搜索。三元组分支用「整体克隆 android-linux 分支再做字符串替换」的方式生成，天然保持缩进一致；补丁落盘后立刻跑 `sh -n config.sub` 自检，把语法错误在打补丁当场拦下，而不是等 configure 报一句指向错误位置的 'cannot run'。另外不要用 `env -u CONFIG_SHELL` 规避 hnp bash：unset 后 autoconf 会回落到硬编码的 /bin/bash 去跑 config.sub，该文件在 OHOS worker 上不存在；应显式把 CONFIG_SHELL/SHELL 设成健康的系统 shell。"
