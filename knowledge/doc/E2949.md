# E2949: 上游自愈不可达 + 能力墙按子命令分面：kma 的 hashMapKMA_load()（hashmapkma.c:275 起）在 :319/320、:349/350、:385/386、:416/417 **无条件**执行 ftok()+shmget()，紧随其后的 if(shmid < 0) { …普通文件读… }（:321-330 等同型）只在 shmget **返回**之后才被判定； 本平台 shmget 命中 seccomp-BPF SECCOMP_RET_TRAP ⇒ 进程在到达该判定之前就收到 SIGSYS(31) 而死（rc=159）⇒ **上游自带的文件回退分支永不可达**，"上游有兜底"不等于"兜底可达"。 同一份 bin/kma 里这堵墙还**按子命令分面**：kma map 默认路径不可用（rc=159、四个输出文件全 0 字节） 而带 -mmap 可用（rc=0、Score 300/Template_length 600/Template_Coverage 50.00/ Query_Identity 100.00/Query_Coverage 200.00）；kma db（db.c:59 直连 hashMapKMA_load）与 kma shm 整条不可用（rc=159）；kma index、kma dist、kma -v、kma -h 不受影响 ⇒ 判据两条：①"探测是否先于兜底、且探测本身终止进程"；②"可用/不可披露按子命令点名"。

## 根因分析
'组合层机制（不是"又一个 syscall 号被拦"，那部分归既有条目）： ① **探测在前、兜底在后**：上游把"共享内存段在不在"的判断写成 `key = ftok(...); shmid = shmget(key, size, 0666); if (shmid < 0) { …普通文件读… }`。 该 else 分支的进入条件是 **shmget 返回负值**；而本平台 shmget 被 seccomp 过滤器 以 SECCOMP_RET_TRAP 投递 SIGSYS，进程**根本不返回** ⇒ if 永不求值 ⇒ 兜底不可达。 上游其实知道这个形状需要桩化：hashmapkma.c:27-36 在 `#ifdef _WIN32` 下把 `ftok`/`shmget`/`shmat` **定义成恒失败宏**（`#define shmget(key,size,perm) ((size != 0) ? (-1) : (-key))`）， 正是"让探测返回值参与判定、从而走普通文件路径"的做法；OHOS 目标 （aarch64-unknown-linux-ohos，_WIN32 未定义）落进 `#else` 的真实 `<sys/shm.h>` 声明， **没有这层桩** ⇒ 同一份源码在 Windows 上自愈、在本平台上是终止型失败。 ⇒ 读码判据：看兜底分支的进入条件是"被拦调用的**返回值**"还是"被拦调用**本身**"； 后者在任何"命中即杀进程"的策略（SECCOMP_RET_TRAP/KILL）下永不可达，不得当退路。 ② **墙按子命令切分**：同一份产物里不同子命令的哈希表加载入口不同 —— 全树 `shm & 32`（-mmap 的运行期开关）只命中 kmers.c 与 sparse.c 两个文件 （kmers.c:85-87、sparse.c:380-382 转向 kmmap.c:33 的 hashMapKMAmmap 纯文件后端）， db.c 里根本没有该分支（db.c:59 直连 hashMapKMA_load）⇒ kma map 有出路、kma db 与 kma shm 没有出路。⇒ 披露判据：可用面/不可用面必须**按子命令**成表并各给依据行号， 写"本包整体可用/不可用"必然失真。'
