# E3003: 配方里 if self.settings.os == "OHOS" 会让本机（标准 settings.yml）conan create 直接失败；改成 str(self.settings.os) == "OHOS" 即可双环境通用

## 基本信息
- **严重度**: 2
- **类别**: portability, conan, recipe
- **作者**: unknown

## 错误特征
```
ConanException: Invalid setting 'OHOS' is not a valid 'settings.os' value.|Possible values are \[.*Linux.*\]
```

## 根因分析
Conan 的 settings 对象重载了 __eq__，右值会被当作 setting 值做合法性校验。真机 CI 的 conan 定制过 settings.yml（含 OHOS）所以 `self.settings.os == "OHOS"` 能跑；但本机 Docker/WSL 里 pip 装的原版 conan，其 settings.yml 没有 OHOS 枚举，比较动作本身抛 ConanException: Invalid setting 'OHOS'——配方在任何非 OHOS profile 下都无法构建，即使该分支逻辑本不该命中。kelbt 等库的直接 == 写法只能在真机定制环境跑，本地回归会误报配方损坏。

## 推荐方案
**方法**: str-cast-settings-compare

**说明**: 把比较写成 `if str(self.settings.os) == "OHOS":`——先转 Python 字符串再比较，不触发 settings 枚举校验。语义完全等价（settings.os 的 str() 输出就是枚举值名），且本机（Linux profile → False 跳过分支）与真机（OHOS profile → True）都能构建。同理适用于 settings.compiler 等其他定制枚举值的比较。这是让"一份配方、双环境（本机原版 conan + 真机定制 conan）可验证"的最低成本写法。

**修复命令**:
```
sed -i 's/self\.settings\.os == /str(self.settings.os) == /g' <conanfile.py> && conan create . --build=missing    # 本机应不再报 Invalid setting
```

**验证**:
```
grep -n 'settings.os ==' <conanfile.py>    # 有命中且右值是定制枚举（OHOS 等）即中招；本机 conan create 复现报 Invalid setting
```
