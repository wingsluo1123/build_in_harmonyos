# E3015: 原上游仓库消失(GitHub 404)的库选源判据——GitHub API 探测原仓库与候选 fork,以下游引用面与发行包(发行版 RPM/deb)佐证 de facto 维护 fork,conandata 直接用 fork 的 tag archive(CMake 项目无 autoreconf 问题)

## 基本信息
- **严重度**: 2
- **类别**: conan, multimedia, source, upstream-selection
- **作者**: 2301_80739235

## 错误特征
```
HTTP 404.*github.com|repository.*not found|无法访问.*上游
```

## 根因分析
小众 C 库的原作者仓库停维护甚至删除(如 libdumb 原作者 katajakasa 的仓库 GitHub 404,IRC 引用为准),但生态仍依赖。此时 conandata 源 URL 面临三选:①已 404 的原仓库(不可用);②个人魔改 fork(违反 R39 官方源精神);③**de facto 维护 fork**(下游引用面最大、发行版打包来源,如 libdumb 的 kode54/dumb——dsda-doom、openSUSE/Fedora dumb-2.0.3 RPM 均出自它)。判据:GitHub API search repos + 发行版打包记录 + 下游 CHANGELOG 引用,三者交叉确认。

## 推荐方案
**方法**: api-probe-plus-distro-packaging-cross-check

**说明**: ①curl -sI 原仓库确认 404;②api.github.com/search/repositories?q=<name> 按 star 数与描述列候选 fork;③openSUSE/Fedora 打包记录交叉确认 de facto fork(发行版打包 = 下游引用面最大的客观证据);④conandata 用 fork 的 tag archive(CMake 项目免 autoreconf),notes.md 记录原上游消亡与 fork 选择理由(R37 版本无冲突前提下)。

**修复命令**:
```
curl -sI https://github.com/<orig>/<repo>; curl -s https://api.github.com/repos/<fork>/<repo>/tags; tar -tzf fork.tar.gz | grep CMakeLists.txt
```

**验证**:
```
curl -sI https://github.com/<owner>/<repo>(原仓库 404 确认);curl -s https://api.github.com/repos/<fork>/tags(候选 fork tag 列表);发行版打包佐证:opensuse.pkgs.org / Fedora koji 搜 <name>-<ver>。
```
