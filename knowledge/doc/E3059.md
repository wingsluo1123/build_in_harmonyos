# E3059: 驱动类程序把中间文件模板硬编码为 /tmp 时，鸿蒙 /tmp 只读会让「除 -E 外任何编译都失败」；修法是让 gettmp() 优先 $TMPDIR 并回退 /tmp，并引用上游自身未启用代码的既有约定

## 基本信息
- **严重度**: 3
- **类别**: platform, tmpdir
- **作者**: Yunan0718
- **来源 PR**: 14348

## 错误特征
```
error: /tmp/ctm.XXXXXX: Read-only file system
```

## 根因分析
pcc 驱动 cc/cc/cc.c 的 gettmp() 把临时文件模板硬编码为 /tmp/ctm.XXXXXX。鸿蒙的 /tmp 是 erofs 只读挂载，于是预处理（-E）以外的每一次编译（-S/-c/-o 等）都会在创建中间文件时失败。上游其实自己已有正确约定：未被启用的 cc/driver/driver.c 里就是 template = getenv("TMPDIR")，即把在用的驱动对齐到上游既有约定即可，无需新造机制。注意：配方侧注入 TMPDIR 只对「已经读环境变量」的驱动有效，对硬编码 /tmp 的驱动是空操作——这是 E002（设 TMPDIR）在此场景下的具体化。

## 推荐方案
**方法**: honour-tmpdir-with-fallback

**说明**: 让 gettmp() 先读 $TMPDIR，取不到再回退 /tmp；引用上游自身未启用代码里的 getenv("TMPDIR") 作为既有约定，避免被质疑为自造机制

**修复命令**:
```
pcc -S -o out.s in.c   # 需 TMPDIR 指向可写目录（与 E002 同源）
```

**验证**:
```
pcc -S -o out.s in.c → error: /tmp/ctm.XXXXXX: Read-only file system；打补丁后同一命令 rc=0 并产出 992 字节汇编
```
