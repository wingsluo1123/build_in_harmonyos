# E3106: OHOS 上 /dev/uinput 对普通进程 EACCES：内核支持存在（/proc/misc 223）、sysroot 头文件齐备，但设备节点受安全策略管控——输入注入类工具需系统级执行域，测试用能力探针 + 双分支断言如实适配

## 基本信息
- **严重度**: 2
- **类别**: limitation, detection, ohos, selinux, runtime
- **作者**: 9C4A

## 错误特征
```
failed to open uinput device.*Permission denied|open\(/dev/uinput.*EACCES|/dev/uinput.*(Permission denied|EACCES)|uinput.*Operation not permitted
```

## 根因分析
输入注入（uinput）方案的编译面与运行面在 OHOS 可分离：编译面完整（OHOS native sysroot 提供 linux/uinput.h 与 linux/input-event-codes.h，struct uinput_setup / UI_DEV_SETUP / UI_DEV_CREATE / UI_SET_EVBIT/UI_SET_KEYBIT/UI_SET_RELBIT 均可用，uinput 客户端代码零改动通过编译）；运行面被安全策略阻断——内核支持存在（/proc/misc 列出 223 uinput），但 /dev/uinput 设备节点对普通进程拒绝访问：open(O_WRONLY) 与 stat 均返回 EACCES(13)，/dev/input 同样被拒（真机域 u:r:hishell_hap:s0）。ydotoold 在打开 /dev/uinput 失败后 exit(2)（perror: failed to open uinput device: Permission denied），虚拟输入设备无法创建，整条注入链在普通执行域不可用。属平台安全模型边界，应用层无解，不是构建缺陷。

## 推荐方案
**方法**: capability-probe-dual-branch-test + document-system-domain-requirement

**说明**: 不要伪造注入能力、不要空壳 stub：1) 保留上游 ioctl 设置代码（编译面可用，无需平台宏）；2) 运行时用真实能力探针（实际 open /dev/uinput）判定分支，而不是按平台名猜测；3) 消费者测试双分支断言——可用：daemon 成为 READY 并经 socket 转发事件；被阻断：断言退出码 2 与 "failed to open uinput device"（错误语义清晰、不崩溃）；4) 与 socket 侧解耦：客户端线协议的字节级断言用用户态 AF_UNIX 对端驱动（不依赖 /dev/uinput），本会话配套草稿给出该范式；5) README/notes 如实标注“完整事件注入需系统级执行域（root/system）”。

**修复命令**:
```
ydotoold -p "$TMPDIR/.ydotool_socket"; echo "rc=$?"; python3 -c 'import os; os.open("/dev/uinput", os.O_WRONLY)'
```

**验证**:
```
python3 -c 'import os; os.open("/dev/uinput", os.O_WRONLY)'  # PermissionError errno 13; cat /proc/misc | grep uinput  # 223 uinput; ydotool: ydotoold -p "$TMPDIR/.ydotool_socket"; echo rc=$?  # failed to open uinput device ... rc=2; 编译面: $CC -c probe.c（struct uinput_setup + UI_DEV_SETUP/UI_DEV_CREATE）-> OK
```
