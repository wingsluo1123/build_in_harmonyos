# E3133: FUSE 消费端在普通进程挂载不可用的平台上如何构造可审计的消费者测试：对可确定启动行为（版本/usage 退出码/目录校验/重复目录消除/mlimit 解析）做硬断言 + 真实挂载尝试做"有界双向判定"（超时=已挂载则尽力卸载；快速非零且含 fuse 诊断=干净边界失败），上游挂载类测试逐项申报 BLOCKED 而不 skip 美化

## 基本信息
- **严重度**: 1
- **类别**: ohos, testing, capability, fuse, quality
- **作者**: unknown

## 错误特征
```
mount.*required.*test|fusermount.*missing.*test|test_package.*mount.*(failed|blocked)|FUSE.*unavailable.*test|functional tests: 0/
```

## 根因分析
上游 FUSE 项目的测试资产（示例：mhddfs 的 7 个 tests/ helper + 10 个 Makefile 挂载类目标，共 17 项）全部以 live mount 为前提；当平台挂载被阻断（见 DRAFT-mhddfs-0.1.39.0-ohos-fuse-consumer-mount-boundary）时，直接照搬必然 0/17。R34/PF3 禁止空壳测试、CI L1e 破坏性反测会击穿假测试，因此需要一套既真实依赖被测二进制、又不以挂载成功为前提的构造：① 硬断言打包后二进制的可确定行为（--version 输出与 rc、无参数/单参数 usage 非零退出、不存在目录的 can not stat 诊断、非目录参数的 is not directory 诊断、重复目录消除消息、mlimit=64m→67108864 bytes 解析、启动信息包含目录列表与挂载点）；② 真实挂载尝试做有界双向判定——子进程带超时：超时未退出=挂载成功（best-effort fusermount -u/umount 清理并如实记录"平台支持"），快速非零且输出含 "fuse" 诊断=干净的边界失败（两条路径都算通过，但都在报告中标注实际走的是哪条）；③ 上游挂载类测试逐项给出技术原因并申报 BLOCKED，绝不改写为 skip 或删除。

## 推荐方案
**方法**: bounded-mount-attempt-plus-cli-contract

**说明**: 消费者测试 = 可确定 CLI 契约硬断言（≥5 项）+ 1 项有界挂载双向判定（subprocess timeout：挂起=挂载成功→清理；非零+含 fuse 诊断=干净失败）+ 报告逐项 BLOCKED 申报。断言必须真实执行被测二进制；挂载尝试必须有超时上界，防止平台支持时测试挂死。

**修复命令**:
```
python3 test_mhddfs.py <package>/bin/mhddfs   # 10/10 passed；上游测试申报见版本 reports/test-report.md
```

**验证**:
```
python3 test_package/test_mhddfs.py <pkg>/bin/mhddfs  # 期望 10/10；conan create 内 L1e 破坏性反测：移走 bin/ 后 conan test 必须失败（证明测试真实依赖被测包）
```
