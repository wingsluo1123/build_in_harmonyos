# E3139: musl regcomp 后端双重 regfree 段错误（上游测试 cleanup 钩子模式）

## 基本信息
- **严重度**: 2
- **类别**: platform, behavior
- **作者**: unknown

## 错误特征
```
"Segmentation fault (core dumped) | regfree() | test_*_cleanup | GIT_REGEX_REGCOMP | double free regex_t"
```

## 根因分析
musl libc 的 regfree() 对已释放的 regex_t 再次调用时无任何防护（无 re_magic 校验路径命中前的崩溃点在 1.2.x 实现里直接解引用已 free 的指针），直接段错误。上游库若提供 regex 后端抽象且 REGCOMP 后端的 dispose 实现为裸 regfree(r)（无 *r=NULL 防护），则任何"循环内 compile→dispose + 测试 cleanup 钩子再 dispose"的用法都会触发双重释放。libgit2 1.9.6 的 test_diff_userdiff__compile_userdiff_regexps 即此模式：builtin/pcre2 后端 dispose 带 *r=NULL 防护所以上游 CI 无感，REGCOMP 后端必崩。这是 musl 与 glibc 的行为差异：glibc regfree 对已释放结构会命中 re_magic==0 检查静默返回，musl 没有。

## 推荐方案
**方法**: 不要显式指定 REGEX_BACKEND=regcomp（musl libc regcomp）。让上游 CMake 自动检测：OHOS 上（无 regcomp_l、无系统 PCRE）会解析为 bundled PCRE2（libgit2 的 "builtin" 后端），其 git_regexp_dispose 是 pcre2_code_free(*r); *r=NULL 带防护。通用化修法：任何在 musl/OHOS 上用系统 regcomp 的库，检查其 dispose/free 封装是否有双重释放防护；测试崩溃在最后一个 regfree（LD_PRELOAD 拦截 regcomp/regfree 打印可确认多余的 free 调用）时优先怀疑 cleanup 钩子模式而非正则内容本身——用最小 C 程序（compile 一次 + regfree 两次）可 5 秒复现定性。
