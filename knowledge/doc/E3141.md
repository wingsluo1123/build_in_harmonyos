# E3141: HMDFS 写回在 close() 后仍短暂持有写句柄，cargo"写完 build-script 即 exec"偶发 ETXTBSY(os error 26)，cargo 构建/测试命令须带锚定错误文本的一次重试

## 基本信息
- **严重度**: 2
- **类别**: hmdfs, build-system, toolchain, cargo
- **作者**: Curator (oh-device-porting-v3, zram-1.2.1 run)

## 错误特征
```
Text file busy|os error 26|ETXTBSY|could not execute process.*never executed
```

## 根因分析
HMDFS（FUSE 型文件系统）的写回在 userspace close() 之后仍短暂持有写句柄；cargo 并发构建对 build-script 可执行文件走"写完立即 exec"路径（libc 等带 build.rs 的 crate 必经），紧邻序列撞上尚未释放的写句柄，exec 返回 ETXTBSY(os error 26)，cargo 记 could not execute process ... (never executed)，make 以 Error 101 失败。竞态窗口导致偶发（同命令重跑即过）；真实编译错误的特征是错误文本含编译诊断而非 os error 26，可据此区分。

## 推荐方案
**方法**: retry-once-anchored-to-etxtbsy-text

**说明**: 对构建/测试命令做一次失败重试，且重试条件锚定错误文本（Text file busy / os error 26）而非盲重：真实编译错误第二轮照样失败并抛出，不掩盖任何真问题；精确锚定避免把无关失败也重试。权衡如实声明：recipe 层若用 catch-all 的"失败即重试一次"（本 run conanfile build() 即此形态）收敛性相同，但会对非 ETXTBSY 失败多做一轮无害工作，且略升 flake 频率被掩盖的观察成本——更优形态是 test_package 中"仅当输出含 Text file busy 才重试"的定向版。

```
见 doc_file 两处实现样例（conanfile.py _run_with_retry 与 test_package _run_upstream_tests 的 Text file busy 定向重试）
```
