# E3158: 内核设备节点门控的用户态运行时库不可适配判定：构建期 REQUIRED 依赖在制品仓零命中 且 运行期硬编码 open("/dev/kfd") 而平台无该内核驱动与硬件时，应直接判 env_unsupported（rocminfo 原型案例）

## 基本信息
- **严重度**: 2
- **类别**: platform, limitation, detection, kernel, portability
- **作者**: Quas
- **来源 PR**: （无 —— 无法适配走 issue 通道，不建配方 PR；本条由【知识库扩展】草稿 PR 沉淀）

## 错误特征
```
Could not find a package configuration file provided by "hsa-runtime64"|
```

## 根因分析
一类库的**全部功能**是"通过某个内核驱动暴露的设备节点，枚举/操作平台硬件"。 它同时具备两个**互相独立**的致命阻塞，任一单独就足以否决适配： 1) **构建期依赖链断裂**：其 CMakeLists 用 `find_package(<runtime> REQUIRED)` 硬性引入 一个"用户态运行时库"（本案例 `hsa-runtime64`），而该运行时既不在 OHOS SDK sysroot 中， 也不在制品仓（本案例 7340 条配方检索 `hsa*`/`hsakmt*`/`rocr*`/`kfd*` 全部 0 命中）， 连配置阶段都过不去； 2) **运行期内核+硬件门控**：即便自行补齐该运行时（可自行写配方编出 libhsa-runtime64）， 其下层 thunk（本案例 libhsakmt/ROCt）**硬编码 `open("/dev/kfd", O_RDWR|O_CLOEXEC)`** （`libhsakmt/src/openclose.c:47` + `runtime/hsa-runtime/core/driver/kfd/amd_kfd_driver.cpp:131`）， 而 `/dev/kfd` 由**内核态驱动** `amdkfd`（AMDGPU 驱动集的一部分）创建，且必须绑定了 **AMD GPU 硬件**才有意义。OHOS PC（麒麟 SoC + 自研 GPU）既无该内核驱动、也无该硬件。 **关键判据（区别于"依赖未适配"）**：阻塞不在"某个库还没人适配"，而在 "该库的语义对象（KFD 驱动 + AMD GPU）在本平台上**不存在**"。因此不是"暂时搁置"， 而是**技术不可行 / env_unsupported**。 **必须做的排除项（防误报平台缺陷）**：OHOS SDK sysroot **已带** AMD 相关 **Linux UAPI 头** （`usr/include/linux/kfd_ioctl.h`、`usr/include/drm/amdgpu_drm.h`），所以 "鸿蒙缺 KFD 头文件"这条论据**不成立**，不得据此申报；真正的缺口是 **内核侧驱动 + 设备节点 + 硬件**三处。同理，制品仓里存在 `libomptarget-rtl-amdgpu` 这类"能编过但注册 0 设备"的 GPU 插件，**不能**反推平台支持 AMD GPU。 另需注意：本类库通常**无降级可用子集**——移除设备枚举后功能不成立，桩化 `hsa_init()` 只会得到一个恒失败的空壳（违反"不得裁剪软件"与空壳红线）。

## 推荐方案
**方法**: detect-kernel-device-node-gated-runtime-then-escalate

**说明**: 判定顺序（全部为可复现命令，见 verification_cmd）： 1) **先看构建期硬依赖**：`find_package(<runtime> REQUIRED)` 出现即记下该运行时名； 2) **查制品仓**：`conan search -r ohpcd` 检索该运行时及其下层 thunk，0 命中 ⇒ 依赖链整条断裂； 若有命中，须**下来看包内容**确认它真能提供所需 .so/头（本案例 `rocm-hipamd/5.7.1` 名为"rocm"实则 `header-library`，只有 `include/` 与 cmake 宏，**无任何 .so、无 hsa.h**， 不能解决 `find_package`）； 3) **查平台是否已有该能力**：`find $SYSROOT`；**同时必须查反例**——把"看似缺失但实际存在" 的东西（本案例 KFD/AMDGPU UAPI 头）明确写进报告，避免被评审以"论据不成立"驳回； 4) **追运行期硬编码**：下载其下层运行时的**对应版本源码**，grep 设备节点字面量 （`/dev/kfd`）与 topology sysfs 路径，确认阻塞在**内核态**而非用户态可绕； 5) **实测配置失败**并把原始报错贴进报告（证据链要求"真实做过的尝试与报错"）； 6) **最有力的补充证据（推荐做）**：在**无该硬件**的宿主上，用**真实**的上游运行时把该工具 **真正编出来并运行**，用 `strace` 抓出那一次失败的系统调用 （本案例实测：`openat("/dev/kfd", O_RDWR|O_CLOEXEC) = -1 ENOENT` → `hsa_init()` 失败 → `HSA_STATUS_ERROR_OUT_OF_RESOURCES` → exit 8）。 这把结论从"构建不过"升级为"**即使构建过了，运行期也确定不可用**"，堵死 "你只是没配好依赖"的质疑； 7) 结论落 `env_unsupported`，按仓库手册【无法适配】issue 通道申报（**不建配方包目录**， 否则 CI 报 `No packages to build` + exit 1 被误判 rule4 编译失败）； 可另开【知识库扩展】草稿 PR 沉淀本条通用判据（先例：mexce 1.0.1）。 禁止项：不得把 `find_package` 的 REQUIRED 去掉/改成非必需来"编过"、不得桩化 `hsa_init()` 等设备入口伪造可用、不得交付预编译二进制、不得把"自己写一个软件 GPU 模拟器" 当作适配交付。

**修复命令**:
```
grep -n 'find_package(.*REQUIRED' CMakeLists.txt; \
```

**验证**:
```
# ① 构建期第一道门：是否 find_package(... REQUIRED) 强依赖某运行时
```
