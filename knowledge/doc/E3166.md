# E3166: OHOS 内核不实现 futex 的 REQUEUE_PI/TRYLOCK_PI 三种操作（ENOSYS 38）：靠 PI-requeue 实现的跨进程条件变量 wait/broadcast 整体失效，而基础 FUTEX_WAIT/WAKE/LOCK_PI/UNLOCK_PI 正常

## 基本信息
- **严重度**: 2
- **类别**: platform, limitation, ohos, kernel, syscall
- **作者**: unknown

## 错误特征
```
fail condition broadcast\[38\]|fail condition wait\[38\]|Function not implemented|FUTEX_CMP_REQUEUE_PI|FUTEX_WAIT_REQUEUE_PI|FUTEX_TRYLOCK_PI|errno=38.*futex
```

## 根因分析
HongMeng 内核的 futex 只实现了基础子集，FUTEX_CMP_REQUEUE_PI、FUTEX_WAIT_REQUEUE_PI、FUTEX_TRYLOCK_PI 三种「PI 重新排队/尝试锁」操作经 syscall(SYS_futex=98) 直接返回 errno=38(ENOSYS)，不是 seccomp 杀进程（无 SIGSYS）。上游 a0（AlephZero）层把跨进程条件变量的唤醒与等待全押在这三种操作上——a0_cnd_wake 走 a0_ftx_cmp_requeue_pi、a0_cnd_timedwait_impl 走 a0_ftx_wait_requeue_pi、owner-died 恢复分支走 a0_ftx_trylock_pi——于是 cond broadcast/wait 恒返回 ENOSYS，事件通知链断裂：日志刷 fail condition broadcast[38] / fail condition wait[38]，依赖广播的用例超时或 abort，锁恢复路径退化。

## 推荐方案
**方法**: probe-futex-op-availability-then-degrade-to-plain-wake

**说明**: 动手前先用 30 行探针对 futex 逐操作打可用性表（逐个 syscall(SYS_futex, &v, OP, 1, 0, NULL, 0) 看 errno），确认哪些操作缺失再改。命中 REQUEUE_PI/TRYLOCK_PI 缺失后按「被禁的具体操作」降级：唤醒侧 FUTEX_CMP_REQUEUE_PI 改 FUTEX_WAKE，等待侧 FUTEX_WAIT_REQUEUE_PI 改 FUTEX_WAIT 并由等待者自己重新加锁（丢失 PI 优先级继承，换来可用），owner-died 恢复分支跳过 trylock_pi 走普通锁路径。若不接受改并发语义，就如实登记为平台限制、在 notes 与 PR 里写清哪些用例因此失败，不要把它误判为包缺陷或测试脚本问题。

**修复命令**:
```
clang futex_probe.c -o futex_probe && ./futex_probe
```
