# E3193: 源码住在发行版包管理器树内（MASTER_SITES=none，无上游 tarball）时，用"目录最后变更 commit + 逐文件 download() 固定 SHA256"获取源码，不引入 conandata.yml、不解压、不自造 tarball

## 基本信息
- **严重度**: 2
- **类别**: conan, distro-in-tree, reproducibility, sourcing
- **作者**: unknown

## 错误特征
```
404 .*raw/commit/[0-9a-f]{8}\b|BadZipFile|BUILD_DIR: parameter not set|invalid sha256
```

## 根因分析
一类上游（FreeBSD ports、pkgsrc 等）根本不发布源码归档，源码文件直接提交在包管理器仓库树内；常规"找 release tarball + conandata.yml"流程在此类包上没有输入对象。同时该场景有三个叠加陷阱：单文件 raw URL 无归档后缀（get()/解压路径会被格式推断为 zip）；conandata.yml 触发 CI pre-download 基础设施缺陷与镜像改写；raw 端点只认完整 40 位 commit（短 sha 404）。

## 推荐方案
**方法**: per-file-download-pinned-commit-no-conandata

**说明**: "配方内写 _files_base=<repo>/raw/commit/<完整sha>/<dir> 与每文件 _sha256，source() 逐文件 download(self, url, name, sha256=...)。取目录级最后变更 commit 把漂移面压到'本包目录被改才失效'。决策顺序：①不自造 tarball 上传私仓（不可复现）；②不用 get()/解压路径（raw 无后缀会被判 zip）；③不写 conandata.yml（避开 pre-download BUILD_DIR 缺陷与镜像 fallback 改写）；④包管理器自带构建文件（bsd.port.mk 片段 Makefile）弃用并在 notes 说明，build() 直接用 Conan conf 提供的编译器。"

**修复命令**:
```
grep -n "download(" <recipe>/conanfile.py   # expect: 逐文件 url+name+sha256，无 get(、无 conan_data
```

**验证**:
```
curl -s "<host>/api/v1/repos/<org>/<repo>/commits?sha=main&path=<dir>&limit=1" | jq -r .[0].sha   # 目录最后变更 commit（完整 40 位）; curl -sfL "<base>/<file>" | sha256sum   # 固化后写进配方
```
