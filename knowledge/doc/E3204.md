# E3204: uefiextract 的 guids 子模式在 GUID 库为空时打印用法并退出 1 —— 收集函数按 text 字段筛选（普通文件该字段恒空），且该分支缺终结 return

## 基本信息
- **严重度**: 2
- **类别**: detection, runtime, cli, silent-failure, upstream
- **作者**: uefitool-adapter

## 错误特征
```
Usage:\s+UEFIExtract\s+\{\-h\s+\|\s+\-\-help（命令行本身合法、输入文件也成功读入，却仍打印用法并 exit 1）| 名为 <img>\.guids\.csv 的输出文件未生成
```

## 根因分析
两处缺陷叠加。① 收集函数 common/guiddatabase.cpp:124 的筛选条件是 `model->type(index) == Types::File && !model->text(index).isEmpty()`，取的是 **text**；而 FFS 文件的可读名存在 **name** 字段里（ffsparser.cpp:2222 `name = guidToUString(fileHeader->Name)`，ffsparser.cpp:2262 作为 addItem 的第 4 个参数传入）。text 是"短注记"字段，只有 Volume Top File / NVRAM store / apriori / protected-range hash 这类特殊文件才会被 setText 赋值 ⇒ **普通文件（FREEFORM、驱动等）的 GUID 永远进不了这个库**。② 库为空时，uefiextract_main.cpp:102-107 的 guids 分支体只有 `if (!db.empty()) { return …; }` 而没有 else —— 控制流落穿整条 if-else 链，执行到第 217-218 行的 `print_usage(); return 1;`。结果是"参数完全合法"与"用户敲错了参数"产生**完全相同**的输出与退出码。

## 推荐方案
**方法**: 不要为这个现象去反复猜命令行语法 —— 它与参数无关。需要完整可读名清单就用 report 子模式（它走 model->name）；需要 .guids.csv 就接受"只收录特殊文件"的现状，或在自造测试镜像里放一个 Volume Top File 让它能产出。若确实要修：把筛选条件换成 model->name(index)，并给 guids 分支补 else 或终结 return（返回一个明确的"无内容可导出"状态）—— 这个改法是可直接向上游提交的（P005）。
