# E3206: 同一上游包内多个 CLI 的契约彼此不自洽（帮助文本承诺的选项实现不认 + 无参数退出码语义相反）—— 消费者测试套统一模板必然误判

## 基本信息
- **严重度**: 2
- **类别**: compat, detection, portability, runtime, testing
- **作者**: uefitool-adapter

## 错误特征
```
Usage: .*\{-h \| --help \| -v \| -version\}|U_INVALID_PARAMETER.*-version|照帮助文本传参后退出码非 0 且只打印 usage
```

## 根因分析
上游把多个可执行文件放在同一棵树里，各自由**独立**的 main() 处理参数，没有共享的选项解析层。于是同一份「Usage」格式在不同二进制里被手工抄写成不同内容，而实现分支各写各的：① 帮助文本与实现不一致 —— 某个二进制的 Usage 行承诺 {-h | --help | -v | -version}，实现只匹配 "-v" 与 "--version"，照文档敲单横线 -version 会落到兜底分支返回参数错误；同包另一个二进制的 Usage 行写的是 --version，与实现一致。② 退出码语义相反 —— 一个二进制把「无参数」当作用法错误（返回非 0），另一个当作「打印帮助即成功」（返回 0）。这类不自洽不会导致任何构建或运行失败，所以上游 CI（本例上游根本没有测试套件）不会暴露它。

## 推荐方案
**方法**: 消费者测试**以源码为准而非以帮助文本为准**，并对每个二进制分别钉住它自己的契约。把「无参数退出码」当作被断言的契约之一（而不是假定它一定非 0）。对"帮助文本与实现不一致"这一项：记录事实但**不写成断言** —— 上游一旦修正，写死的断言会变成假失败。

**修复命令**:
```
逐个二进制单独断言：# uefiextract 无参数 -> 1（视为用法错误）；# uefifind 无参数 -> 0（打印帮助即成功）；# uefifind <img> <非法模式> -> 1；# uefifind <img> 不命中 -> 8；# 两者 -v/--help -> 0；# 两者 <缺文件> -> 5
```

**验证**:
```
对每个二进制逐条按帮助文本敲一遍并记录退出码：BIN -h; BIN --help; BIN -v; BIN --version; BIN -version; BIN（无参数）; BIN /nonexistent。再把结果与各自 Usage 行逐字对照。例：`uefifind -version; echo $?` 与 `uefiextract -version; echo $?` 的差异即可复现。
```
