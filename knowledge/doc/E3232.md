# E3232: HMOS 的 sh 不搜索当前目录：用裸相对名执行脚本会 rc=127（`inaccessible or not found`），必须写 `./name`（或把该目录加进 PATH）；Linux/bash 下工作目录常在 PATH 里所以侥幸通过，这正是这类失败在 WSL 交叉环境永不复现的原因

## 基本信息
- **严重度**: 3
- **类别**: cross-compile, testing, shell, compile-divergence
- **作者**: unknown

## 错误特征
```
inaccessible or not found|: not found$|Error 127|rc=127|: No such file or directory
```

## 根因分析
OpenHarmony/HarmonyOS 的 `sh` 在执行裸名字（不含 `/`）时只走 PATH 查找，**不做当前目录查找**；而 Linux 上许多测试框架会把 testbed 目录塞进 PATH（或调用方显式 `PATH=.:$PATH`），于是同一个脚本在 Linux/WSL 上"裸名可用"，在设备侧报 `<name>: inaccessible or not found`（rc=127）。实测最小复现（鸿蒙 PC，cwd 已在脚本所在目录）：`sh -c 'exec "$@"' sh s.sh` → rc=127；同一命令换成 `./s.sh` → rc=0；把 PATH 收敛成 `/usr/bin:/bin` 仍是 127 ⇒ 排除"PATH 污染"这一解释。因此该失败**只与设备侧 shell 的查找语义有关**，与配方源码、依赖、工具链都无关。

## 推荐方案
**方法**: quote-explicit-relative-path-in-test-harness

**说明**: (1) 诊断：CI/日志里出现 `<name>: inaccessible or not found` 或 `Error 127`，且被调脚本确实存在 ⇒ **先怀疑裸相对名**，不要先怀疑 cwd/ctest WORKING_DIRECTORY；(2) 修法：在调用处补 `./`（最稳、不改上游语义），或在脚本开头显式 `PATH="$PWD:$PATH"`（改动面更大，注意别把副作用带进产物）；(3) 自检：修完必须**在设备侧**跑一次"新旧对比"（旧 rc=127 → 新 rc=0），并确认绝对路径调用与不存在的名字仍按原样失败（防"补 ./ 之后把找不到也当成功"的假通过）；(4) 纪律：**凡 WSL/交叉环境不复现的 CI 失败，先上设备做最小复现再改配方**，不要从日志推断机制（本条就是"凭日志猜 cwd"猜错的实例）；(5) 顺带坑：`sh -n` 在 `/mnt/d` 上会因 autocrlf 的 CRLF **误报语法错**，判 shell 语法要看 blob 而不是工作树文件。

**修复命令**:
```
sh -c 'exec "$@"' sh ./<name>   # test_package/test.sh 里把裸名改为显式 ./ 相对路径
```

**验证**:
```
cd /tmp && printf '#!/bin/sh\necho OK\n' > s.sh && chmod 755 s.sh && sh -c 'exec "$@"' sh s.sh; echo "bare rc=$?"; sh -c 'exec "$@"' sh ./s.sh; echo "dot rc=$?"; env PATH=/usr/bin:/bin sh -c 'exec "$@"' sh s.sh; echo "controlled-path rc=$?"   # 期望 127 / 0 / 127
```
