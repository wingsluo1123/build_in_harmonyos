# E3274: bishengjdk17 的 libfontmanager.so 按 ELF NEEDED 依赖 libfreetype.so.6 而 OHOS PC 设备不提供该库，任何触发 AWT/字体栈的 Java 代码运行必败（UnsatisfiedLinkError），消费者应走 headless-safe 路径

## 基本信息
- **严重度**: 2
- **类别**: platform, ohos, musl, java, runtime
- **作者**: sea_crab

## 错误特征
```
UnsatisfiedLinkError.*libfontmanager\.so|Error loading shared library libfreetype\.so\.6|ExceptionInInitializerError.*SunFontManager|NoClassDefFoundError.*sun\.font|NoClassDefFoundError.*java\.awt
```

## 根因分析
bishengjdk17 的 libfontmanager.so 的 ELF NEEDED 项含 libfreetype.so.6（工具实现证据：llvm-readelf -d 列出 NEEDED [libfreetype.so.6, libawt.so, libjava.so, libjvm.so, libc++_shared.so, libc.so]）→ musl 动态链接器按 NEEDED 逐项解析，设备运行库目录（/usr/lib、/system/lib64、HNP 目录）均无 libfreetype.so.6 → dlopen libfontmanager.so 失败，JVM 抛 java.lang.UnsatisfiedLinkError: ... Error loading shared library libfreetype.so.6: (needed by .../libfontmanager.so) → 该错误发生在 sun.font.SunFontManager 静态初始化（<clinit>）内，升级为 ExceptionInInitializerError → 之后任何触碰该类的消费者得到 NoClassDefFoundError 连锁（本库上游测试 15 项连锁失败留档，均同根因）→ 归类：平台运行库供给缺口（NEEDED 缺失是加载期硬失败），非移植缺陷、非上游依赖问题。

## 推荐方案
**方法**: headless-safe-consumer-path

**说明**: 消费侧走 headless-safe 路径，绕开字体栈而非修补它：1) 类存在性断言一律用三参形式 Class.forName(name, false, classloader)——不触发静态初始化，避开 SunFontManager <clinit> 连锁；2) 只实例化确认无 GUI/字体依赖的契约类（引擎类、启动器类），实例化前用 -Djava.awt.headless=true 运行环境；3) 触碰上游测试中 AWT/字体路径的用例如实记录为平台缺口连锁，不修改测试 oracle、不预置答案、不整体跳过。本范式在 jakarta-jmeter 2.13 test_package 全量实证（纯 JDK 反射消费者，12 断言全过）。

**修复命令**:
```
test_package 断言形如：Object engine = Class.forName("org.apache.jmeter.engine.StandardJMeterEngine").getConstructor().newInstance();（headless-safe 实例化断言）；类存在性用 Class.forName(name, false, cl)。运行环境 java -Djava.awt.headless=true。
```
