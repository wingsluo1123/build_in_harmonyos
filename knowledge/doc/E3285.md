# E3285: 设备面缺失型 CLI 工具的可交付判定与四段配方口径（fbset 2.1 实证）：编译墙/运行期墙分界 + make 变量覆盖 + L2 信息型退出码 + 双态消费者断言

## 基本信息
- **严重度**: 2
- **类别**: platform, headers, build-system, runtime, testing
- **作者**: 主理-4
- **来源 PR**: (本 PR)

## 错误特征
```
open /dev/fb0.*No such file or directory|ioctl FBIOGET_VSCREENINFO.*|unknown type name '__u32'|make.*gcc.*No such file or directory
```

## 根因分析
设备面缺失（本平台无可访问 /dev/fb*）本身不是停手理由，停手判据只有"编译墙"（头文件不可得/汇编或私有工具链无法跨平台补齐）。fbset 的真实阻塞有四段且互不相同：① fbset.h 把 #include <asm/types.h> 包在 #ifdef __GLIBC__ 内，musl/OHOS 不定义 __GLIBC__ ⇒ __u32 未定义（编译错 14 处，一行级可移植性修复）；② 上游裸 Makefile 写死 CC = gcc -Wall -O2 -I. 且 INSTALL = install（本平台均不存在）⇒ 只能 make 命令行覆盖 CC/CFLAGS/LDFLAGS，安装改 package() 手工 copy（上游 install 目标写 /sbin、/usr/man 并 mknod /dev/fb*，在包内不可执行）；③ 上游 Usage() 经 Die() 恒 exit(1) ⇒ L2 smoke 判定 --help/--version 非 0 即失败；④ 设备查询失败信息（open /dev/fb0 …）若被当成"测试失败"则无法交付。

## 推荐方案
**方法**: compile-vs-runtime-wall-split-then-four-surface-delivery

**说明**: 分四段：① 先证明"不是编译墙"——头文件内置/可补即继续（glibc 条件包含去条件化，如 #ifdef __GLIBC__ 包 <asm/types.h>），只有头文件不可得、私有汇编或私有工具链才停手；② 构建面零补丁变量化——make CC=<conf 中 tools.build:compiler_executables:c> CFLAGS/LDFLAGS 命令行覆盖写死值，flex/bison 未预生成则 tool_requires( flex/2.6.4 + bison/3.8.2 )，不用上游 install 目标、由 package() 手工安装并按需自签；③ L2 smoke 保信息型请求退出 0——用文件级状态变量让 -h/--help 分支 exit(Die_status=0)，错误路径仍 1（先例 E503 的解法，本例签名不同：工具本有长选项，只是经 Die() 退出）；④ 消费者测试双态断言——设备在则断言真实输出（模式/版本横幅），设备不在则断言"诊断信息指名设备或裁决点"，两个分支都判真，同时把运行期墙写进 notes/README/PR 披露（rule4/R51 的 N_static=0 与设备能力一并如实申报）。

**修复命令**:
```
make CC="clang -O2 -Wall -fPIE -I." LDFLAGS="-pie -Wl,-z,relro,-z,now" LDLIBS="" -j1  （配方内由 conf 取编译器，R33）
```

**验证**:
```
make CC="clang -Wall -O2 -I." 2>&1 | head -5（修复前首错 fbset.h:41:5 error unknown type name __u32；修复后 make rc=0；./fbset --help 后 $? 为 0；./fbset -s -fb /dev/null 报 ioctl FBIOGET_VSCREENINFO Not a tty；conan create 消费者测试输出 6 assertion(s), 0 failure(s)）
```
