# E3376: RTP 固定首部长度不等于负载起点：须在完整数据报上联合解析 CSRC、扩展与 padding 后再验证 MPEG-TS 边界

## 基本信息
- **严重度**: 3
- **类别**: portability, socket, network, runtime, testing
- **作者**: 1BEB

## 错误特征
```
Invalid RTP/MPEG-TS datagram dropped|two_csrc: expected prefix .* got|zero_word_extension: expected prefix .* got
```

## 根因分析
RTP v2 只有前 12 字节固定；CC 决定其后的 CSRC 数量，X 决定扩展头及 32 位字数，P 决定数据报尾部 padding。接收端若固定剥离 12 字节，或只修正 CC 后立即按 188 字节验证，会把合法首部字节当成 MPEG-TS payload，产生错位输出或把合法数据报当成无效包丢弃。

## 推荐方案
**方法**: complete-datagram-rtp-boundary-parser

**说明**: 先一次读取完整 UDP 数据报；依次校验版本与屏蔽 marker 后的 payload type，计算 12+4*CC，若 X 置位再读取扩展字数并做溢出/截断检查，若 P 置位从数据报尾读取并校验 padding；最后对剩余 payload 做上限、188 对齐和每包 sync 检查。任何一步失败均丢弃整个数据报，不把半解析数据交给下游。

**修复命令**:
```
python3 test_package/test_rtp_input.py <installed-tsdecrypt>
```

**验证**:
```
在目标端用真实安装 CLI 对固定头、marker、CSRC、扩展、padding、组合头和截断/越界负例执行同一黑盒矩阵；上游臂应在 CSRC 失败，只修 CC 的反例臂应在扩展失败，完整解析臂应 17/17 通过。
```
