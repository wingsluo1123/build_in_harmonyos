# E3413: A '-vvvv' payload TRACE makes a stderr 'grep ERROR' harness check false-positive on binaries that embed the word ERROR

## 基本信息
- **严重度**: 1
- **类别**: false-positive, logging-verbosity, test-harness, triage
- **作者**: 4456

## 错误特征
```
"\[FAIL\] \(succeeded - was supposed to fail\)|Client has errors|grep -E .FATAL\|ERROR. <stderr> >/dev/null$"
```

## 根因分析
Test harnesses commonly assert 'no errors' by grepping the process stderr for FATAL|ERROR. When the program under test traces its transferred bytes at maximum verbosity, the payload itself lands in stderr. On OHOS, /bin/ls is the toybox multi-call binary whose embedded string table contains the literal 'ERROR :Range for -f is 1 to %ld (max ttl)', so a byte-identical file-transfer test reports 'has errors' even though the pipeline never logged an error. The same suite passes on GNU coreutils because that binary does not embed that literal.

## 推荐方案
**方法**: separate-payload-trace-from-real-errors

**说明**: Do not weaken the upstream assertion and do not patch the program. Triage by (1) proving the transferred payload is byte-identical (sha256 + size of sent vs received), (2) showing every stderr ERROR hit is inside a TRACE payload dump line ('Received:' / 'Trying to send:' / '[STDIN] Producer received:'), and (3) confirming the literal originates from the payload (strings <payload-file> | grep ERROR). Record it as a harness false positive in the report with the raw counts, and keep the true denominator: the case is reported as failed-by-harness, not silently dropped.

**修复命令**:
```
python3 -c "import hashlib;print(hashlib.sha256(open('/bin/ls','rb').read()).hexdigest())" ; strings /bin/ls | grep ERROR
```

**验证**:
```
strings /bin/ls | grep -c ERROR ; grep -c 'TRACE .*Received:' <client_stderr>
```
