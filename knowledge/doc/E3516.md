# E3516: HarmonyOS HMDFS can expose a mapped file-owner UID and reject hardlinks, while app UIDs may have no passwd record; treat these as separate platform capabilities

## 基本信息
- **严重度**: 2
- **类别**: hmdfs, ohos, libc, filesystem, passwd-db
- **作者**: iKalous_OscarP
- **来源 PR**: 15271

## 错误特征
```
File owner mismatch|link(at)? .*Operation not permitted|cannot determine user name|cannot determine my username|getpw(uid|nam).*NULL|comsat.*passwd
```

## 根因分析
On the captured HarmonyOS PC device, getuid() returned 20020085 while stat().st_uid for a newly created HMDFS file returned 20001006. HMDFS also rejected linkat() with EPERM. Separately, the application UID had no traditional passwd database entry, so getpwuid()/getpwnam() could legitimately return NULL. Callers that require st_uid == getuid(), assume linkat() always works, or dereference a NULL passwd result fail for different reasons.

## 推荐方案
**方法**: hmdfs-owner-aware-test-fixture-plus-scoped-rename-fallback-and-null-safe-current-user-lookup

**说明**: (1) Keep production mu_file_safety_check() intact; in the File Safety test helper, use stat().st_uid as the expected file owner when HMDFS reports a mapped UID. A consumer assertion still rejects an explicit foreign UID. (2) For a Maildir temporary-to-destination transition, attempt linkat() and fall back to same-filesystem renameat() only for known unsupported-link errors; propagate other errors. (3) Check passwd lookup results before dereference. Use LOGNAME/USER only as a fallback for the current process identity, limit comsat's user-switch bypass to test mode, and in test mode accept a non-root .biffrc owner when HMDFS maps it. Keep all upstream cases running rather than skipping the platform-sensitive cases.
