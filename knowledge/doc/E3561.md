# E3561: HMDFS 对已签名 ELF（CI 发布件带 .codesign 段）实施加载期完整性校验：任何内容改写（patchelf/python 字节替换/tar 重打包）都触发 dlopen Permission denied；逐字节原样复制则正常

## 基本信息
- **严重度**: 1
- **类别**: platform, hmdfs, ohos
- **作者**: unknown

## 错误特征
```
Error loading shared library.*Permission denied|dlopen.*Permission denied|cannot open shared object.*Permission
```

## 根因分析
HMDFS 在 mmap-exec 装载时校验 ELF 的 .codesign 签名。发布件（conan 制品仓下载的 OHOS aarch64 二进制）都带 CI 签名；本地任何内容级修补都会使签名失效，加载器直接拒载（错误形态是 Permission denied 而非 ELF format error，极具迷惑性）。决定性对照实验：同一新鲜签名件 (a) 逐字节原样复制（os.open 创建、mode 770）→ 加载推进到「缺依赖」而非拒载；(b) 仅翻转 0x200 一个字节 → 立即 Permission denied。同批实验证伪了「创建方式/mode 位决定 exec」的早期假说：无签名的自编译 .so 无论 python 写(660+chmod)/os.open(770)/tar/cp 哪种方式落盘都能加载（mode 位与创建方式都不是判据，chmod 三规律见 harmonyos-specifics.md）。注意与「已签文件写侧 EPERM」（见 DRAFT-SIGNED-ELF-OVERWRITE-EPERM）区分：那条是 open(wb) 写入被拒，本条是写入成功了但签名坏了、加载期才炸。

## 推荐方案
**方法**: restore-original-bytes

**说明**: (1) 禁止对已签名库做内容级修补——包括「看起来无害」的等长字符串替换；(2) 需要 NEEDED/CWD 级修复时用不改字节的方案：相对 NEEDED 用 test_package cwdroot 模式（硬链/cp 基名库 + chdir，见 kturtle test_package/conanfile.py），绝对 NEEDED 断链用 rm+cp 逐字节填充；(3) 已改坏的文件唯一出路是恢复原始字节：conan remove <pkg> -c && conan download <pkg> -r=<remote>（conan 解包/全新 cp 是实测可信的字节来源）；(4) 缓存体检用 detect-hmdfs-exec-integrity.sh（知识库拓展四件套，archives/k/kturtle/26.04.0/knowledge-extension/）。

**修复命令**:
```
conan remove "<pkg>/<ver>" -c && conan download "<pkg>/<ver>" -r=<remote>
```

**验证**:
```
f=<已签名so>; /data/service/hnp/bin/readelf -S "$f" | grep -c codesign; python3 -c "import shutil,subprocess,sys; d=bytearray(open('$f','rb').read()); d[0x200]^=0xFF; open('/tmp/t.so','wb').write(bytes(d))" && python3 -c "import ctypes,sys; sys.stderr= open('/tmp/t-err.log','w'); ctypes.CDLL('/tmp/t.so')" 2> /tmp/t-err.log; cat /tmp/t-err.log
```
