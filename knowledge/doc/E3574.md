# E3574: **老 Java 源码常是 Latin-1（ISO-8859-1）编码**：用 `javac -encoding UTF-8` 编译会报 `unmappable character (0xNN) for encoding UTF-8` → 必须按 `-encoding ISO-8859-1` 编译（上游 `build.xml` 往往不指定 encoding，即依赖 javac 的**默认平台编码**，在 UTF-8 环境下就会踩到）

## 基本信息
- **严重度**: 2
- **类别**: build-system, python, java
- **作者**: 41B8

## 错误特征
```
unmappable character \(0x..\) for encoding UTF-8|警告: unmappable character|编码错误
```

## 根因分析
2000s 前后的 Java 源码常在注释/字面量里含 Latin-1 单字节字符（如 0xA4 = "¤"、0xA7 = "§"）。 上游构建脚本未声明 `encoding` 时，javac 用平台默认编码读源码——在 UTF-8 默认的现代环境里， 这些字节无法映射 → 编译失败（或（警告形式）静默替换成 U+FFFD，造成字面量悄悄变样）。

## 推荐方案
**方法**: compile-with-iso-8859-1-when-upstream-omits-encoding

**说明**: ①遇到 `unmappable character (0xNN) for encoding UTF-8` 时**不要**去改上游源码或加 `-nowarn` 了事；②先取字节级证据（`python3` 列出 >127 的字节），确认是老编码；③把编译命令改为 `javac -encoding ISO-8859-1 …`（与 javac 在上游默认环境下行为一致），并在配方注释/notes 里写明原因；④若同一工程里新旧文件编码混杂，可按目录分别编译或逐个试探；⑤消费者校验仍要端到端真跑（编码错误在被 `-nowarn` 掩盖时可能变成"字面量悄悄变样"，只有真跑能发现）。

**修复命令**:
```
python3 -c "b=open('src/x.java','rb').read(); print(sorted({hex(x) for x in b if x>127}))" ; javac -encoding ISO-8859-1 -d classes $(find src -name '*.java')
```

**验证**:
```
①`file <src>` 或 `grep -P '[\x80-\xff]' <src> | head`（找非 ASCII 字节）②`python3 -c "b=open('<src>','rb').read(); print([hex(x) for x in b if x>127][:8])"` ③用两种 encoding 各试一次编译，看哪种通过
```
