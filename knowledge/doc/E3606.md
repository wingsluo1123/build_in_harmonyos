# E3606: 上游测试驱动是 Go 源码（go test 驱动 run_test.go）而平台无 Go 工具链：把 harness 语义（调用参数/归一化正则链/执行顺序/xfail 语义）逐行忠实移植到平台可用语言（Python），容器预验证暴露 3 处移植偏差——移植偏差与平台差异必须分开归因，kati 355 用例真机 fail=0 实证

## 基本信息
- **严重度**: 2
- **类别**: ohos, portability, go, testing, methodology
- **作者**: unknown

## 错误特征
```
go: command not found|go: cannot find GOROOT|上游 run_test\.go 无法执行|
```

## 根因分析
大量 Google 系项目（kati 等）的上游测试由 Go 源码驱动：run_test.go 内嵌着完整测试语义——被测物调用参数、stdout/stderr 归一化正则链（含"circular 行先抽取置顶再比对"的非常规步骤）、沙箱目录布局、执行顺序（先全部 make 侧再全部 kati 侧、同 .mk 的 testN 共用目录）、xfail/TODO 语义（TODO 钉住的用例输出相等即 XPASS=rc1）。OHOS 无 Go 工具链 → 该文件无法执行，上游 355 个行为用例整体不可运行。**关键认知：要移植的是语义而非代码**——正则抄错一条、顺序语义漏掉一层，产生的失败会被误归因为"平台差异"钉进 xfail，永久掩盖真残差。

## 推荐方案
**方法**: line-by-line-faithful-port-with-audit-table

**说明**: 四步：(1) **逐行对照表**：按 run_test.go 的函数顺序列移植表（Go 源码行号 → Python 行号 + 语义注释），作为可审计工件进 PR；normalize() 这类多步正则链逐条抄，特殊控制流（circular 前置抽取：匹配行先从输出删除、移到开头、再整体比对）不得简化；(2) **非明显语义显式保真**：执行顺序（先 make 后 kati）、沙箱共享（同 .mk 的 testN 顺序共用目录）、xfail 双向判定（XPASS=rc1 与 FAIL 同级）——这三类在 Go 里是隐式控制流，移植时最易丢，丢了就产生"看起来像平台差异"的移植偏差；(3) **容器预验证做移植偏差探测器**：在 musl 容器先跑全量，失败逐个问"是移植偏差还是平台差"——预验证暴露的 3 处偏差（circularRE 漏移植、布局深度、顺序语义）全部属于前者，对齐 run_test.go 后消解；预验证分布不代表真机（make 版本不同），只用于语义验证；(4) **移植偏差与平台差异分开归因**：移植偏差修移植代码，平台差异才进 xfail 钉单——混流会把 bug 钉成"平台特性"永久掩盖。平台扩展点（workdir 参数化、SHELL 注入、python3 发现链）独立成节并注明与上游的差异及原因，与忠实移植部分物理隔离。
