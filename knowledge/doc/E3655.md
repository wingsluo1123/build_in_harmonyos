# E3655: getopt() result stored in a plain char: where char is unsigned the EOF that ends option scanning becomes 255, so the CLI rejects every valid invocation ("Unknown option" naming a valid option, exit 1) while -h and library-level tests stay green; a rescanned option list has one receiver per scan and fixing only one is a half-fix

## 基本信息
- **严重度**: 2
- **类别**: portability, testing, abi, c-language, signedness
- **作者**: 1370

## 错误特征
```
Unknown option .-[A-Za-z]'.*Try .[a-z]+ -h|Unexpected option '-[A-Za-z]'|comparison of constant -1 with expression of type 'char' is always true
```

## 根因分析
On a target whose plain char is unsigned (OHOS aarch64: CHAR_MIN 0, __CHAR_UNSIGNED__ 1; every AAPCS64 Linux target; x86 Linux is signed) a CLI that keeps the int result of getopt() in `char ch` can never see EOF: -1 is stored as 255, `while (-1 != (ch = getopt(...)))` never ends, and once the last option has been handled the next call's EOF falls into the `default:` branch of the switch. The program then prints its unknown-option diagnostic and exits 1; vendored getopts that set optopt on every call (mar 0.5's ntp_getopt) make the message name the last option parsed, which is perfectly valid, e.g. "Unknown option `-s'" for `mar -s name=hello a.mar`. Options that return before the scan finishes (-h) and library-level test programs never reach the faulty loop, so smoke checks and `make check` stay green. mar 0.5 scans its option list twice (main() pre-scan, then mar_run() after `mar_optind = 0`) and has a `char ch` in each: fixing only main() lets mar_run() perform the write and then fail ("Unexpected option '-s'", exit 1, data already stored); fixing only mar_run() fails in the pre-scan before anything is written (no archive file is created). clang 15 does report -Wtautological-constant-out-of-range-compare for the comparison by default, but it is only a warning and the build succeeds.

## 推荐方案
**方法**: widen-getopt-receiver-to-int-at-every-scan

**说明**: Declare every variable that receives the getopt() result as int and leave the comparison with -1/EOF alone: one line per receiver, no platform macro, upstreamable. Grep all call sites (`grep -n getopt src/*.c`) because a rescanned option list (optind reset to 0, as mar and NTP's getopt are designed to allow) has one receiver per scan. Turn the compiler's existing warning into a guard by promoting just that group in the recipe's CFLAGS. Prove it with a consumer test that drives the packaged CLI with valid options and asserts exit status 0 and empty stderr, then reads the result back through the library; a -h/--version smoke check or a library-only `make check` cannot detect the defect. Link the CLI -static-pie so that test executes the delivered binary under qemu-aarch64 on x86 runners.

**修复命令**:
```
sed -i 's/^    char ch;$/    int ch;/' src/<prog>.c   # after grepping that every `char ch;` is a getopt receiver; recipe: CFLAGS='-O2 -fPIC -Werror=tautological-constant-out-of-range-compare'
```

**验证**:
```
clang -c <prog>.c 2>&1 | grep "constant -1 with expression of type 'char'"   # source side: a hit inside an option loop is the bug; then run ONE valid invocation with the delivered binary: qemu-aarch64 ./<static-pie prog> <valid option and argument> ...; echo rc=$?   # rc=1 plus "Unknown option" naming a valid option confirms it; `<prog> -h` still returns 0 and proves nothing
```
