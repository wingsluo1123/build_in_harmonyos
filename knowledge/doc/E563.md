# E563: "For X11 clients that depend on libXft, take the whole stack

## 基本信息
- **严重度**: P1
- **类别**: dependency
- **作者**: unknown

## 错误特征
```
"libx11/6.4.0 and libx11/1.8.13 do not match|Version conflict: requested libx11/6.4.0 but resolved|conflict between libx11/1.8|dependency graph conflict.*libx11"
```

## 根因分析
"This repo ships TWO parallel lineages of the same X11 client library: libx11/1.8.10-1.8.13 (+libxext/1.3.x, the prebuilt-stack companions) and libx11/6.4.0 (+libxext/6.4.0, the self-built family adopted by merged recipes after CI #28097). The intermediate library libxft hard-pins the OLD lineage in its own recipe (verified on ohpcd: libxft/2.3.9 resolves requires -> fontconfig/2.18.Z freetype/2.14.Z libx11/1.8.Z libxrender/0.9.Z xorgproto/2025.1; libxft/2.3.8 pins the same). Therefore any X client that needs libXft CANNOT also require the audited libx11/6.4.0 convention - the version ranges are disjoint and Conan fails with a version conflict, not with a build error."

## 推荐方案
**方法**: "For X11 clients that depend on libXft, take the whole stack from libXft's own pinned range instead of mixing: declare only requires(libxft/<ver>) and let libx11/libxrender/freetype/fontconfig/xorgproto be resolved transitively, or pin libx11 to the same 1.8.Z range explicitly. Do NOT copy the libx11/6.4.0+libxext/6.4.0 pattern from merged non-libXft X recipes (e.g. xeyes) into a libXft-consuming recipe. Before choosing, read the .requires list of the published binary with conan graph explain --requires=libxft/<ver> -pr:h <ohos profile> -r ohpcd."
