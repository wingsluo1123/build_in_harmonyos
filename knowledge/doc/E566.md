# E566: OHOS 上 config.guess 双重失败：uname -s "HarmonyOS" 不被识别 + 编译探测 dummy.c 在 HMDFS TMPDIR 下 Permission denied，configure 报 cannot guess build type

## 基本信息
- **严重度**: 3
- **类别**: platform, detection, hmdfs, build-system, autotools
- **作者**: unknown

## 错误特征
```
config.guess: unable to guess system type|cannot guess build type|dummy\.c: Permission denied|UNAME_SYSTEM  = "HarmonyOS"
```

## 根因分析
autotools 的 configure 在未显式传 --build/--host 时会运行 m4/config/config.guess 探测构建平台。该探测在 OHOS worker 上双重失败：(1) config.guess 无法把 uname -s "HarmonyOS"、uname -r "HongMeng Kernel 1.12.0" 映射为已知三元组，输出 "unable to guess system type"；(2) 即使绕过 uname 映射，config.guess 内部的编译器探测会向 TMPDIR（HMDFS 挂载点，如 /data/storage/el2/base/cache 或源码目录）写入 dummy.c 并尝试编译，HMDFS 对该写入/重定向返回 Permission denied（E114 同类），探测同样失败。最终 configure: error: cannot guess build type; you must specify one。纯分析产物：该失败与包源码无关，任何需要 config.guess 探测的 autotools 包在 OHOS 上都会复现（puredata 0.54.1 CI #56266 实测）。

## 推荐方案
**方法**: explicit-build-host-triplet

**说明**: 在 configure 调用中显式传入 config.sub 认可的三元组（--build=aarch64-unknown-linux-ohos --host=aarch64-unknown-linux-ohos），使 configure 完全跳过 config.guess 探测，同时规避 uname 不识别与 HMDFS tmp 编译探测两个失败点。这是仓库内多个已合入配方的成熟方案：argp-standalone、abiword-plugin-*（clarisworks/pdb 等）、a52dec、aalib、abiword-plugin-docbook 等。注意 --host 会让 configure 按 cross-compiling 语义处理（交由 OHOS clang 工具链本身无影响）；若上游 config.sub 版本过旧不认识 *-linux-ohos 后缀，可退化为 aarch64-unknown-linux-gnu 或 aarch64-linux（abiword-plugin-docbook/a52dec 用法）。

**修复命令**:
```
conanfile.py build(): self.run("./configure --prefix=/ --build=aarch64-unknown-linux-ohos --host=aarch64-unknown-linux-ohos ...", env="conanbuild", cwd=self.source_folder)；使用 AutotoolsToolchain 的配方则为 tc.configure_args.append("--build=aarch64-unknown-linux-ohos"); tc.configure_args.append("--host=aarch64-unknown-linux-ohos")
```

**验证**:
```
修复后 conan create archives/<pkg> -pr:h=ci/conan/profiles/ohos-aarch64 -pr:b=ci/conan/profiles/ohos-aarch64 --build=missing 应通过 configure 阶段；configure 输出中不再出现 config.guess 探测与 "cannot guess build type"。
```
