# E574: Compile-fail (expect-to-fail) upstream test suites on OHOS: driver substitution, TMPDIR pinning, and diagnostic-oracle governance

## 基本信息
- **严重度**: 2
- **类别**: portability, clang, compilation, testing, shell
- **作者**: 9C4A

## 错误特征
```
parallel: (not found|command not found)|mktemp:.*(Read-only file system|can't create)|verify_compilation_error.*FAIL|expect(ed)?-to-fail.*(compiled|succeeded)|negative compil(e|ation) case.*(passed|did not fail)
```

## 根因分析
A class of upstream projects encodes compile-time contracts as expect-to-fail test cases: one translation unit per contract, each expected to FAIL compilation with a diagnostic that must match a declared oracle (trompeloeil compilation_errors/ uses `// pass: <regex>` over compiler output plus `// exception: <regex>` exclusions matched against the compiler command line). These suites assume a GNU user space and a known compiler family: they fan out with GNU parallel and create per-case logs with mktemp in /tmp. OHOS provides neither (toybox has no parallel; /tmp is read-only, E002), so the suite cannot start at all - and its negative assertions are silently lost if the package is skipped, which is the strongest assertion class such a package has. Even when forced to run, the suite is only trustworthy if the OHOS compiler emits the diagnostics the oracles declare: the assertion is the diagnostic text, not the exit code. Existing entries cover single ingredients (E002 /tmp, E063 -Werror, E325 shell resolution for test_package wrappers) but none defines the execution model, the per-case PASS/FAIL/excluded accounting, or the no-silent-skip governance that makes such suites meaningful.

## 推荐方案
**方法**: recipe-driven-compile-fail-suite-runner

**说明**: Keep the upstream cases, the per-case verify script and every diagnostic oracle untouched; replace only the fan-out and environment layer inside the recipe: (1) drive each case from the recipe (Python ThreadPoolExecutor(2) or xargs -P2) calling the same verify script; (2) export CXX from tools.build:compiler_executables (R33) and CXXFLAGS=-std=c++NN; (3) pin TMPDIR to a build-folder subdirectory; (4) count PASS/FAIL per output line exactly like the upstream driver does (FAILURES = grep FAIL | wc -l), fail conan create on any FAIL, and treat cases printing neither as upstream // exception: exclusions; (5) run at least the default standard and the newest supported one (C++20 for coroutine-guarded cases) and report cases/executed/pass/fail/excluded per standard in notes and the PR body; (6) never rewrite // pass: regexes - diagnostic drift, if ever observed, is reported with the raw compiler output instead of being silenced.

**修复命令**:
```
ThreadPoolExecutor(2) -> subprocess.run(["sh", "../verify_compilation_error.sh", case], cwd=neg_dir, env={CXX, CXXFLAGS, TMPDIR}); fallback: CXX=<clang++> CXXFLAGS=-std=c++NN TMPDIR=<writable> sh -c 'ls *.cpp | xargs -P$(nproc) -n1 sh ../verify_compilation_error.sh'
```

**验证**:
```
cd <src>/<negative-dir> && CXX=<clang++ abs path> CXXFLAGS="-std=c++14" TMPDIR=<writable build dir> sh -c 'ls *.cpp | xargs -P2 -n1 sh ../verify_compilation_error.sh' | grep -c FAIL   # expect 0; PASS lines = executed cases; neither = upstream // exception: exclusion
```
