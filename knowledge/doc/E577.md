# E577: 用固件自身 CLI 在无 mount/mkfs -d 宿主上构建块设备测试夹具：devnum/参数全 hex、载体零建逐扇区覆盖、GPT 盘脚本自足

## 基本信息
- **严重度**: 2
- **类别**: testing, device-test, fixture, sandbox
- **作者**: LIMInGZE666 <LIMInGZE666@noreply.gitcode.com>

## 错误特征
```
Bad device specification|** Bad device|read: all zeros|Partition Map|ENODEV
```

## 根因分析
上游 pytest 的块设备夹具（test_ut.py setup_bootflow_image/setup_fedora_image/setup_efi_image）依赖 mount、`mkfs.vfat -d` 目录注入、debugfs——OHOS 无 mount 权限、busybox mkfs.vfat 无 -d 参数、无 debugfs。以固件自身 CLI（u-boot sandbox -c）staging 时踩四坑：① blk_get_device_by_str 用 hextoul 解析设备号（"mmc 10"=设备 16 → -ENODEV，do_part_list 静默返回 1 零输出），② usb read 全参数 hex 且不收设备号（maxargs=5），③ 测试中途会格式化载体介质（bootflow_efi mkdosfs 写 0x800 引导扇区），保存过的载体副本可能是被污染后的 FAT 镜像，后续 fatwrite 把 extlinux.conf 写成全零，④ 夹具生成脚本必须全套自足：cros/android 的 GPT 盘（mmc5/7/8）若靠一次性手动运行预生成器留下的镜像，脚本自身不生成——全新环境静默缺夹具，4 个子测试（bootflow_cros/bootstd_images/bootflow_android_v2/v4）无盘可挂。

## 推荐方案
**方法**: zero-build-explicit-overlay

**说明**: 载体（transport 介质）一律 dd zero 自建 + 逐扇区显式 dd 覆盖每个 payload 偏移，永不复用保存副本；块设备号按 hex 书写（设备 10 写 "mmc a"）；staging 命令所有数值参数按 hex；mkimage 生成段必须排在消费其产物的文件系统构造段之前（boot.scr 被 ext2 构造器读取）；每个 fatwrite 之后用 fatload+md 回读闭环校验。

**修复命令**:
```
dd if=/dev/zero of=testflash.bin bs=1M count=4; dd if=extlinux.conf of=testflash.bin bs=512 seek=2048 conv=notrunc; u-boot -d dtb -c "usb start; usb read 0x1000000 0x800 4; fatwrite mmc 1:1 0x1000000 extlinux/extlinux.conf 0x253; ...; part list mmc a; exit"
```

**验证**:
```
夹具后 `u-boot -d test.dtb -c "fatload mmc 1:1 0x1000000 extlinux/extlinux.conf 0x253; md.b 0x1000000 32"` 回读与源文件逐字节一致；`part list mmc a` 出 Partition Map。
```
