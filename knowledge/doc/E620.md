# E620: Legacy bcopy(s,d,n) to memcpy(d,s,n) compatibility macro defined before #include <string.h> leaks into the system bcopy declaration and breaks the OHOS build

## 基本信息
- **严重度**: 2
- **类别**: legacy-source-compat
- **作者**: unknown

## 错误特征
```
conflicting types for 'memcpy'|expanded from macro 'bcopy'|previous declaration is here
```

## 根因分析
Old GNU C sources (termutils 2.0 tparam.c and many contemporaries) define `#define bcopy(s, d, n) memcpy ((d), (s), (n))` under HAVE_STRING_H/STDC_HEADERS and only afterwards include <string.h>. On the OHOS musl sysroot <string.h> pulls in <strings.h>, which declares `void bcopy (const void *, void *, size_t)`. The macro is still in scope at that point, so the system declaration expands to `void memcpy((const void *), (void *), size_t)` and clang fails with "conflicting types for 'memcpy'" (note pointing at both the macro expansion and the previous declaration in string.h). Build hosts with glibc may not surface the conflict because their headers order or omit bcopy differently.

## 推荐方案
**方法**: reorder-system-include-before-compat-macro

**说明**: Move the system include above the compatibility macro inside the same conditional block - `#if defined(HAVE_STRING_H) || defined(STDC_HEADERS)` then `#include <string.h>` then `#define bcopy(s, d, n) memcpy ((d), (s), (n))` then `#endif`. Double inclusion is harmless (include guards), the system bcopy declaration is parsed before the macro exists, and the package's own bcopy call sites keep expanding to memcpy on every platform. Do not use #undef after the header, do not guard with platform macros (R8), do not patch the sysroot.

**修复命令**:
```
apply the include reorder and rebuild with conan create archives/t/termutils/2.0 -pr:h=ci/conan/profiles/ohos-aarch64 -pr:b=ci/conan/profiles/ohos-aarch64
```

**验证**:
```
conan create archives/t/termutils/2.0 -pr:h=ci/conan/profiles/ohos-aarch64 -pr:b=ci/conan/profiles/ohos-aarch64
```
