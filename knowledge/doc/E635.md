# E635: Conan 2 配方 generate() 只产出 CMakeToolchain 而漏掉 CMakeDeps：find_package 会静默命中宿主上的同名库，产物被塞进运行期动态依赖（编译器不报错）

## 基本信息
- **严重度**: 1
- **类别**: build-system, cmake, linking, conan, dependency
- **作者**: unknown

## 错误特征
```
CMakePresets\.json was not found|Conan: Target declared 'ZLIB::ZLIB'|ZLIB_DIR:PATH=.*harmonybrew|needed .*libz\.so|NEEDED\)\s+Shared library: \[libz\.so|libz\.so\.1
```

## 根因分析
Conan 2 里 CMakeToolchain 与 CMakeDeps 是两个独立生成器：前者写 toolchain/presets，后者才生成 <Pkg>Config.cmake 等依赖配置文件。配方 generate() 若只调 tc = CMakeToolchain(self); tc.generate()，构建目录里就没有 ZLIBConfig.cmake，于是 CMakeLists 里的 find_package(ZLIB REQUIRED) 走 CONFIG 模式去别处找同名包，命中了宿主上另一个 zlib（本例 /storage/Users/currentUser/.harmonybrew/lib/cmake/ZLIB，来自 PATH 派生的前缀搜索）。结果：链接了动态 libz.so.1，产物带运行期依赖、静态隔离（R26）失效、包不再自足。CMakeCache 里的 ZLIB_DIR 是唯一能一眼看穿的证据。同类隐患：任何 find_package(X) 的 X 在宿主上另有一份安装（zlib/openssl/libpng/sqlite3 等高频系统库）都会触发。次级症状：漏 CMakeDeps 时若连 generate() 都没写，先报 "CMakePresets.json was not found in .../generators folder"（更早暴露，但也可能被误当成工具链问题）。

## 推荐方案
**方法**: emit-cmakdeps-then-assert-no-host-lib-needed

**说明**: (1) 配方 generate() 必须成对产出两个生成器：deps = CMakeDeps(self); deps.generate(); tc = CMakeToolchain(self); tc.generate()。(2) 想更保险可在 CMakeLists 写 find_package(ZLIB REQUIRED CONFIG)，把"必须由 Conan 提供配置"变成硬约束（模块模式下的内置 FindZLIB 会绕过 CMakeDeps）。(3) 验收侧必须检查产物的运行期依赖：readelf -d <bin> | grep NEEDED / strings <bin> | grep libz.so，把"无非预期 .so 依赖"写成 test_package 的断言——这正是本例中唯一抓住该缺陷的用例（编译、conan create、conan-verify 全绿）。(4) 反向排查：CMakeCache 的 <PKG>_DIR 指向本仓之外的路径，即说明命中了宿主库；对系统同名库（libz.so 等）应始终走静态 Conan 依赖（R26）。(5) 判据口径：包管理器前缀通常由 PATH 派生进入 CMake 的前缀搜索（<prefix>/lib/cmake），故装机环境越"干净"越不容易暴露——不能以"我这台机器没问题"结案。

**修复命令**:
```
readelf -d "$(conan cache path xmill/0.8 | xargs dirname)/p/bin/xmill" | grep NEEDED   # 兼容写法见 verification_cmd
```

**验证**:
```
grep -E "ZLIB_DIR:|ZLIB_LIBRARY:" <build>/CMakeCache.txt ; readelf -d <pkg_folder>/bin/<exe> | grep NEEDED ; strings <pkg_folder>/bin/<exe> | grep "libz\.so"
```
