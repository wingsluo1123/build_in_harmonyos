# E658: 脚本型 CLI（无库 API、无构建系统、只有一个 C 助手）：合成"助手自有格式"的输入来驱动脚本，目标架构正确性改用 ELF 头纯文件断言 —— 别让整段测试被架构守卫跳过

## 基本信息
- **严重度**: 1
- **类别**: platform, ohos, build-system, testing, arch
- **作者**: unknown

## 错误特征
```
SKIP.*build machine is|only run.*when.*machine|can_run.*False|skip.*target execution|no writable scratch directory
```

## 根因分析
交付物被拆成架构相关与架构无关两部分时，只有前者受"本机跑不了目标产物"限制，但实践中两者常被同一个 arch 守卫一起跳过：脚本主体是纯解释器代码、在任何主机上都能真跑，却白丢断言；C 助手若只能靠目标机原生执行验证，本地门禁对这段逻辑零覆盖。更隐蔽的一层是"测试自己往源码树里写产物"：test_package 没有自己的 layout 时 Conan 把 build_folder 指到 archives/<l>/<pkg>/<ver>/test_package/ 本身，驱动写出的采集归档(.tar)会留在树里，被下一次 git add 连同配方一起提交（JC3/PF2 事后才拦）。

## 推荐方案
**方法**: synthesize-the-tool-own-input-format-then-split-assertions-into-file-level-and-exec-level

**说明**: (1) **先给断言分类**：文件级（存在性、可执行位、shebang、脚本能否被目标解释器 compile()、ELF class / e_machine / PT_INTERP、man 与许可证齐全）无条件执行，x86 与 aarch64 都跑；执行级（真跑目标产物）才加 platform.machine() 守卫，SKIP 时打印明确原因。这样"只能目标机跑"不再等于"本地零断言"。(2) **给脚本主体合成确定性输入**：读助手 C 源码，照它的 writeheader()/归档写出顺序用 Python 逐字节复刻一份输入，数值字段填成手算得出���期望值，再逐列断言——不必依赖目标机的 /proc 与 /etc。(3) **交付产物的运行取证按 macutils 先例做**：静态重链 + qemu-aarch64 实跑，并在 notes.md 写明"静态副本不等于交付产物，动态产物由 AArch64 CI worker 原生执行"。(4) **测试产物一律别落进 archives/**：驱动自选暂存目录（优先 $SMEM_TEST_WORKDIR，其次 tempfile.gettempdir()，最后才退回自身目录），三条都不通才报错——既不假设 /tmp 可写，也不会污染源码树。

**修复命令**:
```
python3 test_package/test_<tool>.py <pkg>/bin   # 驱动自选暂存目录；跑完 git status 必须为空
```

**验证**:
```
python3 -c "import struct;d=open('<pkg>/bin/<tool>','rb').read();print(struct.unpack('<H',d[18:20])[0])"   # 期望 183 = EM_AARCH64 ; python3 test_package/test_<tool>.py <pkg>/bin
```
