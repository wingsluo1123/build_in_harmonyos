# E660: OHOS sysroot 的 <libintl.h> 是空壳且不提供 libintl（gettext 属 glibc 的 libc）：直接调用 dgettext()/bindtextdomain() 的源文件须显式包含 <libintl.h>，并由配方链接制品仓 gettext 包（-lintl + -L<gettext libdir>）

## 基本信息
- **严重度**: 3
- **类别**: ohos, libc, musl, headers, build-system
- **作者**: weijiapan <weijiapan@noreply.gitcode.com>

## 错误特征
```
dgettext.*undeclared|bindtextdomain.*undeclared|undefined reference to .*(dgettext|bindtextdomain|gettext)|libintl\.h.*stub|cannot find -lintl
```

## 根因分析
glibc 平台把 gettext 的 libintl 并进 libc，因此 GNU 工具链下「不显式包含 <libintl.h> 也能编译通过」是常见的历史写法；OHOS 基于 musl、sysroot 里的 <libintl.h> 仅为空壳且不提供 libintl 符号。后果有两个层面：①编译期——直接调用 dgettext()/bindtextdomain() 而未包含 <libintl.h> 的源文件报 undeclared（项目自身的 i18n 封装头若未包含 <libintl.h>，其使用者全部受影响）；②链接期——符号未解析，报 undefined reference。本仓制品仓的 gettext 包提供真实 libintl.h + libintl.so。

## 推荐方案
**方法**: include-libintl-and-link-gettext-artifact

**说明**: ①确认 sysroot 头是空壳：读 OHOS sysroot 的 <libintl.h>（通常只有少量声明或为空）并用 nm 检查是否存在 libintl；②为上游那些直接调用 gettext 家族的源文件补 #include <libintl.h>（尤其项目自带的 i18n 封装头，补在封装头里可一次覆盖全部使用者，比逐文件补更稳）；③配方 requirements 加 gettext 依赖，并把 -lintl 与 -L<gettext libdir> 注入链接（autotools 用 LIBS/LDFLAGS，CMake 用 extra_linkflags）；④若上游有 NLS 开关而本次不需要翻译，也可 nls=OFF 规避——但这只是绕过，须在 notes.md 写明取舍；⑤注意区分「上游 NLS 特性位本身的 bug」（如 schroot 的 NLS 特性位误取自 ${pam}）与本模式——两者常同时出现，须分别定位。

**修复命令**:
```
-DLDFLAGS="-L<gettext pkg>/lib -lintl" ... ; recipes: self.requires("gettext/0.22.5.1")
```

**验证**:
```
printf '#include <libintl.h>\nint main(){dgettext("d","s");return 0;}\n' > t.c && clang -c t.c -o /dev/null && echo HEADER_OK; nm -D <gettext pkg>/lib/libintl.so | grep -w dgettext
```
