# E666: 上游把 TRUE/FALSE 当作"到处都有的宏"直接使用却从不定义：这类缺陷在 glibc 与 musl(OHOS) 上同样编译失败，必须先确认它不是平台问题再去找平台差异

## 基本信息
- **严重度**: 1
- **类别**: platform, build-system, cross-compile, upstream-defect
- **作者**: unknown

## 错误特征
```
use of undeclared identifier 'TRUE'|use of undeclared identifier 'FALSE'|‘TRUE’ undeclared
```

## 根因分析
rt-app tag v1.0 的 src/rt-app_parse_config.c 有 28 处以 TRUE/FALSE 作为参数传入 get_int_value_from/get_string_value_from/get_in_object（rt-app_parse_config.c:284,474,484,521,537,544,657,695,746,761,765-773,779,784,806,976），但整个 src/ 与 libdl/ 树里没有任何 #define TRUE/FALSE，config.h（autoconf 生成）也不提供。TRUE/FALSE 是 X11 与部分 BSD 头文件的扩展，glibc 与 musl 的标准头都不定义它们，因此这不是 OHOS 特有问题——用宿主 gcc 编译同一份未修改源码同样报 ‘TRUE’ undeclared。典型误判是"交叉编译才炸"，实际是上游发布标签本身不可编译。

## 推荐方案
**方法**: grep-for-true-false-before-blaming-the-cross-compiler

**说明**: (1) 遇到 "use of undeclared identifier 'TRUE'" 时，先用宿主 gcc 对同一份源码做一次 -fsyntax-only 复现；宿主也失败即证明是上游缺陷而非平台差异，改源码/打补丁即可，不必再找 OHOS 相关原因；(2) 修法是在被所有编译单元共享的头文件里加 #ifndef TRUE / #define TRUE 1 / #ifndef FALSE / #define FALSE 0 的守卫定义（rt-app 用的是 src/rt-app_types.h），不要在单个 .c 里局部定义；(3) 在 notes.md 明确写"上游标签在任何 libc 上都不可编译"并附宿主复现命令，避免后续评审反复怀疑是适配引入的；(4) 注意补丁里不要顺手用 __OHOS__ 之类平台宏包一层，守卫式通用定义对 glibc 同样安全。

**修复命令**:
```
python3 - <<'EOF'\nimport io\np='src/rt-app_types.h'; s=io.open(p,encoding='utf-8').read()\nold='#include <sched.h>\\n\\n#include "config.h"\\n'\nnew='#include <sched.h>\\n\\n#include "config.h"\\n\\n#ifndef TRUE\\n#define TRUE 1\\n#endif\\n#ifndef FALSE\\n#define FALSE 0\\n#endif\\n'\nio.open(p,'w',encoding='utf-8').write(s.replace(old,new,1))\nEOF
```

**验证**:
```
grep -rn "#define TRUE\|#define FALSE" src/ libdl/ | wc -l   # 期望 0；再 gcc -fsyntax-only 复现宿主端同样失败
```
