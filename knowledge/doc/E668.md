# E668: tarball 里"预生成骨架"与"骨架源"内容不一致却 mtime 相同时，make 不会重生成，补丁必须打在真正生效的文件上并强制其 mtime

## 基本信息
- **严重度**: 2
- **类别**: build-system, determinism, patch-strategy
- **作者**: unknown

## 错误特征
```
yy_c_buf_p = NULL.*(char \*\) 0|mkskel|skel\.c: flex\.skl|Check successful, using COMPRESSION|scan\.c .*differ|diff scan\.c
```

## 根因分析
发布包内同时带 skel.c（生成物）与 flex.skl（源），两者内容不同：skel.c（以及与之一致的 initscan.c）写 `yy_c_buf_p = (char *) 0`，而 flex.skl 已改成 `NULL`。但 tar 打包把三者的 mtime 归一到同一秒（2025-01-01 05:56），Makefile 规则 `skel.c: flex.skl mkskel.sh` 因 mtime 相等而判定"已是最新"，永不触发重生成 —— 因此构建实际使用的是发布版 skel.c，flex.skl 是陈旧旁支。把补丁打在 flex.skl 上既不生效（不改构建输入），又会让 make check 的自举逐字节比对暴露不一致（重新生成的 scan.c 用 NULL，而 initscan.c 用 (char *) 0）→ 误判成"补丁破坏了构建"。

## 推荐方案
**方法**: patch-the-effective-file-and-force-its-mtime

**说明**: (1) 动手前先识别"谁是真正的构建输入"：对同一逻辑的两个候选文件跑 `ls -la`（看 mtime 是否被 tar 归一到同秒）与 `diff -q`（看内容是否已分叉）；若 mtime 相等而内容不同，make 的规则不会触发重生成，**生效的是 dist 里那个已经存在的生成物**。(2) 补丁打在生效文件上（本例 skel.c），而不是看起来更"源"的模板（flex.skl）。(3) 在 recipe 的 build() 里用 `os.utime(<生效文件>, None)` 把它抬到模板之上，避免 mkskel.sh 在增量/并行构建或缓存复用时回写覆盖补丁 —— 这一步不是锦上添花，去掉它修复会随构建顺序时有时无。(4) 验收用包自带的逐字节自举比对（make check）确认"改动既生效又未破坏既有输出一致性"。

**修复命令**:
```
python3 -c "import os;os.utime('skel.c',None)"   # conanfile.build() 内对 source_folder/build_folder 各调一次
```

**验证**:
```
ls -la skel.c flex.skl && grep -n 'char \*) 0' skel.c | head -3 && ./configure && make -j1 && make check
```
