# E680: A complex PETSc build stays fully self-contained by reusing the bundled f2cblaslapack (its z-routines are already f2c'd in), and PETSC_USE_COMPLEX propagates to consumers through the installed petscconf.h rather than through recipe -D flags

## 基本信息
- **严重度**: 2
- **类别**: conan, recipe-dependencies
- **作者**: unknown

## 错误特征
```
download-f2cblaslapack|zgemm|zdotc|zheev|PETSC_USE_COMPLEX not defined|undefined reference to `zgemm_|no BLAS provider|self-contained BLAS
```

## 根因分析
The instinct when moving from real to complex scalars is that a complex build now needs a real BLAS/LAPACK provider carrying zgemm/zdotc/zheev - normally OpenBLAS or MKL - which would drag an unpublished dependency into the OHOS graph. That is unnecessary for PETSc: configure's --download-f2cblaslapack=1 fetches f2cblaslapack-3.8.0.q2, a netlib f2c port that already contains blas/zgemm.c, blas/zdotc.c and lapack/zheev.c alongside the real routines. The second half of the problem is ABI visibility: it looks like consumers must be told the variant via -D PETSC_USE_COMPLEX, but PETSc generates the macro into the installed petscconf.h and petscsys.h includes it, so the header path already carries the correct ABI and a recipe that "helpfully" defines it is only duplicating an existing guarantee.

## 推荐方案
**方法**: reuse-bundled-f2cblaslapack-plus-header-borne-abi-macro

**说明**: Keep the same self-contained configure as the real-scalar sibling: --with-fc=0 --with-mpi=0 --download-f2cblaslapack=1, adding only --with-scalar-type=complex --with-precision=double. No requires() entry for BLAS/LAPACK and no external provider in the graph. Before assuming otherwise, verify the bundled mirror really covers the variant - for f2cblaslapack-3.8.0.q2 the complex routines are present (blas/zgemm.c, blas/zdotc.c, lapack/zheev.c), which is what makes the self-contained claim true rather than lucky. On the consumer side, do NOT rely on the recipe's cpp_info.defines to establish the ABI: PETSC generates PETSC_USE_COMPLEX into <prefix>/include/petscconf.h and petscsys.h (pulled in by petsc.h) includes it, so any consumer compiling against the installed headers gets the variant ABI automatically. Keep the defines in package_info() only so the generated CMake/pkg-config files are self-describing; treat the header as the source of truth. package() must still install the generated petscconf.h (i.e. use PETSc's own `make install`, do not hand-copy include/), otherwise consumers lose both the macro and the config values. Also keep package_type="library" with libs ["petsc","f2clapack","f2cblas"] and system_libs ["m","stdc++"] on Linux/OHOS.

**修复命令**:
```
conan create archives/p/petsc-complex/3.25.4 -pr:h=ohos-aarch64 -pr:b=ohos-aarch64 --build=missing -nr
```

**验证**:
```
tar -tzf f2cblaslapack-3.8.0.q2.tar.gz | grep -E 'blas/zgemm\.c|blas/zdotc\.c|lapack/zheev\.c' && conan create archives/p/petsc-complex/3.25.4 -pr:h=ohos-aarch64 -pr:b=ohos-aarch64 --build=missing -nr
```
