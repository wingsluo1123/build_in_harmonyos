# E682: PETSc's configure names its build tree from sys.platform and auto-detects the build host's X11: pass --with-petsc-arch to keep make/install in sync, and --with-x=0 so the host's libX11 does not get baked into libpetsc.a and pushed onto consumers

## 基本信息
- **严重度**: 3
- **类别**: conan, recipe-configure
- **作者**: unknown

## 错误特征
```
arch-ohos-c-opt/lib/petsc/conf/files: No such file or directory|No rule to make target .*/arch-.*/include/petscconf.h|undefined reference to `XGetGeometry'|undefined reference to `XSetIOErrorHandler'|undefined reference to `XSetForeground'|PETSC_ARCH should not contain path characters
```

## 根因分析
Both failures come from the same mistake - assuming configure looks at the TARGET platform. (a) config/PETSc/options/arch.py:32 builds the default tree name as 'arch-' + sys.platform + '-' + clang + '-opt', so on a Linux build host it is arch-linux-c-opt no matter what OHOS the compiler targets. A recipe that hardcodes 'arch-ohos-c-opt' in its make/install lines but never tells configure gets a tree named arch-linux-c-opt, and make dies with 'arch-ohos-c-opt/lib/petsc/conf/files: No such file or directory'. (b) --with-x defaults to auto-detect and probes the BUILD HOST's X11 headers; on any worker with libX11-dev the X draw backends are compiled into libpetsc.a, PetscInitialize then references them, and EVERY consumer link fails with undefined references to XGetGeometry / XSetIOErrorHandler / XSetForeground even for pure-numeric code. The second one is nastier because it is invisible until a consumer links, and it silently depends on what happens to be installed on the worker - the same recipe builds on one worker and fails on the next.

## 推荐方案
**方法**: pin-the-arch-name-and-disable-host-autodetected-x

**说明**: Pass the same arch string to configure and to make/install: --with-petsc-arch=<name> (also settable as a bare PETSC_ARCH=<name> option, or via the PETSC_ARCH environment variable) alongside make PETSC_DIR=... PETSC_ARCH=<name> all/install. With the name pinned, the recipe stops depending on the worker's sys.platform and the two stages can never disagree. Then add --with-x=0: PETSc's draw/X11 backends are useless on OHOS (and on any headless target) and the auto-detect is what drags the build host's libX11 into a supposedly self-contained static library. Symptom signature to watch for if it is omitted: a consumer that only calls PetscInitialize/VecNorm still fails to link with undefined references to XGetGeometry, XTranslateCoordinates, XGetWindowAttributes, XSetForeground, XSetIOErrorHandler, XDrawPoint - i.e. the X viewer objects were pulled in transitively by PetscInitialize's viewer registration. Note the failure is worker-dependent (only workers with libX11-dev reproduce it), so it looks like flakiness rather than a recipe bug. General rule this instantiates: for every configure-driven package, list which decisions are made by a NATIVE probe and pin them explicitly before trusting a cross build.

**修复命令**:
```
python3 ./configure --prefix=/tmp/pfx --with-cc=gcc --with-fc=0 --with-mpi=0 --with-petsc-arch=arch-ohos-c-opt --with-x=0 --with-scalar-type=complex --with-precision=double --download-f2cblaslapack=1 && make PETSC_DIR=$PWD PETSC_ARCH=arch-ohos-c-opt all
```

**验证**:
```
python3 ./configure --prefix=/tmp/pfx --with-cc=gcc --with-fc=0 --with-mpi=0 --with-petsc-arch=arch-ohos-c-opt --with-x=0 --with-scalar-type=complex --with-precision=double --download-f2cblaslapack=1 && make PETSC_DIR=$PWD PETSC_ARCH=arch-ohos-c-opt all
```
