# E720: 测试框架自适配的退出码契约陷阱：minunit 的 MU_EXIT_CODE 是"失败计数"而非"成功布尔"（官方 ci/check_example.sh 断言 exit==6 才算 PASS），零退出码期望会把完全正确的运行误判为失败——先读上游 check 脚本，再按契约精确断言退出码+报告输出

## 基本信息
- **严重度**: 2
- **类别**: conan, testing, ci-gate
- **作者**: unknown
- **来源 PR**: 14375

## 错误特征
```
Error 6 while executing|[0-9]+ tests, [0-9]+ assertions, [0-9]+ failures|expected_exit_code|MU_EXIT_CODE|minunit_fail
```

## 根因分析
minunit 的退出码语义是"失败计数"：MU_EXIT_CODE 展开为 minunit_fail 计数器。官方自测套件 minunit_example.c 的 11 个 MU_TEST 中 6 个是框架故意演示失败的用例（*_fail 系列 + mu_fail，用途是验证断言捕获能力），因此一次完整正确的运行必然 exit 6——上游官方 CI 契约 ci/check_example.sh 明确写 expected_exit_code=6，非 6 反而判 FAIL。适配者若按"测试程序退出码非零=失败"的默认语义包裹该套件（conan build() 内 self.run 不带 ignore_errors 直接炸 "Error 6 while executing"，或门禁/统计把非零码当通过率损失），会把一次完全符合上游设计的运行误判为适配失败；反之若只 ignore_errors 而不校验具体码值，则丢失"6 个设计失败全部如期发生"的验证价值——码是 5 或 7 同样说明框架行为异常，精确断言才能同时防两类误判。

## 推荐方案
**方法**: assert-official-exit-contract-exactly

**说明**: (1) 适配前先读上游官方 CI 入口脚本（.travis.yml/appveyor.yml 的 script 段 → ci/check_example.sh），提取官方对退出码的精确契约——本例 expected_exit_code=6，"非零退出码是 PASS 判据"；(2) build() 内用 self.run(cmd, ignore_errors=True) 取回 retcode（Conan 2.x run() 语义：ignore_errors=True 时返回退出码而不抛异常），按契约精确断言 retcode == 6，不符则 raise ConanException 带期望值与实际值；(3) 消费者侧 test_package 同法做契约断言：故意失败用例数 N → 断言 exit == N，并同时校验 MU_REPORT 输出行（"10 tests, 10 assertions, 5 failures"）与 setup/teardown 触发计数，把"退出码+报告行+钩子计数"三重证据做实，防止只对码漏对行为；(4) PR 统计表与 MANIFEST 如实写"官方契约口径：exit 6 == PASS（6 个 designed-to-fail 演示用例按设计失败）"，防止后续人工审查把非零退出码误读为通过率问题（rule4 高频打回点）。

**修复命令**:
```
retcode = self.run("./minunit_example", cwd=self.build_folder, ignore_errors=True); if retcode != 6: raise ConanException("upstream official test FAILED: ci/check_example.sh contract expects exit code 6, got %d" % retcode)
```

**验证**:
```
cd <src> && clang -std=c99 -I. minunit_example.c -lm -o minunit_example && ./minunit_example; echo "exit=$?"   # 期望 "11 tests, 11 assertions, 6 failures" 且 exit=6（官方契约）
```
