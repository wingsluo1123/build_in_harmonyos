# E721: CI 失败摘要行"源码下载超时"的误诊判别：完整日志若为 SSH bridge connection refused(111) + worker-prep/git-clone/cleanup 三步全挂 + 毫秒级 elapsedTime（连 git --version 都失败）＝Worker 侧基础设施故障，构建从未开始——正确处置是裸 /rebuild 重试，绝不是按评论修复指导改 conandata 加镜像（R39 违规）

## 基本信息
- **严重度**: 2
- **类别**: network, environment, infrastructure
- **作者**: unknown
- **来源 PR**: 14375

## 错误特征
```
SSH bridge exec failed: connect failed: connection lost before ready: Connection was refused by other side: 111|program finished with exit code -1|worker-prep.*git-clone.*cleanup.*❌
```

## 根因分析
CI 机器人的失败评论摘要行按报错类别粗分类（"网络问题/源码下载超时"），其修复指导（"预缓存源码/使用镜像替代地址"）针对的是"下载源 URL 不可达"这一情形。但另一类失败——Worker 的 SSH 桥接服务未就绪/拒连（connection refused 111）——会被归入同一个"网络问题"摘要下。判别特征（四条同时成立即可定性）：①失败步骤为 worker-prep + git-clone + cleanup 三步全部 ❌（真实构建流程 conan create 从未启动）；②各步骤 elapsedTime 为毫秒级（0.001–0.007s，真实源码下载至少是秒级超时）；③日志原文含 "SSH bridge exec failed: connect failed: connection lost before ready: Connection was refused by other side: 111"；④连不涉及网络的 `git --version`（0.006s 内）都失败。此情形下源码 URL 完全无辜：改 conandata.yml 加镜像前缀/多源列表反而触发 R39（官方单 URL 纪律，CI 会自动为 GitHub URL 加镜像 fallback），把一个平台侧故障固化成配方违规。实测同一 PR 连续 5 轮命中（CI-002×3、CI-034×2），第 6 轮调度到健康 Worker（CI-019）即绿——集群故障是间歇性的，重试是唯一正确动作；他队 PR（#13398）同款签名多轮后亦在健康机通过。

## 推荐方案
**方法**: read-full-log-then-bare-rebuild

**说明**: (1) 收到 CI 失败评论先全文读"失败步骤完整日志"原文（诊断三铁律之一：摘要行很泛不能定性）；(2) 命中四判别特征（SSH bridge refused 111 / 三步全挂 / 毫秒级 elapsedTime / git --version 失败）→ 定性为 Worker 基础设施故障，配方无问题；(3) 处置＝评论裸命令 /rebuild 重试（不带任何补充说明文字），可多次——实测同 PR 第 6 轮在健康 Worker 通过；同类网络故障重试上限 3 轮纪律适用于真实下载失败，基础设施拒连可按"集群恢复证据"（看板其他 PR 近期 passed）加试；(4) 禁止动作：改 conandata.yml 加镜像/多源（R39 违规）、预缓存 s/ 目录、回退配方——源码 URL 未被证伪前一律不动配方；(5) 重试仍持续失败超 30 分钟跨 3 轮以上 → 平台侧报障（Worker 摘除维修），不是适配层能修的。

**修复命令**:
```
grep -c "SSH bridge exec failed" <ci-log> && grep -o "elapsedTime=0\.00[0-9]*" <ci-log>   # =3 且全毫秒级 → 裸命令重试：/rebuild
```

**验证**:
```
打开失败评论的"失败步骤完整日志"段：grep -c "SSH bridge exec failed" <log>   # 三步各一次=3；并核对 elapsedTime 是否全部 <0.01s
```
