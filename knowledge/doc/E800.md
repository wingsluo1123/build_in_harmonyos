# E800: GitHub codeload 自动生成的 tar.gz 封装非字节稳定 — 同一 commit 不同请求可得到不同 sha256，单哈希钉死会让 source() 偶发失败

## 基本信息
- **严重度**: 2
- **类别**: source-download-checksum
- **作者**: unknown

## 错误特征
```
sha256 hash failed for .* file\.|Provided hash: [0-9a-f]{64}|Computed hash: [0-9a-f]{64}
```

## 根因分析
codeload.github.com（github.com/<org>/<repo>/archive/<ref>.tar.gz 302 的落地端）按请求即时生成归档，gzip 封装不保证字节稳定：2026-09-12 对 coin3d/dime commit edcbe949ae67 实测，curl 两次均得 6d9f7d0c...，conan 的 Python 下载器同日得到 065a7d74...，两者解包后 209 个文件逐文件 sha256 完全一致（差异仅在 gzip 封装层）。conandata 只钉一个 sha256 时，source() 是否成功取决于当次请求被分到哪个 CDN/后端节点，表现为"配方有时过有时不过"的偶发失败。

## 推荐方案
**方法**: multi-framing-sha256-set-in-source

**说明**: 在 source() 中用 download() 落盘后显式校验一组已知等价哈希：先把已知变体列入 _SOURCE_SHA256 元组（conandata 保留主变体满足门禁），不匹配即 raise 并在报错里写明核实方法（解包后与官方 orig tarball 逐文件 sha256 对比，确认仅封装差异后才可追加）。校验永不跳过——这是接受同一棵树的多种封装，不是放松校验。禁止用 get() 传 sha256=None 绕过。

**修复命令**:
```
grep -n "_SOURCE_SHA256" <recipe>/conanfile.py
```

**验证**:
```
curl -sL <archive-url> -o /tmp/a.tgz && curl -sL <archive-url> -o /tmp/b.tgz && sha256sum /tmp/a.tgz /tmp/b.tgz   # 对比两次；再与 conan 报错的 Computed hash 对照
```
