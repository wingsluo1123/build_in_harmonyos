# E805: CI 的 L0h（R33）是行级 grep：注释里出现 self.run( 与 ${CC} 同行即被判失败 —— 配方代码正确也会红，须改注释写法

## 基本信息
- **严重度**: 2
- **类别**: conan, ci-gate, false-positive, recipe-style
- **作者**: unknown

## 错误特征
```
L0h: conanfile\.py 在 self\.run\(\) 中依赖未定义 shell 变量|shell_env_var_in_run
```

## 根因分析
ci/conan/build_and_test.sh 的 L0h 实现为 `grep -nE 'self\.run\(.*\$\{(CC|CXX|CFLAGS|CXXFLAGS|LDFLAGS|AR|RANLIB)\}' <conanfile.py>`，**按整行匹配、不过滤注释**。R33 的立法本意是禁止在 self.run() 里做 shell 变量展开（CI 环境不保证 CC/CFLAGS 已定义），但只要同一行**文本上**同时出现 `self.run(` 与该字面组合就命中——包括形如 `# R33: f-string 嵌入到 make 参数，不在 self.run() 里用 ${CC}/${CFLAGS} 展开` 的**解释性注释**。实测 detachtty 11.0.0：conanfile.py 的 build() 已用 f-string + 局部变量，代码完全合规，仅因第 39 行注释触发 L0h，导致 L0j/L0k/L0m/L0n 全绿而 L0h 单点红、L1 被 blocked_by_L0 跳过。删掉注释中的字面组合后立刻通过（build #43365 → #43404）。

## 推荐方案
**方法**: reword-comment-keep-conf-based-cc

**说明**: 两步：(1) 先本地复跑 L0h 的同一条正则（见 verification_cmd）定位命中行——它往往在注释里而非代码里；(2) 改写该行注释，去掉 `self.run(` 与 `${…}` 的**字面共现**（例如写成"编译器经 f-string 注入 make 参数，不使用 shell 变量展开"，把 ${CC} 字样换成不带 ${} 的 CC/CFLAGS），或把说明拆成两行。**不要改代码逻辑**：合规写法应保留 conf 优先解析（tools.build:compiler_executables > CC 环境变量 > 裸 clang），因为 CI profile 只提供 conf，不提供 CC 环境变量；把编译器解析写成 conf 优先同时满足 R33 立法本意与工程正确性。防复发：把"注释里也不要写出 self.run 与 ${CC} 同行"写进配方模板注释规范。

**修复命令**:
```
# 本地判据（等价于 CI 的 L0h）\ngrep -nE 'self\.run\(.*\$\{(CC|CXX|CFLAGS|CXXFLAGS|LDFLAGS|AR|RANLIB)\}' archives/<l>/<名>/<版本>/conanfile.py
```

**验证**:
```
Select-String -Path archives/<l>/<名>/<版本>/conanfile.py -Pattern 'self\.run\(.*\$\{(CC|CXX|CFLAGS|CXXFLAGS|LDFLAGS|AR|RANLIB)\}'   # 任何输出即会被 L0h 拦
```
