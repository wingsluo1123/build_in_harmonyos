# E806: 上游 tarball 同时带 bison/flex 生成产物与其源，Makefile 有再生成规则 —— 时间戳一变就要求 bison/flex（CI 不具备）；直编绕开即可

## 基本信息
- **严重度**: 2
- **类别**: make, conan, build-deps, generated-sources
- **作者**: unknown

## 错误特征
```
bison: (command )?not found|flex: (command )?not found|No rule to make target '(gram|lex)\.(c|h)'|make.*\*\*\* \[.*\.c\]
```

## 根因分析
很多 tarball 会**同时**打包词法/语法分析器的**生成产物**与**生成源**（如 `gram.c`/`gram.h` 与 `gram.y`、`lex.c`/`lex.h` 与 `lex.l`），并在 Makefile 里保留再生成规则（`gram.c: gram.y` → `$(BISON) …`）。`make` 按**时间戳**决定是否重建：只要 `.y`/`.l` 比 `.c` 新——解包顺序、文件系统时间精度（FAT/网络盘 2s 粒度）、甚至 `touch` 都会造成——`make` 就去调 `bison`/`flex`。而 CI 构建镜像通常**不装 bison/flex**（它们是"开发机工具"而非运行时依赖），于是构建在"与本包源码毫无关系"的一步失败，报错形如 `bison: not found` 或 `No rule to make target 'gram.c'`。绕过 make、直接编译随包 `.c` 是最省事的根治：既消除工具依赖，又保证与上游发布时一致（发布包里的生成物就是上游用某个 bison 版本产出的）。

## 推荐方案
**方法**: compile-shipped-generated-sources-directly

**说明**: 三步处置：(1) **判定**——`ls *.y *.l` 有命中，且同名 `.c` 也在包里 → 属"生成物随包"型，直编即可；若只 src 无生成物 → 反过来必须声明 `tool_requires("bison/…")`/`flex`。(2) **直编**——把目标文件列表里 `gram.o`/`lex.o` 等**照样编译随包的 `.c`**，不要试图跑 make（顺带绕开上游常见的一堆问题：混合 BSD/GNU make 方言 `.PATH`/`.PARSEDIR`/`$(shell …)`、`CFLAGS` 里塞编译器等）。(3) **留证**——在 notes.md 写明"使用随包生成物、不触发 bison/flex"及理由，便于审计者知道构建图与上游发布一致。附带检查：`gram.c` 与 `gram.h` 必须来自**同一次**生成（同名且同时打包），否则会因原型不一致报编译错误。

**修复命令**:
```
# 判定\nls *.y *.l 2>/dev/null; ls -la gram.c lex.c 2>/dev/null\n# 直编（示例）\nclang -O2 -Wall -I. -c gram.c -o gram.o && clang -O2 -Wall -I. -c lex.c -o lex.o
```

**验证**:
```
ls *.y *.l 2>/dev/null && ls -la gram.c lex.c ; grep -nE '^(\S+)\.(c|h):.*\.(y|l)' Makefile
```
