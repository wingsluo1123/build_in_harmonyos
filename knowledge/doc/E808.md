# E808: 手写 config.h 替代 configure 产物时必须与 config.h.in 完全 parity：能力宏与 #include 成对出现，只补宏不补 include 会让 HAVE_* 形同虚设

## 基本信息
- **严重度**: 2
- **类别**: autotools, cross-compile, conan, config-h
- **作者**: unknown

## 错误特征
```
use of undeclared identifier '(O_RDONLY|O_WRONLY|LONG_MAX|INT_MAX|SEEK_SET)'|incomplete definition of type 'struct utimbuf'|conflicting types for '[a-zA-Z_]+'|expected '\)'
```

## 根因分析
autoconf 生成的 config.h 里，**能力宏与头文件包含是成对出现的**——`#undef HAVE_FCNTL_H` / `#ifdef HAVE_FCNTL_H` / `#include <fcntl.h>` / `#endif`，即"包含动作发生在 config.h 内部"。绕过 configure 直编时（tarball 常常只有 `config.h.in`、没有 `config.h`，而每个 C 文件第 2 行都是 `#include "config.h"`），若手写的 config.h **只写 `#define HAVE_FCNTL_H 1` 而漏掉配对的 `#include` 块**，则：宏确实被定义了，但头文件从未被包含，于是所有依赖该头文件的符号在**每个 TU 里都 undeclared**。症状集中在 `O_RDONLY`/`O_WRONLY`（fcntl.h）、`LONG_MAX`/`INT_MAX`（limits.h）、`struct utimbuf` 不完整（utime.h）、以及因缺声明导致的 `conflicting types`——**看起来完全像"上游老代码不兼容 clang 15"，因此极易被引入歧途**（去改源码、加 `-Wno-*`、甚至想打补丁）。实测 cpmtools 2.23：首轮 9 个 error 全部源于此，补齐 include 块后**零源码改动**直接通过。

## 推荐方案
**方法**: config-h-full-parity-with-template

**说明**: 生成 config.h 时**逐条镜像 config.h.in 的结构**，而不是"把 #undef 换成 #define"：(1) 先列出模板里全部能力宏；(2) 对每个要开启的宏，同时写出 `#define X 1`、`#ifdef X`、`#include <对应头>`、`#endif` 四行；(3) 把模板尾部的固定片段（`_POSIX_PATH_MAX` 兜底、`extern char **environ;` 等）原样带上；(4) 生成后自检 `grep -cE '^#include' config.h` 必须 >0；(5) 上游通过 CPPFLAGS 注入的**字符串字面量宏**（如 `-DDISKDEFS=\"…\"`、`-DFORMAT=\"…\"`）也一并放进 config.h —— 既省去跨 shell 引号转义，又保证所有 TU 一致可见。参考实现：archives/c/cpmtools/2.23/conanfile.py 的 `CONFIG_H` 常量（含 6 组成对 include 与 DISKDEFS/FORMAT 定义）。

**修复命令**:
```
grep -nE '^(#undef|#define|#ifdef|#include|#endif)' config.h.in   # 逐条对照生成
```

**验证**:
```
grep -cE '^#include' config.h   # 生成后自检：若为 0，说明只补了宏没补 include 块（与 config.h.in 不成 parity）
```
