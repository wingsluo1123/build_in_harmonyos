# E810: 伞形源码包（如 klibc：一份 tarball 内含 libc + dash + kinit + utils + gzip）中拆分单组件成独立 Conan 包：版本号沿用父发行版本、用 patch 收窄顶层构建范围、只打包该组件产物，并显式声明「组件自身无上游测试」

## 基本信息
- **严重度**: 1
- **类别**: portability, build-system, conan, packaging, structure
- **作者**: unknown

## 错误特征
```
$\(Q\)\$\(MAKE\) \$\(klibc\)=usr/|^subdir- :=|umbrella tarball component split|all: klcc klibc
```

## 根因分析
发行版/镜像侧常按「组件」命名拆包（klibc-dash、klibc-run-init、klibc-nfsmount），但上游只发布一份伞形 tarball。若直接照搬整树构建：①会连带编译无关组件（klibc 顶层 Kbuild 的 all = scripts/basic + usr/klibc + usr/kinit + usr/dash + usr/utils + usr/gzip），引入无关失败面；②组件版本号无处可取（dash 自身 config.h 里是历史 0.5.7，与 klibc 2.0.14 不一致）；③上游若已有同源整包配方（klibc/2.0.14 用 patch 0004 显式跳过 usr/dash），重复适配边界容易互相踩。klibc 的 usr/dash 无任何测试目录/注册（dash 的 tests/ 未随导入），若按常规「必须跑通上游测试」处理会误判为失败；真正可跑的最近入口是 make test → usr/klibc/tests（测的是它静态链接的同树 libc）。

## 推荐方案
**方法**: inherit-parent-version-and-narrow-build-scope

**说明**: ① 版本号取父发行版本（读 <src>/usr/klibc/version 或等价 version 文件），并在 notes/README 里说明与组件自身版本串（dash 0.5.7）的区别，避免下游误判；② 用 patch 收窄顶层构建范围的 all 目标，只保留本组件及其必需的同树依赖（klibc-dash → scripts/basic + usr/klibc + usr/dash），不要依赖「顶层 all 恰好可用」；③ 组件与其同树依赖静态链接成自包含产物（bin/sh），不引入第三方 requires，也就不需要为同树 libc 单独发布依赖包；④ 构建产物是可执行文件 → package_type="application" + 软件级 commands.json（R38）+ package_info().bindirs=["bin"]；⑤ 上游无 install 目标（无 GNU install，E098）时用 Conan copy 手动打包；⑥ **上游测试按组件口径如实申报**：组件目录无测试要附清点证据（目录清单 + grep 结果 + 上游 README 说明），并把同树唯一自动化入口（make test）真实执行、逐项留档，不要用 test_package 冒充上游测试统计（R51）。

**修复命令**:
```
patch -p1 < patches/0004-narrow-all-target.patch && make KLIBCARCH=arm64 CC="clang --target=aarch64-linux-ohos" ... -j1 && make ... -j1 test
```

**验证**:
```
tar tJf <tarball> | grep -E '^[^/]+/(usr/|src/)' | head; grep -n 'all:' -A 12 <src>/Kbuild; cat <src>/usr/klibc/version
```
