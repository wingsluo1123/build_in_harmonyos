# E910: 先按制品仓精确包名校准依赖，再为无扩展名 codeload 提供 filename，并用结构化 subprocess 绕过 Windows buildenv 的 POSIX 激活边界

## 基本信息
- **严重度**: 3
- **类别**: platform, ohos, make, conan, dependency-resolution
- **作者**: 2301_80739235

## 错误特征
```
No package.*libcurl|Package.*not found|filename.*required|'. .*not recognized|conanbuildenv.*sh
```

## 根因分析
上游库名、Conan 制品名和链接目标名可能不同（ccurl 使用 libcurl API，OHPCD 制品名为 curl，CMake 目标为 curl::libcurl），直接照上游名称查包会得到缺包假象。GitHub codeload 的提交归档 URL 末段没有 .tar.gz 扩展名，Conan get() 需要显式 filename 才能稳定识别归档文件名。Windows Conan buildenv 生成的 POSIX shell 激活脚本不能作为 PowerShell/Windows 原生子进程命令执行；将脚本字符串交给 shell 会在副作用前失败。

## 推荐方案
**方法**: exact-package-then-fixed-source-and-structured-build

**说明**: 先在 OHPCD 以 --build=never 解析依赖并记录实际包名、RREV/PREV 和闭包；源码使用不可变 commit codeload URL、显式 filename 与 SHA-256；build() 从 tools.build:compiler_executables 读取 cpp/ar，使用 subprocess.run(list, check=True) 直接执行，不解析或 source POSIX 激活脚本。package_info() 再将实际 Conan 目标映射给消费者。

**修复命令**:
```
conan install --requires=curl/8.15.0 --build=never -r=ohpcd -pr:h=ohos-aarch64
```

**验证**:
```
conan download curl/8.15.0 -r=ohpcd --only-recipe; conan install --requires=curl/8.15.0 --build=never -r=ohpcd -pr:h=ohos-aarch64; python -m py_compile archives/c/ccurl/1.0.0/conanfile.py; conan create archives/c/ccurl/1.0.0 --build=missing
```
