# DRAFT — 诊断只打印「尾部」会吃掉关键错误：pytest 收集期失败必须打**首条** traceback

> 触发事件：greenlet 3.5.6（PR #10408）。收集期失败的自查信息只打印了输出尾部，
> 导致根因被截掉，只能靠猜（2026-10-02 CI 实测）。

## 症状（元层面：诊断本身出问题）

CI 日志里能看到「失败」但看不到「为什么失败」：

```
ERROR src/greenlet/tests/test_generator_nested.py
ERROR src/greenlet/tests/test_greenlet.py
... （15 行文件清单）
!!!!!!!!!!!!!!!!!!! Interrupted: 15 errors during collection !!!!!!!!!!!!!!!!!!!
no tests collected, 15 errors in 0.24s
```

诊断代码 `"\n".join(cout.strip().splitlines()[-12:])` 取的是**最后 12 行** ——
恰好全是文件清单与汇总，**点名异常的那一行**（`ImportError: Error loading shared library ...`）
在每块的开头附近，被整段截掉。

## 根因分析

pytest 收集期失败的输出结构是：

```
<每个失败文件的 ERROR 块：块首即异常行>  …  <最后汇总 Interrupted: N errors>
```

取**尾部切片** ⇒ 只保留「哪些文件失败 + 失败总数」，丢弃「为什么失败」。
而失败的**首个根因**总是位于块的**开头**。于是：

- 日志自述「15 errors」，却无一字说明错误类型；
- 只能凭环境线索猜因 → 本条实测导致一轮 CI 在猜测中修正方向。

**通用原则**：汇总式输出（收集期、批量测试、多目标构建）的尾部是**统计**，
根因在**开头**。诊断信息必须包含「第一个根因」，而不是「最后一个统计」。

## 推荐方案

按分隔线切块，打印**每块的前若干行**（前 12 行足够露出异常类型与缺失对象），
并限制块数避免刷屏：

```python
blocks = [b for b in out.split("\n_ _ _ _") if "Error" in b or "E " in b]
for b in blocks[:4]:
    detail += "\n".join(b.strip().splitlines()[:12])
```

无块可切时，退回打印输出**开头** 40 行（而非尾部）。

**备选**：失败时把完整输出写入构建目录日志文件，异常消息里给出路径，需要时人工查看 ——
即「不在消息里做截断决策」。

## 禁止做法

- ❌ **不要**用 `splitlines()[-N:]` / `tail -N` / `head -N` 作为**唯一**的失败诊断输出：
  汇总式输出的尾部是统计与清单，根因在块首。
- ❌ **不要**在证据不足时先假定某个环境原因并据此改配方：先在诊断上多花一步，
  胜过按猜测改配方多跑一轮（并且改动会引入新变量，使后续诊断更乱）。

## 验证证据

- **主证据（CI）**：greenlet 3.5.6 / PR #10408，`15 errors / 0 collected`，
  尾部切片未含任何异常行（只有 15 行 `ERROR <file>` 与汇总）。
- **改进后**：诊断改为打印每块前 12 行（最多 4 块），下次同类失败会直接给出异常类型。
- 本地验证：以同样的 pytest 输出样本走两版诊断，确认新版能取到 `ImportError` 行、旧版不能。
