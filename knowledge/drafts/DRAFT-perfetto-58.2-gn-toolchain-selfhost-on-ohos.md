# DRAFT: GN（generate-ninja）私有构建工具链在 OHOS aarch64 的自举与全树驱动

- 条目主题：以 GN 为构建系统（`BUILD.gn` / `.gn` / `gn args` / `isolate`）的上游库适配到 HarmonyOS PC
  （aarch64 / musl）时，上游不提供、且现有预编译 gn 全部不可用场景下的**源码自举 + 全树驱动**诊断与方案。
- 状态：草稿（待知识库主编审核）
- 关联：perfetto 58.2（`archives/p/perfetto/58.2`，分支 `feat/perfetto-58.2`，路径C 高难度挑战）
- 类别：构建系统 / GN / OHOS 签名 / musl / conan
- 配套：`DRAFT-osm2pgrouting-3.0.0-ohos-exec-eperm-126-unsigned-elf-not-noexec`（签名执行策略）、
  `E545-draft-3BD6-meson-ninja-detect-ohos`（OHOS python subprocess 工具链子进程坑）

## 适用场景

上游用 GN 构建（不是 CMake/meson/autotools），且：

- 上游**不 vendor gn 二进制**：`tools/gn` 只是下载器（`run_buildtools_binary` → `buildtools/<os>/gn`），
  该目录被 gitignore，tarball 内**没有任何 gn 可执行文件**；
- 上游预编译 gn 只有 x64 / glibc 版，OHOS aarch64 上**跑不起来**。

## 症状（典型报错）

```
timeout: exec ./gn-arm64: Permission denied          # rc=126
fatal error: 'last_commit_position.h' file not found  # src/gn/scope_per_file_provider.cc:15
CalledProcessError: ['git','describe','HEAD','--abbrev=12','--match','initial-commit'] 128
```

## 根因（三层叠加，缺一不可）

1. **架构层**：CI/官方预编译主体是 x86-64（Chromium 系 gn 预编译）。
2. **libc 层**：少数上游（如 perfetto 自建桶）确有 arm64 预编译，但为 **glibc**
   （`file` 显示 interp `/lib/ld-linux-aarch64.so.1`）；OHOS 是 **musl**（系统仅 `/lib/ld-musl-aarch64.so.1`，
   全盘无 glibc loader）→ 无法加载。
3. **签名层**：OHOS 用户存储（hmdfs）中的 ELF 执行需 `.codesign` 段，外部下载的二进制默认没有
   → `execve` 返回 `EACCES`（表单为 `Permission denied`，rc=126）；**这不是 noexec 挂载问题**
   （见配套草稿的误诊路径）。

⇒ 三层任一命中都无法用"下载一个 gn"解决，**唯一稳的路是源码自举**。

## 诊断步骤

1. 定位 gn 来源：读 `tools/gn` / `run_buildtools_binary.py` / `tools/install-build-deps`，
   确认是下载器还是自带二进制，并抄下上游 pin 的 gn revision 与 sha256。
2. 判定预编译可用性：
   ```sh
   file gn                       # 看架构 + interp
   readelf -l gn | grep -i interpreter
   readelf -d gn | grep NEEDED   # 看 libc 族
   readelf -S gn | grep -i codesign  # 有无 .codesign（无 → 会被拒执行）
   ./gn --version                # EACCES=签名；ENOENT=interp 缺失
   ```
3. **对照组**：把任一**已知可跑**的 musl 二进制拷到同一目录执行——
   同样 `Permission denied` ⇒ 是"位置/签名"问题而非二进制本身。

## 方案（源码自举，已实证）

```bash
# 1) 取 pin 版源码（googlesource 常不可达 → 用 GitHub 镜像；镜像须含上游 pin 的 revision）
curl -sSL -o gn.tar.gz \
  https://codeload.github.com/JiauZhang/gn/tar.gz/0725d7827575b239594fbc8fd5192873a1d62f44
tar xzf gn.tar.gz && cd gn-0725d7827575b239594fbc8fd5192873a1d62f44
# 2) 生成 ninja 文件（无 .git 时必须 --no-last-commit-position）
export CC=clang CXX=clang++
python3 build/gen.py --no-last-commit-position
# 3) 手工补 gen.py 跳过的头（否则 scope_per_file_provider.cc 报 file not found）
printf '// Generated by build/gen.py.\n#ifndef OUT_LAST_COMMIT_POSITION_H_\n#define OUT_LAST_COMMIT_POSITION_H_\n#define LAST_COMMIT_POSITION_NUM 0\n#define LAST_COMMIT_POSITION "0 (unknown)"\n#endif\n' \
  > out/last_commit_position.h
# 4) 构建（OHOS clang 链接期自动加 .codesign，产物可直接执行）
ninja -C out
# 5) 验证
./out/gn --version          # → 0 (unknown), rc=0
cd <upstream> && <gn> gen out/x --args='...'   # → Done. Made N targets
```

## 坑位清单

- **`--no-last-commit-position` 的副作用**：必须手工补 `out/last_commit_position.h`（3 处宏）。
- **别放只读挂载**：OHOS `/tmp` 是 erofs **只读**，日志/构建目录别用 `/tmp`。
- **conan 内调用**：OHOS python subprocess **不搜裸名**（`subprocess.run(['ninja'])` 直接 FileNotFoundError），
  ninja 用 `tool_requires("ninja/1.13.2")` 或把绝对路径写进环境变量（参见 E545）。
- **pin 一致性**：用上游 CI 指定的 gn revision，避免"新 gn 语法/行为漂移"造成的假失败。
- **exec 位置**：构建/执行统一在可写工作区；`/data/local/tmp` 在 OHOS PC 对普通用户不可写。

- perfetto 58.2（v58.2, commit `add693d8…`）：

## 附：同批发现的 OHOS 测试基建/打包事实（与 GN 无关，但同源场景必踩）

1. **测试框架硬编码 `/tmp`**：OHOS 的 `/tmp` 是**只读 erofs**。googletest 用
   `/tmp/captured_stream.XXXXXX` 做捕获流临时文件，`mkstemp` 失败后走到 `FOPEN` FATAL →
   整个测试二进制 abort。修法：googletest 的 OHOS 分支改用 `TMPDIR`；自家测试代码里硬编码 `/tmp`
   的路径改用 `GetSysTempDir()`（该函数本身已尊重 `TMPDIR`）。
   ⇒ **OHOS 上测试/工具必须用 `TMPDIR`，且 `/tmp` 可写不能假定**。
2. **文件路径型 unix socket 被拒**（比 `/tmp` 更硬的一层）。跨盘探针：hmdfs `EPERM(1)`、
   `/data/local/tmp` `EACCES(13)`、`/tmp` `EROFS(30)`、`/dev/shm` `EACCES(13)`；**仅抽象 socket 可用**。
   所有「以文件路径做 unix socket」的 IPC/round-trip 测试会 SIGSEGV 或失败（perfetto 的
   `UnixSocketTest`/`ClientImplTest`/`HostImplTest`/smoke 均如此）。
   ⇒ **OHOS 上做 IPC 优先用抽象 socket；排查时先做跨盘 bind 探针，别只怀疑 `/tmp`**。
3. **CLI `--help` 惯例**：perfetto 的 `CmdLine` 打印 usage 后返回 **1**（非 0）；断言应校验「输出含 Usage」。
4. **conan 打包两条**：①可执行文件以 `rpath $ORIGIN/.` 链接同目录 `.so` 时，包布局把 `.so` 放 `lib/`
   会让 `bin/` 下程序加载失败 → `bin/` 也放一份；②公共头若 include **生成头**（如
   `perfetto_build_flags.h`），打包须把生成头一并放进 `include/`。
5. **配方侧 conan API 三坑**：`get()` 不接收 `tar_format`（也不认 codeload 的无扩展名 URL，须显式传
   `filename=`）；`self.run(env=...)` 只接受**环境脚本名列表**（变量要用 `Environment().define()` 落脚本）；
   传给 shell 的 `gn gen --args=` 必须用**单引号**包裹，否则内层 `""` 被吞。
6. **filemgr（HMDFS）写读延迟**会读到半截文件（本任务踩 3 次：补丁生成、编译、脚本）→ 改完 sleep 20-45s 再编。
