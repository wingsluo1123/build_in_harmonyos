# E14735 草稿：getopt() 的返回值存进 plain char——无符号 char 平台上选项扫描结束的 EOF 变成 255，CLI 对每条有效命令都报 `Unknown option` 并退出 1（`-h` 与库级测试照常通过）

## 错误特征

构建成功，`mar -h` 正常，库自带的 C++ 测试也通过，但**每一条真实命令都失败**：

```
$ mar -s name=hello a.mar
Unknown option `-s': Try `mar -h' for more information        # exit 1，a.mar 没有被创建
```

报错点名的 `-s` 是**合法**选项，这是误导：诊断打印的是最后一次解析到的选项。clang 在编译期其实已经报过：

```
mar_main_c.c:303:15: warning: result of comparison of constant -1 with expression of type 'char' is always true [-Wtautological-constant-out-of-range-compare]
```

但它只是告警，构建成功，容易淹在日志里。

## 触发条件

- 目标平台的 plain `char` 无符号：OHOS aarch64（`CHAR_MIN` 为 0、预定义 `__CHAR_UNSIGNED__ 1`）以及所有 AAPCS64 Linux 目标；x86 Linux 上 `char` 有符号，所以上游开发机上看不出来。
- 程序用 `char ch` 接收 `getopt()`（或随包自带的 getopt，如 mar 的 `ntp_getopt`）的 `int` 返回值，并以 `-1 != ch` 作循环条件。

## 根因

`getopt()` 在选项耗尽时返回 `-1`。存进无符号 `char` 后变成 255，`-1 != ch` 恒真：循环永不结束，选项处理完之后的下一次调用返回的 EOF 落进 `switch` 的 `default:`，程序打印“未知选项”并退出 1。随包 getopt 每次调用都会设置 `optopt`，所以消息里出现的是最后一个合法选项。

`-h` 在扫描结束之前就返回了，库级测试程序根本不经过这个循环——它们在所有平台上都通过，只有“一条需要走到选项末尾的有效命令”才暴露问题。

mar 0.5 把选项表扫描**两遍**：`main()` 先预扫描收集标志，再把 `mar_optind` 置 0 交给 `mar_run()` 真正执行。两处各有一个 `char ch`，只改一处会得到更难诊断的半修复状态（见下表）。

## 实测证据（x86_64 构建机 + OHOS NDK clang 15.0.4，交叉到 aarch64，静态链接后经 `qemu-aarch64` 运行；未在真机上运行）

同一条命令 `mar -s name=hello X.mar`：

| 构建 | 退出码 | 输出 | `X.mar` |
|---|---|---|---|
| A 上游原样 | 1 | ``Unknown option `-s': Try `mar -h' ...`` | 未创建 |
| B 上游原样 + `-fsigned-char` | 0 | 无 | `name=hello` |
| C 两处改 `int ch`（本 PR 补丁 0003） | 0 | 无 | `name=hello` |
| D 只改 `main()` | 1 | `Unexpected option '-s'` | **已写入** `name=hello`（53 字节） |
| E 只改 `mar_run()` | 1 | ``Unknown option `-s'`` | 未创建 |

与 mar 无关的最小复现（`getopt_char.c`，`char c; while (-1 != (c = getopt(argc, argv, "ab:"))) {...}`），同一命令 `./t -a -b x`：

| 构建 | 结果 |
|---|---|
| OHOS clang aarch64，默认 | 打印 `option a`、`option b=x` 后进入 `default`，退出 1（libc 的 getopt 不在成功时设置 optopt，消息里是 `optopt=0`） |
| 同上 + `-fsigned-char` | `done`，退出 0 |
| 把 `char c` 改成 `int c` | `done`，退出 0 |
| x86_64 主机 gcc | `done`，退出 0（char 有符号） |
| clang 默认选项 | 报 `-Wtautological-constant-out-of-range-compare`（告警，不阻断） |
| `-Werror=tautological-constant-out-of-range-compare` | 编译失败，拦住该缺陷 |

对已打补丁的 mar 0.5 整库（除 Windows 专用的 `mar_windows_c.c`）与 C++ 测试对象开启该 `-Werror=`：编译通过、零误伤；对未打补丁的 `mar_main_c.c` 开启：两处报错（303、397 行）。

## 推荐处理

1. 把每个接收 `getopt` 返回值的变量声明为 `int`，比较保持 `-1`/`EOF`：每处一行，无平台宏，可提交上游。先 `grep -n getopt` 找全调用点——选项表重扫描（`optind = 0`）时每遍一个接收变量。
2. 把编译器已有的告警变成护栏：配方的 CFLAGS 里加 `-Werror=tautological-constant-out-of-range-compare`（只提升这一条，旧代码里别的告警不受影响）。
3. 用消费者测试证明修复，并让它**执行交付的二进制**：用有效选项驱动包内 CLI，断言退出码 0 且 stderr 为空，再通过库把结果读回来核对；把 CLI 链成 `-static-pie`，x86 运行器才能经 `qemu-aarch64` 运行同一个交付产物。只跑 `-h`/`--version` 或库级 `make check` 抓不到这个缺陷。

## 禁止做法

- ❌ 用 `-h`/`--version` 烟测或库级 `make check` 全绿来证明 CLI 可用：它们都不经过出错的循环。
- ❌ 用 `#ifdef __OHOS__` 区分：char 符号性是目标 ABI 属性而不是操作系统，`int` 在所有目标上都正确，平台宏会让补丁无法上游、同一缺陷在下一个无符号 char 目标复发。
- ❌ 只改第一处接收变量就收工：重扫描的选项表会进入“数据已写入但退出 1”或“什么都没写”两种半修复状态。
- ⚠️ `-fsigned-char` 只当诊断开关（证明符号性是唯一变量），不当交付方案：源码仍是错的，手写 Makefile 若忽略/替换 `CFLAGS` 会悄悄丢掉它，同时改变同包内其它 `char` 数据的语义。

## 验证

```bash
clang -c <prog>.c 2>&1 | grep "constant -1 with expression of type 'char'"     # 源码侧：选项循环里的命中即该缺陷
qemu-aarch64 ./<static-pie prog> <有效选项及参数> ...; echo "rc=$?"            # rc=1 且 Unknown option 点名了合法选项即确认；<prog> -h 仍返回 0
```
