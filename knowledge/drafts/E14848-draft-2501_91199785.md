# 静态库仍可能具有运行时数据依赖

## 现象与根因

Conan 的 `static-library` 类型容易被误读为“运行时没有依赖”。静态链接只消除了共享库装载要求，不会把 XML、字典、着色器等数据嵌进可执行文件。若公开 API 在运行时读取包内文件，构建和链接都会通过，但消费者运行时找不到数据。flam3 3.1.1 的调色板 XML 属于这个类别。

## 修复与验证

配方保留静态库类型，同时声明 `package_type_traits = {"run": True}`，把已安装的调色板路径通过 `runenv_info` 的 `flam3_palettes` 变量传给消费者。用 `conanrun` 启动消费者，真实调用版本、随机数和 `flam3_get_palette`，确认不仅文件存在，而且 API 能读取并返回有效颜色。真机日志 SHA-256 `0220933c516cef062cd1e72ca33a8ba562ed61193a57e3adc2416ea4d5b95844` 记录消费者 1/1 通过；上游发布包没有注册 `make check` 目标，故上游为 0/0。

## 适用范围和边界

适用于静态库 API 仍依赖包内运行时资源的场景；没有运行时文件读取的普通静态库不需要设置 run trait。路径必须由当前安装包目录计算，不能硬编码某台机器的 Conan cache 或用户目录。只检查 `flam3_palettes` 环境变量非空，或只检查链接成功，都不足以证明数据可用；应执行实际读取该数据的库 API。

## 2026-10-10 增量：运行时证据不能代替构建输入闭包

CI80120 给出一个新的可复用反例：先前静态库和数据消费者可以在开发机通过，
但配方用开发机 Automake/share 目录中的 config.sub 掩盖了源包自身旧
canonicalizer 的能力缺失；精简 worker 没有该未声明 helper 时，在 configure
之前就失败。因此，“静态链接 + 运行时数据 API 已实测”与“配方在发布环境
自包含”必须分别证明，不能把前者当后者。

此次保留数据 run trait 和真实读取 API 的消费者，只将构建前置改为使用
源码归档中 hash-bound 的 config.sub。2007 版 helper 分别判断裸 CPU、
CPU-vendor、kernel/OS 和 OS 后缀，四个精确 anchor 都需支持 aarch64/OHOS。
只改 OS 后缀不足，只有四段 tuple 成功也不足以证明三段 compiler tuple 可用。
不得依赖未声明的开发机工具目录，也不得伪装为 Linux GNU 或跳过特性检测。
