# 完整 API 消费者才能验证 Conan 公共头与链接闭包

## 场景与根因

同一个图形库可以同时暴露轻量入口和完整设备层。仅调用轻量入口的 `test_package` 可能编译、链接、运行都通过，却没有触及完整 API 公共头中引用的依赖类型，也没验证设备层所需的传递链接。Conan 依赖图中存在包，不等于它的公共头会传给下游；消费者必须从“只直接依赖被测包”的视角验证。

## 可复用方案

在配方中对公共 API 所需依赖设置 Conan 的传递头语义，并在 `cpp_info.requires` 中列出实际依赖边。消费者包含安装后的完整 API 与一个代表性设备层头，执行创建、销毁和结果检查。测试程序不能仅打印成功标记，也不能用轻量入口代替完整入口。对于只发布 lite API 的包，则应明确收窄交付范围，不能宣称完整 API 已验证。

## 本次证据与适用边界

libwmf 0.2.15 的配方对 FreeType 要求 `transitive_headers=True`，并显式导出依赖边。最终消费者调用 `wmf_api_create`、SVG 设备层函数及 `wmf_api_destroy`。鸿蒙 PC 真机事务 `libwmf-w3-20261004T074946Z` 中，上游 Automake `check-examples.sh` 1/1（内部 3 个转换器 × 17 个素材），消费者 1/1，通过且完成释放后核对；原始日志 SHA-256 为 `80cf006f0d80b09b439ee8b2646b37b646dfb77af94686792d56220857444d16`。

适用于公共头暴露依赖类型或存在轻量/完整 API 分层的包。已有知识讨论自定义 CMake 模块遗漏传递 include，本条补充 Conan 2 的 requirement 传播与“测试入口选择会掩盖闭包缺陷”的包级边界。不能把这次消费者结果外推到未测试的全部渲染格式。

## 2026-10-10 增量：验证入口不能依赖开发机的辅助数据定位

PR #14657 的完整 HEAD `89184ca431863da6d7ad27bda93cccab8a6be912` 在 CI #80112 尚未进入上述 API 验证就失败：`automake executable missing`。配方并未需要执行 Automake，而是借其可执行文件位置寻找 `config.guess/config.sub`，并要求恰好一个目录及开发机版本的固定哈希。这把完整 release 的构建闭包错误地扩展成了环境私有工具安装布局。

本轮核验官方 release SHA-256 `bbc90f22b9e86d5f1890d7da11cf7a8e61f429d4c220d900c285021deabe7a52` 内已包含生成的 configure/Makefile.in；bundled 2024 `config.sub` 本身已接受 linux-ohos。配方仅在 OHOS 校验两份 bundled helper 的精确哈希、保存并复算任务内备份，然后运行 Conan 配置中的编译器 `-dumpmachine`，让 bundled `config.sub` 规范化它。任务内 `config.guess` 只回显该实测规范元组，并在 configure 前再执行校验。不再依赖 ambient Automake，不执行不必要的 autoreconf，也不强塞伪造的 Linux `--build/--host`。

本地对实际 recipe helper 执行正向、错误 tuple、helper 哈希漂移三项检查，全部符合预期。新真机事务 `libwmf-repair-w3-20261010T101340Z` 实测 `aarch64-unknown-linux-ohos`，原上游 `check-examples.sh` 1/1 和已安装完整 API 消费者 1/1 全通过，12 阶段及 release/postrelease 通过。独立回读的完整 Conan 日志 SHA-256：`1d0b71e6e07518828eff74709358f63e5c7d2d92c186e472298072e65e4badbd`。这是当前修复候选的真机证据，不代表比赛 worker 新 CI 已通过。

该增量适用于带生成文件的 Autotools release：应区分“构建生成器”和“运行 configure 所需的辅助数据”。不适用于缺 configure 的 Git 快照、修改 configure.ac/Makefile.am 后必须再生的项目。helper/编译器输出漂移必须失败，非 OHOS 分支保留上游原行为，不能用这些检查绕过完整上游或消费者测试。

### 2026-10-12 新反例：完整 API 验证需区分官方执行转换与源码漂移

本轮修复两条 config.status 临时目录分支后，完整API与上游测试已通过，但旧外层验证因 CI 生成的 conandata 镜像列表而真实返回失败。原 YAML 与 `.orig` 相同，源码SHA与补丁完全未变；发生的是官方 build_and_test.sh 的精确 GitHub镜像转换，不是配方偷偷换源码。该失败事务保持 FAIL，不追认成 PASS。

复用“CI mirror fallback and post-result candidate identity”边界，在新事务冻结前绑定原始 bytes，逐字节重放官方有序镜像列表，要求 `.orig` 精确相等、实际文件等于重放、其他 recipe/test/patch 字节不变。不能笼统忽略 YAML差异，不能接受 file://、额外镜像、SHA或补丁变化。提交分支仍保留官方单URL。

新事务 `libwmf-w3-20261012-hmdfs-tmp-substep-r2` 运行官方W3子步骤，check-examples1/1（3转换器×17原素材全部执行）、完整安装API消费者1/1、12阶段与释放全部通过。日志SHA256 `b181ba78c1159b15d3febff7e992df7070a32b0984646111a768c27e48938d8e`。此次给原“完整API闭包”知识增加真实执行输入与保护文件的反例边界，不重复申报已有的镜像机制，也不冒称完整 finish 或比赛CI通过。
