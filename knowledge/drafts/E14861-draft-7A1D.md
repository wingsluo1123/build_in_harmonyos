# E14861 草稿 — 测试不得依赖 Check 宏生成的内部函数名

## 适用范围

旧 C 项目使用 Check 的 `START_TEST(name)` 或类似测试宏，并在测试体内验证
包含 `__func__`、函数签名或调用位置的日志文本。宏参数形成的逻辑用例名可以
保持稳定，但宏展开后的 C 符号属于框架实现细节，不能作为跨版本契约。

## 真实失败与根因

`ladvd 1.1.2` 的 `configure.ac` 接受 `check >= 0.9.4`。其
`START_TEST(test_my)` 内部触发 `my_log()`；生产宏有意把当前 `__func__`
写入日志，但测试把期望值硬编码为：

```c
errstr = "test_my: debug\n";
```

Check 0.12.0 将测试体展开为 `static void test_my(...)`，所以旧期望成立。
Check 0.13.0 重写 `START_TEST` 后，逻辑用例仍叫 `test_my`，实际测试函数却变成
`test_my_fn`；当前已发布依赖 Check 0.15.2 保留该展开。因此迁移使用
`check/0.15.2` 时，被测日志正确输出 `test_my_fn: debug`，上游断言却稳定报告
`invalid output`。这不是 HarmonyOS 日志实现错误，而是旧测试依赖了新版依赖
从未承诺的内部符号。

## 推荐修复

测试要验证的是“日志前缀与当前执行函数一致”，就在同一个测试函数中从
`__func__` 构造期望值，再保留完整字符串比较：

```c
char expected[1024];
snprintf(expected, sizeof(expected), "%s: debug\n", __func__);
errstr = expected;
```

这不是放宽断言：消息、换行、输出通道和完整相等比较都不变。若测试真正要
验证 Check 的逻辑用例名，应另用框架公开的用例结果接口，不能猜测 `_fn`
之类的内部拼接规则。

## 可复用诊断流程

1. 先读取构建脚本声明的测试框架版本范围，不能只依据当前闭包中的版本判断
   兼容性；版本范围允许多个宏实现时，内部展开结果就不能充当测试契约。
2. 对相关测试源执行预处理展开，并对照至少两个允许版本的公开头文件，定位
   逻辑用例名、注册符号与实际 C 函数名分别来自哪里。
3. 搜索测试期望中是否硬编码了 `__func__`、`__FUNCTION__`、宏生成符号、
   参数化测试后缀或框架生成的异常文本。
4. 分清失败发生在被测程序行为、框架注册、测试发现/执行，还是期望字符串；
   本例的 45 个用例能正常发现并执行，唯一失败发生在期望字符串比较。
5. 依据 C 语言公开语义或框架公开接口构造期望，并保持原有完整相等断言。
6. 保留旧硬编码、新硬编码和自反期望三个对照，证明修复建立了跨版本不变量，
   而不是追随当前版本改一个字符串。

判断准则是：若测试期望依赖测试框架宏生成的内部标识符，而构建约束允许多个
实现不同的框架版本，则该期望不稳定；应从当前公开语言语义或稳定框架接口
派生，不能硬编码某一版本的宏展开产物。

## 错误修复反例

- 把硬编码改成 `test_my_fn`：只对 Check 0.13+ 有效，回到项目声明支持的
  0.9.4–0.12 系列又会失败。
- 改写 `START_TEST` 宏或注入编译参数：会破坏框架注册结构。
- 删除、过滤 `check_util`：会丢掉原有日志行为回归，不构成修复。

## 三臂验证与边界

1. 原始臂：Check 0.15.2 展开为 `test_my_fn`，未应用补丁时期望仍为
   `test_my`，日志断言失败。
2. 假修复臂：硬编码 `_fn` 在 0.15.2 通过，但在同一 HarmonyOS PC 真机上
   用官方 0.12.0 源码构建的隔离实验中失败，实际输出函数名为 `test_my`。
3. 正确臂：期望由当前 `__func__` 派生；同一真机上的 0.12.0 与 0.15.2
   隔离实验均通过。正式依赖闭包仍只使用已发布的 `check/0.15.2`，其中
   `check_util` 8/8 通过，并保持完整 `make check -j1` 的 7/7 程序、45 个
   用例覆盖。

宏演进可以直接由官方发布源码复算：

```sh
grep -A5 '#define START_TEST' check-0.12.0/src/check.h
grep -A5 '#define START_TEST' check-0.13.0/src/check.h
grep -A5 '#define START_TEST' check-0.15.2/src/check.h
```

可执行的最小复验在两个版本中使用同一段测试体：先用 `__func__` 生成
`actual`，再分别用固定 `test_my`、固定 `test_my_fn` 和当前 `__func__`
生成 `expected`，最后执行 `strcmp(actual, expected) == 0`。六个组合的预期
退出码依次为 `0,1,0` 与 `1,0,0`。实验完整命令、源码来源、结果和日志哈希
记录于 `archives/l/ladvd/1.1.2/reports/path-b-evidence.md`。

该知识不主张所有日志都应动态忽略函数名；只有当产品语义本来就是“记录当前
调用函数”时，测试才应从当前函数构造自反预期。若产品 API 明确规定固定函数
名，则仍应断言固定文本。
