# E15119：wheel 与包管理器同 SONAME 的单提供者闭包

## 触发特征与根因

当 Python wheel 带有 `*.libs/` 原生共享库，同时 C++ 消费者通过 Conan
引入同名运行库时，应核对两条来源。`DT_SONAME` 一致、文件都存在，甚至
一组导出符号都存在，也不能证明 ABI 等价。平铺覆盖或只追加搜索路径会
隐藏不同来源；一个入口的成功不能替另一种语言的真实运行作保证。

## 可复用决策与修复

先保全两个下载归档及其 SHA-256，分别记录 SONAME、ELF 架构、原消费者
真实需要的符号和依赖。选择一个真实发布且能够覆盖双方需求的提供者；
如果不能选定，应继续修复或隔离，不能以同名认定兼容。只在本任务私有
物化目录排除另一份伴随库，并保留该排除的来源记录；原 wheel、Conan
共享缓存和系统运行库不改动。

生成阶段用真实依赖元数据绑定 CMake 链接与执行路径，保留官方 Python
发行元数据。随后实际构建、签名、运行完整原测试，再对安装后的 C++
和 Python API 分别验证数学结果。输入、产物、实际执行和发布是四种
不同证据；没有实际 live maps 时，不声称看到了全部动态加载路径。

## 与既有知识的区别

E316 处理缺失 SONAME 实体；本次不是文件不存在。E546 处理不同符号集
与生成环境重写；本次进一步处理“同名、两侧关键符号均存在”的输入选择、
私有物化边界及安装后跨语言实测。不能据此归纳为随意删除所有wheel伴随库。

## 安全与适用边界

适用于确有双重运行库来源的多语言栈。线程、整数宽度、异常或其他 ABI
合同不明时仍须继续诊断。下载/符号扫描不是目标运行，运行不是发布，
上述数学范围也不是所有 ABI 的普遍证明。不改公共库/原归档、不借用
异平台头文件、不使用空实现、不隐藏普通缺依赖或原测试失败。
