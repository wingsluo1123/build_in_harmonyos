# E15124 — 只为查询工具路径而构造 VirtualBuildEnv，也可能关闭自动环境生成

## 错误特征
`tool_requires` 的工具已下载，临时 `vars().apply()` 中能找到工具，但之后
`self.run()` 报 `meson: inaccessible or not found`。并非依赖缺失，也不能只凭
`shutil.which()` 的临时成功判断后续构建环境有效。

## 触发条件
- Conan 2 配方依赖默认的自动 VirtualBuildEnv 生成。
- `generate()` 或其助手函数为查询工具而调用 `VirtualBuildEnv(self).vars().apply()`，没有显式 `.generate()`。
- 构建系统可为 Meson、Autotools、CMake；失败最终出现在后续构建命令中。

## 根因分析
`VirtualBuildEnv` 构造器默认 `auto_generate=False`，立即把
`conanfile.virtualbuildenv` 置为 False。这是手动管理环境时的预期行为，但只借用
临时环境查询工具的调用也会触发它；此前 Toolchain 对自动环境的请求不能抵消
这个后发生的副作用。Python 上下文退出后，临时 PATH 也随之恢复。

另一个容易遗漏的边界：`auto_generate=True` 只是不关闭自动生成，**不主动把已经
False 的标志恢复为 True**。因此应修复所有临时构造调用，或明确生成所需环境。

## 解决方案

### 推荐方案
对纯查询调用显式保留自动生成：

```python
with VirtualBuildEnv(self, auto_generate=True).vars().apply():
    ninja = shutil.which("ninja")
```

随后将解析出的绝对路径通过 Conan `Environment.save_script()` 提供给后续命令。
另一种适用于明确手动管理环境的方案是显式调用 `.generate()`，不要只做临时
`.apply()`。继续保留正确的 `tool_requires`、真实工具存在性检查及正常 Conan 激活。

### 禁止做法
- 不以全局 PATH、系统同名工具或删除 `tool_requires` 掩盖环境丢失。
- 不在任意较晚位置加一次 `auto_generate=True` 并宣称已恢复先前被关闭的标志。
- 不修改生成的脚本来掩盖构造器生命周期，也不把这个根因与保存脚本顺序混为一谈。

## 验证
本轮用实际 Conan 构造器完成 3/3 定向检查：True→默认 False 后变 False；
True→显式 True 保持 True；已经 False→显式 True 仍为 False。

libupnpp 1.0.4 真机 r3 在工具已安装后仍找不到 Meson；修复后 r4 能完成 Meson
配置，后续其他故障另行处理。最终 r13 在同一台 OHOS 6/arm64、Clang 15 真机上
完成 `conan create` RC0、原始驱动 1/1（8 原始向量）、安装消费者 8/8、12 阶段
回执及清理，并由冻结 validator 返回 W3_PASS。日志 SHA-256：
`1f3966a4876418e718f77ee84db3fb57a1a6571436eafcf28958ffc3e9ff5cf9`。

适用范围是 Conan 构造器生命周期；工具包缺文件、ELF 加载失败、环境变量互相
覆盖或脚本保存顺序错误，必须按其各自根因处理。本轮未宣称比赛 CI 已通过。
