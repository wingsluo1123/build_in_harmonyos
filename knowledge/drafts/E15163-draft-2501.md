# 从缺 Makefile 向前追踪旧 Autoconf 的配置生成失败

## 现象和根因

旧的预生成 Autoconf 脚本可能在 `config.status` 写临时替换脚本、Makefile 或 config.h 失败后仍执行后续命令。外层 configure 未使配方停下，最终 Conan 报错行位于 `make`，末尾是 `No targets specified and no makefile found`。这不是编译器错误，也不是“上游没有 Makefile”；必须按时间找到更早的配置生成失败。

## 可复用步骤

1. 保存完整原始日志，先区分是否进入真实编译，不只读最后的 ConanException。
2. 从无 Makefile 向前检查 config.status 的创建、替换和移动命令；将首个权限或模板错误与派生的 rm/mv/make 错误区分。
3. 核对官方发布脚本。遇到 HMDFS 的 confstat 权限失败，复用 E114/E129：在配方的私有 TMPDIR 内以兼容创建掩码修复两条目录创建分支，保留上游清理逻辑；不能靠事后 chmod 或全局替换所有权限。
4. 用干净 Conan 缓存重建，执行完整上游与安装消费者；configure 的退出码不能代替最终生成、编译和业务验证。

## 本次新增证据

libuninum 的 CI86351 先在 `confstat*/subs.sed`、`out` 和 config.h 出现 Permission denied，随后确实进入 make 并报无 Makefile。修复候选事务 `libuninum-w3-r12-20261012-ci-hmdfs-tmp` 的官方本地 CI exit0，原始 Tcl 两脚本 70/70、安装消费者8/8，12阶段及 release/postrelease 均通过。完整日志 SHA256 为 `5d52f7d79d2a872701d33300a33ca77f30736b8a377da04e03d88c59f8d011c9`。

E114/E129 已覆盖临时目录权限机制，本条不重复申报该机制。新增的是“配置生成错误继续传播到 make、成功返回的 configure 不足以证明配置完整”的可复核诊断边界。完整 finish 仍为 RC1，step5b/step8 另由提交合同处理，不冒称整体 finish 或比赛 CI 成功。

适用于上述日志顺序和生成阶段失败；如果 Makefile 已生成、真正的编译/链接失败，则不能套用。不得忽略配置生成错误、删除测试或伪造配置文件。
