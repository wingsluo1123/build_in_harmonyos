# E15168 — ELF AArch64 FFI 聚合类型需要调用与回调对称的 PCS 合同

## 错误特征
标量调用已通过，但结构体按值调用/回调未实现，或原生 C 与 FFI 对聚合参数及返回值的寄存器、栈位置不一致。常见定位点是 HFA 溢出、普通聚合体接近 x7、大结构体副本，以及 x8 隐藏返回指针。单纯增加平台宏或 Conan 参数无法补齐这些功能。

## 触发条件
- 小端 ELF AArch64 的动态调用 VM、回调 trampoline、JIT 或语言运行时桥接。
- 使用 float/double HFA 和整型/指针聚合体的按值 C 接口。
- 标量 marshalling 和可执行内存正常，不代表聚合 PCS 已实现。

## 根因分析
一个聚合体的正确调用依赖五个层面：类型分类、参数分配、汇编入口、回调保存帧和结果解码。它们必须共享同一 ABI 合同，不能分别沿用标量逻辑。

1. HFA 按实际叶子成员类型与地址分类，最多四个成员；嵌套数组递归展开，union 重叠地址不能重复计数，混合类型不能冒充 HFA。
2. HFA 必须整体放入剩余 FP 寄存器；不足时整体放栈并耗尽 FP 参数寄存器，不改走 GPR。
3. 不超过 16 字节的普通聚合体整体放入剩余 GPR；不足时整体放栈并耗尽 GPR，不能拆成 x7 加栈尾部。
4. 超过 16 字节的普通聚合体通过调用者持有的副本间接传递。副本必须存活到调用结束，不能指向会重分配的缓冲区。
5. 间接结果指针使用 x8，不消耗 x0。直接返回需保存 x0/x1 或 d0–d3；回调入口同样要保存 x8 与聚合类型元数据，C 声明和汇编帧偏移需编译期断言。

以上规则针对本条已验证的标量成员聚合体。不要将其扩张为完整 SIMD/HVA、half 类型或其他平台 PCS 的支持声明。

## 解决方案

### 推荐方案
先使用目标 C 编译器生成函数调用作为判定基准，然后一起实现上述五个层面的正向和反向路径。保留 VM 参数副本的明确所有权，在 reset/free 时释放；聚合栈写入做容量、对齐和零填充检查。

验证必须有两个方向：FFI 调原生 C；原生 C 调 FFI 回调。除正常寄存器分配外，特意先放七个 GPR 参数或六个 FP 参数，验证整体溢出和后续参数位置；再验证大聚合参数副本以及 x8 结果，最后用 Conan 安装后的包外消费者验证头文件、符号、签名和加载闭包。

### 禁止做法
- 仅启用 feature 宏而不实现结构体 marshalling/回调。
- 把 HFA 当普通字节数组、拆分 x7 与栈，或让隐藏 x8 结果消耗 x0。
- 为了通过测试删除聚合套件或把回调替换为空 stub。
- 从 Linux/Windows/Darwin 某一个 PCS 的成功推断其他 PCS 也支持。

## 验证
本次证据来自 dyncall 1.4：原版本聚合类型套件失败；实现后两个未修改的上游生成套件各 400 个用例全部通过。正式 Conan `conan create` 在 HarmonyOS PC / Clang 15.0.4 下执行全部 19 个上游程序，5,010/5,010 用例通过；包外消费者 15 项断言通过，回调内存保持 RX，并验证原生 NX 保护测试。

- 正式事务：`dyncall-official-w3-20261013-r2`，唯一 launch，12 项回执完整，release/postrelease 通过。

## 关联条目
- 已有 `DRAFT-lfortran-complex32-c99-hfa-abi` 指出了 complex32 向量/HFA 错位。本条新增的是通用 FFI 的嵌套/union 分类、寄存器整体溢出、大副本、独立 x8 和回调帧/返回捕获的对称闭环，非同义重写。
- E374 说明 `can_run()` 不能证明签名执行能力。本次真实签名和目标执行是 ABI 验证前提，不能用编译成功代替。
- 规范：[ARM AAPCS64](https://github.com/ARM-software/abi-aa/blob/main/aapcs64/aapcs64.rst)。

## 适用范围与安全边界

适用于小端 ELF ARM64、公开 C 标量字段聚合 ABI。当前不支持 Darwin/Windows PCS、大端 AArch64、HVA/SIMD 或未表达的显式过对齐；这些路径不得打开本次 feature 宏。类型描述与 callback 生命周期按 API 要求持有，不能从被测配置推断未测 ABI 功能。
