# 固定宽度样本流的读取边界不是记录边界：跨 `read()` 保存残余字节

> 状态：DRAFT（路径 B 知识库扩展候选）｜来源：multimon/1.0 HarmonyOS PC 适配｜日期：2026-10-16
> 候选编号：E202610160200｜机器可读层：`E202610160200-draft-6F91.kv`

## 结论

FIFO、管道、socket 等字节流的 `read()` 返回边界与应用记录边界无关。解析 16/24/32 位 PCM 或其他固定宽度记录时，不能在每次读取内把长度向下取整后丢掉尾部；必须把不足一个记录的字节保存为下一次读取的前缀。

EOF 也必须分层：没有残余字节是干净结束，仍有残余是截断记录，负返回且非 `EINTR` 是错误或暂时不可读状态。`EAGAIN/EWOULDBLOCK` 不是 EOF：非阻塞描述符必须保留残余并等待可读事件或交回事件循环，不应原地忙重试。

## 机械触发条件

以下源码形态同时出现时可优先审计：

```c
n = read(fd, buffer, sizeof(buffer));
for (p = buffer; n >= sizeof(sample); n -= sizeof(sample), ++p)
    consume(*p);
if (n != 0)
    warn_or_ignore();
```

可搜索：

```bash
rg -n 'read\(|fread\(|sizeof\(.*sample|noninteger number of samples|odd byte|partial frame' src
```

若循环结束后的 `n` 没有复制到下一轮，警告并不能保护数据。常规文件往往返回大块偶数字节，因此必须用 FIFO、匿名管道或 socket 主动制造 1、3、5 等奇数分片。

## multimon 的生产故障

multimon 1.0 的 `input_file()` 是 `multimon -t raw` 的真实生产路径。它用 `read(fd, short_buffer, sizeof(buffer))` 获取数据，在当前读取内逐个转换完整 `short`，剩余 1 字节只打印警告后丢弃。

对 `gen -t raw -d 123A` 生成的同一输入：

- 规则文件路径解码得到 `1, 2, 3, A`；
- 继承匿名管道首次只写 1 字节后再写剩余数据，原实现丢弃该字节，后续 16 位样本永久错位，四个符号全部消失；
- 生产命令仍返回 0，因而仅检查退出码会形成假绿。

上层没有偶数字节保证：`-t raw` 直接 `open()` 用户给出的路径，随后直接 `read()`；经 `/proc/self/fd` 暴露的继承匿名管道可稳定进入该路径。

## 三臂验证

| 臂 | 实现 | 相同分片管道的结果 |
|---|---|---|
| A 原实现 | 每轮只解析完整 `short`，尾字节告警后丢弃 | 返回 0，但 `DTMF` 序列为空 |
| B 错误修复 | 对奇数读取增加告警、重试或向下取整，但不保存尾字节 | 仍丢字节，输出与规则文件不一致 |
| C 正确修复 | 字节缓冲保留 `total % sizeof(short)`，下一轮从残余后读取 | 返回 0，规则文件与管道输出逐字一致，得到 `1,2,3,A` |

负向边界同时验证：空流为干净 EOF 并返回 0；只有 1 字节的流以“truncated 16-bit sample”非零失败。恢复 `0003-preserve-partial-pcm-samples.patch` 前的循环后，同一安装后消费者场景稳定失败。

## 正确实现

```c
carry = 0;
for (;;) {
    n = read(fd, bytes + carry, sizeof(bytes) - carry);
    if (n < 0 && errno == EINTR) continue;
    if (n < 0) return IO_ERROR;
    if (n == 0) return carry == 0 ? CLEAN_EOF : TRUNCATED_RECORD;

    total = carry + n;
    complete = total - total % record_width;
    consume_complete_records(bytes, complete);
    carry = total - complete;
    memmove(bytes, bytes + complete, carry);
}
```

如果接口一次只交付一个记录，可改用 `read_exact(record_width)`；它仍须区分“读到任何字节前 EOF”和“读到部分记录后 EOF”。

## 为什么直觉修复无效

### 只增加重试

正数短读不是错误，也不要求下一次调用补齐相同缓冲。没有保存尾字节时，重试只会从内核读取后续字节，已经消费的残余不会自动出现。

### 只向下取整或扩大缓冲区

缓冲区大小不改变流的分片语义。写端、调度和设备驱动仍可使任意一次 `read()` 返回奇数个字节。向下取整正是数据丢失发生的位置。

### 只比较退出码

原实现告警后继续并返回 0。测试必须比较规则文件与分片流的业务输出或最终内容哈希，不能只断言进程成功。

## 可执行验证

正式配方运行安装后的两个命令：

```bash
conan create archives/m/multimon/1.0 \
  -pr:h=ci/conan/profiles/ohos-aarch64 \
  -pr:b=ci/conan/profiles/ohos-aarch64 \
  --build='multimon/*'
```

消费者先执行包内 `gen -t raw -d 123A fixture.raw`，再分别让包内 `multimon -t raw -a DTMF` 读取规则文件和经 `/proc/self/fd` 暴露的继承匿名管道。分片场景先启动安装后的 `multimon`，再写入首字节；测试用 `FIONREAD` 在读端观测队列归零，确认消费者已单独取走该字节后才写入余量。这一握手将奇数短读从调度概率变为可观测前置条件。测试要求两条路径完整 stdout 相等，不把内部转换函数复制进测试。

## 适用与不适用边界

适用于没有消息边界保证的定宽二进制输入：原始 PCM、传感器采样、定宽遥测记录、像素或网络字节流。multimon 本次实证范围是阻塞文件/管道输入；若迁移到非阻塞 socket 或字符设备，除保存 `carry` 外还必须在 `EAGAIN/EWOULDBLOCK` 时等待可读事件，不得原地忙转。

不适用于：

- 上层 API 明确一次返回完整记录；
- `SOCK_SEQPACKET` 等保留消息边界且应用验证了单消息长度；
- 按字节处理、没有固定记录宽度的协议；
- 需要处理可变长帧的解析器；后者应保存完整解析状态而不只是固定余数。

## 查重边界

`E13539-draft-tank_you` 同样讨论跨块边界，但对象是 JPEG 可变长标记匹配和 C++ stream failbit/seek 状态；本条的机械触发条件是固定记录宽度、`read()` 正数短读、余数保存和截断记录 EOF。修复状态、反例与验证预言机均不同。正式知识和开放草稿中未发现同一“固定宽度记录余数被丢弃”机制。
