# 长生命周期外部计算进程的请求必须共享单调总截止时间

> 状态：DRAFT（路径 B 知识库扩展候选）｜来源：qsoas/3.3 HarmonyOS PC 适配｜日期：2026-10-16
> 候选编号：E202610160430｜机器可读层：`E202610160430-draft-6F91.kv`

## 结论

复用外部解释器或数值程序时，一笔请求的超时必须覆盖进程启动、请求写入、响应组帧和完成标记，
并由同一个单调时钟截止时间约束。循环内反复使用固定相对超时不是总超时：对端只要在每轮到期前
输出一个无意义字节，就能让等待永久续期。

截止检查不能只放在“当前没有可读数据”的分支。对端若持续输出完整行，缓冲区可能始终可读；
循环仍必须在每轮消费数据和接受完成标记之前检查同一截止点，并为累计响应设置独立大小上限。

失败处理也是协议的一部分。总预算耗尽、写入失败、子进程退出或响应非法时，应终止并回收当前
子进程，同时丢弃半包响应。下一笔请求只能由新的协议实例处理，不能让旧进程的迟到输出满足
新事务。

## 机械触发条件

优先审查以下组合：

1. 客户端保存一个可跨请求复用的子进程对象；
2. 请求先后调用启动等待、写入等待和多次读取等待；
3. 响应依赖 `DONE`、空行、长度字段或完整 JSON 才结束；
4. 循环中的每次等待使用同一个固定毫秒数或 API 默认值；
5. 超时后只返回错误，没有 kill、wait/reap 和半包清理。

```bash
rg -n 'waitForStarted|waitForBytesWritten|waitForReadyRead|poll\(|select\(' src
rg -n 'DONE|complete|length|fromJson|partial|pending' src
```

## QSoas 的真实故障

QSoas 3.3 的外部函数接口复用 `QProcess`，向 Python 助手发送一行 JSON，再读取响应，直到出现
`// -> DONE`。原实现没有检查启动、写入等待的结果；读取循环反复调用无参数
`waitForReadyRead()`。该 API 每次调用都有自己的等待窗口，不能表达整笔事务的总时限。

真机助手先返回合法 JSON 行，随后每 50 ms 输出一个空格并保持存活，永远不发送完成标记。
安装后的真实 `qsoas --pyfunc` 在外层 3 秒看门狗内不返回，退出码为 124。故障来自生产协议
状态机，不是测试替身内复制出的等待循环。

第二个助手连续输出带换行的完整响应行，使缓冲区保持可读且永不发送完成标记。它专门验证
截止检查不依赖 `readLine()` 返回空；正确实现仍在 500 ms 总预算内终止并回收助手。

## 三臂验证

| 实验臂 | 实现 | 同一慢滴流助手 |
|---|---|---|
| A 原实现 | 每轮使用 QProcess 默认相对超时 | 3 秒外层看门狗终止，退出码 124 |
| B 伪修复 | 每轮改为 `waitForReadyRead(200)` | 50 ms 碎片持续续期，仍由外层看门狗终止 |
| C 正确修复 | 单调总截止时间，所有阶段消费同一剩余预算 | 约 500 ms 后非零退出，助手已回收 |

正常对照由助手返回 `{"values":[8.0]}` 和 `// -> DONE`；安装后命令执行
`sample(2, scale=4)` 得到 8，退出码为 0。撤销总截止时间补丁后，慢滴流用例稳定恢复为外层
看门狗失败。

## 正确实现

```cpp
QElapsedTimer timer;
timer.start();
const int budget = transactionTimeout();

auto remaining = [&]() {
    qint64 value = budget - timer.elapsed();
    return value > 0 ? int(value) : 0;
};

if (remaining() == 0 || !process.waitForStarted(remaining()))
    fail_and_discard_process();

queue_request();
while (process.bytesToWrite() > 0) {
    if (remaining() == 0 || !process.waitForBytesWritten(remaining()))
        fail_and_discard_process();
}

while (!response_complete()) {
    if (remaining() == 0)
        fail_and_discard_process();
    if (has_complete_line()) {
        consume_one_bounded_line();
        continue;
    }
    if (!process.waitForReadyRead(remaining()))
        fail_and_discard_process();
}
```

单调时钟避免墙钟调整改变预算。每一步都重新计算剩余时间，但截止点只有一个；收到数据不会延长
它。同步实现发生失败后直接销毁旧进程和半包，因此无需额外保留进程代际编号；异步实现若允许旧
回调稍后到达，则还须在回调中比较 generation/request id。

## 为什么常见修复无效

### 只给每次读取设置超时

这限制的是“相邻两批数据之间的最大空闲时间”，不是事务总时长。慢滴流始终在单次等待到期前
到达，整体仍可无限延长。

### 只检查进程仍在运行

进程存活不等于协议进展，更不等于完整响应。故障助手正是保持存活且持续输出无效碎片。

### 调用者超时后直接返回

如果助手继续运行、半包仍在缓冲区，下一请求可能读到旧事务的完成标记或 JSON 尾部。必须在失败
点回收进程并清空事务状态。

## 适用与边界

适用于长生命周期解释器、数值计算助手、插件宿主、语言服务器和编译服务等有请求/响应边界的
子进程协议。一次性进程也应有总预算，但若一个有界 `wait` 已覆盖从启动到退出的完整生命周期，
不需要分阶段剩余预算。

总截止时间并不替代取消传播或异步 request id；这些是相互独立的边界。本例同时设置响应
大小上限，但本条主张限定于同步事务的时间预算、失败回收和半包隔离。

## 查重边界

现有知识中与子进程相关的正式条目主要处理测试 stdin 未关闭、错误输出未透传、PTY 启动竞态
或平台断言，未发现相同正式机制。

开放草稿 `E429-draft-58E6` 也要求单调总截止时间，但其核心故障是持久 TCP 客户端把一次正数
短读误作完整 SCPI 消息，主修复是按终止符/声明长度增量组帧；QSoas 原实现已经使用明确的
`DONE` 完成标记，不存在消息边界未知问题。本条新增的机械触发点是“启动、写入和已知帧界的
多轮等待各自使用相对超时，碎片进展可无限续期”，并要求失败后的可复用子进程回收与半包隔离。
两者可组合使用，但根因入口和主要状态机不同。
