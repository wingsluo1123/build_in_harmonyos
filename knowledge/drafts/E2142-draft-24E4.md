# E2142 — OHOS libc 的 `<mntent.h>` 只有读侧：`addmntent(3)` 是 glibc 扩展，链接期 `undefined symbol`

## 错误特征

编译一路绿灯（clang 只给 warning），到链接才炸：

```
shfsmount.c:215:13: warning: call to undeclared function 'addmntent';
  ISO C99 and later do not support implicit function declarations [-Wimplicit-function-declaration]
ld.lld: error: undefined symbol: addmntent
>>> referenced by shfsmount.c
clang-15: error: linker command failed with exit code 1 (use -v to see invocation)
```

实测复现（设备 clang 15）：

```bash
printf '#include <mntent.h>\n#include <stdio.h>\nint main(void){\n  FILE *f=fopen("/tmp/x","w");\n  struct mntent m; m.mnt_fsname="a"; m.mnt_dir="/b"; m.mnt_type="c"; m.mnt_opts="d"; m.mnt_freq=0; m.mnt_passno=0;\n  return addmntent(f,&m);\n}\n' > "$TMPDIR/m.c"
clang "$TMPDIR/m.c" -o "$TMPDIR/m"      # ld.lld: error: undefined symbol: addmntent
```

## 触发条件

- 构建系统: makefile / autotools / cmake 皆可，只要源码调 mtab 写侧
- 阶段: linking（**不是** compilation —— 这是最容易误判方向的一点）
- 高发族群: 自己维护 `/etc/mtab` 的用户态挂载工具 —— shfs（本条实证）、sshfs/fuse-utils、smbnetfs、mhddfs、curlftpfs、zfs/zpool 用户态栈（E627 的组合签名里也含这条）
- 排查命令: `grep -rn "addmntent"`；或对已建二进制 `nm -u <bin> | grep mntent`

## 根因分析

mtab 读写 API 在 libc 里是**不对称**的。OHOS sysroot 的 `<mntent.h>` 只提供 Unix/POSIX 读侧四个符号，没有任何写侧：

```
$H/mntent.h:11:  #define MOUNTED "/etc/mtab"
$H/mntent.h:32:  FILE *setmntent(const char *, const char *);
$H/mntent.h:33:  int endmntent(FILE *);
$H/mntent.h:34:  struct mntent *getmntent(FILE *);
$H/mntent.h:35:  struct mntent *getmntent_r(FILE *, struct mntent *, char *, int);
```

`addmntent()`（以及 rmmntent 之类）是 **glibc 扩展**，musl 系 libc 根本不实现。注意 `MOUNTED` 宏就定义在这个头文件里（值为 `/etc/mtab`），而 `<sys/param.h>` 只给 `MAXPATHLEN 4096` —— 可读不可写是刻意的 API 面，不是 SDK 装漏了包。

两个放大误判的因素：

1. clang 15 把隐式函数声明默认降为 `-Wimplicit-function-declaration` **warning**，所以错误面出现在 `ld.lld`，容易被读成"少链了某个库"，进而去加 `-lmount` / `-lmnt`。
2. 同一文件里 `setmntent()`/`getmntent()` 都能正常链接，看起来"mtab 相关代码是好的"。

## 解决方案

### 推荐方案（priority 1）：包内补 static 写侧 helper（可上游提交）

mtab(5) 就是六字段单行文本（`fsname dir type opts freq passno`，空格分隔），直接 `fprintf` 写出即可，并保持 `addmntent` 的"出错返回非 0"契约。shfs 0.35 落地形态（`patches/0002-shfsmount-shfsmount.c.patch`、`patches/0003-shfsmount-shfsumount.c.patch`）：

```c
/* addmntent(3) is a GNU libc extension; libc that only ships the read side of
 * <mntent.h> needs the mtab line written directly.  Same 1-on-error contract.
 */
static int
shfs_addmntent(FILE *f, struct mntent *m)
{
        return fprintf(f, "%s %s %s %s %d %d\n", m->mnt_fsname, m->mnt_dir,
                       m->mnt_type, m->mnt_opts, m->mnt_freq, m->mnt_passno) < 0;
}
```

调用点只换函数名。**注意同步改判定**：上游是 `if (addmntent(mtab, &ment) == 1)`，helper 用 `< 0` 返回，须改成布尔判非 0（shfsmount.c 就是 `if (shfs_addmntent(mtab, &ment))`）；shfsumount.c 的 `addmntent(new_mtab, ment)` 本来就忽略返回值，替换时保持不变即可。

无平台宏、遵循上游风格（P005），改动天然可向上游提交；补丁用 `refresh-patch --auto shfs 0.35` 生成，带完整元数据 header（P011）。

### 回退方案（priority 2）：平台守卫下跳过 mtab 记账

若该软件写 mtab 仅为记账，且平台本来就没有可用的 `mount(2)`（OHOS 挂载 syscall 不可用，SIGSYS 边界见 `knowledge/drafts/DRAFT-mhddfs-0.1.39.0-ohos-fuse-consumer-mount-boundary.kv` 与 syscall 能力矩阵草稿），可用 `#ifdef __OHOS__` 守卫跳过 mtab 更新 —— 但**必须有实质逻辑**（跳过写入并保留原有错误提示），这是功能降级而非伪造成功（P013），需在 notes.md 与 PR 说明里写清取舍。

### 禁止做法

- ❌ 加 `-lmount` / `-lmnt` 之类的 `LDFLAGS`：符号在 libc 里根本不存在，没有任何库能提供 `addmntent`，只会把错误换成 "library not found"（R44：CI 失败先 diagnose 再动手）。
- ❌ `#ifdef __OHOS__ ... return 0; #endif` 空壳 stub：违反 R6（平台宏必须承载实质逻辑），把"mtab 没写成"伪装成成功，测试发现不了，PR 复盘时按欺骗性实现处理。
