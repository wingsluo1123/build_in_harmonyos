# E2143 — Conan `Copying sources to build folder` 报 `[Errno 13] Permission denied`，路径落在一个符号链接上

## 错误特征

`conan create` / `conan install` 在**进入 `build()` 之前**就失败，日志形如：

```
shfs/0.35: Copying sources to build folder
ERROR: shfs/0.35: [Errno 13] Permission denied: '/…/debian/changelog'
Error copying sources to build folder
```

失败路径指向一个符号链接成员；没有任何编译器输出。

实测最小复现（设备 Python 3.12.8 + clang 15）：

```bash
python3 -c "
import os,shutil
d=os.environ['TMPDIR']+'/slp'; shutil.rmtree(d,ignore_errors=True)
os.makedirs(d+'/src/debian'); open(d+'/src/Changelog','w').write('x')
os.symlink('../Changelog', d+'/src/debian/changelog')
shutil.copytree(d+'/src', d+'/bld', symlinks=True)
"
# shutil.Error: [('/…/src/debian/changelog', '/…/bld/debian/changelog', '[Errno 13] Permission denied')]
```

## 触发条件

- 构建系统: 无关（纯 Conan 侧行为）
- 阶段: installation（source→build 复制），**早于 configure/make**
- 前提: 源码归档内**含符号链接成员**。shfs-0.35.tar.gz 里唯一一个：

```
'shfs-0.35/debian/changelog'  type=b'2'(LNK)  mode=0o120777  linkname='../Changelog'
```

- 高发面: SourceForge/GitHub 老 tarball（Debian 打包目录的 `debian/changelog` 软链、`docs/` 软链、autotools 的 `config.guess/sub` 软链、`tests/` 软链）

## 根因分析

三步链条，每一步都可单独验证：

1. **Conan 默认复制源码树**。`no_copy_source` 未声明 ⇒ `conan/internal/graph/installer.py:87` 执行
   `shutil.copytree(source_folder, build_folder, symlinks=True)`。
2. **CPython 3.12 的 `_copytree` 对符号链接成员做两次操作**（`shutil.py:522-523`）：

   ```python
   os.symlink(linkto, dstname)
   copystat(srcobj, dstname, follow_symlinks=not symlinks)   # symlinks=True ⇒ follow_symlinks=False
   ```

3. **`follow_symlinks=False` 的 copystat 走 lchmod/lutimes，鸿蒙存储文件系统不支持修改符号链接自身**。分步实测：

   | 操作 | 结果 |
   |---|---|
   | `os.symlink('../Changelog', …)` | OK（建链本身可用） |
   | `os.readlink(…)` | OK |
   | `shutil.copystat(…, follow_symlinks=False)` | **PermissionError(13, 'Permission denied')** |
   | `shutil.copytree(…, symlinks=True)` | **失败**（同一路径、同一 errno） |
   | `shutil.copytree(…, symlinks=False)` | OK（走内容复制，不碰链接属性） |

   ⇒ 坏的不是"链接创建"，也不是"目录权限不足"，而是复制链接后的那次 **lchmod**。errno 文案 "Permission denied" 极易误导成后者。

补充一个容易看错的细节：`untargz(..., strip_root=True)` 只在 `member.linkpath` 以根目录名开头时改写链接目标
（`conan/tools/files/files.py:483-486`）。`../Changelog` 不以 `shfs-0.35` 开头，所以按原样建链，链接本身指向是对的 —— 不要去"修链接目标"。

**同族症状（同一个 lchmod/lutimes 缺口的另一张脸）**：绕过 conan 直接 `tar xf shfs-0.35.tar.gz` 也会失败：

```
tar: settime 1086095779 shfs-0.35/debian/changelog: Permission denied
tar: had errors
```

即"换用裸 tar 解包"不是出路（除非显式关掉时间戳还原）。本机 toybox 0.8.12 实测：
`tar xf shfs-0.35.tar.gz -m`（`-m` = Ignore mtime，必须跟在 `xf` 之后，写在前面会被当成
`-txc` 报错）零错误解完；不带 `-m` 则稳定复现上面两行报错。两组实验的解包目标都在应用私有沙箱内
（`$TMPDIR` 与 conan 缓存同属 `/data/storage/el2/base/...` 这层 HMDFS 挂载），与配方实际失败时的
文件系统一致，不存在"换个工作目录就好了"的余地。
本次实测里 `finish` 的第 2.5 步（`scripts/ohc/finish.py:167 step25_g0_clean_verify` →
`scripts/ohc/clean_verify.py:87` 直接 `subprocess tar xf`）走的就是不带 `-m` 的裸 tar 路径，因此它报
`tar: had errors`，而同一次 `finish` 里 conan 的 G1–G4 全绿——两者不矛盾，别把这个 tar 报错当成
配方失败。注意命名撞车：`clean_verify` 自称的 "G0"（`finish` 第 2.5 步，解包+打补丁+configure 冒烟）、
`conan-verify-report.md` 里的 "G0 预构建风险评估"（知识图谱预查询）、以及 CI 侧的 "G0e 根目录白名单检查"
（`ci/conan/build_and_test.sh:162`）是**三个互不相干的东西**，本段说的是第一个。

## 解决方案

### 推荐方案（priority 1）：解压阶段排除含软链的子树

让 `source_folder` 天然没有符号链接成员。conan 2.29 里有 `excludes` 形参的是解包类 API
（`inspect.signature` 实测：`get(..., excludes=None)`、`unzip(..., excludes=None)`；
`download()` 没有该形参，它只取文件不解包），且
`untargz` 用 `fnmatch` 对**未 strip_root 的原始成员名**做匹配（`files.py:466-467`），所以模式要带根目录前缀：

```python
def source(self):
    get(self, **self.conan_data["sources"], strip_root=True,
        excludes=["*/debian/*"])
```

shfs 0.35 采用此法（`archives/s/shfs/0.35/conanfile.py:45-50`）：既去掉唯一符号链接成员，又顺手丢掉 Debian 打包噪音，`source_folder` 与复制耗时同时下降。

### 回退方案（priority 2）：`no_copy_source = True`

直接跳过复制阶段（Conan 在 `source_folder` 原地构建）。**适用条件严格**：`build()` 及其调用的构建系统绝不能往源码树写东西（in-tree configure、生成 `config.h`、`.o` 落在源码目录都不行），否则同一 `source_folder` 会被多 profile/多版本并发污染。选它必须先确认中间产物全部落在 `build_folder`。

### 回退方案（priority 3）：把必要成员从软链换成普通文件

若被排除的子树确实要参与构建，就针对那一个成员落地一份等价文本副本（把 `readlink` 目标内容复制成普通文件）。改动面比整树排除大，作为最后手段。

### 禁止做法

- ❌ `chmod -R` / `os.chmod(build_folder, …)`：errno 来自 lchmod 语义不支持，不是目录权限不足；改普通文件权限碰不到链接。失败点纹丝不动，还会污染补丁校验哈希（R43 调参螺旋）。
- ❌ 在 `build()` 里 `rm -rf debian`：失败发生在 `installer._copy_sources()`，早于 `build()`/`configure` 的任何一行代码，删不到 `source_folder` 里那份链接 —— 典型症状是"改了但报错一模一样"。
- ❌ `unzip(..., keep_permissions=True)`：只把归档 mode 落到普通文件上，与链接的 lchmod 失败无关；在 HMDFS 上（权限被固定为 660）只会引入新的权限差异。

## 验证

```bash
conan create archives/s/shfs/0.35 --profile=<ohos-arm64>        # 越过 "Copying sources to build folder"
ls -l <source_folder>/debian                                     # 期望不存在（已排除）
# 回归确认：源码树内容对构建无影响 —— make 目标与 test_package 全绿
```
