# 必需 checkpoint 结构的 EOF 失败传播与 fscanf/header 消费合同

来源：solvate 官方 Debian 包装1.0，原程序banner1.0.1，任务10798/orrkri。本文是知识草稿，未获官方接受或计分。许可仍为源包原no_fee声明，不能改称MIT/BSD或OSI许可。

## 问题与最小复现

程序真实 `-ug` / `-ub` 路径读取当前目录的 `gaussians.lis` / `boundary.lis`。在私有cwd放原包bpti.pdb，创建空checkpoint或没有LF的截断首header，运行 `solvate -ug bpti result` 或 `solvate -ub bpti result`。原版到达reader后持续等待不存在的LF；Windows本次四场景均2秒超时，取证测试kill，未成功返回。没有声称已测CPU占用，也不是OHOS专属缺陷。

## 根因与修复

原helper是 `fgetc(fp); for (; fgetc(fp)!='\n';) ;`，返回值没有存入char。EOF本来就是int，缺的是EOF出口；将变量改int不能补这个分支。两个读取位置都要在EOF/读错时沿现有fatal-error非0退出。

它的消费合同也不是普通skip-line：首次调用跳过首header；在fscanf后，先丢弃遗留LF，再跳过下一header。直接改成遇第一个LF就返回，会留下header供下次fscanf读取。修复保留原两个阶段，只增加必需结构的失败出口。两个reader共42个float和2个int转换检查成功字段数==1，避免缺字段沿用先前fdummy；不改数值格式、结构或物理计算，不扩展为全文件严格解析器。

最后一个所需数值成功读取后即使立刻EOF也应接受，不能把任何EOF都当错。正常生成的两个checkpoint去掉末尾LF后，两个resume入口均成功，是这一边界的反例。

## 可执行验证与输入输出

```sh
python3 archives/s/solvate/1.0/test_package/verify_checkpoint.py \
  --binary <actual-package>/bin/solvate --data <actual-package>/share/solvate \
  --output <new-private-dir> --environment OHOS-native
```

binary必须是本次真实包；data为同原包四个PDB/PSF原输入；output须不存在且可写。输出每场景stdout/stderr、摘要和result.json，错误输入要求非0、fatal消息、无成功标记且无result.pdb；合法流程要求0、成功标记、真实ATOM/TIP3且无NaN。

## 近邻差异与适用边界

已复用2026-10-16正式索引、草稿和三篇正文的有限筛选证据：kevlar getc-char-eof-loop是plain-char吞掉EOF，且明确排除已用int的循环；本项没有char存储。skewer eof-negative-return-discarded-block是调用侧丢弃尾批记录，本项无负返回值批处理。arena-allocator newline-eof是编译告警，不是运行期checkpoint结构读取。新增点是必需结构EOF失败传播与fscanf遗留LF/header消费合同；不宣称全球原创。

适用其他手写科学计算restart/checkpoint reader前，先核其真实消费合同和哪些结构为必需。普通逐行文本、允许无换行末行、char签名问题及流式reader正常EOF不直接套用。本修复不提供全格式校验、范围/NaN完整审计或任意损坏文件的恢复保证。
