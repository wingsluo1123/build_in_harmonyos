# E429 — stub 机制库（Tk 系）消费者测试必须先绑定宿主 stub 表：未绑定即调 API 直接 SIGSEGV

## 错误特征

```
$ ./consumer_test
[1/5] 头文件自包含 ................. OK
[2/5] Tcl 初始化 + expr 2+3 ........ OK
[3/5] Tk_Init ...................... 无显示 → 预期失败(rc=1)
[4/5] Tk_GetReliefFromObj ......... Segmentation fault (Signal 11)
```

崩溃点落在**被测库 API 内部**（Tk 库自身函数），不是消费者代码，退栈常被误读为
「链接冲突」「库损坏」或「ABI 不匹配」。判定特征：

- 崩溃为 SIGSEGV，且仅发生在**调用库公共 API**的那一条，宿主初始化之前一切正常；
- 同一二进制在**有宿主初始化入口被调用过**之后（哪怕该入口本身失败）就不再崩溃；
- `nm -D` 能查到 API 符号，但看不到 stub 表符号（表是数据符号，由宿主填入）。

## 触发条件

- 构建系统: 任意（Autotools / CMake / 手写消费者）；本条目实测于 Autotools 产出的 tk 8.6.16
- 阶段: testing（conan test_package 的 consumer test）/ runtime
- 工具链: OHOS clang 15（aarch64-linux-ohos），其余平台同构

## 根因分析

库以 `USE_TCL_STUBS` 语义编译（Tk 标准做法）：库内**所有** Tcl API 调用都经
`tclStubsPtr` 间接表跳转，而不是直接调用 `libtcl8.6.so` 的符号。这张表**只由宿主
初始化入口绑定**——`Tk_Init()` 内部会走 `Tcl_InitStubs()` 把表填好。

消费者若只 `-ltk8.6 -ltcl8.6` 就调 `Tk_GetReliefFromObj()`，此时表仍为 NULL，
第一次解引用即空指针崩溃：

- 崩溃位置在库内部 → 看起来像库的 bug，实际是调用时序问题；
- 无显示环境下 `Tk_Init()` 必然返回失败（`no display name and no $DISPLAY`），
  容易被误判为「环境不支持、不能测」而跳过；
- 但 `Tk_Init()` 在**检查 display 之前**就已经完成了 stub 表绑定——「调用它、
  容忍其失败、再调 API」是完全可用的路径。

## 解决方案

### 推荐方案（rec_approach: host-init-before-api-call）

1. 消费者先调宿主初始化入口并**接受其环境性失败**：

   ```c
   int rc = Tk_Init(interp);           /* 无显示 → 返回错误（rc=1） */
   /* 不要据此 return；此时 stub 表已绑定 */
   Tcl_Obj *o;
   Tcl_NewStringObj("sunken", -1);
   int relief = Tk_GetReliefFromObj(interp, o);   /* 不再崩溃 */
   ```

2. 把失败的**原因**钉在 display 上（读解释器的错误消息断言包含
   `display`/`DISPLAY`），使测试结论明确指向平台限制而不是库故障；
3. 断言 API 的真实返回值（如 `Tk_GetReliefFromObj(interp, "sunken") == TK_RELIEF_SUNKEN`），
   避免只断言「没有崩溃」的弱测试。

### 回退方案（fallback_approach: dlopen-dlsym-symbol-contract）

无宿主二进制可调、或不想引入宿主初始化时：

- `dlopen` 包内 `.so`，`dlsym` 校验**真实导出**的公共符号（如 `Tk_Init`、`Tk_MainEx`）；
- 再用包内 CLI（`wish8.6`）以脚本文件参数形式跑一次端到端探针；
- 断言失败原因仅为缺 display。

### 禁止做法

- ❌ `dlsym(handle, "Tk_InitStubs")`：该符号由**静态** stub 库 `libtkstub8.6.a`
  提供，不在 `.so` 动态符号表，`dlsym` 恒 NULL → 消费者测试以假失败收场，
  掩盖真实适配问题（实测：必须用 `-ltkstub8.6` 静态链接才拿得到）；
- ❌ 崩溃前用 `printf(...\n")` 后接管道：stdout 块缓冲会把最后几行吞掉，
  崩溃点被误判到更早的位置，浪费排查轮次（复现脚本日志一律重定向到文件）。

## 适用边界 / 反例

- **适用**：Tk 家族及一切经宿主 stub 表导出 API 的库——Tk 8.6/9、Tcl 扩展
  （expect/itcl/tdbc 等 stubs 风格扩展）、Tk 扩展；消费者测试/Runtime 阶段。
- **反例**：直接链接 tcl 且未开 stubs 的库（直连符号，无此问题）；
  消费者**从不调用**库 API（纯 `dlopen` 探测的场景，不触发）；
  真实运行在有 display 的环境中且走了完整宿主初始化（表已绑，不触发）。

## 验证证据

tk 8.6.16（OHOS PC，aarch64-linux-ohos，clang 15）实测：

- 未绑定 stub 表即调 `Tk_GetReliefFromObj` → `Signal 11`，rc=139；
- 先调 `Tk_Init`（容忍其因无显示失败，rc=1）再调同一 API → rc=0，
  断言 `Tk_RELIEF_SUNKEN == 5` 通过；
- `conan create` 的 test_package 五组契约全过（L1_RESULT=pass，1/1，100%），
  见 `archives/t/tk/8.6.16/reports/test-report.md`；
- 上限说明：真实渲染/GUI 路径需 X display，平台不可实测（E530），
  见 `archives/t/tk/8.6.16/reports/r51-upstream-tests.txt`。
