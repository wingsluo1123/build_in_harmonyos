# 非阻塞 TLS ready 转换后未重新调度应用发送队列：握手成功但服务端首帧永久滞留

> 状态：DRAFT（路径 B 知识库扩展候选）｜来源：umurmur/0.3.1 HarmonyOS PC 适配｜日期：2026-10-12
> 候选编号：E429｜机器可读层：`E429-draft-4084.kv`

## 结论

事件驱动服务器的 TLS 握手成功，不等于握手前排队的应用消息会自动进入 TLS 写路径。
如果应用允许在 TLS 未 ready 时排队消息，而事件掩码只观察 TLS 的
`WANT_READ/WANT_WRITE` 和已经序列化的发送缓冲，那么 `ready: false → true` 必须同时
触发一次应用发送调度。只更新 ready 布尔值会让 server-first 的首帧永久滞留。

正确修复是在 ready 转换点重新检查并排空队列；把“应用队列非空”无条件映射为
握手前 `POLLOUT` 不仅不能保证发送，还会在可写 socket 上形成忙轮询。

## 稳定症状与机械触发条件

典型症状不是编译错误，而是以下组合：

```text
TLS handshake succeeds
server-first Version/greeting/banner is not received
client has not sent application data
```

源码同时满足以下四项即可机械判定为高风险：

1. 接受连接后、握手完成前允许 `enqueue(application_message)`；
2. 未 ready 时发送函数把消息放入应用队列；
3. `poll/epoll` 写掩码只观察序列化发送缓冲或 TLS `WANT_WRITE`，不观察应用队列；
4. 握手完成路径只更新 ready 状态，没有 `flush/schedule/wakeup` 应用发送器。

可先做静态定位：

```bash
rg -n 'SSL_accept|SSL_do_handshake|SSL_ERROR_WANT_(READ|WRITE)|SSLready|POLLOUT|send.*queue|txMsgQueue' src
```

这不是 HarmonyOS 专有 TLS 语义；HarmonyOS PC 真机迁移使该潜伏状态机缺口得到实际
复现。可复用价值在于对任何非阻塞 TLS + 分层发送队列实现建立 ready 转换契约。

## 根因

uMurmur 的连接建立顺序如下：

```text
Client_add
  ├─ 创建非阻塞 SSL，SSLready=false
  ├─ 创建 Version 消息
  └─ Client_send_message → 因 !SSLready 加入 txMsgQueue

Client_getfds
  └─ 仅 txsize>0 或 readBlockedOnWrite 时订阅 POLLOUT

Client_read
  └─ SSLi_nonblockaccept → SSLready=true
       （上游没有重新检查 txMsgQueue）
```

队列和事件掩码属于两个不同调度层。握手完成消除了“不能发送”的前置条件，却没有
制造新事件把队首消息变成 `txsize>0`。客户端若按照协议等待服务端 `Version` 后才发
Authenticate，双方就会永久互等。

## 正确修复

将队列推进收敛为一个具有严格前置条件的函数：

```c
static int flush_queued(client_t *c)
{
    if (!c->tls_ready || c->tx_size != 0 || queue_empty(&c->send_queue))
        return 0;
    return send_next_message(c);
}
```

只在两个位置调用：

1. 非阻塞握手刚刚把 ready 从 false 转为 true 后；
2. 当前 TLS 写缓冲完整发送后。

如果架构要求 TLS 层和应用层隔离，可在 ready 回调投递一个可去重的 one-shot
应用写任务，语义仍是“状态转换触发一次重新评估”，而不是“队列非空就永久监听
`POLLOUT`”。

## 为什么直觉修复错误

在握手前把应用队列非空直接映射为 `POLLOUT/EPOLLOUT` 有两处错误：

- TCP socket 通常立即可写，即使客户端尚未发送 ClientHello；水平触发循环会不断唤醒，
  本次真机重跑 1 秒测得 105 CPU ticks；
- 原写回调若要求 ready 或只处理既有序列化缓冲，收到写事件仍不会从应用队列取消息。

同理，仅做“TLS handshake succeeded”冒烟也是假绿，因为它没有观察应用队列是否在
状态转换后得到调度。

## 适用与不适用边界

适用于 OpenSSL 或同类非阻塞 TLS、握手与应用写队列分层、且协议由服务端先发首帧的
守护进程，例如 greeting/banner/version 型协议。

不适用于：

- 同步阻塞握手；
- 握手前禁止排队应用消息；
- ready 回调已经显式唤醒应用发送器；
- 仅因字符设备不报告 `POLLOUT` 而挂起的情形；
- 普通端口、证书、ELF 签名或 `dlopen` 问题。
