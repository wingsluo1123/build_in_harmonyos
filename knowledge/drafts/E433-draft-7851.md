# E433 — 受限 CI worker 上 fork EAGAIN 使 autotools 探针静默回落为 no（伪装成「缺依赖」）

- **条目 ID**: E433
- **分类**: ci, autotools-config, environment, detection, diagnostics
- **严重性**: 2（🟡 间歇性阻塞）
- **来源事件**: miredo 1.2.6 适配，PR #15840，CI 构建 #93375（worker CI-035，SHA `e39b052a`）

## 1. 现象

CI 在 `autotools.configure()` 处失败，日志末行为：

```
configure: error: Required tdestroy() or Judy dynamic arrays.
```

CI 侧归类为「编译失败 / Autotools configure 失败」，并给出「检查缺少的库或头文件 / 添加
`CONFIG_SHELL=/bin/zsh` / patch configure 脚本」这类**指向配方与源码**的修复建议。
同一时间日志里散布着 40+ 条：

```
.../b/configure: fork: retry: Resource temporarily unavailable
.../b/configure: fork: Resource temporarily unavailable
```

## 2. 判别依据（为什么是环境而非配方）

autoconf 的每个探针都是「fork 一个子 shell 去编译/运行测试程序，看退出码」。
**configure 无法区分「子进程 fork 失败」与「特性确实不存在」——两者都让结果为 no。**
因此 fork 压力下会出现一批在物理上不可能成立的探针结果，这些才是判据：

| 日志行 | 为什么不可能 |
|--------|--------------|
| `checking for sys/types.h... yes` 之后紧接 `sys/stat.h... no`、`stdlib.h... no`、`string.h... no`、`stdint.h... no`、`unistd.h... no`、`dlfcn.h... no` | 标准头不可能缺失；扫描在某个时刻开始全盘回落 |
| `checking whether byte ordering is bigendian... yes` | aarch64 是小端 |
| `checking if /data/service/hnp/bin/clang accepts -Wall... no` | clang 必然接受 `-Wall` |
| `checking for Judy.h... no`（配方已经过 `AutotoolsDeps` 注入 `-I<judy>/include`） | 注入路径正确时不可能为 no |
| `checking for tdestroy... no` | 必需回退项也被误判 |

上游项目真正要求的两个可替代项（`tdestroy()` **或** Judy 动态数组）**同时**被误判为缺失，
于是报出看起来像「依赖没装」的硬错误。

**对照证据（同 SHA、不同 worker，结果相反）**：

| 构建 | Worker | SHA | 结果 |
|------|--------|-----|------|
| #91888 | CI-035 | `501fc22a` | ✅ 通过（L0/L1 + 上游 `make check` + test_package） |
| #91926 | CI-021 | `e39b052a` | ✅ 通过（同上） |
| #93375 | CI-035 | `e39b052a` | ❌ `configure` fork EAGAIN |

同一 `e39b052a` 在 CI-021 全绿、在 CI-035 失败；失败点集中在 `fork` 而非编译/链接
→ worker 资源竞争（多个 CI job 共用 `uid=100`，进程数/内存吃紧时 `fork()` 返回 EAGAIN）。

## 3. 诊断步骤

```bash
# 1) 统计 fork 失败次数（>0 即高度可疑）
grep -c "fork: .*Resource temporarily unavailable" <ci.log>

# 2) 找「不可能成立的探针结果」——标准头批量 no / 字节序判反 / -Wall 不接受
grep -nE "checking for (sys/stat|stdlib|string|stdint|unistd|dlfcn)\.h\.\.\. no" <ci.log>
grep -nE "byte ordering is bigendian\.\.\. yes|accepts -Wall\.\.\. no" <ci.log>

# 3) 对照：同一 SHA 换 worker 重跑（PR 上评论 /rebuild），或与本地 W3 复验结果对比
```

判据小结：**同一 commit 在不同 worker 上结果相反 + 日志中存在物理上不可能成立的探针结果
+ 失败点是 fork 而非编译/链接** ⇒ 环境性，不是配方缺陷。

## 4. 推荐方案（priority 1）

**先判环境、别改配方。** 确认为 worker 资源竞争后：

1. 配方侧只做**降低 fork 压力**的最小加固，不碰构建语义：
   - 用自带预生成 `configure`/`Makefile.in` 的官方发布包，避免 `autoreconf` 自举链；
   - `autotools.make(args=["-j1"])` 串行化 make；
   - 不在 `build()` 与 `test_package` 里各起一个重型服务（进程/pid 限额紧的 worker 必挂）。
2. 在 PR 上重触发 `/rebuild`，让它落到空闲 worker（CI 为评论触发型）：

   ```bash
   python3 scripts/ohc-run.py submit <name> <ver> --resume   # 内置评论 /rebuild + 轮询
   ```
3. 把失败日志与「同 SHA / 不同 worker」对照写进该包 `notes.md`，供评审识别为环境性失败。

## 5. 回退方案（priority 2）

换 worker 仍间歇失败时：

- 进一步压低 configure 期间并发（配方内不做并行探针、make 保持 `-j1`）；
- 对**仅匹配 EAGAIN 特征**（`Resource temporarily unavailable` / `can't fork` / `cannot fork` /
  `fork: retry`）的失败做退避重试；**其他错误首次即失败并原样输出日志**，禁止把真错误掩盖成 infra；
- 仍不收敛则按 R41/R42 停损上报，不无限重试。

## 6. 禁止策略

- ❌ 把环境失败当配方缺陷，删改正常构建逻辑（删探针、硬编码「依赖已存在」的 `config.h`、
  去掉必要的 configure 参数）。根因在 worker 资源竞争，探针回落只是症状；改配方会把环境问题
  固化成错误产物，并永久掩盖真实缺失项。
- ❌ 把失败改成通过 / 跳过测试（伪造 `.ci-result.json`、删上游测试）以绕过间歇失败（R9/R42）。

## 7. 与既有知识的关系

- 与 `DRAFT-11327`（受限 CI worker 上的间歇性 `can't fork`：autoreconf 自举链 fork 失败）
  **同源**——同属「worker 资源竞争导致 fork EAGAIN」。
- 差别：DRAFT-11327 覆盖的是「高 fork 开销的**自举**链（autoreconf/aclocal/automake）失败」，
  签名是 `can't fork - try again` / `Out of memory`；本条目覆盖的是**不跑自举、直接执行
  预生成 `./configure`** 也会命中的形态，签名是 `fork: retry: Resource temporarily unavailable`
  加上「标准头批量 no / 字节序判反」的探针回落假象，最终伪装成「缺依赖」的硬错误。

## 8. 同一根因的两种表现形态（miredo 1.2.6 实测两次命中）

fork 资源不足在同一个包上可以表现为**落在不同位置**的两种假象，判别时不要被位置带偏：

**形态 A — 探针静默回落（`#93375`，worker CI-035）**
fork 失败落在 `configure` 中段，探针全部回落为 no，最终报出形似缺依赖的硬错误：

```
checking for sys/types.h... yes
checking for sys/stat.h... no        ← 标准头不可能缺失
checking for stdlib.h... no / string.h... no / unistd.h... no / dlfcn.h... no
checking whether byte ordering is bigendian... yes   ← aarch64 是小端
checking if .../clang accepts -Wall... no            ← clang 必然接受
checking for Judy.h... no / checking for tdestroy... no
configure: error: Required tdestroy() or Judy dynamic arrays.
```
伴生 40+ 条 `.../b/configure: fork: retry: Resource temporarily unavailable`。

**形态 B — 环境脚本阶段直接 fork 失败（`#93954`，worker CI-003）**
fork 失败发生在 `configure` **启动之前**，shell 连 conan 注入的环境脚本都 fork 不出来，
`configure` 根本没跑到探测：

```
miredo/1.2.6: RUN: ".../b/configure" --enable-shared ... --enable-static --enable-shared
/system/bin/sh: .../b/build-release/conan/conanautotoolstoolchain.sh[13]: can't fork - try again
miredo/1.2.6: ERROR: Error in build() method, line 148  autotools.configure()
```

同批日志中 **CI 自身的检查脚本也 fork 失败**
（`ci/scripts/knowledge_check.sh: fork: retry: Resource temporarily unavailable`），
且该次 `git-clone` 耗时 **3m03s**（正常秒级）——「同批其它脚本也 fork 失败 + 非编译步骤异常变慢」
是判定资源饥饿的旁证，比单看失败位置可靠。

**两次命中的共同判据**：失败点落在 `fork` 而非编译/链接；同一份代码在其它 worker 上通过。
miredo 1.2.6 的完整对照：**通过 3 次**（CI-035 `#91888`、CI-021 `#91926`、CI-011 `#93917`）、
**失败 2 次**（CI-035 `#93375`、CI-003 `#93954`），两次失败之间未改动任何配方文件。
