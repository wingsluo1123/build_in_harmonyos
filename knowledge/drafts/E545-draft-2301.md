# E545 — KF6/Qt6 模块矩阵缺口：先选仓库真能交付的版本集，再动手适配

> 草稿（draft），配对结构化条目：`knowledge/drafts/E545-draft-2301.kv`
> 样例库：`archives/j/juk/26.04.0`（KDE Gear 26.04 音乐播放器）

## 1. 触发场景

一个 KDE Gear / KF6 消费方在**首次 configure 就硬停**，报错形如：

| 报错特征 | 真实含义 |
|---|---|
| `ERROR: Version conflict: Conflict between qtbase/6.11.1.1 and qtbase/6.11.1` | 需要的两个 KF6 模块分别住在**互斥的两个 qtbase 生态**里 |
| `Could not find a configuration file for package "KF6xxx" that is compatible with requested version "6.x"` | 上游 `KF6_MIN_VERSION` 版本闸拒了仓库能给的唯一版本 |
| `KF6KIOWidgetsConfig.cmake does not exist`（配方钉 `kio/6.26.0`） | 该 kio revision 是 `KIOCORE_ONLY`，不含 widgets |
| `Qt6::DBus` not found | 普通 `qtbase` 的 `FEATURE_dbus=OFF`，需 `qtbase-sql-dbus` |
| `find_package(Taglib)` 找不到 / 目标 `ZLIB::ZLIB` not found | conan 包导出的目标名与上游要求不一致 |
| `KX11Extras` 头文件缺失 | 源码无条件包含 X11 专用头 |
| `DocBook 4.5` DTD 缺失（`kdoctools` 文档链） | OHOS 的 kdoctools 不带 DocBook DTD |
| `relocation R_AARCH64_... can not be used when making a shared object`（静态 `libz.a`） | 静态 zlib 非 PIC |

两个事实让这一类特别贵：**模块按版本覆盖不均**（6.26 有的模块 6.18 没有，反之亦然），且**两个 qtbase 生态不能同图**。逐包试错的代价是数小时构建后才发现断链。

## 2. 根因

1. **双生态互斥**：`qtbase/6.11.1`（无 DBus，`kconfig/kcoreaddons/ki18n` 6.26 线等居此）与 `qtbase/6.11.1.1`（`kdbusaddons` 6.29 线居此）不能出现在同一张依赖图；`Qt6::DBus` 只能由独立包名 `qtbase-sql-dbus/6.11.1` 提供。
2. **模块级覆盖缺口**：`kio` 只有 6.14.0（全量，含 KIOWidgets/KIOFileWidgets）与 6.26.0（`KIOCORE_ONLY`）；`kdbusaddons/kjobwidgets/kconfigwidgets` 无 6.26 构建；`kdoctools` 仅 6.19。于是"统一钉最新"必然失败，必须**按模块选各自可用的版本，且落在同一生态**。
3. **上游版本闸**：`find_package(KF6 <KF6_MIN_VERSION>)` 的 ConfigVersion 检查会拒掉生态内可用的较低版本（`PACKAGE_VERSION < PACKAGE_FIND_VERSION` → NOT COMPATIBLE）。

## 3. 适用范围

* **适用**：OHOS PC 上任何 CMake 里同时要 Qt6 与 KDE Frameworks 6 组件的 C/C++ 项目（KDE Gear 应用、Kirigami 应用、KF6 库自身）。
* **不适用**：纯 Qt6 无 KF6（无模块矩阵）、KF5（模块集合不同）。

## 4. 处理策略（四类，juk 26.04.0 全部实测）

1. **版本钉选 / 生态选择**：先枚举组件集，再读实时矩阵，选**一个**生态后逐模块钉"该生态内最新可用 revision"。juk：`kio/6.14.0`（要 widgets）、6.18 线共享基底、`kwindowsystem/6.26.0`、`zlib/1.3.2`（PIC）。
2. **补丁模板**：上游构建文件/源码假定 OHOS 不成立时改源码而非环境。juk：`patches/0001` 裁 `kdoctools` 文档链（DocBook DTD 缺）；`patches/0002` 用 `__has_include` 守卫 X11 专用 `KX11Extras` 的头与调用点。
3. **`generate()` 内 wrapper/alias**：conan 包已存在但目标名与上游不符时**不改上游 CMake**。juk：`Taglib::Taglib` → `TagLib::tag` 别名 + `ZLIB::ZLIB` UNKNOWN IMPORTED 目标（kfilemetadata 6.28.0 范式）。
4. **`env_unsupported`（正确地放弃）**：矩阵根本满足不了、且依赖发布顺序也救不回来时（如消费方硬依赖 6.19+ 新 API，而该 API 只在第二生态里）→ 先按拓扑序发布缺失模块再迁移整体生态，在此之前对消费方报 `env_unsupported`，**不要**留"半个钉版"导致图里两个 qtbase。

## 5. 限制

* 检测脚本读的是**配方/源码**，不是二进制：版本在仓库里不等于 binary 已上传；判定必须 `conan download <pkg>/<ver> -r=ohpcd --only-recipe`（R35），**禁止**用 `conan list` 判 binary 是否存在。
* 仓库矩阵会变，配方里的钉版必须现场重读，不得照抄文档里的数字。
* 检测脚本面向开发机/CI（bash + conan）；OHOS 无 `/bin/sh`，刻意不做设备侧脚本（R5）。
* 检测通过 ≠ 保证成功，只排除本文记录的错误签名族。

## 6. 复现脚本

```bash
# 源码特征 + 仓库矩阵（发现风险项 exit 1）
archives/j/juk/26.04.0/reports/kf6-matrix-gate-check.sh <src-dir>

# 对已有构建日志做错误签名归类
archives/j/juk/26.04.0/reports/kf6-matrix-gate-check.sh --scan-log <conan-create.log>

# 图级复核
conan graph info <recipe-dir> -pr:h ohos-aarch64 -pr:b default 2>&1 \
  | grep -E "Version conflict|Missing binary"

# 样例树自证（源码 → 绿包）
cd archives/j/juk/26.04.0 && conan create . --build=missing -pr:h ohos-aarch64 -pr:b default
```

配套材料：`archives/j/juk/26.04.0/reports/kf6-matrix-gate-check.md`（四件套 README + 关/开双向验证表）。

## 7. 证据（juk 26.04.0 关/开双向）

| 触发点 | 关（实测失败） | 开（修复后） |
|---|---|---|
| DocTools 文档链 | `po-uk-docs-juk-index-cache-bz2` 目标失败：DocBook 4.5 DTD 缺失 | `patches/0001` → configure 通过 |
| X11 `KX11Extras` | `systemtray.cpp` 编译失败（头缺失） | `patches/0002`（`__has_include`）→ 编译通过 |
| `Taglib::Taglib` / `ZLIB::ZLIB` | `find_package(Taglib)` 目标缺失、`ZLIB::ZLIB` 未定义 | `generate()` wrapper → configure 通过 |
| 静态 `zlib/1.3.1` | `relocation R_AARCH64_... can not be used when making a shared object` | `zlib/1.3.2`（PIC）→ 链接通过 |
| `kio/6.26.0` | 构建里没有 `KIOWidgets`/`KIOFileWidgets` | `kio/6.14.0` → `DT_NEEDED` 含 `libKF6KIOWidgets.so`（`test_package` 断言） |
| 制品仓二进制的构建机 `DT_NEEDED` 绝对路径（E537） | `juk --version` → `Error loading shared library ...`（exit 127） | 物化绝对路径 + link-farm CWD → `juk --version` 正常输出 |

最终态：`conan create` 全绿，`test_package` 实际执行 `bin/juk --version` 并断言 `DT_NEEDED`；上游 `tagguessertest` 1/1 Passed。
