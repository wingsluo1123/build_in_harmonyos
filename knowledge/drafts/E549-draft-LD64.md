# 有界线程池的全员集合测试必须绑定实际容量

## 场景与根因

常规并发互斥测试往往让每个任务先等待“所有 N 个任务已进入”，再执行
读写逻辑。如果这些任务在容量 C 的线程池上运行且 N>C，最先进入的 C 个
任务会占住全部线程，尚未进入的任务却需要这些线程才能进入。全员集合条件
永远不可满足。这不是延长测试超时就能解决的问题。

触发特征是 CPU 数乘经验系数推导 N、执行器容量另有固定或配置上限，以及
任务体中的 `while (workers < n)` 或等价集合屏障。CPU 数不是执行器容量。

## 实际证据

libdispatch 6.4.1 在 HarmonyOS PC 新机（20 个在线 CPU）上，readsync
按 `activecpu*NTHREADS` 推导 1280 个任务，而实际内部 pthread 池的源码容量
是 255。r11 中该项在输出启动横幅后超时 120.06 秒。

修复从实际 `src/shims.h` 的容量定义生成测试常量，适用于被选择的内部工作队列
后端；将 N 限制为容量扣除原测试预留的两个线程后可实际运行的值253。LAPS=10000、
两种队列布局、max readers=N、max writers=1 和读写重叠计数为0的断言均保留。
没有删除入口，也没有缩短总迭代数。

r13 原生探索的完整注册清单与 JUnit 均为37/37，readsync 8.58秒；消费者1/1。
12阶段事务回执、release/postrelease与精确日志回读完整。原始日志SHA-256：
`12df14bd07eb7592527e9d69981264695705127617643081613d744f66b52917`。
以上为原生探索证据。后续独立的正式 Conan run
`libdispatch-conan-w3-20261014-r1` 以相同源码补丁分别完成 shared/static
37/37 上游测试和1/1公开安装包消费者；正式日志SHA-256：
`41fdf8b428ec0b95e83504db9747b9fadd2a01a6c4df2b57cd249243815d270a`。
两种链接模式是同一用例清单的重复验证，不增加独立测试分母。

## 可复用修复步骤

1. 区分等待集合屏障、被测互斥操作和测试结束等待，确认超时发生在哪里。
2. 沿实际后端查容量定义、配置覆盖和必要保留线程，不能只读 CPU 估算值。
3. 常规互斥测试应在可实际同时就绪的容量内设置 N，保留原总迭代数及所有断言。
   用可复算容量导出常量，并在无法解析容量时显式报错。
4. 输出实际 N，盘点真实测试 ID，完整运行、回读 JUnit，拒绝失败、错误或跳过项。
5. 容量内验证仅证明该范围内的功能，不能宣称1280个线程已经同时运行。

## 边界与无效方案

只适用于夹具把“全员同时到达”当作前置条件的常规功能测试。如果测试本来就
检验超额并发、线程耗尽或调度伸缩性，缩小 N 会改变目标，必须保留失败并修复
执行器或资源处理。后端容量不明时也不能挑一个方便通过的数字。

不删除测试，不把超时改成 PASS，不只延长 timeout；不得因此改变生产库的
线程池上限，更不得停掉共享设备上的其他任务以制造资源余量。
