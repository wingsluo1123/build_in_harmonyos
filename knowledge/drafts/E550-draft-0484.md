# E550 — PG16+ 在 OHOS 上 COPY/多行插入报 `FileFallocate Permission denied` 的免补丁运行时补救

> 状态：草稿（draft）。与 `DRAFT-postgresql-fallocate-eacces-filezero`（源码补丁路线）
> 是同一错误面的**两种互不冲突的解法**，本条目记录其中的**运行时免补丁**路线。

## 现象

在 OHOS PC（aarch64）上运行的 PostgreSQL 实例中执行 `COPY`（或任何触发成批 relation
扩展的多行插入）时中断：

```text
ERROR:  could not extend file "base/5/16384" with FileFallocate(): Permission denied
HINT:  Check free disk space.
CONTEXT:  COPY prefixes, line 3000
```

> 注：错误串里的 `<表空间>/<库OID>/<relfilenode>` 随集群与每次运行而异（另一次复现为
> `base/16384/16455`）；可核的是错误文案与 `CONTEXT: COPY prefixes, line 3000`。

关键鉴别特征（用于和"真的磁盘满"区分开）：

- 单行 `INSERT ... SELECT`（逐条扩展）**正常**，只有 `COPY`/批量插入失败；
- `stat -f` 显示同目录仍有充足可用块（本次实测约 **639 GB**），与 HINT 矛盾；
- `python3 -c "import os; fd=os.open(p,os.O_CREAT|os.O_WRONLY); os.posix_fallocate(fd,0,1<<20)"`
  直接返回 `EACCES (13)`，而普通 `write()+fsync()` 正常。

## 根因

PG 16 起默认用 `posix_fallocate()` 预分配数据文件空间，对应 GUC
**`file_extend_method`**（PG 18 枚举值：`posix_fallocate` | `write_zeros`，默认
`posix_fallocate`）。OHOS 的用户文件系统拒绝 `posix_fallocate` 返回 `EACCES`，而
`mdzeroextend()` 对失败没有回退分支，于是直接 `ERROR`。单行插入走的是逐块 `FileWrite`
路径，因此不受影响——这也解释了"同一套回归里 `falcon`（99999 行单行插入）通过、
`prefix`（`\copy` 多行插入）失败"的怪象。

## 修复（推荐：运行时配置，免源码补丁）

启动服务端时把扩展方式改为零填充写入：

```bash
postgres -c file_extend_method=write_zeros
# 或
pg_ctl -D "$DATADIR" -o "-c file_extend_method=write_zeros" -w start
```

`write_zeros` 用零填充写入扩展文件，不再依赖 `posix_fallocate`；无需重建 PostgreSQL，
也没有修改任何上游源码。

## 回退方案

目标 PostgreSQL 版本没有 `file_extend_method` GUC（PG < 18）时，改走源码补丁路线：
在 `HAVE_BROKEN_FALLOCATE` 语义宏下让 `FileFallocate()` 把 `EACCES`/`EPERM` 与
`EINVAL`/`EOPNOTSUPP` 同等回退到 `FileZero()`。该路线另见
`DRAFT-postgresql-fallocate-eacces-filezero`。

## 适用边界

- OHOS 上运行的 PostgreSQL 16+（含 18.x）测试实例与服务实例；
- 任何 `fallocate`/`posix_fallocate` 被 `EACCES`/`EPERM` 拒绝的文件系统
  （hmdfs、tmpfs 等）；
- 反例：错误中同时伴随真实空间不足（`stat -f` 可用块确为 0）时，本条目不能替代扩容；
- 需要运行期校验的对象：PG < 18 无该 GUC，须走回退方案。

## 验证证据（真实 OHOS/aarch64 目标机，PostgreSQL 18.3）

### 1. 最小复现（修复前，默认配置）

```bash
# 用默认配置起一个一次性实例（不传 file_extend_method）
pg_ctl -D "$DATADIR" -o "-p 5432 -c unix_socket_directories=''" -w start
psql -c "SHOW file_extend_method;"          # → posix_fallocate
psql -c "CREATE TABLE prefixes (prefix text primary key, name text not null,
         shortname text, state char default 'S', check(state in ('S','R')));"
psql -c "\copy prefixes from 'prefixes.fr.csv' with delimiter ';' csv quote '\"'"
```

实测输出（逐字）：

```text
posix_fallocate
ERROR:  could not extend file "base/5/16384" with FileFallocate(): Permission denied
HINT:  Check free disk space.
CONTEXT:  COPY prefixes, line 3000
SELECT count(*) → 0
```

### 2. 修复后（同一实例加 `-c file_extend_method=write_zeros` 重启）

| 阶段 | 结果 |
|---|---|
| 上游号段表装载 | 11966 行全部装载成功（`count(*) = 11966`） |
| 上游回归套件 | `pg_regress` **5/5** 通过（含以 `\copy` 装载号段表的 `prefix` 用例） |
| 消费者端到端用例 | **CONSUMER-1 1/1** 通过（`archives/p/prefix/1.2.11`，真实 OHOS 目标机） |

> 该现象另有独立佐证：`DRAFT-postgresql-fallocate-eacces-filezero.md`（`postgresql/16.10`
> 适配时 `make check` 48/217 因同一 `FileFallocate ... Permission denied` 级联失败），
> 与本条目的最小复现互为印证。

## 禁止做法

- ❌ 依据该错误的 HINT「Check free disk space.」去清理磁盘/扩容——真实根因是
  `posix_fallocate` 被拒，与可用空间无关（实测同目录约 639 GB 可用）；
- ❌ 为绕过该错误而关闭/跳过需要 `COPY` 的测试用例——错误指向运行环境配置缺失，
  不是被测算法的缺陷，跳过只会隐藏平台适配缺口。
