# E7739 — 非 ASCII 字节比较不能盲用 native strcasecmp 作测试 oracle

## 错误特征
字节库内部使用 unsigned-byte `toupper`，上游测试却用 `strcasecmp` 的符号作为期望值。ASCII 通过，高位字节对出现 `strcasecmp (0) and octstr_case_compare (1) differ`。

## 触发条件
- 字节字符串 API，非 Unicode 文本 API；测试拿 libc 字符串函数代替独立预期。
- 阶段为运行测试，原始输入含非 ASCII 单字节。

## 根因分析
当前 OHOS 真机中，原始 `abc e5 e4 f6` 与 `ABC c5 c4 d6` 的 native strcasecmp 返回0，而 toupper/tolower 保留这些高位字节。Octstr 生产算法逐 unsigned byte 比较，不进行 Unicode 规范化，二者不能被假定为同一契约。此证据只针对实际平台/locale，不宣称所有 libc 相同或所有非法 UTF-8 都归一化为同一字符：E5/FF 反例实测比较值为-26。

## 解决方案

### 推荐方案
1. 核对公共接口、实际字节实现、输入编码与 locale；先排除 signed-char 未定义行为、缺原型及真正生产错误。
2. 独立观察 native 比较和逐字节 ctype 的结果，定位 oracle 与契约的差异。
3. 在受影响平台用显式字节折叠顺序表达预期，保留所有原始输入和所有原始比较。不直接调用被测函数来生成自己的预期。
4. 用消费者检查嵌入 NUL、高位字节和双向排序，完整执行上游套件；公开说明上游测试修改。

例证保留六个原始字符串及36对大小写比较，独立 C-locale ASCII 折叠后顺序等级为0,1,2,3,5,4；原 strcmp 比较不变。这个数表只是本例，跨库应用必须按其接口和输入重新推导。

### 禁止做法
- 删除非 ASCII 输入、跳过原测试、把差异直接视为 PASS。
- 为追随不一致的 oracle 而改变字节 API 为 Unicode 语义。
- 用被测算法自身产生期望，形成自证循环。
