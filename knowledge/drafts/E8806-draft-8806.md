# 递归 Mapping 快速路径前须执行严格具体类型策略

mergedeep 1.3.4 的三个 TYPESAFE 策略承诺冲突值的具体类型一致。Counter 与 dict 都属于 Mapping，却是不同具体类型；递归快速路径先行时，严格策略会被绕过。这是通用 Python 库缺陷；H1-003已完成OHOS真实Conan与功能验证，不能称鸿蒙专属问题或全部适配门禁已收口。

## 固定输入与症状

来源为 upstream `v1.3.4` / commit `ab871aff9eccb5e1bf0ea237c3cff8f6787ebc56`，完整归档 SHA256 `9710916ed71b5b872fbdf3e221da3e8bf4e70da892aff5f85e0390d64308d221`。README 的严格策略约定要求不同值类型抛 TypeError，支持集合示例包括 Counter。原 host 对照已记录正常 `Counter(a=1)` 与 `{'b': 2}` 在同一键上的错误静默合并；本次复用该记录，不重跑旧 probe。

```python
from collections import Counter
from mergedeep import Strategy, merge
dst = {'key': Counter(a=1)}
src = {'key': {'b': 2}}
merge(dst, src, strategy=Strategy.TYPESAFE_REPLACE)
```

原结果是合并后的 Counter，没有错误；按公开约定应抛具体类型不一致的 TypeError。新增消费者以 `AssertionError: Strict Mapping conflict silently merged` 精确报告“本应拒绝却成功”的失败；KV 不匹配修后预期 TypeError、普通 Counter 输出或测试通过日志。

## 根因与最小修法

`_deepmerge` 先执行 `_is_recursive_merge`，发现两边为 Mapping 后直接递归；`_handle_merge_typesafe` 只在非递归 dispatch 才执行。分类正确，策略前置检查顺序错误。

补丁只在每个冲突节点选择递归前，对 `TYPESAFE`、`TYPESAFE_REPLACE`、`TYPESAFE_ADDITIVE` 使用原实现的 `type(dst[key]) is not type(src[key])` 检查和原 TypeError 文本。保持同类型 dict 递归、Counter replace/累加分支、非严格 Mapping 合并与公开 API 不变。不要吞掉 TypeError、强转 Counter 为 dict、禁用递归或重写整个算法。

```text
python3.12 -B -m unittest -v mergedeep.test_mergedeep
python3.12 -B archives/m/mergedeep/1.3.4/test_package/consumer.py --package-folder <真实Conan包目录>
```

Conan 配方固定来源并应用 `patches/0001-mergedeep-mergedeep.py.patch`；build() 明确运行原 suite，test_package() 使用实际 Python 供应和已安装 mergedeep 包，消费者检查模块路径及版本。消费者须经真实包环境启动，不能把源目录预置到 PYTHONPATH 冒充安装。

## 增量与边界

本机制是“递归结构快速路径绕过严格策略前置条件”。2026-10-13 原卡已核正式库/草稿和官方 Issue/PR 的有界近邻：collections-abc silent-loss 是旧别名导入及虚类注册遗漏；twodict 是测试观察存储方式错误；E239 是多条消费者命令的诊断保全。三者不涉及本算法的递归策略顺序。本条不宣称全局原创、上游维护者已认可或官方知识已接受。

适用于有明确具体类型一致契约、且结构递归分支早于策略检查的深合并器。只比较抽象 Mapping 能力或有显式跨类型转换契约的实现不能照套；其他 Mapping 子类、跨键原子性、自引用图和并发均未新增验证。不为知识增量另做第二套算法或整个平台重构。
