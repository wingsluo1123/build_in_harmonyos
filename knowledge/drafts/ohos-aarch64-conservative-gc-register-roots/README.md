# OHOS/AArch64 上保守式收集器的寄存器根发现不成立

> 知识条目：`knowledge/drafts/DRAFT-ohos-aarch64-conservative-gc-register-roots.kv`
> 来源：`saclib/2.2.8` 的 OHOS 适配（`archives/s/saclib/2.2.8/`）

## 结论

自行实现「栈扫描式（保守式）」垃圾回收的库，如果在 AArch64 上沿用 x86_64 的
**「N 个哑局部变量交给 dummy 函数，靠调用把它们挤到栈上」**这一手法来捕获寄存器根，
那么这个捕获是**不成立**的：

- **AAPCS64 允许调用者把仍然活跃的值留在被调用者保存寄存器 x19–x28 里跨过该调用**，
  栈扫描看不到它们，活跃对象会被当成垃圾回收；
- AAPCS64 还给叶子函数 **16 字节 red zone**（`sp` 之下），编译器会把溢出槽放在那里，
  扫描下界若取「辅助函数自己的帧地址」就会漏掉调用者刚溢出的指针。

## 实测证据（HarmonyOS PC / aarch64 / clang 15.0.4）

对象：SACLIB 2.2.8 的 `GC()`，同一份 `libsaclib.a`，只替换归档里的 `GC.o`。

| 实验 | 结果 | 说明 |
|------|------|------|
| 哑参数写法，`-O0/-O1/-O2` 各 6 次 | `-O0` 6/6；`-O1`、`-O2` **0/12** | 与优化级别强相关 |
| 把测试里 3 处 `GC()` 注释掉 | 三个级别各 6/6 | 失败 **100%** 来自收集器 |
| `+N20000` / `+N5000000`（使收集不发生） | 仍 0/6 | 不是「回收太频繁」 |
| baseline `GC.c` 全矩阵 | `-O0` 6/6，其余 **0/18** | 复现缺陷 |
| **`setjmp()` 版 `GC.c`** | **24/24** | 修复生效 |

> 同一份 `GC.c` 在 x86_64 宿主上编译运行是**通过**的 —— 所以本机 x86_64 验证
> 不能作为此类缺陷的证据，必须在目标架构上跑。

## 修复模式

1. **用 `setjmp()`（或 `sigsetjmp`）强制溢出**：ABI 要求 `setjmp()` 返回后被调用者保存
   寄存器保持不变，编译器必须把它实际用到的每个 x19–x28 先写进栈帧 —— 恰好就是仍可能
   持有活跃对象的那组寄存器。经典保守式收集器（Boehm GC 的 `GC_push_regs` 一类）用的
   就是这一手法，可移植、无需内联汇编。
2. **扫描下界取执行扫描者自己的局部变量地址**，以覆盖调用者 red zone 内的溢出槽。
3. **把 `-O1/-O2` 纳入验证矩阵**：只在 `-O0` 通过不能证明寄存器根正确，`-O0` 会把所有
   局部变量放在栈上，恰好掩盖缺陷。

## 本目录内容

| 文件 | 用途 |
|------|------|
| `gc_root_test.c` | 通用复现负载：N 个独立大整数全部跨收集存活，收集后逐个重新推导比对；同一份源码在 `-O0/-O1/-O2/-Os` 下分别构建 |
| `reproduce.sh` | 构建并多轮运行上述负载，输出每个优化级别的通过数；失败时打印诊断与修复模式 |
| `detect_conservative_gc.py` | 静态检出：标出「哑参数落栈且无 `setjmp`」的 RISK 文件与行号，识别 `setjmp` 强制溢出的 OK 情形 |

```sh
# 静态检出
python3 detect_conservative_gc.py <源码目录>

# 动态复现（--prefix 指向已安装的包前缀，含 include/ 与 lib/*.a）
./reproduce.sh --prefix /path/to/package --cc clang --runs 3
```

## 适用范围

不限于 SACLIB：任何自带保守式/栈扫描 GC 的库移植到 aarch64 都适用
（解释器、Lisp/Scheme/ML 运行时、数学内核、CAD/符号计算库等）。
判定要点不是「有没有 GC」，而是「根发现是否依赖把活跃值落到栈上」。
`malloc/free`、引用计数、精确 GC 的库不适用。
